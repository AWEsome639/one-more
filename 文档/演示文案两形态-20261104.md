# 演示文案的两种形态与触发条件

> 2026-11-04（第 1229 轮）建档。来源：第 1218~1228 轮对 **7 个不同类别**游戏的
> 真机演示抽样（宝石迷阵 / 打砖块 / 推箱子 / 速算 / 西蒙序列 / 字谜定义 / 反应点击）。
>
> ⚠️ **看这份文档的人请注意**：如果你在真机或 dump 里看到
> 「看到了吗？再看一遍」或「看清楚：这是第 N 步」这种**泛泛的**演示文案，
> **那不是 bug** —— 那是「通用回退」形态，见 §2。

---

## 1. 背景：演示 = 代打跑一遍

`ai/Hint.ets` 里演示的实现只有三行核心：

```ts
static readonly DEMO_MS: number = 520;      // 每步间隔（比代打的 320 慢，看得清）
static readonly DEMO_STEPS: number = 6;     // 最多 6 步
static demoOnce(key: string): boolean {     // ⚠️ 作用域是「App 生命周期」，不是「每次进游戏」
  const k: string = 'demo_seen_' + key;
  if (AppStorage.has(k)) { return false; }
  AppStorage.setOrCreate<boolean>(k, true);
  return true;
}
```

各游戏的 `aboutToAppear` 统一是：

```ts
if (Hint.demoOnce('GXxx')) {
  setTimeout(() => { this.demoStart(); }, 3000);   // 进来 3 秒内没人动就开始演
}
```

⇒ **要重看某款游戏的演示，必须 `aa force-stop` 后重新启动 App**；
  仅仅回到首页再点进去**不会重演**（`AppStorage` 里 key 还在）。

## 2. 两种文案形态

演示条那一行字（`demoMsg`）有两种来源，代码里按「游戏能不能算出下一步点哪」分支：

### 2.1 具体指引（首选）

```ts
// GQuickMath 为例（修好之后）
const hr: HintResult = this.computeHint();
this.demoHintText = (hr.ok && hr.zh.length > 0) ? hr.zh : '';
this.demoMsg = TG2('看这里：{0}', this.demoHintText);
```

⇒ 取的是该游戏**自己的** `computeHint().zh`，所以文案是**具体的**：

| 游戏 | 具体指引文案 |
|---|---|
| 宝石迷阵 | 「看这两颗，交换它们，三个同色就消除（演示不计分）」 |
| 速算 | 「答案是第 2 个（演示不计分）」 |
| 西蒙序列 | 「按顺序第 1 下点「1」号（演示不计分）」 |
| 反应点击 | 「点第 7 个（演示不计分）」 |
| 数字金字塔 | 「答案是第 4 个（演示不计分）」 |
| 多米诺拼盘 | 「点一颗宝石，再点它相邻的一颗」 |

### 2.2 通用回退（`computeHint` 给不出「点哪」时）

```ts
if (this.demoHintText.length > 0) {
  this.demoMsg = TG2('看这里：{0}', this.demoHintText);
} else {
  this.demoMsg = TG2('看清楚：这是第 {0} 步', String(this.demoRound + 1));
}
// 第 2、3 轮统一变成：
this.demoMsg = this.demoRound >= 3
  ? TG('就是这样玩。碰一下屏幕，换你来')
  : TG('看到了吗？再看一遍');
```

⇒ 全项目 `「看清楚：这是第 {0} 步」` 共出现 **352 次**（兜底用），
   实测看到它的游戏举例：**字谜定义 / 打砖块 / 推箱子**。

## 3. 两种形态的判定规则

```
游戏能算出「下一步该点哪」吗？
├─ 能  ⇒ computeHint().ok === true 且 zh 非空 ⇒ 走 **具体指引**
└─ 不能 ⇒ computeHint().ok === false 或 zh 为空 ⇒ 走 **通用回退**
```

**「不能」的典型情形**：
- 动作类（打砖块）：球在飞，「下一步」取决于物理，无法预先给出一个点
- 拼图类（推箱子）：最优解需要搜索，超出 `Hint.BUDGET_MS`（500ms）
- 文字类（字谜定义）：拼词路径太多，给不出一句具体指引

**⇒ 这不是缺陷，是有意的降级。**

---

## 4. 排查时怎么区分「设计」与「bug」

| 你看到的 | 判定 |
|---|---|
| 「看这里：点第 7 个」 | ✅ 具体指引，正常 |
| 「看这里：答案是第 **2** 个」（选项 4 个） | ✅ 正常，`2 ∈ 1..4` |
| 「看这里：答案是第 **101** 个」 | ❌ **bug**（答案数值当索引用，第 1224 轮已修） |
| 「看到了吗？再看一遍」 | ✅ 通用回退（第 2 轮起），正常 |
| 「看清楚：这是第 3 步」 | ✅ 通用回退（第 1 轮），正常 |
| 「就是这样玩。碰一下屏幕，换你来」 | ✅ 演示收尾，正常 |
| 演示条根本不出现 | ⚠️ 查 `AppStorage` 里 `demo_seen_*` 是否已存在（判据 602） |

## 5. 演示期间会锁住的入口

实测 **3 个不同类别**（拼图 / 记忆 / 竞速）都做到了同一件事：
**演示进行中「提示」与「AI 代打」两个按钮变灰不可点。**

原因：两者都会写同一份游戏状态，与演示的定时器冲突。

⇒ 详见判据 609。**新增游戏时若忘了锁这两个入口，演示会与代打抢状态机。**

## 6. 相关判据

| 编号 | 内容 |
|---|---|
| 602 | `AppStorage` 是进程级，「每次进入只演示一次」实为「每次 App 生命周期一次」 |
| 604 | 验逐帧推进时，采样间隔必须 ≤ 单步时长的 1.2 倍（实测 0.54s/帧） |
| 605 | 「差 0 的帧」可能是设计中的等待期（`setTimeout 3000`） |
| 607 | 采样窗口 = 延时 × 1.5 + 2s（本项目 3000×1.5+2000 ≈ 6.5s，取 8s） |
| 608 | 「画面变了」是弱证据，「状态量变了」是强证据（看得分/步数/计数） |
| 609 | 自动模式必须显式禁用会冲突的入口 |
| 610 | 抽样要按**类别**报，不能只报数量 |
| 618 | 模板 + `String(expr)` 会抹平语义 ⇒ 模板旁必须注释 `{0}` 的语义 |
| 621 | 每一类抽样都要产出「本类暴露了什么差异」，空着的行 = 待重抽 |
| 622 | 本文档的来源判据 |
