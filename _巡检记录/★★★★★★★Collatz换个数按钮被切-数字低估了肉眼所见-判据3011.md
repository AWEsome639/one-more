# 判据 3011：`blk=24px` 看着像「贴边」，截图是**按钮被切掉一截**

## 一、数字说了什么

```
Collatz  2026-11-19T04:00:44  OK
lowest='换个数'  blk=1/24px  blkh=80px  cov=5  max=24  over=0px
```

按 `3009` 换算：`出屏 vp = (24 − 24) / 3 = **0vp**` —— **一点没出屏幕**。
按 `3005` 换算：`切% = 24/80 = **30%**`。

⇒ 两个数都显得「不算大事」：一个说出屏 `0`，一个说三成落在阈值带里。


⇒ **`换个数` 按钮只剩上部，下沿正好压着屏幕边被切。**

量一下：按钮可见高度约 `38px = 13vp`，而 `blkh=80px = 27vp`
⇒ **被切约 `42px = 14vp`**，比 `blk` 报的 `24px = 8vp` **多出近一倍**。

## 三、为什么数字低估了

`blk` 的 `over` 是 `y2 − 1576`。而按钮的**底边已经到 `1600`（屏幕边）**，所以：

| 量 | 值 | 含义 |
|---|---|---|
| `over` | `0px` | 没有**超出屏幕** |
| `blk` | `24px` | 越过 `1576` 阈值 `24px` |
| **实际被切** | **`≈42px`** | 按钮本应 `80px` 高，只显示了 `38px` |

⇒ **`blk` 只算「越过 `1576` 的部分」，但按钮从 `1576−? ` 就已经开始被裁**
  —— 因为**它的父容器比它矮**，`Column` 把按钮压扁了。

⇒ 这正是 `2605` 那条的另一个面：
   **`blk` 量的是「相对阈值」，不是「相对元素本该有的高度」。**

## 四、判据

> **`blk` 与「被切掉多少」是两件事 —— 前者相对阈值，后者相对元素应有高度。**

⇒ 三条：
1. **`blkh` 给了「这块现在多高」，但只要没有「本该多高」，就算不出被切比例**
2. **`over=0` + `blk=24` 的组合最容易骗人** —— 看着「刚好贴边」，实际按钮被压扁了 `52%`
3. **凡是「贴边」的款，必须看截图** —— 今晚 `Collatz` 是第一个被截图推翻的（`3009` 说 `0vp`，实际切一半）

## 五、这个缺陷要不要修

`Collatz` 的版面（横屏 `533` 高）：
```
chrome 175 + 统计行 84 + 大数字区 ~130 + 选项 2 行 ~120 + 说明 ~40 + 提示 ~30 + 换个数 27 = 606vp > 533
```

⇒ **超了约 `73vp`**。要修只能砍内容或缩，而这与判据 `2992`/`2994` 的结论一致：
   **横屏专属，竖屏（`853` 高）余量充足。**

⇒ **今晚不改。** 但它是「横屏确实会切按钮」的**最清晰证据**，
   比 `Shadow Pivot`（`over=58px` 但那款是棋盘整体）更贴近「用户会碰到」的场景。

## 六、这条与 `3009` 的关系（要让下一个人看明白）

| 判据 | 说什么 | 局限 |
|---|---|---|
| `3009` | `blk=24` ⇒ 出屏 `0vp` | **只测「出屏幕」，不测「被压扁」** |
| `3005` | `切% = max/blkh` | **分母是「现在的高度」，不是「应有高度」** |
| **`3011`** | **两者都可能低估：元素被父容器压扁时，`blk` 与 `blkh` 一起变小** | 必须看截图 |

⇒ **一句话：指标能量出「有没有超出边界」，量不出「本来就该多大」。**
