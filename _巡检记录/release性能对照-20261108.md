## 0. 结论（一句话）

**release 对「冷启时长 / 开屏 fps」几乎没有影响（都在噪声内），唯一稳定可见的是内存少 1.8–4.6 MB、`.hap` 常驻少 3.5 MB。**
⇒ **release 的价值主要在包体和内存，不在"跑得更快"。**

## 1. 三项对照

| 指标 | **release-cur** | **debug-cur** | 差 |
|---|---|---|---|
| **包体** | **34.25 MB**（34,249,179 B） | 46.14 MB（46,142,883 B） | **−11.89 MB（−25.8%）** |
| **冷启 animMs**（3 次） | 2238 / 2239 / 2237 ⇒ **2238** | 2230 / 2239 / 2242 ⇒ **2237** | **+1 ms（+0.04%，噪声）** |
| **开屏 fps**（3 次） | 56.3 / 55.8 / 56.3 ⇒ **56.1** | 56.5 / 58.1 / 56.2 ⇒ **56.9** | **−0.8（−1.4%，小于组内波动）** |
| **RSS** | **359,588 kB（351 MB）** | 361,400 kB（353 MB） | **−1,812 kB（−1.8 MB）** |
| **PSS total** | **226,097 kB（221 MB）** | 230,711 kB（225 MB） | **−4,614 kB（−4.6 MB）** |
| native heap | 98,500 kB | 98,776 kB | −276 kB（−0.3%） |
| ark ts heap | 49,608 kB | 49,994 kB | −386 kB（−0.8%） |
| `.hap` 常驻 | **12,288 kB** | 15,872 kB | **−3,584 kB（−3.5 MB）** ← 与 abc 更小一致 |
| `.so` | 43,646 kB | 43,770 kB | −124 kB |

**判读**：
1. **冷启时长完全由时间轴决定**（`Splash` 的 `TOTAL=1660` + `HOLD=2230`），帧率高低不改时长 ⇒
   **release 优化在"用户感知的启动速度"上赚不到东西**（两版都是 ~2238ms）。
2. **fps 差异小于组内波动**（release 55.8–56.3，debug 56.2–58.1，区间重叠）⇒ **不能写"release 更流畅"**。
3. **内存稳定更低**：RSS −1.8 MB、PSS −4.6 MB，其中 **`.hap` 常驻 −3.5 MB** —— 因为 release 的 `modules.abc` 更小，
   被 mmap 进来的页更少。**这是 release 唯一可复现的运行时收益**（虽然对用户不可感）。


## 4. 边界 / 偏差（必须写清楚）

1. **两次构建的源码不完全相同**：构建期间有队友在改 `games/GPong.ets`（`git status` 里是 `M`），
   debug 于 18:52 完成、release 于 18:57 完成 —— **中间可能夹了一次队友的编辑**。
   ⇒ 结论里"差 1.8–4.6 MB"的量级可信，**但 0.1 MB 级别的差不能当真**。
2. **构建期间还有另一路 hvigor 在跑**（debug 那次花了 **9 分 21 秒**，明显被抢 CPU），
   构建时长**不代表**正常情况。
3. **只有 3 次采样/版**：fps 组内波动 ±1.0，**差值 −0.8 在波动范围内**，所以不下"谁更流畅"的结论。
4. **包体对照受 sourceMaps 污染**（见 §2），**不能把 34.25 vs 46.14 当成"优化收益"**——
   真正的代码/资源差异要等 sourceMaps 关掉后再量。

## 5. 建议
1. **先解决 §2 的 sourceMaps 混入**，再重跑一次包体对照（预期 22.3 vs 46.1）。
2. **性能对照这件事本身可以收尾**：冷启/fps 不因 debug/release 而变（时间轴驱动 + 组内波动），
   内存差 2–5 MB 属"真实但不可感"。
3. 若想找**真正可感的 release 收益**，应该量 **游戏内帧率**（棋盘连消/物理类，如 `GBejeweled`/`GBreakout` 的
   连续动画帧间隔），而不是开屏 —— 开屏天然被时间轴钉死，量不出差别。
