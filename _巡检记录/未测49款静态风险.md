## 3. 我最建议先改的三款（改法完全一样，可一次改完）

| 顺序 | 款 | 为什么先它 |
|---|---|---|
| **1** | `GSpatialConflict`（`GStroopNumberSize` 同族） | 180vp = **52%** 预算，和 `Stroop` 的问题结构一致（一张大卡 + 选项 + 按钮）；改法一行、风险最低 |
| **2** | `GStroopNumberSize` | 同上；而且它和 `Stroop Test` 是"同族题"（都是颜色/大小冲突），一起改便于对比验收 |
| **3** | `GTemporalOrderJudgment` | 同上；三款都在 533 下用 `height(180)` |

**统一改法**（三款都一样）：
```ts
-  .width('100%').height(180)
+  .width('100%').height(Bp.isShort() ? 140 : 180)
```
⇒ 533 下每款省 **40vp = 120px**；竖屏不变（`Bp.isShort()` 只在高 < 690 时真）。

## 4. 方法与可复现

1. `工具/ets_parse.py` 的 `strip_comments` 去注释（否则会把「原来是 `.width('86%')`」这种**已修记录**误判成现状 —— 我第一版扫描就是这样多出 40+ 假阳性）；
2. 认棋盘：`}, (x: number) => …)` 收尾 + 下一行 `}.width(…)` ⇒ 这是「两层 ForEach」的棋盘容器；
3. 看它的**同链修饰**是否含 `constraintSize`/`layoutWeight`，以及全文件有没有 `Math.min`/`boardPx()`；
4. 固定块：`.height(N)`（N ≥ 100）按 **vp** 算（`height(180)` = **180vp = 540px**，不是 px —— 今晚的教训之一）。
