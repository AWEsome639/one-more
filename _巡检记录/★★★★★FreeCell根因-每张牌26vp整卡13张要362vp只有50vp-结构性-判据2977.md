# `FreeCell` 根因：**每张牌占整卡 `26vp`，`13` 张要 `362vp`，实际只有 ~`50vp`** ⇒ 结构性

> `2026-11-19 00:58`。看了图 + 读了容器结构，用 `2974`/`2976` 的不等式法定案。

## 一、⇒ 图里到底发生了什么（`2560×1600` ⇒ `3px = 1vp`）

| 区域 | 像素 `y` | vp | 说明 |
|---|---|---|---|
| 标题栏 | `0-220` | `0-73` | |
| `提示` / `AI 代打` | `245-310` | `82-103` | 两个宽按钮 |
| 步数/已归位/自由格 | `330-410` | `110-137` | |
| `4` 自由格 + `2` 家 | `425-675` | `142-225` | |
| **牌桌（分配到的）** | `680-870` | **`227-290`（约 `63vp`）** | |
| **`自动归位` 条** | `765-805` | `255-268` | **在牌桌内** |
| 底部留白 | `870-1600` | | |

**⇒ 牌桌只分到约 `63vp`，而它要放 `3` 行牌。**
**⇒ 每张牌高 `Cell.of(30) = round(30×0.85×1.0) = 26vp`，列内 `space:2`：**
```
3 张：3×26 + 2×2 + 4(padding) = 86vp  >  63vp  ⇒ 已经溢出
13 张（一列最多 52/4）：13×26 + 12×2 + 4 = 366vp  >  63vp  ⇒ 差 5.8 倍
```

## 二、⇒ 为什么表现成「浮层压住」

**⇒ 牌桌 `Row` 只有 `.width('100%').layoutWeight(1)`，**没有 `.clip(true)`**（`GFreecell.ets:884-885`）⇒ 子元素超出边界照样绘制。**
**⇒ 而 `自动归位` 在流里排在牌桌**之后**（`893` 行的 `Row`）⇒ 后绘制 ⇒ **盖在溢出的牌上**。**
**⇒ ⇒ 所以「浮层」是假象：**是牌溢出 + 按钮后画**，两个都对，谁也不特殊。**
**⇒ 同一张图里还能看到提示文字「点一张牌选中…」也被压住 ⇒ 三样东西叠在一起，根因只有一个。**

## 三、⇒ 为什么不是改常数能解决的

**⇒ 用 `2976` 的两约束联立，**高度方向的解不存在**：**
```
可用高 63vp；一列最多 13 张；N 张需要 N·h + (N−1)·2 + 4 ≤ 63
⇒ 13 张时 h ≤ (63 − 4 − 24)/13 = 2.7vp
⇒ h = 2.7vp 的牌无法阅读 ⇒ 无解
```
**⇒ 即使把上方所有区域压到极限（假设给牌桌 `150vp`）：`h ≤ (150−28)/13 = 9.4vp` ⇒ 仍然不可读。**

## 四、⇒ 正确的做法（结构性，需拍板）

**⇒ 手机 `FreeCell` 的标准解是**层叠扇形**：每张牌只露出顶部一条（约 `10vp`），而不是整张 `26vp`。**
```
13 张 = 26（首张全露）+ 12×10 = 146vp
⇒ 若牌桌能到 150vp 就刚好装下；把「点一张牌选中」提示行挪到别处即可
```
**⇒ 三种实现路径（按改动大小）：**
1. **`Column({space: -16})` 负间距** —— 最小改动，但 `space` 负值在 ArkUI 上是否被接受需实测；
2. **`Stack` 逐张 `.offset({ y: k * 10 })`** —— 最稳，但要重写列渲染；
3. **列内 `Scroll` 纵向滚动** —— 最省事，但「一列要滑」在纸牌游戏里手感差。

## ⇒ 判据 `2977`

**⇒ 「看起来像浮层」的东西，先算**内容是否超出了容器**（本例牌 `366vp` vs 容器 `63vp`），再看**绘制顺序**。**
**⇒ ⇒ 浮层假象的两个必要条件：① 容器没有 `.clip(true)`；② 遮挡物在流里排在其后。**两个都满足时，任何后继元素都会「变成浮层」。**
**⇒ 推论：`rowClip` 之后不要再去找「谁设了 absolute」—— 大概率没人设。**
