# 判据 3062：**syscap 声明了，运行时却是 `undefined`** —— 「声明支持 ≠ 真能用」在 RAG 上复现

## 一、跑出来的证据（真机日志，不是推测）

触发方式：`aa start -b com.andrewoscar.onemore -a EntryAbility --ps ragTest true`
（自检类 `core/LocalKRagSelfTest.ets`，只写 hilog、默认不跑）

```
RAGTEST: RESULT start db=onemore_kb.db table=game_rule
RAGTEST: STEP open-db ok        ← ✓ RDB 打开成功
RAGTEST: STEP table ok rows=3   ← ✓ 建表成功、3 条规则在库里
RAGTEST: RESULT fail code=-1 msg=Cannot read property getKnowledgeProcessor of undefined
```

⇒ **链路的前三步全通**：开库 → 建表 → 灌数据。倒在 `knowledgeProcessor.getKnowledgeProcessor`。

## 二、★ 那个 `undefined` 是谁

我加过一行诊断：
```typescript
const kpFn: boolean = knowledgeProcessor.getKnowledgeProcessor !== undefined;
```
它**没有打印** —— 因为**这一行本身就是抛出点**：
`knowledgeProcessor` 这个**命名空间导入在运行时是 `undefined`**，
所以访问它的任何属性都抛 `Cannot read property … of undefined`，被我的 `catch` 接住、
打出来的正是那句「of undefined」。

⇒ 也就是说：**`@kit.DataAugmentationKit` 在这个模拟器镜像上没有实现**，
   `import { knowledgeProcessor } from '@kit.DataAugmentationKit'` 拿到的就是 `undefined`。

## 三、与 syscap 的矛盾（这才是关键）

`3051`/`3061` 查过设备 `/system/etc/syscap.json`：
```
SystemCapability.DataAugmentation.KnowledgeProcessor   ✅ 声明存在
SystemCapability.DataAugmentation.RAG                  ✅
SystemCapability.DataAugmentation.Retrieval            ✅
```
设备 `emulator`、API `26`（≥ 20）。

⇒ **声明了六项能力，运行时一项也没有。**

⇒ 这正是 `AGENTS.md` 五铁律里那条：
> **「声明支持」≠ 真能用。**

⇒ 而且是同一个错误的第三次复现（前两次：`blk=0` 不等于修好、`pgrep -f` 判活不可靠）——
   **代理量（syscap 清单）与真值（运行时函数）对不上，就必须换掉它、不能继续用它推结论。**

## 六、判据

> **验证能力，不能只看「设备声明的能力清单」，要看「运行时那个函数在不在」。**

⇒ 四条：
1. **`syscap.json` 只是声明**，模拟器镜像可以声明而不实现
2. **「属性访问抛 undefined」和「函数内部返回 undefined」是两回事** ——
   这次我一开始把 `Cannot read property X of undefined` 当成「X 缺失」，
   其实是**整个命名空间都缺失**；区分办法：在属性访问**之前**先判断命名空间本身
3. **诊断代码本身可能就是抛出点** —— 加日志时要先确认这行不会先炸
4. **设备能力类结论必须标「在哪台设备上验的」** —— 这次是 `emulator`，不能替真机背书

## 七、★ 补测（`21:50`）：**同一个 kit 里「有的真、有的是空」**

加了一个探针（在同一个自检里顺带报 `LocalLLM.available()`）：

```
RAGTEST: DIAG localChatModel available=true stat={"ready":false,"reason":"idle",...}
RAGTEST: RESULT fail code=-1 msg=Cannot read property getKnowledgeProcessor of undefined
```

⇒ **`localChatModel` 是真的存在**（`available=true`），
   而 `knowledgeProcessor` 是 `undefined`。

⇒ 结论精确到模块级：

| `@kit.DataAugmentationKit` 的导出 | 本模拟器 |
|---|---|
| `localChatModel` | ✅ **实现完整**（`SystemCapability.DataAugmentation.LocalChatModel` 为真）|
| `knowledgeProcessor` | ❌ **`undefined`**（syscap 声明了、模块没实现）|
| `retrieval` / `rag` | ❌ 同样 `undefined`（同一个 kit，同一个缺口）|

⇒ **不是「整个 kit 没加载」** —— kit 加载了，只是部分模块是空的。
   ⇒ 这也解释了为什么现有「提示 / AI 代打」功能一直是好的：它只依赖 `localChatModel`。

## 八、顺带做的一处加固（已编译通过）

`core/LocalLLM.ets` 的 `available()` 原来只有一行 `return canIUse(SYS_CAP);` ——
**只看声明**。今天证明了「声明为真、实现可以缺失」⇒ 加了运行时存在性检查：

```typescript
static available(): boolean {
  try {
    if (!canIUse(SYS_CAP)) { return false; }
    // ⚠️ ArkTS 禁止把命名空间当对象比较（arkts-no-ns-as-obj）⇒ 只能做**属性**访问。
    //   命名空间本身为 undefined 时，属性访问会抛 ⇒ 由外层 try 接住 ⇒ 同样是 false。
    if (localChatModel.init === undefined) { return false; }
    return true;
  } catch (e) { return false; }
}
```

⇒ 效果：以后真遇到「声明有、实现无」的设备，会走**干净的 `reason='no-syscap'` 降级**，
   而不是「以为有、一调就炸」。
⇒ 在本模拟器上实测 `available=true`（因为 `localChatModel` 确实在）⇒ **不影响现有行为**。

## 九、判据补充

> **「能力缺失」要精确到模块级，不能停在「这个 kit 不行」。**
> 同一个 kit 里可以有「实现了的」和「只是声明的」并存 —— 笼统结论会误伤好功能。

⇒ 两条：
1. **逐个导出验**（`localChatModel` ✅ / `knowledgeProcessor` ❌）—— 一次运行就能分清
2. **`canIUse` 之后必须加运行时存在性检查** —— 这是今天唯一能防止「声明陷阱」的代码级措施
