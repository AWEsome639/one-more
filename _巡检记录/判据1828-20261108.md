# 判据 1828（2026-11-08 立）

## 1828 · 改常量时，要搜「所有**隐式依赖**它的地方」，不只是「直接用它的地方」

**触发事件**：`GDoodleJump` 的 `P_H` 从 `9%` 改到 `28%`（**为了让判定盒 = 视觉高**）。

**数学上改对了**：
- `P_H = 28% × 71.3vp = 19.96vp` ≈ **视觉 `20vp`** ⇒ **`1.00×`** ✓
- 落地公式 `py = p.y − P_H` ⇒ **视觉底边贴平台顶面**（**误差 `0.04vp`**）✓

**但游戏活不过 1 秒**：
- **`reset()` 里 `py = 70`**（**写死的数字，不是 `P_H` 的表达式**）
- **第一块平台 `y = 85`**
- **新 `P_H = 28%`** ⇒ **起始碰撞底边 = `70 + 28 = 98%` > `85%`**
- **下落判定 `prevBottom <= p.y && bottom >= p.y` 永不成立** ⇒ **直接穿到屏幕底部**
- **真机：重开后按 ◀ 后 1.5 秒内变「掉下去了，高度 0 米」**；**结算用时 0.9 秒、得分 0**

---

## 为什么「搜不到」

**`py = 70` 这个 `70` 是「出生高度」，写死在 `reset()` 里** —— **它和 `P_H` 的关系是隐式的**：
**「出生高度」必须低于「第一块平台高度」至少 `P_H`**，但**代码里没有任何注释或表达式表达这个关系**。

**⇒ `grep P_H` 搜不到 `py = 70`。**

---

## 判据

**改一个常量时，问三个问题**：
1. **谁直接用了它？**（`grep` 能搜到）
2. **谁**「**必须和它保持某个关系**」**？**（**隐式依赖，`grep` 搜不到**）
3. **有没有「写死的数字」其实是它的函数？**（**本判据**）

**⇒ 特别是「起点/边界/初始值」这类常量** —— **它们和「尺寸/速度/间距」的关系常常是隐式的。**

---

## 修法（`verifier-dev` 给的一行）

```ts
this.py = 85 - P_H;   // = 57%
```

**但更好的写法是让关系显式**：
```ts
// 出生在第一块平台上方的 PY_START_GAP 处（保证出生必落在平台上）
this.py = firstPlatformY - P_H;
```

**⇒ 后者的好处**：**`P_H` 再变，`py` 自动跟着变** —— **不会再犯同一个错。**
