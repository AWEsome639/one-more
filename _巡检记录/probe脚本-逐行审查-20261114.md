## 1. 🔴 hdc 调用可靠性

```bash
 32  S() { "$HC" -t "$TGT" shell "$1" >/dev/null 2>&1; }
 19  TGT=$("$HC" list targets 2>/dev/null | head -1 | tr -d ' \r')
```

| 问题 | 结论 |
|---|---|
| `$TGT` 带 `\r`/空格？ | ✅ **基本够**：`tr -d ' \r'` 去掉了空格与 CR。**但没去 TAB**（`\t`）—— hdc 输出一般不含 tab，风险低；要更稳改成 `tr -d ' \r\t"'`（顺带去掉可能的引号）|
| 坐标要不要额外引号？ | ✅ **不用**：`"$1"` 把整条 `uitest uiInput click 2276 264` 当一个参数交给 `hdc shell`，设备端 sh 再解析 ⇒ 与 `shot_game.py:628/630` 的写法完全一致 |
| `uinput -K -t '时序判断'` 会不会被二次解释？ | ✅ **不会**：单引号在**双引号字符串内部**，本地 shell 不剥；到设备端 sh 才剥。**唯一风险**是 `$WORD` 本身含单引号（默认值没有）|
| **真正的坑** | ⚠️ `S()` **吞掉所有输出与返回码**（`>/dev/null 2>&1`，且脚本没有 `set -e`）⇒ 点歪了/打字失败/设备掉线，**脚本照样往下走**，最后给出一份「什么都没命中」的结论 |

**结论：调用写法没问题；问题是「不检查成功与否」。**

## 3. 🟡 dump 与 file recv 的时序 —— **这里是最大的静默失败源**

```bash
 44  "$HC" -t "$TGT" shell "uitest dumpLayout -p /data/local/tmp/probe.json" >/dev/null 2>&1
 45  "$HC" -t "$TGT" file recv /data/local/tmp/probe.json "$OUT" >/dev/null 2>&1
 46  if [ ! -s "$OUT" ]; then echo "❌ dump 没拿到"; exit 1; fi
```

| 问题 | 结论 |
|---|---|
| `dumpLayout` 是同步的吗？ | ✅ **实践上是**：`shot_game.py` 的 `dump()` 一直是「`dumpLayout -p` → 立刻 `cat`」，台账里 417 行 `lowest=` 都成功 ⇒ 同步可依赖（❓严格意义仍需真机确认，但有生产证据）|
| **但旧文件会冒充新文件** | 🔴 **两个固定路径都不清**：`/data/local/tmp/probe.json`（远端）与 `/tmp/probe_nocard.json`（本地）|
| 后果 | 若本次 `dumpLayout` 失败（设备忙/超时），`:45` 的 `file recv` 会**把上次的远端文件拷过来**；若 `file recv` 也失败，`:46` 的 `-s "$OUT"` 仍会因为**上次的本地文件存在**而通过 ⇒ **分析的是旧 dump** |
| 够不够？ | **不够**。`-s` 只证明「文件非空」，不证明「是这次的文件」。建议：① `:44` 前 `S "rm -f /data/local/tmp/probe.json"` ② `:45` 前 `rm -f "$OUT"` ③ 检查 recv 返回码 |

对比 `shot_game.py` 的 `dump()`（`:108-136`）：它**先 `rm -f`、失败返回 `None`、用完再 `rm`** —— probe 缺的正是这三件事。

## 4. 🟡 分析段：正则、空值、递归

```python
 57  def parse_b(b):
 58      m = re.findall(r'-?\d+', b or '')
 59      return tuple(int(x) for x in m[:4]) if len(m) >= 4 else None

 82      for dep, t, b, bb in exact:
 83          y1 = bb[1]          # ← 没有判空
 84          w = bb[2]-bb[0]
```

| 检查项 | 结论 |
|---|---|
| `bounds` 格式不是 `[x1,y1][x2,y2]` 会怎样？ | ⚠️ `parse_b` 只取**前 4 个数字**，格式变了不报错、会**静默算错**（例如 `{x:1,y:2,...}` 取到 `1,2` 就返回 2 元组 ⇒ 长度 <4 ⇒ None，反而安全）。**最危险**是「恰好有 4 个数字但含义不同」——当前 ArkUI dump 是 `[a,b][c,d]`，与 `shot_game.texts()` 同一写法 ✅ |
| `bb` 为 `None` 时？ | 🔴 **会崩**：`:76` 明明写了 `bb[1] if bb else '?'`（说明作者知道可能为 None），但 `:83` 直接 `bb[1]` ⇒ 只要有一个「文本等于目标词但 bounds 缺失/不可解析」的节点，就 `TypeError` 退出 |
| `walk()` 无深度上限 | 🟡 **风险低**：ArkUI dump 树通常 <50 层，Python 默认递归上限 1000；但**恶意/异常树**（含环）会 `RecursionError`。建议加 `if dep > 80: return` |
| `n` 不是 dict 时？ | ⚠️ `walk` 直接 `n.get(...)` ⇒ 若 children 里混入字符串会 `AttributeError`。`shot_game.texts()` 也没防，但两边都只在自己产出上跑，风险低 |
| **命中判定过宽** | 🔴 `:67`（原文）：`if t and (word in t or any(ch in t for ch in word[:2] if ch.strip()))` —— `word[:2]` = `时序`，所以**任何含「时」或「序」的节点**都会进 `hits`（比如「时间」）⇒ `:88` 的「只有部分字符命中 ⇒ 标题被拆」这条结论**会被误触发** |
