# ★★ `fixed_audit.py --opt` 有真 bug：负余量 ⇒ 裁决出物理不可能的「放大到 533」

> `2026-11-14 10:4x`。队友 `769c6a52` 审计 + 我复现修复。**明早第一件事就要信这个工具，
> 若不修，明晚会按「放大到 566」这种数去改布局。**

## 一、bug 是什么（一行）

```python
bottom = mx - HEADER_VP - bh        # mx = max_bottom/3
cap    = 533.0 - HEADER_VP - bottom # 零余量下的盘面上限
```

**⇒ `bottom` 若是负数，`cap` 就**大于** `533 − 104 = 429`，即「盘面比屏幕减去头部还高」——物理不可能。**

**根因**：`max_bottom` 只统计**有文字**的节点（`shot_game.py:134 texts()` 只遍历带 `text` 的节点）。
盘面/按钮底部没有文字时，`max_bottom` 偏小 ⇒ `bottom` 变负。

## 二、配对前后数值（同一份合成台账，`/tmp/test_ledger.tsv`）

构造一条病态行：盘面 `400×300px`（`300px = 100vp`），但 `max_bottom` 只有 `200px`（`66.7vp`）。

| 项 | 修复前 | 修复后 | 物理上限 |
|---|---:|---:|---:|
| `底部` 列 | **`-137`** | **`0`** | — |
| `盘面上限` | **`566`** | **`429`** | **`429`** |
| 判读 | **「可放大 +466 ⇒ 放大到 566」** | **「可放大 +329 ⇒ 放大到 429」** | — |
| 对照款 `Normal` | `193` | `193` | **不变（无回归）** |

**⇒ 原 bug 在物理上限 `429` 的屏上给出「放大到 `566`」，超 `32%`。**

## 三、修法（两行守卫，已落）

```python
bottom = max(0.0, bottom)             # 负余量无意义，钳到 0
cap = 533.0 - HEADER_VP - bottom      # 原式
cap = min(533.0 - HEADER_VP, cap)     # 上限 429：盘面不可能高于「屏高 − 头部」
```

**验证**：`python3 -m py_compile` 通过；`final_check.sh` 十步仍全绿
（`37` 处在位 / 断言 `200359 / 0` / `cov` 回归 `5/5` / 总检「✅ 全部就绪」）。

## 五、队友核过、确认**没问题**的（这些可以放心）

- **阈值**：溢出判 `>533.5`、放大判 `cap−board > 15`、否则「正好」—— 与文档一致
- **`HEADER_VP` 会约掉**：它在整条公式里抵消 ⇒ 头部估 `104` 还是 `122` **不影响裁决与 `cap`**，只影响打印的「底部」列
- **格式/单位**：`board=WxH@x,y` 全整数 `px`；`board` 与 `max_bottom` **都是 px、统一 `/3`** ⇒ **没有混单位**；
  `@x,y` 的逗号**干扰不到**正则；`board=-` 不匹配 ⇒ 正确跳过；**用 H 不用 W** ✓
- **老行**：`if m and f[3].isdigit()` 先门控 ⇒ **不会被当成 `board=0`** ✓（自测里「无 board」与「`board=-`」两款都正确缺席）

## ⇒ 判据（`2053`）

**一个「裁决类」工具，必须对「输入越界」有钳制，否则会把**不可能的答案**当建议输出。**
`bottom = max(0, …)` 与 `cap = min(物理上限, …)` 是两行成本；
没有它们，今晚跑完的数据会让明早做出「把盘面放大到比屏幕还高」这种决定 —— **而这恰好是最容易被信任的一类输出，因为它带着两位小数。**
