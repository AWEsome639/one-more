# ⛔ 清 `.hvigor/cache` 的代价：**约 `35` 分钟冷编译 + 一次误判**

> `2026-11-15 14:20–15:05`。**一次自己给自己挖的坑，记下来。**

## 一、⇒ 发生了什么

**为了排查“构建卡住”的怀疑，我执行了：**

```bash
rm -rf .hvigor/.build-lock .hvigor/cache
```

**⇒ 清锁是对的（`.build-lock` 是僵尸锁），但**清 `cache` 是错的**：**

**⇒ 它把增量构建缓存删了 ⇒ 之后每一次构建都变成**冷编译**（`12` 分钟起）。**
**⇒ 连带后果：**
1. **一次冷编译跑到 `22` 分钟仍无输出（日志一直 `79` bytes）⇒ 我误判为“卡死”、杀掉了它。**
2. **但那次其实是**在正常编译**（CPU `68%`）—— 杀掉后 HAP 被清理步骤删除。**
3. **又重试一次，`12` 分钟才成功。**

**⇒ 总代价：约 `35` 分钟的机器时间 + 一次误杀 + 一个中间态“没有 HAP”。**

## 二、⇒ 真正的判断依据（而不是日志）

**`hvigor` 的日志**不实时刷**（`79` bytes 可能就是“还在编译”）。**

**⇒ 可靠的进度判断（按优先级）：**
1. **`ps` 里 `hvigorw` 的 CPU 占比** —— `>30%` 就是在干活，`~0%` 才是卡住
2. **HAP 文件是否存在 + 时间戳**
3. **`find entry/src/main/ets -name '*.ets' -newer <hap>` 的数量**（`0` = 已对齐）
4. **日志字节数** —— **最不可靠**

## ⇒ 判据（`2728`）

**`hvigor` 的进度只能靠**进程 CPU** 与**HAP 时间戳**判断，不能靠日志字节数；**
**⇒ 卡住的真判据是「CPU 长期 `<5%` 且日志/HAP 都不动」，不是「日志不涨」。**

## ⇒ 判据（`2729`）

**⛔ 不要清 `.hvigor/cache`**（除非确定缓存损坏）：它换来的是**每次构建 `12` 分钟**。
**⇒ 要清只清 `.hvigor/.build-lock`（僵尸锁）；`cache` 只在“确定缓存导致错误”时才动。**
