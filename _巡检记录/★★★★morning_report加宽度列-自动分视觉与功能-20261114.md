# ★★★★ `morning_report` 加「bounds 宽度」列 ⇒ **自动分出视觉级与功能级**

> `2026-11-14 18:1x`。判据 `2306`（bounds 可能是整行）的工具化。

## 一、加了什么

**③ 节多一列「宽度」+ 标 `← 整行`（宽度 `> 1000px`）：**
```
⚠️ Base Conversion Run     '把进制换算对，答错扣' 可见  6px  宽度 2440px ← 整行
⚠️ Fraction Matcher        'B'                 可见 14px  宽度   28px
⚠️ Fractional Pizza        '提示：分母 = 一共'   可见 10px  宽度 2440px ← 整行
⚠️ Kakuro Mini             '6'                 可见 12px  宽度  474px
⚠️ Magnets                 '2＋'                可见  3px  宽度   68px
⚠️ Percentage Shopping     '3'                 可见  5px  宽度   26px
```

## 二、⇒ 这一列**自动分出了两档**

| 宽度 | 是什么 | 档 |
|---|---|---|
| **`2440px`** | **一整行说明文字**（屏宽 `2560` 的 `95%`）| **视觉级** |
| `26`–`68px` | 单个元素（选项/线索格）| **功能级** |
| `474px` | ⚠️ 比一个键（`Cell.tap(44)=132px`）大得多 ⇒ 可能是**多格容器**或**跨列文字** | 需细看 |

**⇒ 而这也与队友的定性一致：**
- `Base Conversion Run` / `Fractional Pizza` = 「说明行被裁」⇒ **视觉级** ✅
- `Fraction Matcher` / `Percentage Shopping` / `Magnets` = 「选项/线索格被切」⇒ **功能级** ✅

## 三、⇒ `Kakuro Mini` 的 `474px` 是个新问题

**它的 `lowest='6'` 宽度 `474px`，而一个键宽 `Cell.tap(44) = 132px`。**
**⇒ `474 / 132 ≈ 3.6` ⇒ 那 `bounds` 覆盖了约 `3`–`4` 个键 ⇒ **是整行键区，不是单个键**。**

**⇒ 所以它的「可见 `12px`」是**键盘那一行**的可见高度，而具体哪个键被切未知。**
**⚠️ 但队友说「`12px`」且是键盘 ⇒ 与「整行」一致。**

## 四、⇒ 所以工具现在能做的判断

```
宽度 > 1000px  ⇒ 说明行（视觉级，低优先）
宽度 < 100px   ⇒ 单元素（功能级，高优先）
宽度 100~1000  ⇒ 需人工看（可能是行、可能是大元素）
```

**⇒ 这条规则**不是**完美的，但它把 `6` 款自动分成了「`2` 视觉 + `3` 功能 + `1` 待看」，不需要逐张看图。**

## ⇒ 判据（`2308`）

**「切的是什么元素」这个判断，可以用**几何**近似：`bounds` 的宽度就是「元素跨越了多宽」。**
**⇒ 整行说明文字横跨屏宽 `95%`，而单个选项只有 `26`–`68px` ⇒ 两者差 `40` 倍，不需要语义就能分。**

**⇒ 判据：能用一个量的**量级差异**分开的类别，不要靠读文字内容去判。
⇒ 这次「宽度 `2440` vs `28`」比「这行字是说明还是选项」可靠得多。*

## ⇒ 判据（`2309`）

**这个改进来自「一个异常值」（`474px` 的 `Kakuro Mini`）——它让我意识到「宽度」这个量本身有信息。**
**⇒ 若我只满足于「`6` 款可见 `< 20px`」，就不会去看宽度。**

**⇒ 判据：看到某个值落在两个类之间（这里 `474` 既不像 `2440` 也不像 `28`）⇒ 那是**分类规则有缺口**的信号，
⇒ 而缺口往往指向一个更有用的量。**
