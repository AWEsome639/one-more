# 定案：**App 本来就请求竖屏，是这台模拟器转不动**

> `2026-11-19 01:18`。A/B 实验 + 窗口管理器日志，两条证据闭合。

## 一、⇒ 实验

| 版本 | `hilog` 里 `com.andrewoscar.onemore` 的请求 |
|---|---|
| 加了 `win.setPreferredOrientation(PORTRAIT)` | `requestOrientation:1` |
| **撤掉（只剩清单 `"orientation": "portrait"`）** | **`requestOrientation:1`（完全相同）** |

**⇒ ⇒ **清单那一行本来就会产生 `requestOrientation:1`。我的运行时补丁是 `no-op`，已 `git checkout` 撤回，树恢复干净。**

## 二、⇒ 系统侧为什么不转

```
WMSRotation: … requestOrientation:1 … fixedRotation: -1 …
SCBSystemScene: transformRect: [0,0,2560,1600] rotation: 0
  "defaultScreenOrientation":0, "landscapeStartFlag":false
DeviceInfoVm: display prop change: width: 2560, height: 1600, orientation: 0
```

**⇒ 请求到了（`requestOrientation:1`），但 `rotation` 始终 `0`、显示属性始终 `2560×1600`。**
**⇒ ⇒ 这台模拟器（`phone`、`2560×1600@480`）**硬件就是横向、且不随应用请求旋转**。**

## 四、⇒ 这条的代价与收获

**⇒ 代价：今晚 `19` 款台账、三张图证、以及我 `01:2x` 以来的一串推理，**描述的都是用户在真机上不会看到的配置**。**
**⇒ 收获：**
1. **知道了台账的边界** —— 它测的是「紧凑布局下的溢出」，不是「用户看到的尺寸」；
2. **知道了 `47` 款在竖屏下的理论值**（`2983` 的静态推演，不依赖设备）；
3. **找到两个与方向无关的真缺陷**（`Kakuro`/`Odd Rotation` 无上限、`FreeCell` 溢出）；
4. **不必去改那 `47` 处算式** —— 它们是对的。
