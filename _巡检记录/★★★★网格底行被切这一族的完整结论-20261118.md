## 三、⇒ 为什么只有处方 2 灵（机理）

**⇒ `GShadowPivot` / `Perspective Taking` 的面板行是**固定个数、且每个子块都是 `layoutWeight(1)`** ⇒ 行本身没有高度时按内容撑高；给它 `layoutWeight(1)` 后它改为**取剩余空间**，子块按比例压缩 ⇒ 全部行进屏。**

**⇒ 其余四款不满足这个前提：**
- 行里有**非块的 `layoutWeight` 元素**（文字）⇒ 文字也吃高度（`2902`）；
- 行是 **`ForEach` 生成**（块数随数据变）⇒ 「行拿多少高」与「块内再分多少高」打架（`2903`）；
- 格子是**宽度驱动**（`layoutWeight + aspectRatio(1)`，高度由宽度定）⇒ 改宽度会被父级 `layoutWeight` 重新分配、且非单调（`2904`）；
- 根列子元素**全是内容高度**时，缩 `space` 也被吸收（本文件处方 7）。

## 四、⇒ 下一步该怎么做（**换思路，不是再调参数**）

**⇒ 剩下四款的正确方向：**把「格子的尺寸」从「容器分配」改成「按可用高度算出固定值」**：
```ts
const cellPx = Math.floor((Bp.height - 固定头部高度 - 间隙) / ROWS)   // 算出来
Stack().width(cellPx).height(cellPx)                                   // 写死，不用 layoutWeight/aspectRatio
```
**⇒ 这样高度**由算式保证**，不依赖任何布局分配 ⇒ 一行都不会切。**
**⇒ 代价：格子不再是「铺满宽度」，而是固定大小居中 —— 视觉上会小一点，但**绝不缺行**。**
**⇒ 这是「慢一点没关系，做浅了才是失败」在本族上的正确取舍。**
