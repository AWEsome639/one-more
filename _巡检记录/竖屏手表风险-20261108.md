# 手机竖屏 / 手表 布局风险 —— 2026-11-08

> 执行：verifier-eng2 ｜ **只读**（未改 .ets、未动 `Bp` 默认值）｜ 高峰时段，一次报完
> 背景：今天所有真机验都是 **853×533 横屏**；`perf-hunter` 指出 **440×956 竖屏 / 195 手表** 未覆盖

## 0. 结论

| 结论 | 内容 |
|---|---|
| **改分辨率** | ❌ **hdc 无路**（`wm` 不存在、`param const.display` 取不到、模拟器 CLI 只能启停实例）⇒ 本次用**静态推算** |
| **竖屏 440×956** | 🟡 **垂直溢出风险低**（宽驱动盘 47 处**全部有高度上限**）；**真风险是「横向密度」+「没有任何降级分支」**（440 既不触发 `narrowScreen(<420)` 也不触发 `tinyScreen(<340)`）|
| **手表 195** | 🔴 **最危险**：`games/` 里 `Bp.tinyWatch` 用了 **0 处**（组件层有 Common 9 处 / GamesTab 2 处，只覆盖首页与卡片）|

## 1. 能不能用 hdc 改模拟器分辨率？**不能**

| 尝试 | 结果 |
|---|---|
| `hdc shell "wm size"` / `"wm density"` | `/bin/sh: wm: inaccessible or not found` |
| `hdc shell "param get const.display"` | `Get parameter "const.display" fail! errNum is:1002` |
| `hdc shell "hidumper -s RenderService -a screen"` | 只回 dump 头，无分辨率字段可写 |
| 模拟器 CLI（`DevEco-Studio.app/Contents/tools/emulator/Emulator`） | 只能**启停实例**，分辨率在发射器实例配置里；改它=停/起模拟器（会打断当前占用，且非 hdc 路径）|

⇒ 结论：**分辨率不能通过 hdc 在运行中改**；要覆盖竖屏/手表只能 ① 新建对应尺寸的模拟器实例，或 ② 静态推算（本次）。

## 2. 手机竖屏 440×956

### 2-1 断点判定（关键：440 落在「两头不靠」的区间）

`Bp.ets` 的判定：
```
tinyWatch()   = height > 0 && height < 210      → 956 ⇒ false
tinyScreen()  = height > 0 && height < 340      → 956 ⇒ false
narrowScreen()= height < 420 || width < 420     → 440 宽 ⇒ false（差 20vp 就触发）
```
⇒ **440×956 既不进任何降级分支**，走的是「正常大屏」路径，但它其实只有 440 宽。

### 2-2 垂直方向：**基本安全**（有既有守卫）

- 仓库自带 `工具/check_layout_guard.py` 实测：**「宽驱动块 47 处 ｜ 缺高度上限 0 处 ✅ 全部有上限」**
  ⇒ 「`.width('100%').aspectRatio(X)` 在窄屏撑爆高度」这一类**已经被守住**。
- 粗算：顶部 chrome ≈ 240vp（标题/demo 条/提示按钮/HUD）＋ 棋盘 ≤ `Bp.height-360 = 596` ＋ 底部 ≈ 85 ⇒ **≈ 921 < 956**（余量仅 **35vp**）。
  ⇒ **临界**，任何一处 chrome 变高（比如多一行提示）就会溢出。

### 2-3 横向方向：**这才是竖屏的主要风险**

| 风险 | 量化 | 受影响的款 |
|---|---|---|
| **大网格被压扁** | 440 宽（扣 40 边距）下每格 = 400 ÷ N | **17 款**维度 ≥8：`GSnake`(20 列⇒**20vp**)`、`GTetris`(16⇒25vp)、`GGomoku`(15⇒26.7vp)、`GColorFlood`(12⇒33vp)、`GTennerGrid`(10⇒40vp)、`GGo9`/`GClassicMaze`/`GBubbleShooter`(9⇒44vp) 等 |
| **定宽按钮被压** | 今早 853 上「找」按钮就被压成 **12vp**（已修：定宽+`flexShrink(0)`）；440 更窄，**同类会再现** | 所有「双按钮/三按钮行」——建议把「定宽 + flexShrink(0)」推广（见 §4） |
| **三块 HUD** | `Column.layoutWeight(1)` 自适应 ⇒ 每块 ~130vp ✅ | 不担心 |
| **首页/卡片** | 2 列（440 < SM），卡片 192×126 ✅ | 不担心 |

## 3. 手表（195 宽）—— **真实空白区**

- **`games/` 里 `Bp.tinyWatch()` 出现 0 次**；只有 **30 款**用了 `Bp.tinyScreen()`（<340，手表 195 高**会**命中，但只有 30/198 款）。
  ⇒ **325 款（355−30）游戏在手表上没有专门布局**。
- 网格类在 195 宽下：400→(195-40)=155 可用 ⇒ 15 列 = **10.3vp/格**、20 列 = **7.75vp/格**、16 列 = **9.7vp/格** ⇒ **手指点不中、字看不见**。
- 首页/卡片是 OK 的（`Common.ets` 9 处 `tinyWatch` 分支 + `GamesTab` 2 处，卡高 58 档已有实测账）。

## 4. 建议（按成本从低到高）

1. **一行口径修正**：把 `narrowScreen()` 阈值从 **420 → 460**（或加 `width < 460`）。
   理由：440 竖屏现在**既不降级也不算窄屏**，「两头不靠」是这次分析里最便宜的修复点。
2. **推广今早那条修法**：所有「双/三按钮行」里的按钮加 `.width(Cell.of(56))` + `.flexShrink(0)`（今早只修了对话的「找」）。
3. **手表降级（要你拍板）**：`games/` 加统一入口判断 —— 手表（`Bp.tinyWatch()`）直接给「请用手机游玩」占位，
   或用 `Bp.tinyScreen()` 批量把棋盘限制为「可滚动的单列」。**355 款逐个适配不现实**，只能统一兜底。
4. **要真机数据**：新建一个 **440×956 竖屏模拟器实例**（不是改现有实例），我可以照今天的流程跑 6 个高频款；
   手表实例同理（195 宽的 watch 实例）。**这需要你在 DevEco 里建实例**，hdc 做不到。

## 边界

- 只读：未改 `Bp` 默认值、未改任何 .ets、未装包；未停/起模拟器。
- 竖屏数字是**静态推算**（chrome 取自 853×533 实测 dump 的比例），不是该尺寸的真机截图 —— 报告里已标注哪些是「实测」、哪些是「推算」。
- 手表没有实测样本（没有 195 宽实例），§3 的「每格 vp」是按宽度线性外推。
