## 一、口径（不说清这三个口径，数字对不上）

### 1.1 怎么取「最新一行」

1. 按 TSV 第 `1` 列时间戳字符串排序（ISO，`YYYY-MM-DDTHH:MM:SS`，可直接字符串比较），**每个游戏名取最新一条**。
2. **但只在「有效行」里取**：`outcome == OK` **且** `extra` 含 `blk=` **且** `lowest` 带 `bounds`。
   理由（都有数）：
   - `NOT_HOME` / `NO_CARD` / `TIMEOUT` / `DUMP_FAIL` / `WRONG_GAME` 共 `161` 行，**没有布局数据**；
   - **`88` 行有 `lowest='文字'` 但完全没 `bounds`**（最晚一条 `2026-11-13T01:49:15`；`bounds` 从 `2026-11-13T02:15:36` 才开始记，判据 1973）⇒ 这些行**判不了 `y2`**，只能算「缺字段」，不能当成「文字没到边」；
   - 好消息：`blk` 字段与 `bounds` **同批出现**，`blk` 行里缺 `bounds` 的是 **0 行** ⇒ 本次 24 款**无一缺 `bounds`**，第 1 类漏洞（「文字没到边」本身没依据）**在本批不成立**。
3. 「绝对最新一行不是 `OK`」的款：24 款里**只有 `Block Count 3D`**（绝对最新 `2026-11-13T22:11:02 NO_CARD`，采用最近一条 OK `21:03:13`）。⇒ 如果按「绝对最新一行」取，它会**静默掉出清单**，而它恰恰是真缺陷。**这条口径必须写死：取「最新一条有布局数据的 OK 行」。**
4. ⇒ `167` 款有「OK + blk」行 ⇒ 其中最新行 `blk>0` 的 **35 款** ⇒ 按 `lowest.y2` 再切：`==1600` 的 **11 款**、`<1600` 的 **24 款**。**24 这个数与你的一致**，说明口径对上了。

### 1.3 ⚠️ `blk` 的读法要改：`N/Mpx` 里的 `M` 是**合计**，不是「最深块」

**源码**（`工具/shot_game.py`）：

```python
over = nums[3] - (GAME_BOTTOM + SLACK)      # 1576 = 1516 + 60        （shot_game.py:808）
if over > 0:
    block_over_n  += 1                      # ① 越界块「个数」        （:810）
    block_over_px += over                   # ② 越界量「合计」        （:811）
    if over > block_over_max:
        block_over_max = over               # ③ 最深「单块」越界量    （:812-813）
```

写出台账的格式串来自 commit `14952217`（`2026-11-13 20:08:50`）：

```python
'lowest=%r %s blk=%d/%dpx max=%d -> %s @%s' % (lo, lo_bounds, block_over_n, block_over_px, block_over_max, out, _ts)
```

⇒ **`blk=N/Mpx` = 「N 个块越界 / 合计越界 M 像素」，`max=K` 才是最深单块的越界量。**

**数据反证**（`303` 行全量）：

- `M >= K` **303/303 全成立**，其中 `74` 行**严格大于**（如 `blk=2/48px max=24`）；
- **没有一行** `M == K` 且 `N > 1`。
- 这两点用「M = 最深块」都解释不通（那 `M` 与 `K` 就该是同一个数）。

**判定线也不是 1540**：`SLACK` 在 `2026-11-13` 由 `24` 校准为 `60`（注释：“用 24 会把「系统条」当成越界块”），所以

```
over = y2 - (1516 + 60) = y2 - 1576        ⇒  最深块 y2 = 1576 + max(K)
```

**两种读法会给出相反的结论**（同一条 `Snake 3D` 行 `blk=4/96px max=24`）：

| 读法 | 最深块 `y2` | 含义 |
|---|---:|---|
| 你的公式 `1540 + M` | `1540+96 = 1636` | 跑到屏外 `36px` ⇒ 一定在切 |
| 源码 `1576 + K` | `1576+24 = 1600` | **正好贴屏底** ⇒ 数值上无法判「贴底/裁切」 |

**⇒ 还有一层更要紧的**：24 款里 **22 款的最深块正好 `= 1600`**，`Number Bonds All` `=1598`，`Kakuro` `=1589`。
⇒ **光看数字，这 22 款全部停在同一个不可判点上**（判据 1933 早写过“`max_bottom=1600` 不等于被裁”）。⇒ 只看数得不出结论，**必须看图**；而图说：20 款是真裁。

### 5.1 `blk` 的三处口径错误（见 §1.3）
`M` 被当成「最深块」、判定线 `1540` 应为 `1576`、`blk>=60px` 被当成「一个大块溢出」——实际是**多个块各溢出 24px**（`4/96 = 4×24`，典型的多层全高容器嵌套）。
⇒ 你担心的“`blk` 很大但文字没到边 ⇒ 溢出的是无文字的大块”**方向对、结论错**：无文字元素确实在溢出，但**无文字元素不等于没有交互内容**（`Snake 3D` 的方向键就是无文字图形块）。

### 5.2 `lowest` 只统计 Text 节点 ⇒ 对「被切的那一类元素」结构性失明
`lowest` 取的是「文字节点里 `y2` 最大」的那个（源码 `texts(d2)`）。盘面格子、图形按钮、撑大的容器**没有 `text`**，所以永远不会出现在 `lowest` 里。
量化「盲区」= `1600 − lowest.y2`（最深文字之下、完全没有被文字信号监控的高度）：

| 盲区 | 款 |
|---|---|
| `904–923px`（≈`301–308vp`） | `Block Count 3D`(923) · `Crown`(904) · `Gomoku`(904) · `Mandelbrot`(904) |
| `796px` | `Snake 3D` |
| `197–373px` | `Memory`(249) · `Simon Says`(309) · `Number Bonds All`(197) · `Skyscrapers`(227) · `Heyawake`(373) |
| `<200px` | 其余 |

⇒ 对 `Crown`，**屏下四分之一（904px）的内容区完全没有被 `lowest` 覆盖**，而盘面正好长在这段里。

还有一条旁证：24 款里 **11 款的第 4 列 `max_bottom` 本身就是 `1600`**（`Block Count 3D` / `Crown` / `Gomoku` / `Gokigen Naname` / `Heyawake` / `Hitori` / `Mandelbrot` / `Memory` / `Number Bonds All` / `Path Intersect` / `Skyscrapers`）。
⇒ **「有东西贴到屏底」这个事实，台账里原本就有**，只是它在「叶子」那一列，而你的交叉表只用 `blk` 和 `lowest` 两列 ⇒ 两个信号一起把「到边」这件事滤掉了。

### 5.3 `cov` 从来没落过账 ⇒ 你问的第 3 种情况完全不可见
- `grep -c 'cov='` = **0**；`grep -c 'board='` = **0**。
- 原因链：`cov` 是 commit `0004521e`（`2026-11-14 07:06:59`）才加的，而**台账最后一行是 `06:44:36`** ⇒ 加完之后没有跑过批。
- 更要紧：**当前 HEAD 的格式化串是坏的**——`'... blk=%d/%dpx cov=%d board=%s max=%d ...'` 有 **9 个占位符**却只给了 **8 个实参**（且位置错位，`cov` 会拿到 `board` 字符串）：

```
TypeError: %d format: a real number is required, not str
```

  ⇒ **下一次跑批走到 OK 分支就会抛异常、那一款直接不进台账**。这条要单独修，否则不只是 `cov` 写不进来，是**整行记录丢失**。
- ⇒ 而「遮挡」这一类**恰好就在这 24 款里**：`Memory`（撑大的卡片盖住统计行）、`Simon Says`（A/B 按钮盖住关卡/得分/状态）、`Number Bonds All`（数字砖盖住目标/已拆/失误）。三款的图我都看过，遮挡是肉眼可见的。**你判「不用改」时，唯一的遮挡信号（`cov`）根本不在台账里。**

### 5.4 截图普查看不见「完全在屏外」的元素 ⇒ 普查系统性低估
`截图普查` 把 `Snake 3D` 判成 🟡（“三层盘面各露 3 行；最后一整行被切（大部分格子可点）”），但**同一张 `截图-Snake_3D-034504.jpeg` 里，方向控制键一个都没有**（`★★★Snake3D方向键完全在屏外` 已证实）。
⇒ 普查只能判「**看见了但被切**」，判不了「**整块不存在**」。⇒ 普查的 🔴 数是**下界**，不是上界。
⇒ 推论：`🟢 2 款`（`Percentage Peak` / `Target Number`）也不能就此结案——它们可能也有整块在屏外的控件。

### 5.7 单样本 + 文字随盘面变 ⇒ 「这一局没到边」不能证明「不会切」
- 24 款里 **22 款只有 1 条 OK 采样**；只有 `Number Bonds All`（4 次）与 `Pattern Sequence Draw`（3 次）有重复。
- 而 `lowest` 的**文字内容会随盘面变**：`Number Bonds All` 四次 `lowest` 分别是 `'4'` / `'1'` / `'1'` / `'12'`。
- ⇒ 对盘面类游戏，「这一局最深的字没到边」只说明**这一局的盘面**没把字放到边上，**不能外推成「这款不会切」**。
- ⇒ 统计上这也解释了为什么 `blk` 比 `lowest` 稳定：`blk` 数的是容器的布局，容器高度由屏幕决定，不随题目变。
