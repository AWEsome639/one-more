| 层 | API | 结论 |

## 为什么性质完全不同

**「环境不支持」** = 死路，只能换路线或放弃。
**「项目 target 低」** = 可以抬，但要付代价 —— 代价是**全局风险**：

- `355` 款游戏、`200,359` 条断言基线全部建立在 API `12` 的语义上
- 抬 target 后，**被移除/改行为的 API 会让编译失败或静默改变布局**
- 而这个项目最难的东西恰恰是**布局**（今天一天都在跟它缠）
- ⇒ **一次 target 升级可能一次打翻今天所有的布局结论**

**⇒ 所以它是「可行但高风险」，不是「不可行」。**

---

## 建议的分阶段路线（不占今晚窗口）

**今晚（`11-15 00:00`）窗口已排死**：装包 + 全量重测 `~6.8h`，没有编译余量。
**明晚（`11-16`）也已排死**：那 `11` 处编辑 + 一次 build。

**⇒ target 升级必须排在第三晚（`11-17`）以后，且要先做隔离实验：**

1. **先只改 `compatibleSdkVersion`，别的都不动，编一次**
   - 目的不是成功，是**拿到失败清单**（哪些 API 被移除、报什么错）
   - **这一步不能和任何功能改动混在一起**，否则分不清是 target 惹的还是改动惹的
2. **若失败清单很小（< 10 处）** ⇒ 逐处修，再验断言基线是否仍 `200,359`
3. **若失败清单很大** ⇒ 记下结论「target 升级成本 > 端侧 LLM 收益」，**正式封存这一项**，
   把理由从「环境不支持」改成「升级成本过高」——**两个理由不一样，不能再混着写**
4. 断言基线必须**逐条复算**，不许只看总数一致（判据：总数相同 ≠ 每条相同）

# 决定性补证（同日 `10:1x`）：**API `12` 就够了，一条都不用抬**

上一节只证明「环境有 API 26」。但那是**次要的** —— 真正的问题是：
**项目 target `12` 下，端侧推理接口到底存不存在？**

查本地 SDK 的 `.d.ts`（`hms_api` + 直接读 `@since`），三条路**全在 `12` 之内**：

| 通道 | 模块 | `@since` | API `12` 可用 | 能力 |
|---|---|---|---|---|
| 底层推理 | `@ohos.ai.mindSporeLite` | **`10`** | ✅ | `loadModelFromFile` + `Model.predict` + `MSTensor` |
| 高层文本 | `@hms.ai.nlp.textProcessing` | **`5`**（核心）/ `26`（新部件）| ✅ 核心 | 文本理解/抽取 |
| Agent 框架 | `@hms.ai.AgentFramework` | **`6`** | ✅ | `AgentController` / `FunctionController`（函数调用型 agent）|
| ~~`@hms.ai.A2A`~~ | — | `26` | ❌ | 太新，与本项无关 |

**`mindSporeLite` 的关键成员逐个查过，全是 `@since 10`：**
`namespace mindSporeLite`、`loadModelFromFile`、`loadModelFromBuffer`、`loadModelFromFd`、
`interface Model`（含 `predict`）、`MSTensor`、`Context`、`CpuDevice`、`DataType`、`Format`。

**⇒ 所以「端侧 LLM 卡在 API 20」这句话，在三个维度上都不成立：**
1. 环境不是没有 API 20 —— **SDK 与模拟器都是 API `26`**
2. 项目 target 不是必须抬 —— **接口从 API `5`/`6`/`10` 就存在**
3. 也不需要「换路线验证」—— **路线就在手边，两条**

---

## 那真正的剩余工作是什么

**不是平台问题，是选型问题。** 两条路，各有代价：

**路线 A：`@hms.ai.AgentFramework` / `nlp.textProcessing`（高层）**
- 优点：不打包模型、不转格式、不管内存，几行代码
- 代价：**能力受限**（函数调用 / 文本抽取，不是自由对话）；**依赖 HMS Core**，
  而模拟器是 `HarmonyOS 7.0.0` 应该带，但**需真机确认 syscap**

**路线 B：`mindSporeLite` + 自带小模型（底层）**
- 优点：**真·LLM**，可控
- 代价：要一个 `.ms` 格式小模型（转换 + tokenizer + 量化），且**内存/帧率要真机量**
  —— 这个项目的红线是「不许卡到不能用」（§0 ①），端侧推理很容易踩这条

**⇒ 建议：先做路线 A 的最小探针**（只验 `syscap` 是否支持、能否返回一段文本），
**一行真机输出就能定生死**；有它再决定要不要为路线 B 付模型转换的成本。

**⇒ 但这件事必须排在第三晚以后**：今晚装包 + 全量重测，明晚 `11` 处编辑 + 一次 build，
两个窗口都已排死。**端侧 LLM 不许挤进这两个窗口** —— 它是新功能，风险等级与前两项不同。

# ⛔ 撤回上一节的一半：`AgentFramework` 是 **API 20**，不是 API 6

**上一节写「`AgentFramework @since 6` ⇒ API `12` 可用」，这是错的，现撤回。**

**错因**：我用 `grep -oE "@since [0-9]+"` 读版本号，
而这个 SDK 的写法是 **`@since X.Y.Z(API)`**，**括号里的数才是 API 级别**：

```
@since 6.0.0(20)                  ← 这是 API 20
@atomicservice [since 6.0.1(21)]  ← 这是 API 21
```

我的正则把 `6.0.0(20)` 截成了 `6`，**丢掉括号那个真值**。
而 `mindSporeLite`（`openharmony` 侧）用的是裸数字 `@since 10`，所以那一条恰好没错、**掩盖了问题**。

## ⇒ 于是第 ④ 项的准确结论是「部分可行」，不是「完全可行」
