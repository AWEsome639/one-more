# ★ 目标第 ④ 项被误判为「已归档」—— 真正阻塞只是项目 target

> `2026-11-14 10:0x` 实测。**这篇是要更正一个已经写进目标的错误结论。**

---

## 原来的说法（目标文本里）

> **端侧 LLM**（第八个想法 v2）：仍卡在 API 20，需换路线验证

早先的分析把它记为**「已归档」**，理由是「需要 API 20+，而项目是 API 12」。

**⇒ 那句话暗示「环境里没有 API 20」——这是错的。**

---

## 实测（三行命令）

```bash
$ cat /Applications/DevEco-Studio.app/Contents/sdk/default/sdk-pkg.json
  "apiVersion": "26",  "displayName": "HarmonyOS 26.0.0"

$ grep -i apiVersion ~/.Huawei/Emulator/deployed/onemore7/config.ini
  os.apiVersion=26.0.0
  os.osVersion=HarmonyOS 7.0.0(26.0.0)
  imageSubPath=system-image/HarmonyOS-7.0.0/phone_all_arm/

$ grep compatibleSdkVersion "/Users/a0000/dev/One More/build-profile.json5"
  "compatibleSdkVersion": "5.0.0(12)",
```

| 层 | API | 结论 |
|---|---|---|
| 模拟器 `onemore7` | **`26.0.0`** | 够 |
| 本地 SDK | **`26`** | 够 |
| 项目 target | `12` | **唯一的阻塞** |

**⇒ 设备与 SDK 都在 API `26`，比要求的 `20` 高 `6` 个版本。**
**⇒ 「没有 API 20 环境」这个前提是假的；真实阻塞只有项目自己的 `compatibleSdkVersion: "5.0.0(12)"`。**

---

## 为什么性质完全不同

**「环境不支持」** = 死路，只能换路线或放弃。
**「项目 target 低」** = 可以抬，但要付代价 —— 代价是**全局风险**：

- `355` 款游戏、`200,359` 条断言基线全部建立在 API `12` 的语义上
- 抬 target 后，**被移除/改行为的 API 会让编译失败或静默改变布局**
- 而这个项目最难的东西恰恰是**布局**（今天一天都在跟它缠）
- ⇒ **一次 target 升级可能一次打翻今天所有的布局结论**

**⇒ 所以它是「可行但高风险」，不是「不可行」。**

---

## 建议的分阶段路线（不占今晚窗口）

**今晚（`11-15 00:00`）窗口已排死**：装包 + 全量重测 `~6.8h`，没有编译余量。
**明晚（`11-16`）也已排死**：那 `11` 处编辑 + 一次 build。

**⇒ target 升级必须排在第三晚（`11-17`）以后，且要先做隔离实验：**

1. **先只改 `compatibleSdkVersion`，别的都不动，编一次**
   - 目的不是成功，是**拿到失败清单**（哪些 API 被移除、报什么错）
   - **这一步不能和任何功能改动混在一起**，否则分不清是 target 惹的还是改动惹的
2. **若失败清单很小（< 10 处）** ⇒ 逐处修，再验断言基线是否仍 `200,359`
3. **若失败清单很大** ⇒ 记下结论「target 升级成本 > 端侧 LLM 收益」，**正式封存这一项**，
   把理由从「环境不支持」改成「升级成本过高」——**两个理由不一样，不能再混着写**
4. 断言基线必须**逐条复算**，不许只看总数一致（判据：总数相同 ≠ 每条相同）

## 顺带一个事实

`onemore7` 的镜像是 **`HarmonyOS-7.0.0`（API `26`）**，
而 TV 实例的底包是 **`HarmonyOS-5.1.1/tv_arm`**（旧得多）。

**⇒ 手机与电视的 API 代差有数个版本。** 电视那三项（`3` 米观感 / 局域网对打）将来若遇到
「某 API 在电视上不存在」，**先想到这是代差，不是代码写错。**

---

## ⇒ 一句话

**第 ④ 项的理由写错了。它不是「环境没有 API 20」，是「项目 target 停在 12」。
这个区别决定它是「死路」还是「高价路」——而高价路要先量出价格，再决定买不买。**
