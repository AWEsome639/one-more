# 诊断卡「点一下刷新」不更新 —— 定位（2026-11-09 02:0x）

> 执行：**perf-hunter** ｜ 设备 `127.0.0.1:5557` ｜包 `updateTime=01:47:52`
> 现象（上一轮实测）：点诊断卡**确实重试了**（hilog `init=false 1024ms` / `1040ms`），
> **但卡面数字一直显示旧的 `初始化 1050 ms` / `模型状态 init-false`**，而且**从未闪过 `idle`**。

---

## 0. 判断（先给结论，日志待下一版包）

**这是「数据侧」还是「渲染侧」，一行日志就能分；目前证据更倾向「渲染侧」，但还不能定死。**

| 假设 | 若成立，日志会打印 | 若成立，卡面会是 |
|---|---|---|
| **H1 渲染侧**：`stat` 是新的（1040），但 `@State` 手动赋值没触发重建 | `initMs=1040`（新值） | 仍 `1050`（旧值） |
| **H2 数据侧**：`stat.initMs` 根本没写进去 | `initMs=1050`（旧值） | 仍 `1050` |

## 1. 我已经加的那一行日志（本轮唯一改动，`SettingsTab.ets` **+8 / −1**）

```ts
private refreshDiag(): void {
  const reason: string = LocalLLM.stat.reason.length === 0 ? 'idle' : LocalLLM.stat.reason;
  hilog.info(0x0001, 'diag', 'refresh reason=%{public}s initMs=%{public}d calls=%{public}d ready=%{public}s',
    reason, LocalLLM.stat.initMs, LocalLLM.stat.calls, String(LocalLLM.stat.ready));
  this.diagReasonV = reason;
  this.diagInitV = LocalLLM.stat.initMs;
  ...
}
```
- **打印的是"即将写进 `@State` 的值"** ⇒ 它和卡面不一致就说明是渲染侧（H1），一致就说明数据侧（H2）。
- 零风险：只多一行 `info`，不改变任何逻辑。

## 2. 为什么「从未出现 `idle`」这条观察很有力

点击链路（我改过的 `retryDiag()`）：
```
onClick → LocalLLM.retry()      // reason='idle'（initMs 仍是 1050）
        → this.refreshDiag()    // diagReasonV: 'init-false' → 'idle'  ★ 这是【变了的值】
        → LocalLLM.init()       // 异步，~1s
        → .then(() => this.refreshDiag())  // reason 回到 'init-false'，initMs 变新值
```
- `diagReasonV` 从 `'init-false'` 变成 `'idle'` 是**不同值** ⇒ 按常理**必须重建一次**（哪怕只有 1 秒）。
- **实测从未出现 `idle`** ⇒ 要么 `refreshDiag()` 根本没被调用（那 init 又从哪来？），
  要么 **`@State` 赋值那一刻界面没重建**。
- ⚠️ 所以**「相同值不触发重建」单独并不能解释**——`reason` 这次确实是变了的；
  但如果连 `reason` 的变化都没反映出来，说明**问题比"相同值去重"更靠上**（赋值没执行 / 组件不在活跃渲染树 / 卡片是 `@Builder` 且父级没参与重建）。

## 3. 下一版包怎么验（两步定死，30 秒）

1. 冷启 → 问一次（制造一次失败，`stat.initMs` 记为 X）→ **等 65s** → 再问一次（`stat.initMs` 记为 Y，**Y≠X**）
2. 进设置页 → 滑到「AI 诊断」→ **点卡片**，同时抓 `hilog`：
   ```bash

   # 点卡片
   hdc -t 127.0.0.1:5557 shell "hilog -x | grep -E \"'diag'|diag:\" "
   ```

   - 若打印 `initMs=<新值>` 而卡面仍旧值 ⇒ **H1 渲染侧** ⇒ 按 §4 修
   - 若打印 `initMs=<旧值>` ⇒ **H2 数据侧** ⇒ 去 `LocalLLM.init()` 里查 `stat.initMs` 的写入点

## 4. 如果确认是 H1（渲染侧）—— 两个现成修法（**未实施，等日志**）

1. **版本号强制重建**（最稳，推荐）：
```ts
@State private diagRev: number = 0;        // 只用来"变一下"触发重建
private refreshDiag(): void {
  ...原有赋值...
  this.diagRev += 1;                       // 每次必变 ⇒ ArkUI 必重建
}
// 卡片上随便挂一个依赖：`.id('diag-' + this.diagRev)` 或把 diagRev 参与某个可见属性
```
2. **先赋哨兵值再赋真值**：`this.diagInitV = -1; this.diagInitV = real;`
   （能骗过"相同值去重"，但依赖 ArkUI 的批处理行为，**不如版本号可靠**）

## 5. 判据（本轮的产出）
> **诊断类 UI 不要只靠 `@State` 手动赋值** —— `LocalLLM.stat` 这种**无观察源的静态对象**，
> 一旦赋值因任何原因（同值 / 不在活跃树 / 批处理）没触发重建，界面就会**长期显示旧值**，且**没有任何报错**。
> ⇒ **要么给它一个"版本号"字段（`diagRev += 1`）强制重建，要么把 stat 放进 `AppStorage` 做真观察源。**
