# 853×533 底部控件被裁（2026-11-08）

> 只读扫描：`games/*.ets`（355 款）+ `pages/GameHost.ets`。**未改任何 .ets。**
> 结论：**这是系统性问题，不是个别款** —— 165 款用「宽度驱动棋盘」且无高度上限；真机已确认 5 款把底部按钮挤到屏外。

## 1. 可用高度：真机实测口径（**与 lead 给的 453 不同**）

在 `hdc -t 127.0.0.1:5557`（853×533）上用 `uitest dumpLayout` 量的（3.0 px/vp）：

| 区段 | 实测 | 依据（设备 px → vp） |
|---|---|---|
| 屏高 | **533** | 1600px ÷ 3 |
| 状态栏（不可用） | **66** | 页面首个节点 `‹` 顶部在 201px = 67vp |
| GameHost 顶栏 | **45** | `‹` 201–333px = 67–111vp |
| 游戏区 bottom padding | **20** | `padding({ bottom: Space.lg })` |
| HintBar | **38** | `barHeight = 38` |
| **游戏主体可用** | **≈352** | 实测：`猜球` 的内容正好铺到屏底（HintBar 底 181vp → 533vp） |

⚠️ lead 的公式 `533−42−38=453` **偏高 89vp**（没扣状态栏 66 与游戏区 padding 20），
用 453 当判据会漏掉「边缘溢出」的款（`GLaserLink` 就是这种：按 364 算刚好、真机却已半裁）。

> 补充：`Cell.of(N) = round(N × Cell.k × Bp.scale())`，平板 `Bp.scale()=1.06` ⇒ 实际按钮比 N 再高 6%，本次估算未计这项（偏保守）。

## 3. 真机实测：5 款已确认被裁（含超出量估算）

| 游戏 | 缺了什么（dump 里查不到） | 机制 | 估算超出 |
|---|---|---|---|
| **`G2048`** | 「重开」 | 棋盘 `aspectRatio(1)` + `constraintSize({maxHeight:'46%'})`=245；下面还有 **3 行 `Cell.of(44)`** ⇒ 245+132+40(HUD)+48(gap)≈**465** | **≈ +113vp** |
| **`GSokoban`** | 「上一关」「重开」「下一关」**整行** | 棋盘 `layoutWeight(1)` 自然高 ~260（8×8 格）+ **5 处 `Cell.of(48)`**=240 + HUD 60 + 状态 20 + 间距 96 ≈ **676** | **≈ +324vp** |
| **`GCountdownMath`** | 「重开」 | 棋盘 `aspectRatio(1)` 无上限 + **4 行 `Cell.of(52)`**=208 + 3 个 stat 卡 ≈ 90 + 题干 40 ≈ **495** | **≈ +143vp** |
| **`GPythagoreanTripleBuilder`** | 键盘 **7/8/9/0 + 确认**（1–6 可见） | 键盘 4 行 × `Cell.of(48)`=192 + 3 stat 卡 46 + 题干 25 + 输入框 42 + tip 20 + gaps 64 ≈ **389** | **≈ +37vp** |
| **`GLaserLink`** | 「重开」（**半裁**，截图可见） | 棋盘已限高 `Math.max(140, Bp.height-360)=173`，其余 40+44+48≈305 ⇒ 按 364 刚好、按实测 352 已踩线 | **≈ +0~15vp（边缘）** |

> 证据：`GLaserLink` 的源码注释（`:28-30`）已经写下同类结论：「横屏 853×533：宽驱动 aspectRatio 无上限 ⇒ 棋盘撑到 813vp 高，而游戏区可用只有 377vp ⇒ 下方按钮与说明整体在窗外」——**这说明该问题早就被发现过一次，只是只修了 1 款。**

## 4. 根因（共性，不是个别款）

1. **布局假设是「竖屏/近方形」**：355 款里 165 款用 `width('100%') + aspectRatio(1)` 求棋盘正方 —— 这假设了「宽 ≤ 高」。
   而 853×533 是**横屏**：宽 853 ⇒ 棋盘 813 高，**单块就超可用高 352 的 2.3 倍**。
2. **底部固定行高度写死**：`Cell.of(44/48/52)` × 3~13 行，不随屏高变化 ⇒ 高屏够用、533 屏必溢出。
3. **限高补丁是「魔法数」且不统一**：`G2048` 用 `maxHeight:'46%'`（533×46%=245，仍太大）；`GLaserLink` 用 `Bp.height-360`（=173，偏宽松）；其余 163 款**根本没有**。

## 5. 修法建议（**不要逐款改**，按性价比排序）

### 方案 1（推荐·一处兜底）GameHost 给游戏区加「高度上限 + 可压缩」
```ts
// GameHost.ets 游戏区 Column（现在只有 .layoutWeight(1)）
.layoutWeight(1)
.constraintSize({ maxHeight: Bp.height - 200 })   // 顶栏45 + HintBar38 + 边距
```
- 收益：**所有 165 款宽驱动棋盘**在横屏下不再把内容顶出屏幕（棋盘会被压到上限内，`aspectRatio` 反推宽度）
- 风险：棋盘变小（但**可玩 > 溢出**）；需 1 处改动 + 真机确认
- 前提：`Bp.height` 在游戏组件里可读（已是项目惯例，`GLaserLink` 就在用）

### 方案 2（中·抽共用组件）`FitBoard`
```ts
// 新组件：按"父宽 vs 可用高"取小的那个做边长
@Builder FitBoard(w: number, h: number) { ... }
// 替换 165 款的：Column().width('100%').aspectRatio(1)
// → BoardBox({ ratio: 1, maxH: Bp.height - 200 })
```
- 收益：一次性根治，且可见面积最优
- 代价：165 处机械替换 + 全量回归（属专项）

### 方案 3（小·固定行压缩）按钮行按屏高自适应
```ts
.height(Cell.of(Bp.height < 600 ? 40 : 48))
```
- 收益：`Cell.of` 那一族（62 款）省 8~24vp，覆盖 `GPythagoreanTripleBuilder`（+37）这类小溢出
- 代价：需逐款改 `Cell.of(4x)` 字面量（可脚本批量）

### 方案 4（小·键盘类专项）
`GPythagoreanTripleBuilder` 的键帽 4 行 → 横屏改 5 列 × 3 行，或把键盘放进 `Scroll`。

**建议落地顺序**：方案 1（GameHost 一处，先止血）→ 方案 3（脚本批量压按钮）→ 方案 2（专项根治）。
真机复验只需看：`G2048` / `GSokoban` / `GCountdownMath` / `GPythagoreanTripleBuilder` / `GLaserLink` 这 5 款的底部按钮是否都回到屏内。
