# 「难度会让网格溢出」是个**伪命题**（对宽度驱动的方阵）—— 判据 `2920`

> `2026-11-18 18:33`。**我自己提出的「难度档位盲区」，被自己的推导推翻。记下来，免得以后又去查一遍。**

## 一、⇒ 推导

**⇒ 方阵网格的格子是 `Row` 里的 `Stack().layoutWeight(1).aspectRatio(1)`，而 `Row` 的宽度是固定的 `W`。**
**⇒ 每格宽 = `W / n`；`aspectRatio(1)` ⇒ 每格高也 = `W / n`。**
**⇒ 网格总高 = `n × (W/n) = W`。**

**⇒ ⇒ **网格总高恒等于它的宽度，与格数 `n` 无关。** 难度升高（`n` 变大）时，格子变小、**总高不变**。**

**⇒ 所以「难度变高会导致溢出」**对方阵不成立**。**

## 二、⇒ 实测印证

**⇒ 静态筛出「网格由 `this.*` 生成（格数随难度变）」的 `18` 款，其中我已修 `2` 款，剩 `16` 款：**

| 款 | `blk` |
|---|---|
| `Crossword` / `Factor Finder` / `Letter Grid Swapper` / `Number Bonds All` | `24` / `0` / `0` / `0` |
| `Path Recall` / `Pixel Mimic` / `Polyomino Tiling` / `Rotating Maze` | 全 `0` |
| `Sum Pyramid` / `Symmetry` / `Symmetry Span` / `Tangram` | 全 `0` |
| `Vector Grid Alignment` / `Word Grid Connection` / `Word Scramble` / `Word Wheel` | 全 `0` |

**⇒ **`16` 款全部 `blk ≤ 24`** ⇒ 与推导一致。**

**⇒ 另：`GSymmetry.rowIdx()` 的实际实现确认了格数确实随 `diffTotal` 变（`n2 = diffTotal`）—— **格数在变，高度没变**，正好印证推导。**

## ⇒ 判据 `2920`

**⇒ 判断「难度会不会导致溢出」，先看**高度由什么决定**：**
- **宽度驱动**（`layoutWeight + aspectRatio`，且父容器宽度固定）⇒ **总高 = 宽度，与格数无关** ⇒ 难度**不会**导致溢出；
- **高度驱动**（行高固定、格数变多则总高变多）⇒ 难度**会**导致溢出。

**⇒ 今天这一族的九个 bug，**全部是「网格太宽、超过可用高度」**，与难度无关 —— 所以修法是「让它变窄」而不是「防它变高」。**

## ⇒ 顺带：真正的风险面在哪

**⇒ 不是「难度」，而是**「同一款在不同屏幕尺寸下」** —— 折叠屏（`356` 款已测）与电视（未测，第 ⑤ 项）才是高度会变的场景。**
**⇒ 这正好回到奥森没拍板的第 ⑤ 项上。**
