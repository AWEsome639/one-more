# 判据 `3089`：`Simon Command` 竖屏四色面板被切一半 + 一个「构建成功但产物没变」的陷阱

## 一、真缺陷（竖屏 `741×832vp`）

`blk=3/72px`，截图确认：**底部「绿/黄」两个面板被切掉一半**。
这是个必须四色全可点的游戏 —— 缺两个就等于没法玩。

## 二、根因：算式只算了「宽被兜住」，没算「两行高加起来」

`GSimonCommand.ets` 两处行宽：
```typescript
}.width(Bp.isShort()
  ? Math.min(Bp.width, Math.max(200, 1.4 * (Bp.height - 400) + 10))   // 横屏：限宽
  : '100%')                                                            // 竖屏：原样
```

原注释的理由是：
> 竖屏 `1.4 × (832−200) = 885vp`，被 `Bp.width(741)` 兜住 ⇒ **竖屏原样不动**。

⇒ 这个推理只证明了「**宽度**不会被撑破 `741`」，**没有算两行面板的垂直加起来会不会超屏**。
⇒ 实际：每行 `741` ⇒ 每块 `365` 宽 ⇒ `365/1.4 = 261` 高 ⇒ 两行 `522vp` ⇒ 加上 chrome 超 `24vp`。

## 三、修法（竖屏也走同一套高度反推）

```typescript
: Math.min(Bp.width, Math.max(200, 1.4 * (Bp.height - 424) + 10)))   // 竖屏
```

⇒ 竖屏扣 `424`（横屏仍 `400`）。

## 四、两次拟合

| 竖屏扣减 | `blk` | 截图 |
|---|---|---|
| `'100%'`（原）| `3/72px` | **绿/黄两面板各切一半** |
| `400`（= 横屏值）| `1/24px` | 四色块全完整，但「不做动作」贴屏沿 |
| **`424`** | **`1/24px`** | **四色块 + 不做动作按钮全部完整** ✓ |

## 五、⚠️ 过程中踩到的陷阱：`BUILD SUCCESSFUL` 但 HAP 字节没变

改完 `-424` 后：
```
> hvigor BUILD SUCCESSFUL in 1 s 97 ms
HAP 53502883  11-20 23:11      ← 和改之前一模一样
```
⇒ **增量构建判定「无需重建」，产物是旧的**。装上量出来的还是改之前的表现。

修法：`hvigorw clean` 再 `assembleHap` ⇒ 这次 `8 min 29 s`、HAP `53502884` / `23:44`。

⇒ **这是「编译通过且 HAP 字节变化才提交」那条纪律的唯一实际防线。**
   看日志说 `SUCCESSFUL` 是不够的 —— 必须看 `ls -l` 的字节数与时间。

## 六、判据

> **「`BUILD SUCCESSFUL`」只说明构建流程没报错，不说明它重建了任何东西。**
> 改完一个常数却只花 `1 秒` 就「成功」，那不是快，那是**没干活**。

⇒ 三条：
1. **每次构建后必须核对 HAP 的字节数与 mtime**；`1 秒` 的「成功」几乎必然没重建
2. **「宽度被兜住」不等于「装得下」** —— 一个纵向排布的行，要算的是**总高度**，不是单行宽度
3. **拟合常数时把「当时多少、改成多少、`blk` 从几到几、截图看到了什么」四样都写进注释** ——
   否则下一个人会以为那是理论值

## 七、修完之后静态扫全库：**这个 bug 类没有第二例**

按「竖屏分支是纯 `'100%'` + 至少有 `2` 个宽高比 > `1` 的 `aspectRatio` 容器」扫 `355` 款：

```
命中 0 款
```

⇒ `Simon Command` 是**唯一一处**「竖屏只算宽、不算高」的写法，改完就清零。

⇒ 同一条判据也扫了「有 ≥2 个扁容器且通篇无 `Bp.height` 反推」⇒ 同样 `0` 款。

⇒ **负结果也要记**：不记的话，下一次我又会怀疑「是不是还有一堆」，白扫一遍。
