## 五、助手设计：`Bp.capMax()`

**核心思想**：**永远不要用「不限制」表达「大屏」**。
限制值应当**永远按可用宽高反推**，而不是让高屏分支返回哨兵。

```ts
// core/Bp.ets
export class Bp {
  /**
   * 「棋盘/容器」的尺寸上限。
   * ★ 判据：高屏 ≠ 不限制 —— 窄屏受宽约束，高屏受高约束，两者取小。
   * @param reserve 游戏区内除盘面外的固定开销（vp），默认 360
   * @param floor   可点/可读的最小边长，默认 140
   */
  static capMax(reserve: number = 360, floor: number = 140): number {
    const byWidth: number = Bp.width - 2 * Space.lg;      // 电视 1240 / 手机横屏 817
    const byHeight: number = Bp.height - 190 - reserve;   // 先扣 GameHost，再扣盘面外开销
    return Math.max(floor, Math.min(byWidth, byHeight));
  }
}
```

**代入验证**

| 场景 | byWidth | byHeight | `capMax()` | 旧写法（`X=360` 哨兵式）|
|---|---:|---:|---:|---|
| 电视 1280×720 | 1240 | 720−190−360 = **170** | **170** | 9999 → **1240** ❌ |
| 手机横屏 853×533 | 817 | 533−190−360 = **−17** → floor **140** | **140** | 173 |
| 手机竖屏 360×780 | 320 | 780−190−360 = 230 | **230** | 614 ❌ |

**⇒ 一改就把 A 类 3 款 + B 类 `GWordle` 全部收口**（电视上自动变小，手机竖屏也不会爆）。

**配套（更重要）：加一条 lint/断言**

> **禁止在「尺寸位置」出现 `9999` / `Infinity` / `≥1000` 的字面常数。**
> 尺寸位置 = `.width()` / `.height()` / `constraintSize` 的 `maxWidth` / `maxHeight`。
> 需要「不限制」时写 `Bp.capMax()`，或显式写一个**有依据的上限**。

**理由**：`9999` 的语义是「没有上限」，而布局里**任何节点都有上限**（屏幕）。
一旦把「无限」交给 `aspectRatio(1)`，它就等于「等于可用宽」——在宽屏上必然炸。
**这类 bug 靠逐个修是修不完的（这次就 107 处），必须从写法上禁掉。**

## 七、`capMax()` 的安全评估：它会不会碰坏现有布局

> 本节全部离线可算：只代入数值，不碰设备。

### 7.1 四设备代入

`capMax(reserve=360, floor=140)`：
```
byWidth  = W − 2×Space.lg
byHeight = H − 190 − reserve
capMax   = max(floor, min(byWidth, byHeight))
```

| 设备 | `W × H` | `byWidth` | `byHeight` | **`capMax()`** |
|---|---|---:|---:|---:|
| 手机横屏 | 853 × 533 | 813 | **−17** | **140**（floor 兜住）|
| 手机竖屏 | 360 × 744 | 320 | 194 | **194** |
| 平板 | 800 × 1280 | 760 | 730 | **730** |
| 电视 | 1280 × 720 | 1240 | **170** | **170** |

**⚠️ 第一个警告**：手机横屏算出来是 **140**，而现在那批 `X=360` 的款是 **173**。
**⇒ 统一替换会让手机横屏的盘面从 173 缩到 140（−19%）。**

### 7.2 与现状逐个对照（手机横屏才是已真机验证的基线）

| 款 | 现（手机） | `capMax` | Δ手机 | 现（电视） | →`capMax` | Δ电视 | 手机侧影响 |
|---|---:|---:|---:|---:|---:|---:|---|
| `GKakuro` | 173 | 140 | **−33** | 360 | 170 | −190 | 🔴 变小（回归）|
| `GKakuroMini` | 173 | 140 | **−33** | 360 | 170 | −190 | 🔴 变小（回归）|
| `GSokoban` | **88** | 140 | **+52** | 9999 | 170 | −9829 | 🔴 **变大**（回归）|
| `GWordle` | **120** | 140 | **+20** | 614 | 170 | −444 | 🔴 **变大**（回归）|
| `GNumberBondsAll` | 300 | 140 | **−160** | 9999 | 170 | −9829 | 🔴 严重缩小 |
| `GShikaku` | 173 | 140 | **−33** | 360 | 170 | −190 | 🔴 变小 |
| `GPhoneticGuess` | **280** | 140 | **−140** | 2000 | 170 | −1830 | 🔴 **缩到一半** |

**⇒ 7 处全部都会变，而且两个方向都有：**
- **变小**（`−33 ~ −160`）：盘面/内容区变小 ⇒ 手机上「本来装得下」变成「更空了」，属**观感回归**
- **变大**（`+20 ~ +52`）：`GWordle` 120→140、`GSokoban` 88→140 ⇒ 手机上**可能反而撑爆**

**⇒ 统一替换 `capMax()` 会同时制造两类回归，不能全局用。**

### 7.3 更严重的一条：`reserve=360` 不适配所有节点

`GPhoneticGuess:514` 是 `maxHeight`（选项区高度），手机横屏已验证 **280**。
`capMax()` 给 **140** —— **比它手机上的实际需要还小一半**，直接会**裁掉选项**。

**⇒ `capMax(reserve=360)` 的 360 是「盘面外开销」的经验值，只对「棋盘」成立；
对「选项区 / 列表区」这类节点，360 太大（把它们压死了）。**
**⇒ 这个助手不能只有一个默认 `reserve`。**

### 7.4 两个方案取舍

| 方案 | 手机/平板 | 电视 | 风险 | 结论 |
|---|---|---|---|---|
| **A. 全局替换** `capMax()` | 7 处全变（两个方向都有回归）| 修好 | 🔴 **高**（手机基线全动）| ❌ **不采纳** |
| **B. 只电视生效** `Bp.isTv() ? capMax(reserve) : <现状>` | **完全不变**（逐字保持）| 修好 | 🟢 低（手机零改动）| ✅ **采纳** |

**B 方案写法：**
```ts
// 盘面：reserve 用 360（已验证的盘面外开销）
.maxWidth(Bp.isTv() ? Bp.capMax(360) : Math.min(Bp.width - 2*Space.lg, Math.max(140, Bp.height - 360)))

// 选项区：reserve 必须另给（例如 200），不能套 360
.maxHeight(Bp.isTv() ? Bp.capMax(200) : (Bp.isShort() ? 280 : 2000))
```

**⇒ B 方案的代价**：每处要写一个 `Bp.isTv() ?` + 一个**合适的 `reserve`**，
比「一处替换到底」啰嗦，但**手机侧逐字不变 ⇒ 零回归**，这是能接受的交易。

### 7.5 一句判断

**这个助手该加，但只能「只在电视分支用」，不能全局替换。**

理由：
1. **手机横屏是唯一经过真机验证的基线**，而 `capMax()` 在手机横屏算出的 140 与现状 173/120/88/280 全都不等
   ⇒ 全局替换等于**把 355 款的手机布局全部重算一遍**，风险与收益完全不成比例。
2. `Bp.isTv() ? capMax(...) : <现状>` 让**手机逐字不变、电视被收口**，正是这次要的效果。
3. **`reserve` 不能只有一个默认值**：`360` 只对棋盘成立，选项区/列表区套 360 会压死内容
   （`GPhoneticGuess` 就是例子，280 → 140）。
   ⇒ 助手签名应强制显式传 `reserve`，或按节点类型给几档常量（如 `CapReserve.BOARD=360 / LIST=200`）。

**⇒ 落地顺序建议**（先止血、后机制）：
1. 先按 §2 的 3 款（`GKakuro` / `GKakuroMini` / `GSokoban`）+ `GWordle` 加 `Bp.isTv()` 分支 —— **4 处，最小改动**
2. 再上 `Bp.capMax(reserve)` 助手 + lint（禁止尺寸位置的 `9999`/`≥1000` 字面量）
3. **最后才考虑**把其余 `isShort()` 尺寸三元逐个收敛 —— 那是 96 处设计尺寸，**不该用 `capMax` 处理**

# §8 结论：`capMax()` **不能全局替换**，只能「只在电视分支用」（我采纳）

## 为什么不能全局：手机横屏是唯一真机验证基线，而它会被改

`capMax(reserve=360, floor=140)` 四设备代入：

| 设备 | `byWidth` | `byHeight` | **`capMax()`** |
|---|---:|---:|---:|
| **手机横屏 `853×533`** | `813` | **`−17`** | **`140`（floor 兜住）** |
| 手机竖屏 `360×744` | `320` | `194` | `194` |
| 平板 `800×1280` | `760` | `730` | `730` |
| 电视 `1280×720` | `1240` | **`170`** | **`170`** |

**⇒ 手机上 `byHeight` 是负数（`533 − 190 − 360 = −17`）⇒ 只能落到 floor `140`。
而多数款手机现值是 `173`、`300`、`280` ⇒ 会被统一压到 `140`。**

| 款 | 现（手机） | `capMax` | Δ | 方向 |
|---|---:|---:|---:|---|
| `GKakuro` / `GKakuroMini` / `GShikaku` | `173` | `140` | `−33` | 🔴 变小 |
| **`GSokoban`** | **`88`** | `140` | **`+52`** | 🔴 **变大** |
| **`GWordle`** | **`120`** | `140` | **`+20`** | 🔴 **变大** |
| `GNumberBondsAll` | `300` | `140` | `−160` | 🔴 严重缩小 |
| **`GPhoneticGuess`** | **`280`** | `140` | **`−140`** | 🔴 **缩一半** |

**⇒ `7` 处全变，且「变小」与「变大」两类回归同时出现。全局替换 = 在修电视的同时打乱手机。**

## 还有一条更狠的：`reserve=360` 只对棋盘成立

`GPhoneticGuess:514` 是**选项区**的 `maxHeight`，手机实测 `280`（已验证能装）。
`capMax(360)` 给 `140` ⇒ **直接裁掉一半选项**。

**⇒ `360` 是「棋盘外开销」的经验值。选项区 / 列表区套它 = 压死内容。**
**⇒ 若要上这个助手，`reserve` 必须强制显式传，或分类型给常量（`CapReserve.BOARD=360` / `LIST=200`），不许有「一个默认值打天下」。**

## ⇒ 采纳的方案：**只在电视分支用**

```ts
// 棋盘（reserve 360）
.maxWidth(Bp.isTv() ? Bp.capMax(360) : Math.min(Bp.width - 2*Space.lg, Math.max(140, Bp.height - 360)))
// 选项区（reserve 200）
.maxHeight(Bp.isTv() ? Bp.capMax(200) : (Bp.isShort() ? 280 : 2000))
```

**⇒ 手机 / 平板逐字不变（走 `else` 分支）⇒ 零回归，只改电视。**

**这与判据 `2052` 一脉相承**：把「设备专属守卫」写成通用判据，就会在你不想要的那台设备上生效。

## 落地顺序（三步，别一次做完）

| 步 | 做什么 | 规模 |
|---|---|---|
| **1. 先止血** | 只给 **`4` 处真炸**（`GKakuro:632` / `GKakuroMini:562` / `GSokoban:704-709` / `GWordle:492`）加 `Bp.isTv()` 分支 | **`4` 处最小改动** |
| 2. 再收口 | 加 `capMax(reserve)` 助手 + lint（**禁止尺寸位置出现 `9999` / `Infinity` / `≥1000` 字面量**）| 助手 + 一条 lint |
| 3. 最后才看 | 其余 `96` 处 `isShort()` 尺寸三元 | **这些是「设计尺寸」（刺激区 `120:180` 之类），不该用 `capMax` 处理** |

**⇒ 关键判断：第 `3` 步大概率是「不做」。**
`Bp.isShort() ? 120 : 180` 这种是**故意的刺激区尺寸**，不是「限高失控」。
**把它也套 `capMax` 会把设计意图一起改掉 —— 那是另一种浅。**

**⇒ 所以电视这件事的真实规模是「`4` 处止血 + `1` 个助手 + `1` 条 lint」，不是「`107` 处全改」。**

## ⇒ 判据（`2055`）

**一个「统一收口」的助手，如果它的默认参数是为某一类节点（棋盘）拟的，
那它对另一类节点（选项区）就是错的。**
**⇒ 收口之前先问：这批节点是同一类吗？** 棋盘和选项区共用 `reserve=360` 的后果是「选项被裁一半」——
而这在手机侧不会暴露（手机走 else 分支），**只会在电视上悄悄发生**。
