# ★ 电视漏网：`84` 处裸 `Bp.height` 比较绕过了 `!isTv()` 守卫

> `2026-11-14 10:1x` 静态扫描。**这是目标第 ⑤ 项「电视 `3` 米观感」的一个具体缺口。**

## 一、已经修了什么

`Bp.isShort()`（`Bp.ets:299`）现在长这样：

```ts
static isShort(): boolean {
  // ★★★ 2026-11-03：620 → 690
  // ★★★ 2026-11-13（队友静态分析）：电视不该进「矮屏」分支 ——
  //   1080p 电视 @dens2.0 ⇒ px2vp(1080) = 540vp ⇒ 原来会判成矮屏，
  //   于是隐藏说明行、棋盘封顶、Cell.of ×0.85 整套减法都在电视上生效
  //   ⇒ 越修越小，而 10-foot UI 恰恰相反（3 米视距需要更大）
  return Bp.height < 690 && !Bp.isTv();
}
```

**⇒ 这修好了 `738` 处 `isShort()` 调用（涉 `334` 款）。**

## 二、漏了什么

**`24` 款里有 `84` 处直接写 `Bp.height < 600`，绕过了 `isShort()`，因此也绕过了 `!isTv()`。**

| 项 | 数字 |

| 幸免的（阈值 `≤540`） | **`0` 处** |

**⇒ 电视上这 `24` 款全部使用「小号」格子与间距 —— 与 `10-foot UI` 的需求正好相反。**

## 三、修法（两种，建议 A）

**A. 加一个语义明确的助手（推荐）**

```ts
// core/Bp.ets
/** 屏幕「紧」到要减尺寸 —— 但电视永远不算紧（10-foot UI 要更大） */
static tight(): boolean {
  return Bp.height < 600 && !Bp.isTv();
}
```

然后 `84` 处 `Bp.height < 600` → `Bp.tight()`。

**好处**：① 一次把所有绕过的点收进同一个语义 ② 以后新增的点不会又裸写
③ 名字直接说明它和电视无关，比裸表达式更难误用

**B. 逐处加 `&& !Bp.isTv()`**
简单但会重复 `84` 次，且下次新写的代码还会漏。

## 四、为什么现在不做

1. **`84` 处 / `24` 款，改动面大** —— 按「一次只改一处」的纪律，这至少要分批
2. **它属于第 ⑤ 项（电视），而第 ⑤ 项排在布局清零之后**
3. **改完必须编译 + 真机验**，而今晚/明晚两个窗口都已排死
4. **且它不影响手机**（手机横屏 `533 < 600` 本来就该走「小」分支，行为正确）

**⇒ 排期：布局清零 → 端侧 LLM 选路 → 电视这条（第三晚以后）**

## 五、一个附带发现

`narrowHeight()`（`Bp.ets:296`，`Bp.height < 420`）**使用量为 `0`**。
它是为「我只关心高度」这件事专门抽出来的，注释里还写了为什么单独一个
（`DemoBar` 演示条、`GameHost` 图标尺寸写过裸的 `< 420`）。

**⇒ 但抽出来后没人用，`84` 处新代码仍旧裸写 `< 600`。**
**⇒ 判据：抽了抽象却不用，等于没抽。** 要么在 code review 清单里加一条「新写的高度判断必须用助手」，
要么就别建这个抽象 —— 否则它会变成「看起来很规范」的假象。

# 六、电视这条线的完整账（同日 `10:2x`，查完了）

## 代码里电视到底做了什么

| 能力 | 有无 | 在哪 |
|---|---|---|
| **遥控器输入 / 焦点视觉** | ✅ **有** | `core/Tv.ets`：`on()` / `focusBorder` / `focusOutline` / `handleKey` / `isArrow` / `arrowDelta` / `isEsc` / `desktopKeys` |
| **尺寸适配（电视要更大）** | ❌ **没有任何原语** | 无 |
| 显式 `isTv()` 判断 | `11` 处 / `5` 文件（全在 `core` / `components`） | **`games/` 里一处都没有** |

**⇒ 结论：电视的「输入」是集中做好的，「尺寸」完全没有集中机制。**
游戏侧只能靠两条路继承：`isShort()`（`11-13` 加了 `!isTv()` 守卫，覆盖 `738` 处）
与 `84` 处裸 `Bp.height < 600`（**绕过守卫**）。

## 两个层次的问题，别混

**第一层（已在上一节给出修法）**：那 `84` 处让电视**变小** ⇒ 改成 `Bp.tight()` 即可「不再变小」。
**第二层（更深，尚未有解）**：`10-foot UI` 需要的是「**变大**」，而库里**没有尺寸放大原语**。
修好第一层后，电视最多是「和手机一样大」，而不是「3 米看得很舒服」。

**⇒ 所以第 ⑤ 项「电视 `3` 米观感」的真实工作量，比「修 `84` 处」大一步：**
**要新增一个尺寸缩放层**（类似 `Cell.of()` 之于手机），电视走一个放大系数。
那是一个设计决策（放大多少、哪些元素放大、会不会撑破 `540vp` 的高度），
**不是一次批量替换能解决的。**

## ⇒ 排期不变，但工作量要重新估

**第 ⑤ 项的电视一条：**
1. 先修 `84` 处 `Bp.height < 600` → `Bp.tight()`（防变小）—— 半天，需一次编译
2. 再做尺寸放大层 + `onemore_tv` 真机看图 —— **这是新功能，不是修补**
3. 且它必须在布局清零之后（否则放大后又会溢出）

**⇒ 判据（`2039`）：一个平台「适配好了」的标志不是「代码里有 isXxx 分支」，
而是「这个平台的**核心需求方向**有对应的机制」。**
电视的核心需求是「更远、更大」，而库里只有「防变小」的守卫，没有「变大」的机制 ——
**这就是为什么它一直「看着像做完了，跑起来不对」。**

# ⛔ 再撤回：**尺寸放大原语一直存在**，是 `Bp.scale()` 电视 `1.45`

**上一节我写「库里没有任何尺寸放大原语，第 ⑤ 项要新增一个缩放层」——错的，撤回。**

**错因**：我只读了 `core/Tv.ets`（它还真的只管输入焦点），就下结论说「没有尺寸机制」。
**没读 `Cell.of()` 的实现** —— 而它才是所有尺寸的唯一入口：

```ts
static of(base: number): number {
  let shrink: number = 1;
  if (Bp.height > 0 && Bp.height < 600 && !Bp.isTv()) {   // ← 电视免于 0.85 压缩
    shrink = 0.85;
  }
  return Math.round(base * Cell.k * Bp.scale() * shrink);  // ← 电视在这乘 1.45
}
```

`Bp.scale()`（`Bp.ets:96`）：

```ts
static scale(): number {
  if (Bp.dev === BpDev.TV) { return 1.45; }   // 3 米视距，必须大
  if (Bp.dev === BpDev.WATCH) { return 0.92; }
  if (Bp.isLg()) { return 1.12; }
  if (Bp.isMd()) { return 1.06; }
  return 1.0;
}
```

**⇒ 放大原语不但有，而且就是「一处改动、`355` 款自动跟着放大」那种集中式设计。**

## 修正后的电视真实账

| 机制 | 状态 |
|---|---|
| **尺寸放大** | ✅ **有**：`Bp.scale()` 电视 `1.45`、PC `1.12`、平板 `1.06`、手机 `1.0`、手表 `0.92` |
| 免于 `0.85` 矮屏压缩 | ✅ `Cell.of()` 里 `&& !Bp.isTv()`（`11-13`）|
| 免进 `isShort()` 分支 | ✅ `isShort()` 里 `&& !Bp.isTv()`（`11-13`）|
| **那 `84` 处的真实影响** | 它们在 `Cell.of(...)` **参数里**二选一（如 `48 : 56`）；电视 `540 < 600` ⇒ 选小的 |

**算一遍（以 `48 : 56` 为例）**：

| 场景 | 实际值 |
|---|---|
| 手机横屏（`1.12 × 0.85`） | `48 × 0.952 ≈ 45.7` |
| 电视**带漏网**（选 `48`） | `48 × 1.45 ≈ 69.6` ⇒ 比手机大 **`52%`** |
| 电视**修好后**（选 `56`） | `56 × 1.45 ≈ 81.2` ⇒ 比手机大 **`78%`** |

**⇒ 所以那 `84` 处让电视「少大了约 `14%`」（`69.6` vs `81.2`），
不是「完全没放大」。严重性远低于我上一节的判断。**

## ⇒ 第 ⑤ 项电视一条的工作量，改回小规模

**不是「新增缩放层」，是「修 `84` 处让它选对基线」** —— 半天，一次编译，不动架构。

# 七、第二条漏网：`77` 处盘面封顶**完全不经过放大层**（`10:3x`）

上一节确认了 `Cell.of()` 是尺寸的放大入口。**那么盘面封顶呢？**

```bash
$ grep -h "Math.min(Bp.width" games/*.ets | grep -c "Cell.of"
0
$ grep -h "Math.min(Bp.width" games/*.ets | wc -l
77
```

**⇒ 全库 `77` 处盘面封顶，`0` 处包在 `Cell.of()` 里 —— 它们都是裸 `vp` 值。**

## 好消息：我全天的布局模型成立

`104 (头部) + cap (裸vp) + 底部 ≤ 533 (裸vp)` —— **式子两边口径一致，不需要乘任何系数。**
所以前面所有 `盘面 + 底部` 的算术**不用重算**。

## 坏消息：电视/PC 上放大层够不到盘面

| 路径 | 被 `Bp.scale()` 放大？ |
|---|---|
| `Cell.of()` 包住的（格子、按钮、行高） | ✅ 电视 `1.45`、PC `1.12`、平板 `1.06` |
| **裸 `Math.min(Bp.width…)` 封顶（盘面）** | ❌ **完全不放大** |

**⇒ 电视上的实际效果：盘面停在 `240vp`（甚至比手机还显小），而周围的格子与按钮都放大了 `1.45` 倍
⇒ 比例失衡，「盘面像缩在中间」。**

**⇒ 这与「`84` 处选错基线」是两个独立问题**：
· `84` 处 ⇒ 电视的元素**不够大**（`52%` 而非 `78%`）
· `77` 处 ⇒ 电视的**盘面不跟着大**，与周围元素不成比例

## ⇒ 第 ⑤ 项电视一条，现在是三件独立的事

| # | 问题 | 规模 | 性质 |
|---|---|---|---|
| 1 | `84` 处裸 `Bp.height < 600` 选错基线 | `24` 款 | 半天，一次编译 |
| 2 | **`77` 处盘面封顶不放大** | **最多 `77` 款** | 需设计决策（盘面要不要也 ×`1.45`？`1.45` 会不会撑破 `540vp` 高度？）|
| 3 | 真机看 `3` 米观感 | 1 款起步 | 需 `onemore_tv` 首启 `3`–`5` 分钟 |

**⇒ 第 2 件是真问题**：若盘面也 ×`1.45`，`240 × 1.45 = 348vp`，加头部在电视上（`540vp` 高度）
⇒ `348 + 头部` 可能就满了，底部没地方。**所以不能简单乘，要重新算电视版预算。**

**⇒ 判据（`2041`）：一个项目里有两条尺寸路径（`Cell.of()` 与裸 `Math.min`），
就必然在「跨设备放大」上分裂 —— 一条跟着放大、一条不动。
所以「换一台设备也成立」这条证据要求，专挑这类地方破功。**

# 八、最大的那条漏网：**字号/间距/圆角完全不放大**（`10:4x`，定量）

## 尺寸系统实际是五条路径，只有一条会放大

| 来源 | 处数 | 电视 `Bp.scale() = 1.45` 生效？ |
|---|---:|---|
| `Cell.of(` / `Cell.tap(`（格子、按钮、行高） | **`1,067`** | ✅ **会** |
| **`FontSize.`**（字号） | **`5,112`** | ❌ **不会**（纯静态常量 `10`–`36`）|
| **`Space.`**（间距） | **`3,965`** | ❌ 不会 |
| **`Radius.`**（圆角） | **`2,895`** | ❌ 不会 |
| `Math.min(Bp.width…`（盘面封顶） | `77` | ❌ 不会 |

**⇒ 会放大的 `1,067` 处 vs 不会放大的 `11,972` 处 ≈ `1 : 11`。**

## 为什么这是电视最要命的一条

`10-foot UI` 的核心是**可读性** —— 3 米外看得清字。
而现在的效果恰好相反：

| 电视上 | 变化 |
|---|---|
| 可点区域（格子、按钮） | **`×1.45`**（变大，好按）|
| **文字** | **不变**（`FontSize.md` 仍是 `16`）|
| 间距 | 不变 |
| 盘面 | 不变 |

**⇒ 结果：按钮变大、字没变大 ⇒ 字在容器里显得**更小**，比手机还难读。**

## 已排除的两条可能的补救

1. **`isLg()`** = `Bp.width >= 840`；电视 `px2vp(1920) = 960` ⇒ 为真。
   **但 `isLg()` 只是宽度条件，本身不放大任何东西**，且全库仅 `17` 处用到。
2. **`games/` 里的 `isTv()`**：**一处都没有**（`11` 处全在 `core`/`components`，且都是输入焦点相关）。

**⇒ 所以电视上没有任何代码把字放大。这不是推测，是「`0` 处」的统计结果。**

## ⇒ 修法需要设计决策，不能批量替换

**不能简单给 `FontSize` 乘 `1.45`**：`FontSize.md = 16 → 23`，而全库 `5,112` 处布局都是按 `16` 算的行高与容器
⇒ 大面积文字溢出（这次是**文字**溢出，`blk` 完全看不见 —— 因为 `blk` 的 `SKIP` 含 `Text`）。

**可能的方向（需实验）**：
- 给 `FontSize` 加一档 TV 专用值（如 `md` 电视 `19`，只放大 `19%` 而不是 `45%`）
- 或按「大字号少放大、小字号多放大」的非线性映射（`micro 10 → 13`、`hero 36 → 44`）
- 且必须先在 `onemore_tv` 上看一次现状（说不定 3 米下现有的 `16` 已经能看）

**⇒ 所以第 ⑤ 项电视一条的**第一件事不是改代码，是**跑起来看一眼**。
在没看过 3 米实际效果之前，任何放大方案都是猜。**

**⇒ 判据（`2042`）：`Bp.scale()` 这类「统一缩放」只在**同一量纲**内成立。
尺寸（`Cell.of`）、字号（`FontSize`）、间距（`Space`）是三个不同量纲，
一个缩放系数只能覆盖其中一个 —— 声称「一处改动、`355` 款自动跟着放大」时，
**必须说清它放大的是哪一维**。**

# ⛔ 重大修正（`10:5x`）：本机电视是 **`720vp`**，不是 `540vp` ⇒ 三件事里一件作废

**我一直用 `540vp`（来自 `Cell.of()` 注释里的「`1080p @dens2.0` ⇒ `px2vp(1080)=540`」）。
但那是**另一种电视**。本机实例不是它。**

实测 `~/.Huawei/Emulator/deployed/onemore_tv/config.ini`：

```
hw.lcd.density=480
hw.lcd.single.width=3840
hw.lcd.single.height=2160
```

**⇒ `1vp = 480/160 = 3px` ⇒ `3840/3 = 1280vp` 宽、`2160/3 = 720vp` 高。**

## 对三件事的逐条影响

| 项 | 按 `540vp` 推 | 实际 `720vp` | 结论 |
|---|---|---|---|
| `isShort()` 会不会触发 | `540 < 690` ⇒ 会，需 `!isTv()` 守卫 | **`720 ≥ 690` ⇒ 不会** | 守卫对**本机**是冗余的 |
| `Cell.of()` 的 `0.85` 压缩 | `540 < 600` ⇒ 会压 | **`720 ≥ 600` ⇒ 不压** | 同上 |
| **`84` 处裸 `Bp.height < 600`** | `540 < 600` ⇒ **全走「小」** | **`720 < 600` 为假 ⇒ 全走「大」** | **对本机不是问题，作废** |

**⇒ 那 `84` 处只对「`1080p @dens2.0 ⇒ 540vp`」那一类电视才有害。**
**本机（4K@480 ⇒ `720vp`）上它们是对的。**

**⇒ `11-13` 加的两处 `!isTv()` 守卫也一样：它们防的是「矮电视」，本机不矮。**
**守卫本身没错（`540vp` 的电视真实存在），但别拿它当「电视已修好」的依据 —— 它对本机无事可做。**

## 剩下的两条**反而更尖锐了**

`Bp.scale() = 1.45` 在 `720vp` 下是**无条件生效**的（既没被 `0.85` 抵消，也不受 `isShort` 影响）：

| 电视上 | 实际 |
|---|---|
| `Cell.of()` 包住的尺寸 | `× 1.45` ✅ 变大 |
| **`FontSize`（`5,112` 处）** | **不变** ❌ |
| **`77` 处盘面封顶** | **不变** ❌ |

**⇒ 所以「格子比字大 `45%`」这个失衡，在 `720vp` 下比在 `540vp` 下更明显**
（`540vp` 时至少还有 `0.85` 压缩把格子压回来一点；`720vp` 什么都不压）。

## ⇒ 第 ⑤ 项电视一条，从三件事缩到两件

| # | 事项 | 状态 |
|---|---|---|
| ~~1~~ | ~~`84` 处选错基线~~ | **作废**（只对 `540vp` 类电视有害，本机无影响）|
| 2 | **`77` 处盘面封顶不放大** | 待决策（`240 × 1.45 = 348`，电视高 `720` ⇒ 头部 + `348` + 底部 是否装得下要现算）|
| 3 | **`FontSize` 不放大** | 待决策 + **必须先看真机** |
| 4 | 真机看 `3` 米观感 | 需 `onemore_tv` 首启 `3`–`5` 分钟 |

**⇒ 第 2 件现在可以算了**：电视 `720vp` 高、头部按比例大约仍是 `100~110vp`
⇒ `110 + 348 + 底部` 若底部 `< 262vp` 就装得下。**比 `540vp` 时宽松得多。**

**⇒ 判据（`2043`）：同一个「设备类型」（`TV`）在不同分辨率/密度下，`vp` 高度可以差 `33%`（`540` vs `720`）。
用「设备类型」推断可用空间，会错一整档。必须查实例的 `density` 与 `single.width/height` 现算。**

# 九、修正后的真风险：不是「盘面显小」，是「格子撑出盘面」（`11:0x`，可算）

上一节修正到 `720vp` 后，问题性质变了。真正可算的是**两条路径的比值**：

## 同一个 `Cell.of(N)` 在两台设备上的实际值

| 场景 | 系数 | `Cell.of(N)` |
|---|---|---|
| 手机横屏 `853×533` | `Cell.k(1) × Bp.scale()(1.12) × shrink(0.85)` | **`0.952N`** |
| **电视 `1280×720`** | `1 × 1.45 × 1`（无压缩） | **`1.45N`** |

**⇒ 比值 `1.45 / 0.952 = 1.523`。**

## 而盘面封顶值**一台设备都不同** —— 它是裸 `vp`

`Math.min(Bp.width - 2*Space.lg, Math.max(F, Bp.height - 360))`：

| 设备 | `Bp.width` | `Bp.height` | 该式取值 |
|---|---|---|---|
| 手机 | `853` | `533` | `min(853-48, max(240, 173))` = **`240`**（受 floor）**|
| 电视 | `1280` | `720` | `min(1280-48, max(240, 360))` = **`360`** |

**⇒ 电视的封顶从 `240` 变到 `360`（+`50%`），格子从 `0.952N` 变到 `1.45N`（+`52%`）。**

**⇒ 巧的是这两个增幅几乎相等（`50%` vs `52%`）！**
**⇒ 所以对「盘面按可用高反推」的那批款，电视上**大致比例是对的** —— 我之前担心的溢出基本不成立。

## 但另有 68 款是「盘面封顶 + 固定尺寸格子」并存

```
既用 Math.min(Bp.width…) 又不只一处 Cell.of/Cell.tap 的：**68 款**
```

最重的几款：`MentalMapping`（`Cell.of 10` / `Cell.tap 9`）、`MazeNav3d`（`6`/`7`）、
`WordSnakeTrail`（`5`/`5`）、`CountdownMath`（`5`/`1`）、`Kakuro`（`5`/`1`）、`Sokoban`（`6`/`0`）。

**⚠️ 这批的真实风险取决于「格子尺寸是由盘面推导，还是写死」**：
- 若格子是 `.layoutWeight(1)` 由盘面瓜分 ⇒ 跟着盘面走，**没问题**
- 若是 `.height(Cell.of(50))` 写死（如 `GVectorGridAlignment:339`）⇒ **盘面 `360` 里塞 `72.5` 一行，
  能塞几行取决于行数**，可能溢出

**⇒ 我无法静态断定这 68 款里哪些会溢出** —— 需要看每款的盘面是「方阵 + layoutWeight」还是「固定行高」。
**但这已经是一个可以真机一击验证的假设**：

**⇒ 「电视上 `68` 款里有若干款会因格子写死而撑出盘面」，跑一遍 `sweep_all` 就有答案。**

**⇒ 判据（`2044`）：跨设备缩放出问题时，**先算两条路径的比值**，比先猜「哪边不够大」有效得多。
这次算出来 `1.523` vs `1.50`，几乎抵消 —— 于是「会不会溢出」从不可知变成「只有固定行高那批才会」。**
