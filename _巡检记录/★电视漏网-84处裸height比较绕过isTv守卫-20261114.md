# ★ 电视漏网：`84` 处裸 `Bp.height` 比较绕过了 `!isTv()` 守卫

> `2026-11-14 10:1x` 静态扫描。**这是目标第 ⑤ 项「电视 `3` 米观感」的一个具体缺口。**

## 一、已经修了什么

`Bp.isShort()`（`Bp.ets:299`）现在长这样：

```ts
static isShort(): boolean {
  // ★★★ 2026-11-03：620 → 690
  // ★★★ 2026-11-13（队友静态分析）：电视不该进「矮屏」分支 ——
  //   1080p 电视 @dens2.0 ⇒ px2vp(1080) = 540vp ⇒ 原来会判成矮屏，
  //   于是隐藏说明行、棋盘封顶、Cell.of ×0.85 整套减法都在电视上生效
  //   ⇒ 越修越小，而 10-foot UI 恰恰相反（3 米视距需要更大）
  return Bp.height < 690 && !Bp.isTv();
}
```

**⇒ 这修好了 `738` 处 `isShort()` 调用（涉 `334` 款）。**

## 二、漏了什么

**`24` 款里有 `84` 处直接写 `Bp.height < 600`，绕过了 `isShort()`，因此也绕过了 `!isTv()`。**

实测（`2026-11-14 10:1x`）：

| 项 | 数字 |
|---|---|
| 裸 `Bp.height <` 比较 | **`84` 处 / `24` 款** |
| 阈值分布 | **`{600: 84}`** —— 全是 `< 600`，无一例外 |
| 电视可用高度 | **`540vp`**（`px2vp(1080)`，`@dens2.0`）|
| 电视会走「小」分支的 | **`84` 处（`100%`）** |
| 幸免的（阈值 `≤540`） | **`0` 处** |
| `narrowHeight()` 使用量 | **`0` 处**（抽象建了，没人用）|

**⇒ 电视上这 `24` 款全部使用「小号」格子与间距 —— 与 `10-foot UI` 的需求正好相反。**

## 三、修法（两种，建议 A）

**A. 加一个语义明确的助手（推荐）**

```ts
// core/Bp.ets
/** 屏幕「紧」到要减尺寸 —— 但电视永远不算紧（10-foot UI 要更大） */
static tight(): boolean {
  return Bp.height < 600 && !Bp.isTv();
}
```

然后 `84` 处 `Bp.height < 600` → `Bp.tight()`。

**好处**：① 一次把所有绕过的点收进同一个语义 ② 以后新增的点不会又裸写
③ 名字直接说明它和电视无关，比裸表达式更难误用

**B. 逐处加 `&& !Bp.isTv()`**
简单但会重复 `84` 次，且下次新写的代码还会漏。

## 四、为什么现在不做

1. **`84` 处 / `24` 款，改动面大** —— 按「一次只改一处」的纪律，这至少要分批
2. **它属于第 ⑤ 项（电视），而第 ⑤ 项排在布局清零之后**
3. **改完必须编译 + 真机验**，而今晚/明晚两个窗口都已排死
4. **且它不影响手机**（手机横屏 `533 < 600` 本来就该走「小」分支，行为正确）

**⇒ 排期：布局清零 → 端侧 LLM 选路 → 电视这条（第三晚以后）**

## 五、一个附带发现

`narrowHeight()`（`Bp.ets:296`，`Bp.height < 420`）**使用量为 `0`**。
它是为「我只关心高度」这件事专门抽出来的，注释里还写了为什么单独一个
（`DemoBar` 演示条、`GameHost` 图标尺寸写过裸的 `< 420`）。

**⇒ 但抽出来后没人用，`84` 处新代码仍旧裸写 `< 600`。**
**⇒ 判据：抽了抽象却不用，等于没抽。** 要么在 code review 清单里加一条「新写的高度判断必须用助手」，
要么就别建这个抽象 —— 否则它会变成「看起来很规范」的假象。
