# 判据 3012：看门狗差点在**奥森起床后**重启重活 —— 两个真 bug

## 一、怎么发现的

`06:46` 跑批按 `06:45` 窗口设计正常结束（`vl=0 sg=0 sweep=0`）。
但看门狗还在跑，它的 tick 是 `900s`。于是等着看它会不会自己退出：

```
[11-19 06:34] ✅ 跑批活着且有产出（台账 2436 行）
[11-19 06:49] ✅ 跑批活着且有产出（台账 2446 行）    ← 跑批 06:46 已经死了
[11-19 07:04] ⏳ 台账无新增，开始计时（2446 行）      ← 走的是「活着但空转」分支
```

⇒ **`07:04` 它判「跑批活着」而实际跑批已死。**

## 二、Bug ①：`pgrep -f 'sweep_all.sh'` 会匹配到自己

`pgrep -f` 匹配**完整命令行**。任何命令行里含 `sweep_all.sh` 的进程都会命中，包括：

- `bash -c "… pgrep -f 'sweep_all.sh' …"` —— **执行这条 `pgrep` 的 shell 自己**
- 我之前手动起的 `bash -c cd "…" && nohup bash 工具/sweep_all.sh > …` 那层 wrapper

⇒ **「跑批活着」这个判据从头到尾都不可靠** —— 它测的是「有没有命令行里带这个字符串的进程」。

## 三、Bug ②：空转重启分支**没有窗口检查**

`已过运行窗口` 在脚本里只出现 **`1`** 次 —— 只在「跑批已死」分支。
而「活着但空转 ≥900s」分支是：

```bash
else
  pkill -f 'shot_game.py'; pkill -f 'verify_layout.py'; pkill -f 'sweep_all.sh'
  nohup bash 工具/sweep_all.sh ... &     # ← 没有任何窗口检查
```

⇒ 配合 Bug ①：`07:04` 进了这个分支 ⇒ **`07:19` 就会把跑批重新起起来**，
  而那时是**早上七点二十**，奥森可能已经起床。

⇒ 这正是 `2998`（我加的产出检查）**引入的新风险**：加了重启逻辑，
  却只在一个分支上继承了原有的窗口保护。

## 四、修法（三处，已单测）

| 改动 | 内容 |
|---|---|
| ① 新增 `sweep_alive()` | **读 `/tmp/sweep_all.lock` 里的 PID 再 `kill -0`**，并用 `ps -o command=` **再确认那个 PID 确实是 `sweep_all.sh`**（防 PID 复用）|
| ② 判活改为 `sweep_alive` | 替掉 `pgrep -f 'sweep_all.sh'` |
| ③ 新增 `past_window()` 并在空转分支调用 | 空转但已过窗口 ⇒ **记一行日志就 `exit 0`**，不续跑 |

### 单测（四场景全过）

```
场景1 锁里 24701（已死）              ⇒ ✅ 判成已死
场景2 锁里 = 当前 shell（活但非跑批）  ⇒ ✅ 判成已死（防住 PID 复用）
场景3 锁文件不存在                    ⇒ ✅ 判成已死
场景4 past_window 在 07:05           ⇒ ✅ 已过窗口
```

## 五、判据

> **`pgrep -f <字符串>` 会把「正在执行这条 `pgrep` 的 shell」算进去 —— 判活/判死不要用它。**

⇒ 三条：
1. **判某件事活没活，用「它自己写的 PID 文件 + `kill -0` + 身份复核」**，不要用命令行匹配
2. **加了重启逻辑，就要检查它继承的保护是否完整** —— `2998` 加了重启、却漏了窗口
3. **窗口/预算这类「边界保护」必须做成函数，每个出口都调** —— 复制粘贴到两个分支必然漏一个

## 六、当下的处置

- **看门狗已手动 `pkill`**（`07:05`），不会在早上重启跑批
- 跑批 `0` 个、模拟器 `0` 个、树干净
- 修好的脚本等今晚 `00:00` 的 `launchd` 再起时生效

⇒ **这一条是今晚最后一个 bug，也是唯一一个「差点在用户起床后干重活」的 bug。**
