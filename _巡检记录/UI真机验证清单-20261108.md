## 一句话结论

**静态检查查的是「代码形态」，真机查的是「布局结果」—— 两者之间有一整类故障是盲区。**
这类的共同特征是：**代码完全合法、类型完全正确、声明完全支持**，
**但渲染出来的几何不是你写的那个几何**。

**⇒ 判据 1815「声明支持 ≠ 真能用」的 6 个具体形态，全部在这一类里。**

## 第二部分：每类的「最小真机验证」（1~2 步）

**核心工具只有一个：`uitest dumpLayout`** —— 它直接给每个节点的 `[x1,y1][x2,y2]`，
**比截图目测精确、比人眼看快**。下面每类都给了 1 条命令。

### 通用起手（所有类都要这步）

```bash
hdc shell "uitest dumpLayout -p /data/local/tmp/a.json"
hdc file recv /data/local/tmp/a.json /tmp/a.json
# 然后按类查下面的东西
```

### #5 编译缓存的验证（**必须在装包前做**，1 条命令）

```bash
# 用你这次改动里「唯一的字符串」去 grep 转译产物
grep -c "<你改动里的独有 token>" \
  entry/build/default/cache/.../debug/entry/src/main/ets/<改的文件>.ts
# 期望 ≥1；=0 ⇒ 缓存没失效，别装包
```

**今天的实例**：`grep -c "flappy' ? 120" GameHost.ts` = **0** ⇒ 白装一次。

### #1 拉伸（1 步）

```bash
# 找那个组件，比它的实际 bounds 和你写的 width
# 声明 .width(44) 的元素，bounds 宽 = 44*vp_ratio；若明显更宽 ⇒ 被拉伸
```

**判据**：`实际宽 > 声明宽 × 1.05` ⇒ 被拉伸。
**修法**：`.flexShrink(0)`（判据 1829 已给）。

### #2 aspectRatio 撑爆（1 步）

```bash
# 找游戏区那个节点，看它高度是否 > 父容器
# 今天实例：棋盘 813vp 高，可用 352vp ⇒ 超 2.3 倍
```

**判据**：子节点 `height > 父节点 height` ⇒ 撑爆。
**修法**：`constraintSize({ maxHeight })`（已有）+ 必要时 `-120` 放宽。

### #3 position 被裁剪（1 步）

```bash
# 看用 position 定位的元素有没有出现在 dump 里 / 位置对不对
# 今天实例：GPong 的球「连节点都没有」⇒ dump 里查不到 = 最直接的证据
```

**判据**：**dump 里找不到那个节点，或它的 x 与逻辑值不符** ⇒ position 没生效。

### #4 / #6 视觉 vs 判定（**算，不用看**）

```bash
# 不需要真机！把两个数代进公式即可：
#   临界尺寸 S = 视觉尺寸 / 判定系数
#   倍数 = (系数 × 实际容器) / 视觉尺寸
```

**今天实例**：`GFlappy` 视觉 34vp、系数 10% ⇒ `S = 340vp`；实际场馆 813 ⇒ **2.39×**。

### #7 组件替换（1 步）

```bash
# 换完只看一件事：它的 bounds 是否等于你声明的 width/height
# 因为 Text 的宽由字形定、组件的宽由 flex 定 —— 换完必须重新量
```

## 第三部分：能不能做成强制清单？

**能，而且应该。** 但**不能只做成一个 grep 脚本** —— 这次三类检查全绿就是教训：
**它们查的维度根本不一样**（文案/方向/焦点），而故障在**布局几何**维度。

### 建议：`tools/check_ui_change.sh`（新增，接进现有闸门）

**思路**：**按"改了什么"决定"必须验什么"，验不过不许说"做完了"。**

```
第一步：从 git diff 里识别改动类型
  ├─ Text(emoji) → SymbolGlyph        ⇒ 触发 R1
  ├─ 新增/修改 aspectRatio            ⇒ 触发 R2
  ├─ 新增/修改 position({...%})       ⇒ 触发 R3
  ├─ 新增/修改 width/height 的组件    ⇒ 触发 R1/R7
  ├─ 新增/修改 constraintSize         ⇒ 触发 R2
  └─ 任何 .ets 改动                   ⇒ 触发 R0（编译产物校验）

第二步：按触发的规则强制要求证据
  R0（编译产物）  ⇒ 自动跑：grep 转译产物里有没有改动 token
  R1/R2/R3/R7    ⇒ 要求贴出 dumpLayout 的对应节点行 + 一句结论
  R4/R6          ⇒ 自动算：把「视觉尺寸 / 系数 / 实际容器」三个数填进公式
```

### 和 `BUILD_STRICT` 的关系

| 现有 | 查什么 | 盲区 |
|---|---|---|
| `check_i18n` | 文案是否走取词 | 布局 |
| `check_rtl` | `direction`/`margin` 方向 | 布局 |
| `check_focusable` | 可点元素有没有 `focusable` | 布局 |
| **`check_ui_change`（建议）** | **布局几何 + 编译产物** | **渲染像素**（仍需人眼）|

**⇒ 它不会取代前三把尺子，而是补上"第四维"：几何。**

### 一个更狠但更简单的做法（建议同时上）

**把「装包前 grep 编译产物」变成硬规矩**（R0）。理由：

- 它**零成本**（一条 grep）
- 它挡掉的是**最气人的一类**：我改了、你看了、测试也跑了、**结果跑的是旧代码**
- 今天已经发生 **2 次**（`GameHost` 的 `-120`、3 个组件的 `SymbolGlyph`）

```bash
# 建议加进出包脚本，编译后立刻执行，失败就中止
CHANGED=$(git diff --name-only HEAD~1 -- '*.ets')
for f in $CHANGED; do
  tok=$(git diff HEAD~1 -- "$f" | grep '^+' | grep -oE "'[a-zA-Z_]{6,}'" | head -1 | tr -d "'")
  [ -z "$tok" ] && continue
  ts="entry/build/.../debug/${f%.ets}.ts"
  grep -q "$tok" "$ts" || { echo "❌ $f 的改动没进编译产物（缓存失效）"; exit 1; }
done
```

## 第四部分：给奥森的一句话解释

**「智能体团队怎么连这个也没发现」——因为我们的检查器只查『代码写了没』，不查『屏幕长什么样』。**

今天三项全绿的检查是：文案有没有走取词、RTL 方向对不对、可点元素有没有焦点。
**「一个色块被 flex 拉长」不在这三个维度里**，它是渲染后的几何，**只能看屏幕**。

**这次的改进**：
1. 立了判据 1829（`SymbolGlyph` 必须 `flexShrink(0)`）
2. 这份清单把「改 UI 必须验什么」写死
3. 建议加一条**硬闸门：装包前 grep 编译产物** —— 挡掉「跑的是旧代码」这类最气的
