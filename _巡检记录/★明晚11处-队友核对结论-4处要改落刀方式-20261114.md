**⚠️ 但要先确认作者的意图（是「两块并排每块 333」还是「合计 333」）。
⇒ 状态：**需读布局上下文**。**

# 第八批的复核（`14:4x`）：`2 ×` 不是 bug，`SimonSays` 也不是「严重超屏」

## 一、`2 × max(140, H−200)` 是**故意**的

**代码注释写清了（`GSimonSays.ets:505-508`）：**
```
// 2026-11-14 真机截图：A/B 两块压住了上面的统计行，且下沿超出屏幕
//   两块是 layoutWeight(1).aspectRatio(1) ⇒ 宽 = 行宽的一半 ⇒ 高也一半
//   2500px 行宽 ⇒ 每块 1250px 高 ≫ 可用 ⇒ 溢出并盖住上方
//   ⇒ 限行宽（判据 1966：限宽即限高）：2 × (Bp.height - 200) = 666vp
```

**⇒ 作者的账：每块高 ≤ `H−200`，每块是行宽一半 ⇒ 行宽 = `2 × (H−200)`。**

**⇒ 我先前判「`2 ×` 是算术 bug」**错了** —— 它是**正确的换算**（行宽 → 每块宽）。**

**⚠️ 但它**没留余量**：**
```
每块 333vp + 上方 200vp = 533vp = 正好等于屏高
```
**⇒ 零余量 ⇒ 任何附加间距都会溢出。**

## 二、而台账数据表明它**没那么严重**

| 指标 | 值 | 含义 |
|---|---|---|
| `max_bottom` | `1291px = 430vp` | 渲染的最深叶子在 `430vp` |
| `blk = 48px` | 最深块 `1588px = 529vp` | 布局到 `529vp`（距屏底 `4vp`）|

**⇒ 我按公式算「块底 `533vp`」，实测 `529vp` ⇒ 只差 `4vp` ⇒ **公式与实际一致**。**

**⇒ 所以它更像 `Skyscrapers`：**完整但贴手势线**。**
**⇒ 普查说「`A`/`B` 按钮超屏」大概率又是**过度解读**（空/无边框大色块的看图困难，判据 `2164`）。**

**⇒ 而「合计被盖」（`cov` 类型）是**另一回事**——那是层级/覆盖问题，不是溢出。**

## 三、⇒ `SimonSays` 的正确处理

| 症状 | 是真问题吗 | 处理 |
|---|---|---|
| 「`A`/`B` 超屏」 | ❌ **不成立**（布局到 `529vp`，距屏底 `4vp`）| 不改 |
| 「贴手势线」 | ✅ 是（`529 > 528vp` 手势线 `1vp`）| 与那 `19` 款同类，**优先级低** |
| 「盖住统计行」 | ⚠️ **需单独看**（`cov` 类型）| 另查，不是限宽问题 |

**⇒ 所以第八批里 `SimonSays` **不需要改限宽**。**
**⇒ 若真要留余量：`2 × max(140, H−240)` ⇒ 行宽 `586`、每块 `293vp`、块底 `493vp`（余 `40vp`）。
但那只是为了「不贴手势线」，不是修功能缺陷。**

## ⇒ 判据（`2171`）

**一个「看起来荒谬」的算式（`2 × 333 = 666`）可能是**正确的换算**。
⇒ 我先前一眼判它是 bug，而读注释后发现它是对的（行宽 = 2 × 每块宽）。**

**⇒ 判据：判「这个数荒谬」之前，先找**它的单位/语义**（是「单个元素」还是「一行」）。
`666vp` 作为**单个元素**荒谬，作为**行宽**完全正常（每块 `333vp`）。**

**⇒ 而这条与判据 `2149`（「需 N vp」与「剩多少」不同）是一类：
**数字本身没有意义，它的语义（是哪个量）才有意义。**

## ⇒ 判据（`2172`）

**同一天里，我两次把一个**正确的换算**当成 bug**（`SimonSays` 的 `2 ×`、更早可能还有）。
**⇒ 而每次都是「读注释/读上下文」纠正的。**

**⇒ 判据：判一段代码「错了」之前，读它的**注释与上下文**（作者通常会写为什么）。
⇒ 这次注释就明写「两块是 `aspectRatio(1)` ⇒ 宽 = 行宽一半 ⇒ 高也一半」——
**不读那句，就会把它当 bug 改掉，然后把它改坏。**

```
lowest = '提示' [?,1547][?,1600] ⇒ 文字 y2 = 1600（贴边）
max_bottom = 1600
```

**⇒ `'提示'` 三个字在 `y 1547-1600`（`53px` = `17.7vp` 高）⇒ 它自己**就贴在屏底**。
⇒ 而 `blk=24px` ⇒ 有块在 `1564px`（距屏底 `12px`）溢出。**

**⇒ 所以：那个 `提示` 文字被切了下缘一点（`12px` = `4vp`）。**

**⚠️ 它是不是功能缺陷？**「提示」是辅助信息，被切 `4vp` **不影响答题**。
**⇒ 判定：**视觉级（🟡）**，不是功能缺陷。**
**⇒ 优先级：低于那 `2` 款真功能缺陷（`Fraction Matcher`、`Pythagorean Triple Builder`）。**

**⇒ 处理：**排在第九批末尾（若明晚时间够，顺手把它的 `padding` 或底部留白调一下）。**

## 四、⇒ 被排除的款及理由

| 类 | 款数 | 排除理由 |
|---|---:|---|
| **只文字贴边、`blk=0`** | `7` | 底部说明行本来就在屏底（`'把进制换算对…'` `y 1594-1600`）⇒ 设计如此 |
| **只 `blk>0`、文字没到边** | `24` | 溢出的是空块/图形块（盘面格子、色块）⇒ 视觉贴边，不是内容被切 |

**⇒ 这 `31` 款**不用改**，且理由已写明（不是「先不管」，是「判定为不需要」）。**

## 五、⇒ 这张表的价值

**它把「`33` 款 `blk>=24`」这个模糊的数字，收敛成了：
`11` 款要修（`10` 已有方案、`1` 款新增）+ `31` 款判定不用改（各有理由）。**

**⇒ 而 `11` 款里，**真功能缺陷只有 `2` 款**（`Fraction Matcher` 的选项、`Pythagorean Triple Builder` 的确认键），
其余 `9` 款是「控件下缘被切一点」的视觉问题。

## ⇒ 判据（`2179`）

**「有多少款有问题」这个问题，只有在**同时定义「什么问题、多严重」**时才有答案。**
**⇒ 今天这个问题被回答成了三个不同的数：**
- `33` 款（`blk >= 24`）—— **任何块越界**
- `11` 款（`blk>0` 且文字贴边）—— **内容被切**
- `2` 款（选项/按钮不可达）—— **功能不可用**

**⇒ 判据：报「N 款有问题」时，必须说清是哪一档。
⇒ 而最有用的表述是**分档列出**：`2` 款功能 / `9` 款视觉 / `31` 款不用改。**

# 第十一批（`12:3x` 定案）：`Magnets` 升为**最高 `P0`** —— 它是「无解」，其余是「难用」

## 一、为什么它要排第一

**先前我把它排在第 `1` 位（按 `3px` 可见高度）。现在查清 `'2＋'` 是**行列提示格**（`CLUE_W = 44vp = 132px`），
可见 `3px` ⇒ 被裁 `97%`。**

**⇒ 磁性数独的核心规则是「每行每列的 ＋ 数必须等于该行/列的数字」。
⇒ **看不到提示 ⇒ 玩家无法推理 ⇒ 游戏无解。**

**而其余四款功能级是「难用」：**
| 游戏 | 缺什么 | 后果 |
|---|---|---|
| **`Magnets`** | **行列提示（规则信息）** | **无解** |
| `Fraction Matcher` | 三个选项 | 答不了（但可猜）|
| `Kakuro Mini` | 一个数字键 | 那一格填不了 |
| `Pythagorean Triple Builder` | 确认键 | 提交不了 |
| `Percentage Shopping` | 选项值 | 可能答错 |

**⇒ 所以严重性排序：`Magnets` > `Pythagorean Triple Builder` > `Fraction Matcher` > `Kakuro Mini` > `Percentage Shopping`。**

## 二、`Magnets` 的具体改法（三件套）

**文件**：`entry/src/main/ets/games/GMagnets.ets`

**要改两处，目的都是「把棋盘上方 `367vp` 压下来」：**

### 改点 1：三张统计卡压成一行紧凑（`A`）

**现状**（`L379-394` 附近）：三个 `Column({space:2})`，各带 `label(xxs) + value(lg) + padding(Space.sm)` + `shadow(Shadow.card)`
⇒ 每张约 `46vp`。

**改成**：`label` 与 `value` **同一行**（`Row`），去掉 `padding` 的上下两项（保留左右）、去掉 `shadow`。
**⇒ 预计每张 `46 → 26vp`** ⇒ 省 `20vp`。

**⚠️ 四处必须同步**：三张卡 + 它们的容器 `Row({space: Space.sm})` 的间距。

### 改点 2：矮屏隐藏按钮行（`B`）

**现状**：棋盘上方有一行「提示 / AI 代打」按钮（约 `39vp`）。
**改成**：`Bp.isShort() ? 不渲染 : 渲染`。
**⇒ 省 `39vp`。⚠️ 但「提示」是功能按钮，隐藏会影响可发现性 ⇒ 考虑改成把「提示」挪到头部圆钮里。**

**「玩家靠它做决策吗」** —— `Magnets` 的提示**是**玩家推理的唯一依据。
**⇒ 截断它 ⇒ 从「不好玩」变成「玩不了」⇒ 必须最高优先。**

## ⇒ 判据（`2205`）

**功能级内部还要再排序：按「缺了它，玩家还有没有替代路径」。**

- `Pythagorean Triple Builder` 缺确认键 ⇒ **无替代**（交不了）
- `Fraction Matcher` 缺三选项 ⇒ **有部分替代**（还能猜 `A`）

- `Percentage Shopping` 缺选项值 ⇒ **有替代**（看题目推）

**⇒ 判据：严重性 = 缺失程度 × （有没有替代路径的倒数）。
⇒ 「全都缺」比「缺一部分」严重；「无替代」比「有替代」严重。**
