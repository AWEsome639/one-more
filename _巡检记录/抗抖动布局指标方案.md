# 抗抖动布局指标方案（替换/补充 `max_bottom`）—— 2026-11-13

> 执行：**perf-hunter**｜**只读 + 只写本 md**（不改 `工具/*.py`、不改 `.ets`、不编译、不碰设备）
> 起因：**判据 1978** —— `Wordle` 同一构建、同一文本，20 分钟内 `max_bottom` 抖动 `1600 → 1591 → 1351 → 1600`（±250px ≈ ±83vp），
> 因为 `max_bottom` = 「最深**叶子**的 `y2`」，而**最深叶子会换人**（键盘开合 / 浮层 / 演示条）。

---

## 0. 先定位病根：不是「量得不准」，是「被量的对象在换人」

现有实现（`工具/shot_game.py:469-484`）：
```python
def _max_y2(n, acc):        # 只数叶子（根容器 100% 高会把 y2 钉在 1600，那是背景）
    if not children: acc = max(acc, y2)
```
⇒ **`max()` 对「身份不稳定」的集合没有抵抗力**：集合里任何一个会随状态生灭的节点，都能把结果拉满。

**要稳，只有四个方向**（下面三个候选分别落在这四个方向里）：
| 方向 | 做法 | 能抗什么 |
|---|---|---|
| ① **换成结构块**（不数叶子，数块） | 只统计**根内容列的直接子节点** | 叶子级生灭（键盘按键、格子）不影响块数 |
| ② **换成正则/比例**（不数绝对位置） | 越界节点 / 总节点 | 节点总数变化时同步缩放 |
| ③ **同身份追踪**（跨多次 dump） | 连续 N 次 dump 的**持久层** | 一次性出现的浮层 |
| ④ **换成语义事实**（不数像素） | 文字截断 / 越界文字 | 「最深节点是谁」完全无关 |

---

## 候选 1 · `overflow_blocks`（结构块越界数 + 越界深度）**推荐主指标**

### 1.1 公式
```
根内容列 R = dump 树里 type ∈ {Column, Flex, Scroll} 且 depth 最小的那个容器
块集合 B = R 的直接子节点（去掉 DemoBar / 高度 0 的占位）
对每块 b： over(b) = max(0, b.y2 − 1516 − TOL)      # TOL = 24px 容差，滤掉 1~2px 抖动
指标：
  block_over_n  = |{ b ∈ B : over(b) > 0 }|          # 越界块数（0 表示全在区内）
  block_over_px = Σ over(b)                          # 越界总量（px）
  block_over_max= max over(b)                        # 最严重的一块
```
> `1516px` = 游戏区下沿（`GameHost:3456` 给游戏区 `maxHeight: Bp.height − 190` ⇒ 533−190 = **343vp**，
> 本机 3px/vp ⇒ 高 **1029px**；上沿 = 1516 − 1029 = **487px ≈ 162vp**，与「状态栏 66 + 顶栏 45 + padding 20 + HintBar 38 = 169vp」吻合）。

### 1.2 为什么抗抖动
- **块的身份稳定**：HUD 行 / 棋盘 / 选项行 / 按钮行 这 4~6 块，**换状态还是那几块**；抖动的是块**内部**的叶子（键盘按键逐个性灭）。
- **块级 `y2` 由布局决定**：键盘在「按钮行」这一块里长出来 ⇒ 该块 `y2` 变化，但**块数不变**，不会出现「同一款 1600/1351 来回跳」。
- **一次 dump 即可**，不需要多次采样 ⇒ 每款仍 ~10s。

### 1.3 怎么从现有 dump 算（伪代码，不改工具）
```python
GAME_BOTTOM = 1516
TOL = 24

def blocks_over(tree):
    root = find_content_root(tree)          # 见下
    out = []
    for b in root.get('children') or []:
        bb = bounds_of(b)                    # attributes.bounds -> [x1,y1,x2,y2]
        if bb is None: continue
        if is_demo_bar(b) or bb[3] <= bb[1]: continue        # 空/隐藏块
        over = max(0, bb[3] - GAME_BOTTOM - TOL)
        if over > 0: out.append((over, type_of(b), bb))
    return len(out), sum(o for o,_,_ in out), max([o for o,_,_ in out] or [0])

def find_content_root(tree):
    """根内容列：depth 最小的 Column/Flex/Scroll，且它的子节点 ≥3（避免命中演示条的包装层）"""
    queue = [(tree, 0)]
    best = None
    while queue:
        n, d = queue.pop(0)
        t = type_of(n)
        kids = n.get('children') or []
        if t in ('Column','Flex','Scroll') and len(kids) >= 3:
            if best is None or d < best[0]: best = (d, n)
        for c in kids: queue.append((c, d+1))
    return best[1] if best else tree
```

### 1.4 已知盲区
1. **块内部被压缩看不到**：格子从 60vp 压到 40vp（触控不达标）但**块没越界** ⇒ `block_over_n = 0` 会判「正常」。
   ⇒ 必须配一条**触控检查**：`Cell` 类节点的 `min(w,h) < 44*3px` 计数（这是另一个指标，见 §5）。
2. **整块被顶出**（如键盘整行在屏幕外）时，`root.children` 里它的 `y2 > 1516` ⇒ 能抓到 ✓；但若系统**不渲染**该块（`visibility(None)`），它也**不出现在树里** ⇒ 抓不到（这正确：不渲染 ≠ 溢出）。
3. **根内容列识别错**（有些游戏根是 `Stack`/`Flex`）⇒ 需要 type 白名单兜底，且**把识别结果写进输出**（`root_type=Column@[60,66]`）便于人工复核。

## 候选 2 · `stable_bottom`（3 次 dump 的「持久层下沿」）**仲裁用**

### 2.1 公式
```
取 3 次 dump（间隔 1.5s，不动屏幕）
对每次：叶子集合 L_i = { (type, x1,y1,x2,y2) }
持久层 P = { k : 出现次数(k) ≥ 2 }                 # 3 次里至少 2 次存在
stable_bottom = max( y2 of k ∈ P )
jitter_span   = max_i max_y2(L_i) − min_i max_y2(L_i)   # 抖动幅度，直接量化「稳不稳」
```

### 2.2 为什么抗抖动
- 一次性浮层/键盘只在**某一次**出现 ⇒ 被 `≥2` 过滤（因为采样间隔足够吞掉一次完整开合）。
- **同时输出 `jitter_span`**：以后任何指标都能自查「这次测的稳不稳」。

### 2.3 伪代码
```python
def stable_bottom(dumps):
    from collections import Counter
    cnt = Counter()
    per = []
    for d in dumps:
        leaves = [ (type_of(n),) + tuple(bounds_of(n)) for n in walk_leaves(d) if bounds_of(n) ]
        per.append(max((k[2] for k in leaves), default=0))     # 各次 max y2
        cnt.update(set(leaves))
    P = [k for k, v in cnt.items() if v >= 2]
    return max((k[4] for k in P), default=0), max(per) - min(per)
```

### 2.4 盲区
- **成本 ×3**（每款 3 次 dump + 2 次等待 ≈ 6~9s）。
- 若抖动状态的**驻留时间 > 采样窗口**（例如键盘一直开着）⇒ 会被当成持久层（此时它确实是当前布局，**不算错**）。
- `bounds` 只要差 1px 就视为不同节点 ⇒ 动画中的游戏（每帧位移）会把真内容也过滤掉
  ⇒ **必须先冻结动画**（停手 1.5s 再采），或对 `bounds` 做 ±2px 归并。

## 候选 3 · `trunc_rate`（内容完整性 / 越界文字比例）**人读副指标**

### 3.1 公式
```
T = 所有 text 非空的节点
T_over = { t ∈ T : t.y2 > 1516 − TOL }
trunc_rate = |T_over| / max(1, |T|)          # 0~1，越小越正常
样本     = 前 5 个越界文字的 (text[:12], bounds)
```

### 3.2 为什么抗抖动
- **比例而非绝对量**：键盘出现时 `|T|` 与 `|T_over|` 同步变大，比值变化平稳（Wordle 键盘全可见 ⇒ 比值 ≈ 键盘占比，不会 0↔1 跳）。
- **不关心「最深是谁」**：只看「多少字被切在区外」，状态切换时不会因为某个节点换人而突变。
- **可人读**：直接给「哪些字掉出屏幕」，比一个 1600 的数字可诊断得多（配合今晚刚加的 `lo_bounds`）。

### 3.3 伪代码
```python
def trunc_rate(tree):
    ts = [ (text_of(n), bounds_of(n)) for n in walk(tree) if text_of(n) and bounds_of(n) ]
    over = [ (t[:12], b) for t, b in ts if b[3] > GAME_BOTTOM - TOL ]
    return len(over) / max(1, len(ts)), over[:5]
```

### 3.4 盲区
- **纯图形游戏**（Canvas / 色块 / 无字棋盘）`|T|` 很小 ⇒ 比值噪声大，甚至恒 0（漏报）。
- 比例掩盖**严重度**：1/100 与 1/3 都是「有越界」，需配合 `block_over_px` 看深度。
- `TOL` 取值影响小（文字行高 42~60px）。

## 4. 对你给的四个方向的取舍（明确回答）

| 你提的方向 | 采纳？ | 理由 |
|---|---|---|
| **中位数/众数（连续 3 次取中位）** | **不完全采纳** | 单独取中位**治不了「身份漂移」**：`1600/1591/1351` 三取中位 = 1591，仍然是「某个会生灭的节点」的值。要配对「同身份」（候选 2 的持久层）才有意义 |
| **「超出游戏区的唯一量」** | **采纳其结构版**（候选 1） | 直接对所有叶子求和会被 **Canvas/背景节点**（`y2` 恒 1600）一颗顶满（判据 1925 的教训）⇒ 改成「按结构块求和」，且块级不重复计数 |
| **「可交互节点覆盖率」** | **采纳为补指标**（§5） | 它测的是**触控**不是溢出，且「`Button`/`Text` 且 `width>44`」会把标签文字算进去 ⇒ 要加 type 白名单（`Button|TextInput|Toggle`） |
| **「内容完整性」** | **采纳**（候选 3） | 最贴「用户能不能看到/点到」，且人读友好；纯图形游戏需兜底 |

## 5. 建议的最终口径（三件套，一次 dump 出全部）

```jsonc
{
  "ok": true,                  // 判定：block_over_n==0 AND trunc_rate<=0.02 AND no_small_touch
  "block_over_n": 0,           // 候选1：越界结构块数        ← 主判据
  "block_over_px": 0,          // 候选1：越界总量
  "block_over_max": 0,         // 候选1：最严重一块的越界深度
  "trunc_rate": 0.0,           // 候选3：越界文字比例
  "trunc_sample": [],          // 候选3：前 5 条越界文字 + bounds
  "small_touch_n": 0,          // 补：min(w,h) < 132px 的可交互节点数（44vp×3）
  "root_type": "Column@[60,66][2500,1421]",  // 根内容列识别结果，便于复核
  "jitter_span": null          // 候选2：仅仲裁跑（3 次 dump）时填
}
```

**判定逻辑（抗抖动版）**
| 结论 | 条件 |
|---|---|
| 🔴 溢出 | `block_over_n ≥ 1 且 block_over_px > 24` |
| 🟡 疑似 | `0 < block_over_px ≤ 24`，或 `trunc_rate > 0.05` |
| ✅ 正常 | `block_over_n == 0 且 trunc_rate ≤ 0.02` |

**为什么这个组合抗抖动**
- 抖动来自「最深叶子换人」⇒ 主判据**不问最深是谁**，只问「有没有结构块整块越界」；
- 块越界是**布局事实**（按钮行被顶出/键盘被切），**状态切换不会让它凭空出现或消失**；
- 万一某次状态确实把键盘推到屏外，`block_over_n` 变 1 —— 那是**真问题**，应该抓；
- 再叠 `trunc_rate` 做交叉验证：**两个独立信号同时报，才判 🔴**（单信号报警降为 🟡，避免再次出现「同一款 20 分钟翻烧饼」）。

## 6. 对比表

| 指标 | 公式骨架 | 抗抖动理由 | 实现难度 | 成本 | 盲区 |
|---|---|---|---|---|---|
| **1 `overflow_blocks`** | 根内容列的孩子里，`y2>1516+24` 的块数与越界和 | 数**块**不数叶子；块身份稳定 | **低**（一次 dump，~20 行） | 1× | 块内压缩看不到（需配触控检查） |
| **2 `stable_bottom`** | 3 次 dump 的叶子集合，出现 ≥2 次的取 max y2 | **同身份**过滤一次性浮层；还能量化 `jitter_span` | 中（3 次采样 + bounds 归并） | **3×** | 抖动驻留 > 窗口会被当持久；动画需先冻结 |
| **3 `trunc_rate`** | 越界文字数 / 总文字数 | **比例**且与「最深是谁」无关；可人读 | **低** | 1× | 纯图形游戏漏报；掩盖严重度 |
| 4（补）`small_touch_n` | `min(w,h) < 132px` 的可交互节点数 | 与溢出正交，专治「块内被压扁」 | 低 | 1× | 需 type 白名单，否则把标签算进去 |

**推荐：主判据用 1，副判据用 3，仲裁用 2（只在 1/3 结论冲突时跑）。**

## 7. 一句话结论

> **`max_bottom` 的问题不是「量得不准」，是「被量的对象会换人」；**
> **换成「结构块越界数（候选 1）+ 越界文字比例（候选 3）」——两个都不问「最深是谁」，状态抖动就传不到指标上。**
> 最省的做法：**一次 dump 同时出 `block_over_n / block_over_px / trunc_rate / small_touch_n` 四个数，两信号同时报才判溢出**。
