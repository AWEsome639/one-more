# 判据 `3082`：**预测器 A 的正则只认「减法」，把「乘法」漏掉了**

## 一、错在哪

`3072` 里判据 A 的写法是：
```python
has_h = re.compile(r'Bp\.height\s*[-−]')     # ← 只匹配 Bp.height - N
```

⇒ 于是**只要游戏用的是 `Bp.height * 系数`，就会被误判成「完全不用高度」**。

### 实测反例

`GFreecell.ets:92`：
```typescript
const avail: number = Math.max(120, Bp.height * (Bp.isShort() ? 0.42 : 0.50));
```

⇒ 它**明明按可用高度算尺寸**，只是用的是乘法。我的正则判它「高风险」 ⇒ **假阳性**。

## 二、宽判据重算（竖屏 `33` 款）

```python
ANY_H = re.compile(r'Bp\.height')     # ← 任何用法：减、乘、除、比较
```

```
完全不用 Bp.height 的：1 款（Perspective Taking）
用了 Bp.height 的    ：32 / 33
```

⇒ 之前报的「高风险 2 款」里，`FreeCell` 是**纯假阳性**；
`Perspective Taking` 确实一次都没用 `Bp.height`，但它 `:358` 有注释说明
**已经用 `layoutWeight(1)` 吃剩余空间修过** ⇒ 大概率也干净。

## 三、这对 `3072` 那个「`11.8` 倍」意味着什么

`3072` 的 `15` 款高风险名单是**用窄正则**算出来的 ⇒ 其中混着「用乘法」的假阳性。
⇒ **倍数 `11.8` 这个结论要打折扣**，不能当铁律用；需要时用宽判据重跑一遍。

（这不是说 A 完全无效 —— 「完全不用 `Bp.height`」确实是个可疑信号；
只是**它的名单要用宽判据重筛一次**再用。）

## 四、判据

> **正则写窄了，会把「换了写法」误当成「没有做」。**
> `Bp.height - N` / `Bp.height * k` / `Bp.height / n` 都是「用了高度」，
> 而我第一版只认第一种。

⇒ 三条：
1. **判「有没有用某个量」时，正则应尽量宽**（`Bp\.height` 而不是 `Bp\.height\s*-`）
2. **假阳性要当场核**（这次是点开 `GFreecell:92` 一行就看见了）
3. **统计结论要带上「判据是怎么写的」** —— 换个写法，名单就变了

## 五、顺带记下两个更靠谱的信号

比「有没有用 `Bp.height`」更可靠的静态线索：

| 信号 | 为什么更靠谱 |
|---|---|
| **代码里有 `layoutWeight(1)` 吃剩余空间** | 这是作者处理过「高度不够」的痕迹（`Perspective Taking:358` 的注释就是）|
| **`Math.max(下限, Bp.height…)` 下限 > 目标形态可用高度** | 下限会**吃死**公式，`3054` 已证 `5` 次 |
| **注释里提到「被屏沿切」/「出屏」** | 作者自己踩过的坑，往往只修了一处 |
