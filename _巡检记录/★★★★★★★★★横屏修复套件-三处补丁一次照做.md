> **用法**：奥森答「要支持横屏」时照这份做。
> 答「只支持竖屏」⇒ **一个字都不用改**（四条缺陷全是横屏专属，`3024`/`3026` 已证）。
>
> 每处都标了「改哪、改什么、怎么验」。**三处互不依赖，可单独上线。**

## 补丁 ①：`Simon Command` —— 唯一的功能性缺陷（`3017`）

### 症状（截图量出来的）
横屏下 **`4` 个色块只有 `2` 个可点**：第一行（红/蓝）被切 `71vp`，第二行（绿/黄）**整行在屏外**。

```
红块 y=956..1599  可见高 644px = 215vp  宽 1202px = 400vp
pad() 是 .layoutWeight(1).aspectRatio(1.4) ⇒ 应有高 400/1.4 = 286vp
⇒ 被切约 71vp（台账 blk 只报 8vp，低估 9 倍）
```

### 根因
**`aspectRatio` 是按宽定高** —— 横屏宽度充裕（每块 `400vp`）⇒ 高度被放大到 `286vp` ⇒ 两行 `572vp > 533vp`。

### 改法（`entry/src/main/ets/games/GSimonCommand.ets:330-341` `pad()`）
```typescript
// 现在
}.layoutWeight(1).aspectRatio(1.4).justifyContent(FlexAlign.Center)

// 改成：宽度仍然均分，但高度受控
}.layoutWeight(1).height(Cell.of(88)).justifyContent(FlexAlign.Center)
```
- `Cell.of(88)` 在横屏 ≈ `round(88 × 0.85 × 1.12 × 0.85)` ≈ **`71vp`**
- 两行 `142vp` + chrome ⇒ 装得下
- **竖屏 `Cell.of(88)` ≈ `80vp`**，两行 `160vp`，比现在的 `242vp` 更省 —— 竖屏**只会更好**

### 验证（必须做）
1. 横屏跑一次，截图确认 **4 个色块都在**
2. 竖屏（`onemore_fold`）跑一次，截图确认**仍然是 4 块**（不能变差）
3. 台账 `blk` 应变成 `0`（但按 `2605`，**`blk=0` 不算证据，以截图为准**）

## 补丁 ②：`Collatz` —— 底部按钮被切（`3011`）

### 症状
底部 `换个数` 按钮可见只 `38px = 13vp`，而 `blkh=80px = 27vp` ⇒ **被切约 `42px = 14vp`**。

### 根因（`3026` 已查清）
**高度驱动**：横屏版面合计约 `606vp > 533vp`，超出约 `73vp`。没有 `aspectRatio`，纯粹装不下。

### 改法（`entry/src/main/ets/games/GCollatz.ets`）
按超出量 `73vp` 砍，优先级从低到高：
1. 说明文字「`偶数 ÷2 · 奇数 ×3 + 1，推到 1`」横屏时隐藏（`Bp.isShort()`）
2. 大数字区 `78` 的上下留白缩一档（`Space.lg → Space.sm`）
3. 选项行 `A/B/C/D` 的 `Cell.of` 基数减 `4~6`
4. 最后才动 `提示` 行

⇒ **一次只改一处、改完量一次**（本夜纪律）。不要四刀一起下。

### 验证
横屏截图确认 `换个数` 底部圆角完整可见（`3011` 的判法：量可见高 ≈ `80px`）。

## 补丁 ③：电视字号 —— 两层（`3022` + `3023`）

> ⚠️ 这条**不属于横屏**，属于「要不要上电视」。放这里是同一份套件的方便。

### 症状
`Cell.of(30)` 电视 `44vp`、手机 `29vp`（`×1.52`）；而 `FontSize.md` 两边都是 `16vp` ⇒ **文字相对小 `34%`**。

### 第一层（必须先做）：`EntryAbility.ets`
```typescript
// onWindowStageCreate 里，Bp.update(...) 之后立刻补一句
Bp.update(wVp, hVp, dev);
UiModeMgr.apply(UiModeMgr.current());   // ★ 保证常量在 Bp 就绪后重算一次
```
**理由**：`apply()` 现在跑在 `Bp.update()` **之前**（`onCreate:60` vs `onWindowStageCreate:188`），
那时 `Bp.dev` 还是默认的 `PHONE`。不补这句，第二层是死代码。

### 第二层：`UiMode.ets` 的 `UiModeMgr.apply()`
```typescript
const fs: number = Bp.isTv() ? Bp.scale() : 1;   // ★ 只对电视生效
FontSize.hero = s.hero * fs; FontSize.xxxl = s.xxxl * fs; ...
Space.xs = s.sxs * fs; ...  Radius.xs = s.rxs * fs; ...
```
**为什么不用 `* Bp.scale()` 直接乘**：`Bp.scale()` 给 `WATCH 0.92` / `isLg 1.12` / `isMd 1.06`
⇒ 直接乘会**把平板和手表一起改掉**。`isTv() ? scale() : 1` 把不影响的设备钉死成 `1`。

### 效果
| 设备 | `fs` | 结果 |
|---|---|---|
| 手机 / 平板 / 手表 | `1` | **逐字节相同** |
| 电视 | `1.45` | `FontSize.md` `16 → 23vp`，文字/格子比 `0.36 → 0.52`（≈手机 `0.55`）|

### 验证
1. 手机/平板各跑一次，截图**与改前逐像素对比**（应完全相同）
2. `onemore_tv` 跑一次，截图确认文字明显变大

## 补丁 ④：`Shadow Pivot` 竖屏压手势条 —— **唯一不依赖「要不要横屏」的一条**（`3028`）

> ⚠️ **这条与前三条不同**：它在**竖屏**就能看到，真机用户会碰到。
> 前三条都能等「要不要支持横屏」的答复，**这条不能**。

### 症状（实测 + 截图双证）
```
竖屏记录 2026-11-19T07:39:36 OK
lowest='重开'  [62,2363][2162,2496]   blk=1/24px   blkh=133px   max=24px
```
- `y2 = 2496` = **屏幕最底边**
- 按 `3009` 换算：`出屏 vp = (24−24)/3 =` **`0vp`** ⇒ 一点没出屏幕
- **但截图（红线 `y=2480` 手势条起点）显示：按钮上半在线上、下半在线下，灰色手势胶囊画在按钮上面**

⇒ 这正是 `2990` 的「`over=0` ≠ 安全」。

### 影响
按钮 `44vp` 高，只有底部约 `16px = 5vp` 被手势条盖住 ⇒ **仍可点**，但用户按最底部时系统手势可能抢走。
⇒ **轻微、真实、只有竖屏能看见。**

### 改法（`entry/src/main/ets/games/GShadowPivot.ets`，两选一）
```typescript
// 方案 A：给内容区底部留出手势条高度
.padding({ bottom: Bp.isShort() ? 10 : 20 })

// 方案 B：把「重开」按钮调小并靠上
.height(Cell.of(40))     // 原为 Cell.of(46)
```
⇒ **优先 A**（不改按钮尺寸，只留白）。

### 验证
1. 竖屏跑一次，`lowest` 的 `y2` 应 **< 2472**（回到阈值内）
2. **截图确认手势条不再盖住按钮**
3. 横屏也跑一次，确认没变差（横屏本来 `120%` 更严重，别借这次把它弄坏）

## 验证计划（四处的共用纪律）

| 步 | 做什么 | 判据 |
|---|---|---|
| 1 | 改前截图存档 | 没有改前图，改后无法对比（`2605`）|
| 2 | 一次只改一处 | 四处一起改 = 不知道是哪处生效 |
| 3 | 改后**先看截图再看数字** | `blk=0` 不代表好了（`2605`/`3011`）|
| 4 | 竖屏也跑一次 | 别修好横屏弄坏竖屏（`3024`/`3026`）|
| 5 | 断言基线 `200359/0` | 改完必须仍绿 |

## 不要做的事

- ❌ **不要给 `Scroll` 再一次机会** —— `6` 款已全部回滚并验证（`3008`）
- ❌ **不要改 `HintBar` 的 `barHeight`** —— 作者 `2026-11-09` 试过并回退（`3007`）
- ❌ **不要给那 `10` 款「没问题」的动版面** —— `Wordle 20.8%` / `Magnets 2.7%` 等都是稳定的历史值（`3008`）
- ❌ **不要信 `blk` 一个数当验收** —— 它最少低估过 `9` 倍（`3011`/`3017`）
