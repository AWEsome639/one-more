## 0. 结论（先给）

**9 款全部「保持」，0 款需要改成两档式。**

**原因是一句算术**：这 9 处 `maxHeight` **管的全是同一个东西** —— `.width('100%') + .aspectRatio(1)` 的**正方形盘面/Canvas**。
正方形在竖屏是**宽度驱动**的，它的自然高 = 盘的可用宽，而不是屏幕高的 70%：

```
竖屏可用宽 = 533 − 2×Space.lg(20)          = 493vp
自然高（正方形）= 493vp                       ← 宽度驱动，封顶前就是它
新定值  = max(140, 853 − 360)               = 493vp   ← 与自然高【恰好相等】
旧 70%  = 0.7 × 853                          = 597vp   ← 从来没绑上（597 > 493）
```
⇒ **旧值 597 在竖屏根本不生效**（盘面自然高只有 493），**新值 493 正好等于自然高** ⇒ **盘面一像素都没变**。
你担心的「597 → 493（−17%）」在这 9 款上**不会发生** —— 那个 17% 是拿「屏幕高的 70%」减去「新定值」算的，
但**盘面从来到不了 597**（它被宽度锁在 493）。

> 补充一个反向情形：若 `constraintSize` 的百分比是按**父容器**（游戏区 `maxHeight = Bp.height − 190` = 663）解析的，
> 旧值 = 0.7 × 663 = **464** ⇒ **旧限制比新的 493 更紧** ⇒ 竖屏盘面反而**变大 6%**（464 → 493），**仍是改善**。
> 两条分支都指向同一个结论：**竖屏没有退化**。

## 2. 什么情况下才会真的退化（给你一条判据）

盘面是否被这个定值绑住，取决于**宽高的算术**：

```
盘面自然高 = Bp.width − 2 × Space.lg        （正方形，宽度驱动）
新定值     = Bp.height − 360
⇒ 只有当  Bp.width − 40 > Bp.height − 360   即   Bp.height < Bp.width + 320   时，定值才会绑定
```
- **竖屏手机 533×853**：`853 > 533 + 320 = 853` ⇒ **恰好卡在边界**（493 vs 493）⇒ **0 变化**
- **20:9 竖屏 400×900**：`900 > 720` ⇒ **不绑**（自然高 360 < 定值 540）✓
- **平板竖屏 800×1280**：`1280 > 1120` ⇒ **不绑** ✓
- **分屏/窄高窗口 700×760**：`760 < 1020` ⇒ **会绑**（自然高 660 → 660 被压到 400）⇒ **这种才退化**

⇒ **判据**：`Bp.height < Bp.width + 320` 时才需要两档式。**当前支持的横屏机与常见竖屏手机都不满足**，
所以**现在不用改**；将来真上「分屏 / 方屏 / 折叠展开的小窗」再加。

## 3. 如果将来要两档式（备用，**当前不必落**）

给一款为例，其余 8 款**同一串**照抄（9 处的原串**完全相同**）：
```diff
-      .constraintSize({ maxHeight: Math.max(140, Bp.height - 360) })
+      // 短屏（横屏 533）：定值 343，救「宽驱动盘面溢出」
+      // 高屏（竖屏/平板）：仍用百分比（宽度驱动时本来也不会绑）
+      .constraintSize({ maxHeight: Bp.height < 600 ? Math.max(140, Bp.height - 360)
+                                                   : Math.max(300, Math.round(Bp.height * 0.7)) })
```
> 竖屏 853：`max(300, 597) = 597` ⇒ 不绑（盘 493 不变）；横屏 533：`343` ⇒ 与现在**逐像素一致**。
> ⚠️ **注意**：`Cell.of` 不受它影响；这条只影响盘面外框。
