## 一、`3` 处可机械改（加 `|| Bp.isTv()`）

### ① `GKakuro.ets:632`

**现在**：
```ts
      .constraintSize({ maxWidth: Bp.height < 600 ? Math.min(Bp.width - 2 * Space.lg, Math.max(140, Bp.height - 360)) : 9999 })   // ★ 2026-11-12（判据 1928）：`aspectRatio(1)` 的棋盘 **`maxHeight` 只裁不缩**，必须用 `maxWidth` 才能真缩小
```

**改成**（只动条件那一段，注释原样留着）：
```ts
      .constraintSize({ maxWidth: (Bp.height < 600 || Bp.isTv()) ? Math.min(Bp.width - 2 * Space.lg, Math.max(140, Bp.height - 360)) : 9999 })   // ★ 2026-11-12（判据 1928）：`aspectRatio(1)` 的棋盘 **`maxHeight` 只裁不缩**，必须用 `maxWidth` 才能真缩小
```

**电视上取值**：`Bp.isTv()` 真 ⇒ 走封顶 ⇒ `min(1280−40, max(140, 720−360)) = min(1240, 360) = 360vp`（原 `9999` ⇒ `1240vp`）。

### ② `GKakuroMini.ets:562`

**现在**：
```ts
            .constraintSize({ maxWidth: Bp.height < 600 ? Math.min(Bp.width - 2 * Space.lg, Math.max(120, Bp.height - 360)) : 9999 })
```

**改成**：
```ts
            .constraintSize({ maxWidth: (Bp.height < 600 || Bp.isTv()) ? Math.min(Bp.width - 2 * Space.lg, Math.max(120, Bp.height - 360)) : 9999 })
```

**电视上取值**：`min(1240, max(120, 360)) = 360vp`（原 `1240vp`）。

### ③ `GSokoban.ets:704–709`（跨行，整块替换）

**现在**：
```ts
      .constraintSize({
        maxWidth: Bp.height < 600
          ? Math.min(Bp.width - 40, this.w * Math.max(10, Math.floor((Bp.height - 440) / Math.max(1, this.h))))
          : 9999
      })
```

**改成**（只改第 `2` 行条件，算式一个字符不动）：
```ts
      .constraintSize({
        maxWidth: (Bp.height < 600 || Bp.isTv())
          ? Math.min(Bp.width - 40, this.w * Math.max(10, Math.floor((Bp.height - 440) / Math.max(1, this.h))))
          : 9999
      })
```

**⚠️ 电视上这个算式的值要现算**：`(720 − 440) / h` = `280 / h`。
`GSokoban` 第 `1` 关是 `8` 列、`h`（行数）视关卡 ⇒ 若 `h = 8` ⇒ `floor(280/8) = 35` ⇒ `max(10,35) = 35` ⇒ `8 × 35 = 280` ⇒ `min(1240, 280) = 280vp`。
**⇒ `280vp` 在 `720` 屏上装得下。但要真机核 `h` 的实际值。**

## 二、`1` 处需要**取值决策**：`GWordle.ets:492`

**现在**：
```ts
      .width(Bp.isShort() ? 120 : 614)
```

**问题**：`isShort()` 在电视上**恒为 `false`**（`Bp.ets:299` 带 `!Bp.isTv()`）⇒ 电视走 `614` ⇒ 超游戏区 `84vp`。

**❌ 不能简单改成 `(Bp.isShort() || Bp.isTv()) ? 120 : 614`** —— 电视盘面会只剩 `120vp`（屏幕宽的 `9%`），**荒谬地小**。

**需要给电视一个专属值。我的算术估计**：
```
电视游戏区 ≈ 720 − 104(头部) = 616vp
键盘 6 行 × KEY_H(40vp) = 240vp + 行距 ≈ 260vp
⇒ 盘面可用 ≈ 616 − 260 ≈ 350vp
```
**⇒ 建议 `Bp.isTv() ? 350 : (Bp.isShort() ? 120 : 614)`，但 `350` 必须真机验。**

**⚠️ 另一个待确认点**：`GWordle:491` 的注释写着「`220 → 185`」，而代码是 `120 : 614`。
队友查了 `git blame`：注释来自 `49097e64`、代码行来自 `b2cacc75`，**注释从出生那天就对不上**
（它诞生时值已是 `150`，只记了中间档 `185`）。
**⇒ 改这处时顺手把注释改成不带数字的写法**（如「矮屏收到键盘三行完整露出为止，终值 `120vp`，见 `b2cacc75`」），免得以后改值再漂移。

## 三、为什么这 `4` 处要一起改、而不是分批

这 `4` 处的共同点是「电视上走了一个不该走的支」，**只有一起改完，电视才有一份可信的观感基线**。
若改 `3` 处就看，会被 `GWordle` 的溢出干扰判断。

## 四、前置与顺序

1. **必须先有电视真机观感**（`onemore_tv` 首启 `3`–`5` 分钟）——**先看不改**
2. 看完再改这 `4` 处
3. 改完**只重测这 `4` 款**（不用全量）
4. 之后再考虑 `capMax()` 助手 + lint（见 `高屏不限制-全库清单`）

## ⇒ 判据（`2057`）

**「`isShort()` 为假 ⇒ 走大值」这种写法，在电视上不是「变大」而是「失控」——
因为它旁边往往没有别的封顶兜着。**
**⇒ 判断一处 `isShort()` 三元危不危险，看一个问题即可：另一支有没有上限？**
有（`Math.min` 兜着）⇒ 最多是「偏大」；没有（裸数字 / `9999`）⇒ 电视上会失控。
