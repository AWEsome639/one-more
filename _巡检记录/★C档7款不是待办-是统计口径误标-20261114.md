# ★ C 档 `7` 款不是待办 —— 是统计口径在误标已修好的款

> `2026-11-14 10:4x`。**我差点把这 `7` 款排进明天的活，查了 git 时间线才发现它们早修好了。**

## 二、我原来的解释错了，正确的是「它们已经修好了」

**我最初想：「台账数据是改动前测的 ⇒ 旧数据」。查完发现不是。**

六款的最后测量时间全在 **`2026-11-14 00:30`–`06:44`**（昨夜那轮）。
再看降档代码是什么时候加的：

| 款 | 降档加入 | 提交说明原文 |
|---|---|---|
| `Area Perimeter Match` | **`11-13 21:34`** | 「✅ `Area Perimeter Match` 修好（`blk 3/72px → 0`）」|
| `Binomial Match` | `11-11 15:17` | 「✅ 触控第二档落地：`60` 处可点尺寸按屏高分档」|
| `Base Shift` | **`11-13 01:12`** | 「**判据 `1973`：`max_bottom` 变大 ≠ 变差** —— 是『最低节点换人』」|

**⇒ 降档全部早于昨夜测量 ⇒ 昨夜的数据已经包含降档 ⇒ 它们不是「旧数据」，是「降档之后的现状」。**

**⇒ 而现状是：`blk=0`（无布局块越界）+ `max_bottom=1600`（有文字排到屏底）。**

## 三、这就是判据 `1973` 自己警告过的误报

`Base Shift` 那次提交的说明写得很清楚：

> **判据 `1973`：`max_bottom` 变大 ≠ 变差** —— 是「最低节点换人」

**⇒ `max_bottom` 的语义是「最低的**有文字**节点的 `y2`」。
一个满屏游戏的说明行/按钮行本来就该排到 `1584` 以下。**
**⇒ 拿「`blk=0` 但 `max_bottom ≥ 1584`」当「待修」，等于要求「所有文字都不能靠近屏底」——那是错的。**

**⇒ 更要紧的一层：`max_bottom` 只统计有文字的节点（`shot_game.py:134 texts()`）。
所以「`max_bottom ≥ 1584`」实际含义是「**有文字排到接近屏底**」，
它既不等于「溢出」，也不等于「被手势线盖住」（手势线在 `1584`，屏底 `1600`，中间还有 `16px`）。**

## 四、所以明天不该追这 `7` 款

**理由三条：**
1. **`blk=0` 是硬指标**（布局块没越界），而这 `7` 款全绿
2. **降档代码在**，且其中一款的提交明确写着「`blk 3/72px → 0`」= 修好并验证过
3. **判据 `1973` 已定**：「`max_bottom` 变大 ≠ 变差」

**⇒ 若还有余力，正确做法是「抽 `1`–`2` 款看截图」（判据 `1998`：`blk=0` 也可能有横向裁切/整行不见），
而不是按 `max_bottom` 去改代码。**

## 五、那 C 档这个统计还有什么用

**有用，但要用对：它是「**嫌疑名单**」，不是「**待办名单**」。**
- `blk ≥ 24`（A 档）⇒ **真溢出，要改**（`Wordle`/`Mandelbrot`/`Magnets` 三款，已在明晚清单）
- `blk=1`–`3px` ⇒ **噪声级，不改**（判据 `2037`，`19` 款）
- `blk=0` 但 `max_bottom ≥ 1584`（C 档）⇒ **看图确认，多数是正常满屏**（本档 `7` 款）

**⇒ 判据（`2062`）：一个「嫌疑名单」被当成「待办名单」用，就会生产出并不存在的活。
判断方法：这个判据有没有对应的「已修好」反例？有 ⇒ 它只能当筛子，不能当工单。**

# 六、`triage.py` 的 `lowest=` 列直接证实了这条结论

我把 C 档的输出措辞改了（纯 `print`，零风险），改完实跑一看：

```
【C 档 · 嫌疑名单】blk=0 但 max_bottom ≥ 1584（有文字排到近屏底）10 款
  ⇒ **多数是正常满屏**，不是缺陷：`blk=0` 是硬指标，而 `max_bottom` 只量**有文字**的节点。
  ⇒ 只看截图确认（判据 1998）；**不要按 max_bottom 去改代码**（判据 1973）。
  Base Conversion Run            max=1600  lowest=把进制换算对，答错扣 3 秒
```

**⇒ 看 `lowest=` 那一列：「最低的文字节点」是一条提示行 ——「把进制换算对，答错扣 3 秒」。**

**提示行贴在屏底是设计如此，不是缺陷。**
**⇒ 这就把「C 档是误报」从我的推断变成了可以当场看出来的事实：
`triage.py` 本来就把 `lowest` 打出来了，只是原措辞（「触到手势区」）在暗示它是问题。**

## 改了什么

```diff
- print('\n【C 档】blk=0 但 max_bottom ≥ %d（触到手势区）%d 款')
+ print('\n【C 档 · 嫌疑名单】blk=0 但 max_bottom ≥ %d（有文字排到近屏底）%d 款')

+ print('  ⇒ 只看截图确认（判据 1998）；**不要按 max_bottom 去改代码**（判据 1973）。')
```

## ⇒ 判据（`2066`）

**一个统计输出里最容易被忽略的那一列，往往就是分辨真假的关键。**
`triage.py` 早就把 `lowest=`（最低节点是什么）打出来了 ——
**只要看一眼就知道那些是提示行**，而不是有东西溢出。
**⇒ 报一个「异常清单」时，必须同时给出「这个异常具体是什么」。
只给数字（`max=1600`）会让人去改代码；给出实体（`lowest=提示行`）会让人去看截图。**

## 这说明什么

**`max_bottom` 是「最低的有文字节点的 `y2`」。**
**⇒ 有 `52` 次，那个最低的节点是「提示」行。**

**而提示行贴在屏底是**设计如此**（判据见本文第五节：`triage.py` 本来就打 `lowest=`，一眼能看出来）。

**⇒ 所以「`max_bottom ≥ 1584`（触到手势区）」这个判据，
在 `52/172 ≈ 30%` 的款上，量到的其实是**提示行**，不是缺陷。**

## 这就把 C 档的结论从推断升级成量化

先前我只说「C 档 `7` 款是误报」（逐个查了 git 时间线）。
**现在还能量化：`lowest='提示'` 占 `52` 次 ⇒ 至少这 `52` 款里，
`max_bottom` 高是提示行造成的，不该按它改代码。**

## 明早怎么用这条

**读 `triage.py` 的 C 档时，先看 `lowest` 那一列：**

| `lowest=` 是什么 | 判读 | 下一步 |
|---|---|---|
| `提示` / `说明行` / `玩法` | 🟢 **多半不是缺陷**（文字贴底是设计）| 跳过 |
| `换一题` / `重开` / `再玩一次` | 🟡 按钮行贴底，可能被手势线压 | 看截图 |
| 盘面格子内容（数字/字母/颜色）| 🔴 **真的是内容溢出了** | 要改 |

**⇒ 这一条能把 C 档的待确认量从 `7`–`10` 款降到真正需要看图的 `1`–`2` 款。**

## ⇒ 判据（`2087`）

**一个「异常指标」的误报率，可以从「它量到的那个对象是什么」直接算出来。**
这次：`max_bottom` 量「最低的文字节点」，而 **`30%` 的款最低节点是提示行** ⇒ **`30%` 的「异常」是假的**。

**⇒ 判据：抱怨一个指标不准之前，先统计「它实际量到了哪些对象」。**
如果最常见的对象是**本来就该在那里的东西**（提示行、按钮行），
那这个指标需要的不是「调阈值」，而是**「分类后再判」** —— 这正是 `lowest=` 那一列的用途。
