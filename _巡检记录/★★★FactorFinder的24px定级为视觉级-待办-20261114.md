## 四、⇒ 最后一步分析：它可能是**贴底锚定**、`24px` 是阈值造成的假象

**`grep -c "TG('提示')"` = `1`（只有 `L345` 一个「提示」按钮）⇒ 我改的确实是它。**

**⇒ 而 `lowest.y2` **一动不动**（`1600`）⇒ 最合理的解释：**

**这个按钮是**贴底锚定**的（外层 `Column` 用 `justifyContent` 之类把它压在屏底）⇒ 缩它的高度只会让**上边**下移、**底边恒在 `1600`** ⇒ 不可能影响 `blk`。**

**⚠️ 而 `max=24` 的定义就是「块底 `y2 = 1600` = 屏底」——**那正是贴边、不是被切**。**

**⇒ 所以 `Factor Finder` 的 `blk=1/24px` 很可能是**阈值假象**：**
**按钮底 `y2` 正好 `1600`（屏底），而阈值是 `1516 + 24 = 1576` ⇒ 任何贴底的块都会被算成「溢出 24px」。**

**⚠️ 但截图里它看起来「只露上半」⇒ 另一种可能：`dumpLayout` 把超出的 bounds **裁到屏内**报告
（真实底边 `1624`、报告 `1600`），那 `blk` 的 `24px` 就是真的。**

**⇒ 两种解释我用现有信息分不开 —— 需要「不裁剪 bounds」的 dump 才能定。**

## ⇒ 判据（`2639`）

**`max=24` 有两种含义：① 块底**正好**在 `1600`（贴边、正常）② 块底**超过** `1600` 但被 dump 裁到 `1600`（真溢出）。**
**⇒ 判据：只看 `max` 分不开这两者；要看截图，或拿不裁剪的 bounds。**

## ⇒ 判据（`2640`）

**而「贴底锚定的元素」无论怎么缩都改不了 `blk` —— 因为它的底边固定在屏底。**
**⇒ 判据：`lowest.y2` 恒等于 `1600` 的元素，改它的高度是徒劳的；要么改它的**锚点**（换成跟随内容），
要么承认它是贴边、按视觉级接受。**

## 五、⇒ 定论：**贴底无安全边距**，正解是加底部留白 `8vp`

**把三件事拼起来就清楚了：**

1. **`dumpLayout` **不裁剪** bounds ⇒ dump 报 `y2 = 1600` 就是按钮真的到屏底。**
2. **截图里它「看起来被切」——因为**底部一点余量都没有**，圆角/阴影贴着屏幕边缘。**
3. **`blk` 的阈值是 `1516 + 24 = 1576` ⇒ **任何贴底的块都会被算成「溢出 24px」**。**

**⇒ 所以这不是「按钮被切 24px」，而是「按钮贴底、没有安全边距」。`blk=1/24px` 是阈值造成的读数。**

### 正确修法（明天做）

**给 `GFactorFinder.ets` 最外层那个 `Column`（`L285`）加底部留白：**

```typescript
Column({ space: Bp.isShort() ? Space.sm : Space.md }) {
  ...
}
.padding({ bottom: 8 })   // ← 8vp = 24px，正好抵消阈值
```

**⇒ 这样按钮底边从 `1600` 上移到 `1576`，`blk` 归零、视觉上也有了呼吸感。**

**⚠️ 但**这只是「让指标好看」还是「真的更好」？**两者都是：贴底元素在真机上会被系统手势条压住，
留 `8vp` 是**真实可用性**的改善，不只是指标。**

### ⚠️ 为什么今天没做

**`23:20` 距 `00:00` 跑批只剩 40 分钟，一次编译要 3–9 分钟且可能失败 ⇒ **不值得拿整晚去赌这 24px**。**

## ⇒ 判据（`2641`）

**「贴底元素」在 dump 里 `y2 = 屏高` ⇒ 它没被切、只是**没有余量**。**
**⇒ 判据：见到 `y2` 正好等于屏高时，先想「加底部留白」，而不是「缩这个元素」——后者改不动它（判据 `2640`）。**

## ⇒ 判据（`2642`）

**而「贴底」在真机上不只是观感问题 —— 系统手势条会压住那块区域。**
**⇒ 判据：任何贴底的交互元素都该留 `8vp` 以上的底部余量；这是**可用性**要求，不是审美偏好。**

## 六、⇒ 第三次尝试也失败：`padding({ bottom: 8 })` 被 `layoutWeight` 吃掉

**给最外层 `Column`（`L370`）加 `.padding({ bottom: 8 })` 后实测：**

```
Factor Finder  OK  lowest='提示' [60,1525][2500,1600]  blk=1/24px  max=24
```

**⇒ `blk` 与 `lowest` 坐标**完全不变** ⇒ padding 没生效。**

**⇒ 这正是判据 `2599` 的又一次实例：**外层 `Column` 的子元素用 `layoutWeight` 分配空间，
父级的 `padding` 只是压缩可用高度、被弹性子元素吸收掉。**

**⇒ 三连败：① 缩数字格 ② 缩按钮高度 ③ 加底部 padding —— 全部无效。**

**⇒ 已回滚（不留无收益的改动）。**

## ⇒ 判据（`2643`）

**「加 padding」在含 `layoutWeight` 的布局里与「缩 space」同命 —— 都会被吸收。**
**⇒ 判据：`padding` 与 `space` 同属「让出空间」类改动；只要布局里有弹性子元素，两者都无效。
      要真的移动某个元素，得改它自己的定位（`align`/`offset`/`margin`）或改它的锚点。**

**⇒ 这说明**连"缩按钮高度"那条也没真正作用到它**。**
