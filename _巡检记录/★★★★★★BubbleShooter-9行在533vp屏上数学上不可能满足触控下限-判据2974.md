# `Bubble Shooter`：**`9` 行在 `533vp` 屏上数学上不可能满足触控下限**

> `2026-11-19 01:25`。从「气泡看起来小」一路算到「这题得改设计」。**全程离线、可复算。**

## 一、⇒ 根因（作者自己写了注释，`GBubbleShooter.ets:428-437`）

```
每格边长（vp）：按「可用高度 / 行数」算，不按宽度算
★★★ 2026-10-30（平板横屏 853×533 真机实测）：
  原来只用 .layoutWeight(1) + aspectRatio(1)：
    每格宽 = 屏宽/9 ≈ 88vp ⇒ 每格高也 88vp ⇒ 9 行 = 792vp，
    远超可用高度（约 400vp）⇒ 气泡网格溢出，压到三张信息卡上…
  ⇒ 改成按高度算：每格 ≤ 可用高度/9。
  ⚠️ 试过 .constraintSize({maxHeight:'100%'}) —— 溢出是没了，
    但格子在 layoutWeight 压扁的行里变得极小（挤在左上角），更糟。
```

**⇒ 现代码：`avail = Bp.height * (isShort ? 0.26 : 0.30)` ⇒ `533 × 0.26 = 139vp` ⇒ 每格 `13.6vp = 41px`。**

## 二、⇒ 算术：为什么 `9` 行做不到

| 项 | 值 |
|---|---|
| 屏高 | `533vp` |
| 其他界面（标题/两按钮/三信息卡/待发射条/两行说明）| 约 `230vp` |
| **留给气泡区** | **约 `303vp`** |
| **`9` 行 × `44vp`（触控下限）需要** | **`396vp`** |
| ⇒ **结论** | **差 `93vp`，数学上不可能** |

**⇒ 各方案实算（可用 `303vp`）：**

| 行数 | 每格 | 结论 |
|---|---|---|
| `9`（现状）| `31.9vp` = `96px` | ❌ |
| `8` | `36.1vp` = `108px` | ❌ |
| `7` | `41.6vp` = `125px` | ❌（差一点）|
| **`6`** | **`48.8vp` = `146px`** | ✅ |
| `5` | `59.0vp` = `177px` | ✅ |

## 三、⇒ 所以这不是「调个数字」，是**设计取舍**

**⇒ `ROWS = 9`、`COLS = 9`（`GBubbleShooter.ets:24-25`）。**
**⇒ 要保持 `9` 行，就必须让每格 `31.9vp`（`96px`）—— 而 `44vp` 是项目定的触控下限（`Cell.tap = max(Cell.of, 44)`）。**
**⇒ ⇒ **要么把行数降到 `6`，要么接受触控不达标。** 没有第三种选择（除非改屏幕布局，把 `230vp` 的其它元素压到 `150vp`，那不现实）。**

## 四、⇒ 明天要问奥森的一句话

**⇒ 「`Bubble Shooter` 的 `9×9` 网格在 `533vp` 手机上，每格最多 `96px`，低于 `132px` 触控下限 ⇒ 要么改成 `6` 行（每格 `146px`），要么保持现状但接受点不准。你选哪个？」**

**⇒ 附带：这也解释了 2026-10-30 那次「溢出修好了但格子变小」—— 当时是在**修症状**（溢出），没意识到「9 行在竖屏上本来就不够放」。**

## ⇒ 判据 `2974`

**⇒ 遇到「元素太小/太大」时，**先把约束写成不等式算一遍**：`行数 × 触控下限 ≤ 可用高度`。**
**⇒ 算完会发现有些问题**根本没有「调参」解** —— 只能改结构（行数/列数/分页）。**
**⇒ ⇒ 而这类问题最容易被误当成「调个数字就好」，于是反复试几个魔数、每次都不对，最后放弃。先做这道算术，能省掉那一圈。**
