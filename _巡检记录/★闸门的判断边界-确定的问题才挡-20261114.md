# ★ 闸门的判断边界：**只在「确定有问题」时挡，不在「我判断不出来」时挡**

> `2026-11-14 11:5x`。审我自己今天写的 `preflight_install.sh` 时发现的**设计缺陷**。

## 缺陷

`preflight_install.sh` 是今晚**唯一能挡住整轮**的闸。原版把所有非 `OK` 情形都 `exit 1`：

| 情形 | 原退出码 | 性质 |
|---|---:|---|
| 本地 HAP 不存在 | `1` | **确定**：没东西可装 |
| 设备不在线 | `1` | **确定**：无法校验 |
| 设备上没装这个 bundle | `1` | **确定**：一定是错的 |
| **解析不出 `updateTime`** | **`1`** | **❗「我判断不出来」—— 不是「确定有问题」** |
| **时间格式解析失败** | **`1`** | 同上 |
| 设备包确实更旧 | `1` | **确定**：真该挡 |

**⇒ 后两种其实只是「我的正则没匹配上」，却会挡住一整夜的活。**

**而 `bm dump` 的输出格式，我从没在真机上见过**（今天没有设备）——**所以这两条失败路径的概率并不低。**

## 改后

```bash
# 解析不出 updateTime ⇒ 打醒目警告 + 手工确认命令，exit 0 放行
echo "  ⚠️ 读不到 updateTime ⇒ 自动校验失败（不是「包旧」，多半是格式与我预期不同）"
echo "     **已放行**，但请先手工确认一次（10 秒）："
echo "       \$HC shell bm dump -n \$BUNDLE | grep -i update"
echo "     把它和本地 HAP 时间（\$HAP_T）比一下：不早于就没问题。"
exit 0
```

**⇒ 现在只在四件事上 `exit 1`**：`cd` 失败、本地 HAP 缺失、设备不在线、**设备包确实更旧**。
**其余「判断不出来」的情形：警告 + 放行 + 给出 10 秒手工确认命令。**

## 为什么不干脆保持 fail-closed

**「安全默认」听起来对，但要算代价：**

| 方案 | 误挡的代价 | 漏放的代价 |
|---|---|---|
| fail-closed（原版）| **一整夜白等**（若只是格式不对）| — |
| fail-open（改后）| — | 若包真旧 ⇒ 白跑一夜 |

**⇒ 关键在于「哪种更可能」**：
- 「格式不对」：**我从没在真机上看过 `bm dump` 输出** ⇒ 概率不确定，且**后果是整夜白等**
- 「包真旧」：需要我说谎/忘记装包才会发生；而 `hdc install` 的 `install bundle successfully` 是**硬回显**，我已经要求必须看见

**⇒ 所以：把「确定的事实」当闸门，把「我的解析结果」当提示。**

## ⇒ 判据（`2090`）

**一个自动闸门必须区分「输入违反了规则」与「我无法解析输入」。**
- 前者：挡住（那是它存在的意义）
- 后者：**放行 + 醒目提示**（否则「我的实现有 bug」会变成「你的流程被否决」）

**⇒ 判据：凡 `exit 1`，问一句「这个分支代表的是**客观事实**，还是**我的判断失败**？」
把后者也当 `exit 1`，等于让工具的实现细节拥有了否决权。**
