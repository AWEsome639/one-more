# ⛔⛔⛔ 方法论错误：**用 `blk` 反推「需要回收多少 vp」根本不成立**

> `2026-11-14 13:1x`。看 `截图-Block_Count_3D-210312.jpeg` 后发现。**这推翻了我今天做的一批「从 `blk` 算出改法」的结论。**

## 一、矛盾的观察

**`Block Count 3D` 的台账：**
```
max_bottom = 1600     ← 恰好等于屏底
blk = 2/48px          ← 最深的越界量 48px
```

**而它的截图（`11-14 09:03`）显示：**
- 三列格子，第一行、第二行完整
- **第三行只露出上沿就被屏幕切断**
- 代码注释也写着「`2026-11-13` 真机截图（`blk=2/48px`）：**棋盘的第三行被切掉（整行看不到）**」

**⇒ 若按 `blk` 的 `16vp` 去回收，第三行只会多露 `16vp`，**仍然看不见**。**

## 二、矛盾的解：**`bounds` 被钳在 `1600`**

**`blk` 的判定阈值是 `1516 + 24 = 1540`（判据 `1978`/`1980`）。**
**`blk=48px` ⇒ 某块 `y2 = 1540 + 48 = 1588`。**

**⇒ 而 `max_bottom = 1600` = 屏底高度。**

**⇒ 所以：屏幕外的子节点，在 `uitest dumpLayout` 的 `bounds` 里**被钳制到 `1600`**。
⇒ 不管它在屏幕外多远，`y2` 都只报 `1600`。**

## 三、这意味着什么（三件事全错）

| 我今天的做法 | 为什么错 |
|---|---|
| 用 `blk` 的 px 值反推「缺多少 vp」 | **`blk` 最多只能报 `60px`**（`1600 − 1540`），超出部分全被钳掉 |
| 用 `max_bottom` 判「贴到屏底了没」 | **它恒等于 `1600`** 时无法区分「刚好贴底」和「溢出很多」 |
| 用 `工具/budget.py --need <blk>` 求目标 `base` | **`--need` 的输入本身就偏小** ⇒ 求出的 `base` 偏大 ⇒ **改完仍不够** |

**⇒ 受影响的结论（今天写的）：**
- `#8` `GBlockCount3D` `88→80`（省 `21vp`）—— **不够，第三行仍看不见**
- `Fraction Matcher` `48→42`（省 `20vp`）—— **不够，选项 `C`/`D` 仍在屏外**
- `Pythagorean Triple Builder` `46→40`（省 `20vp`）—— **不够，`确认` 行仍被切**
- `Magnets` 的 `-360 → -376`（省 `16vp`）—— **不够**

**⇒ 四处的「省 `20vp` 左右」都源自同一个错误前提。**

## 四、那「缺多少」该怎么量

**`bounds` 被钳，所以**不能从 dump 量**。三个可行办法：**

| 办法 | 做法 | 代价 |
|---|---|---|
| **A. 看截图目测** | 按 `1600px = 533vp` 换算，量「还有多少内容在屏外」 | 粗糙，但**立刻可用** |
| **B. 用 `board=`/`cov=`** | 今晚首次产出；`board=` 给盘面矩形，能算盘面占了多少 | 只对有盘面的款有用 |
| **C. 加一个新指标** | `shot_game` 统计「`y2 == 1600` 的叶子数」⇒ 被钳的节点数 | **要改代码**，今晚不能 |

**⇒ 短期用 A（截图目测），中期用 B，长期用 C。**

### A 具体怎么目测（以 `Block Count 3D` 为例）

**截图 `1600px` 高 = `533vp`（`3px = 1vp`）**
- 第三行格子上沿在约 `y = 915/1006 × 1600 ≈ 1455px ≈ 485vp`
- 而第三行要高 `Cell.of(88) = 75vp` ⇒ 需要到 `560vp` ⇒ **超出可用 `533vp` 约 `27vp`**
- **再算上答案区（若在第三行下方），还要更多**

**⇒ 所以真实缺口 ≈ `30vp`–`80vp`，而不是 `16vp`。**

## 五、⇒ 修正后的做法（明晚批次）

**`#8` `BlockCount3D` 不能再按「`88→80` 省 `21vp`」执行。**
**正确做法：**
1. **先按截图目测真实缺口**（上面算的 `≈27vp` 只够让第三行勉强露完，还不含答案区）
2. **再决定改多少** —— 可能要 `88 → 64`（省 `(75−54)×3 = 63vp`）
3. **⚠️ 而 `Cell.of(64) = 54vp` 仍 > `touchMin 44`** ⇒ 可点性没问题

**⇒ 所以这款该改的幅度比原计划大 `2`–`3` 倍。**

## ⇒ 判据（`2125`）

**一个测量值若**被钳制**（clamp / saturate），它就不能用来反推「超出多少」。**
**这次 `bounds` 被钳在屏底 ⇒ `max_bottom` 恒 `1600`、`blk` 恒 ≤ `60px`。
它们仍能回答「**有没有**溢出」，但**不能**回答「**溢出多少**」。**

**⇒ 判据：用任何指标做定量推算之前，先问「它的值域有没有上限/下限」。
若有，逼近那个上限时它就不再有分辨力 —— 而「逼近上限」恰恰是最需要分辨力的时候。**

## ⇒ 判据（`2126`）

**我今天犯的最大一个错，是「从 `blk` 算出精确的改法」——它看起来很科学（有数字、有工具、有公式），
但**输入是一个被钳制的量**。**

**⇒ 判据：精确计算会掩盖输入的错误。一个用 `budget.py` 算出的「最小可行 `base = 81`」，
比一句「大概要缩小一点」更像结论，但它可能同样是错的 —— 而且更难被质疑。**

**⇒ 所以：越是算得精确，越要先验证输入量是否可信。**
