## 0. 结论

**实测是 `init-false`（`code-hunter` 对）。`no-syscap` 在这台机上不会出现。**

| 项 | 值 |
|---|---|
| 卡片「模型状态」 | **`init-false`** |
| 卡片「初始化」 | **1118 ms** |
| 卡片「首字延迟」 | `—`（从没出过 token） |
| 卡片「问答次数」 | **0** |
| 其余 | 「规则版已启用」 |

**旁证（`hilog`，比卡片更硬）**：
```
11-09 01:24:23.644 ... I A00000/com.andrewoscar.onemore/LocalLLM: init=false 耗时 1118ms
```
这正是「触发成功、但 `localChatModel.init()` 返回 false」的那行日志（`LocalLLM.ets:78`），
**时间 01:24:23 与我发问的时刻吻合**；**且日志里没有** `设备无 LocalChatModel syscap ⇒ 降级到规则版`（`LocalLLM.ets:66` 那句）。
⇒ **`canIUse(SYS_CAP)` 通过了、系统模型服务调起来了、但 `init()` 返 false** ⇒ **`init-false` 分支**。

## 2. 规则版的答案（顺便记录：这是「88% 准确率」的一次实证）

**问**：`想玩个简单的`
**答**：**`按「简单」找：`** 后面跟三款：

| 建议 | 注册表 `difficulty` | 注册表 `tags` 里有 `easy`？ |
|---|---|---|
| 宝石迷阵 | `NORMAL` | ✅ 有 |
| 打砖块 | `NORMAL` | ✅ 有 |
| 弹珠消 | `NORMAL` | ✅ 有 |

**⇒ 这条答案是对的**（三款确实都带 `easy` tag）。
**⚠️ 但有个容易误判的点（我自己差点写错）**：它们的 `difficulty` 字段都是 **`NORMAL`**，
如果只看 `difficulty` 会以为"答错了"。
真实机制（`ChatFinder.ets:281–289`）：**全库 `EASY` 只有 0 款、`HARD` 1 款、354/355 是 NORMAL**
⇒ 早就改成**按 `tags` 里的 `easy` 匹配**，UI 上那句「难度对得上」指的是 **tag 命中**，不是 `difficulty` 字段。
⇒ 这正是**判据 1819 第五类（现象对、机制错）**的现场：只看字段会得出"标签与结果不一致"的错误结论。

## 3. 为什么「问答次数 = 0」不是坏事

`ChatFinder.parseWithLLM`（`ChatFinder.ets:475–493`）：
```ts
const base: Intent = ChatFinder.parse(text);   // 规则版先算好
const ready: boolean = await LocalLLM.init();
if (!ready) { return base; }                   // ← 我们走这里：init=false ⇒ 直接返回规则版
```
⇒ **LLM 从没成功回答过一句** ⇒ `calls` 自然是 0。
**这不是"没触发"** —— 触发有两条硬证据：
① `hilog` 那条 `init=false 耗时 1118ms`；
② 卡片里的「初始化 **1118 ms**」与日志数值**完全一致**（卡片读的就是 `LocalLLM.stat.initMs`）。

## 4. 给 lead 的两条结论

1. **`no-syscap` 分支在这台设备上不可能出现** —— `canIUse(SYS_CAP)` 为真（否则会打那句 syscap 日志、且 `initMs` 会保持 0/不写 1118）。
   要在真机上看到 `no-syscap`，只能：① 换一台没有该 syscap 的设备；② 代码里临时 `return false` 打桩。
2. **`init-false` 之后系统应该做什么，现在是符合设计的**：规则版保底、UI 显示 `init-false` + 1118ms、问答次数不虚增。
   ⇒ **"AI 诊断卡 idle + 0 次" 与 "init-false + 0 次" 是两个不同状态**，前者是"没试过"、后者是"试过但系统模型没起来"。**判断"真的没能力"必须触发过一次**（本报告做的就是这件事）。
