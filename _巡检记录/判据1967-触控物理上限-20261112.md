# 判据 1967：**横屏 `533vp` 下，棋盘列数有物理上限**

## 这个数字是硬约束

**可用高预算 `343vp`；`Cell.tap` 的触控下限 `44vp`。**

**⇒ `N` 列格子的棋盘要能点，需要 `N × 44 + 间距 ≤ 343`：**

| 列数 | 需要的宽 | 能塞进 `343vp` 吗 |
|---:|---:|---|
| `4` | `176` | ✅ 宽裕 |
| `5` | `220` | ✅ |
| `6` | `264` | ✅ |
| `7` | `308` | ✅ 勉强 |
| **`8`** | **`352`** | ❌ **超了** |
| `10` | `440` | ❌ |

**⇒ `8` 列以上，横屏**不可能**同时做到「全部可见」与「格子可点」。**

## 而今晚我做的事，恰好踩了这个上限

**我给 `12` 款棋盘加宽度封顶（`.width(Math.min(Bp.width - 40, Bp.height - 360))`），
`533` 屏下封顶 `173vp`。按 `(173 - 6×(N-1)) / N` 算格子宽：**

| N | 格子 vp | 判定 |
|---:|---:|---|
| `4` | `39` | 偏小但可接受 |
| `5` | `30` | 偏小但可接受 |
| `6` | `24` | 踩线 |
| `7` | `20` | **点不准** |
| **`8`** | **`16`** | **完全点不准** |
| `10` | `12` | 不可用 |

**⇒ 队友 `cbb43f1b` 审出 `7` 款 ≤`24vp`：
`WordSearch`(16) `PixelMimic`(16/困难12) `RotatingMaze`(20/困难14) `FindWord`(24) `PolyominoTiling`(≈22) `PathRecall`(≈22) `MathMaze`(≈23)**

**⇒ 我为了「修溢出」把它们改成了「看不见内容但格子能点」的反面 —— 「看得见但点不准」。**
**⇒ 判据 1957 说的是「功能优先」，而我这次的选择**牺牲了功能**换来「全可见」。**

## 正解（明天做，不能再压宽度）

**`8` 列以上的棋盘，只有三条路：**

1. **横屏减列**（`8 → 6`）：最干净，格子回到 `24vp` 以上；游戏规则略变（可在 `Bp.isShort()` 时用更小的关卡）
2. **盘面可滚动**（`Scroll` 包棋盘）：保持列数，用户滑动查看 —— 但「找词类」游戏滚动会破坏「整体可见」的核心体验
3. **接受格子小**：只有 `≤6` 列时可行

**⇒ 我的判断：`WordSearch` / `FindWord` / `PixelMimic` 这类「需要看清全盘再点」的游戏，**必须走第 1 条（减列）**；
`RotatingMaze` / `MathMaze` / `PathRecall` / `PolyominoTiling` 可先试第 2 条。**

## 今天的真实教训

**「溢出清零」这个指标本身是有害的** —— 它能被「把内容缩到格子点不准」来满足。
**⇒ 判据 1967 的正确用法：先算「这个 N 在这个屏上能不能既可见又可点」，不能就先改玩法（减列），别改尺寸。**
