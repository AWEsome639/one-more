# ★★★★ `max(240,…)` → `max(140,…)` 的量化收益：**`19` 款盘面从「压手势条」变成「清空 `66vp`」**

> `2026-11-14 14:3x`。给这个改动算清账，让它从「理论上该改」变成「有明确收益」。

## 一、当前状态（`19` 款一致）

```
盘面限宽 = max(240, 533−360) = 240vp
盘面（4×4 方阵）= 240vp 高
盘面底 = 1588px = 529.3vp
手势线 = 1584px = 528vp
⇒ 压住手势区 4px
```

## 二、改后（`max(140, …)`）

```
盘面限宽 = max(140, 173) = 173vp
盘面 = 173vp 高 ⇒ 比现在小 67vp
盘面底 = 529.3 − 67 = 462.3vp = 1386px
⇒ 距手势线 1584px 还有 197px（66vp）清空
```

## 三、⇒ 收益

| 项 | 现在 | 改后 |
|---|---|---|
| 盘面底位置 | `1588px` | **`1386px`** |
| 与手势线关系 | **压住 `4px`** | **清空 `66vp`** |
| 盘面占用的纵向空间 | `240vp` | **`173vp`** |
| 腾出的空间 | — | **`67vp` 还给「统计/按钮/线索」** |

**⇒ `19` 款同时受益。**
**⇒ 而那 `67vp` 原本是从别的元素那里抢的 ⇒ 改后那些元素各回各位，
可能顺带修好「块盖住 HUD」那 `3`–`4` 款（`Memory` / `Simon Says` / `Number Bonds All` / `Block Count 3D`）。**

## 四、为什么这个改动风险低

| 条件 | 状态 |
|---|---|
| 改的是结构吗 | ❌ 只改一个整数常量（`240` → `140`） |
| `140` 有依据吗 | ✅ **全库主导值（`73` 处）**，且目标文本称其「真机三次打脸后收敛」 |
| 会引入新问题吗 | **提高下限不会**：`max(140, 173)` 仍取 `173`（因为 `173 > 140`）⇒ 只有「算出值 < 140」的极小屏才会受 `140` 约束 |
| 可回滚吗 | ✅ 一个常量，随时改回 |

**⇒ 而且它**只在算出值 ≥ 140 时无影响**（`173 ≥ 140`）⇒ 对其它设备（平板/电视）**完全无变化**。
**⇒ 只有手机这种 `Bp.height - 360 < 140` 的情形才会被 `140` 限制 —— 而那时盘面本来就该很小。**

## 五、⚠️ 但仍要一次只改一款

**理由不是「不确定对不对」，而是「要拿到配对数据」：**
- 改 `13` 处一次编译，今晚/明晚跑完**只知道整体 `blk` 变了**
- 改 `1` 处（`GSkyscrapers`）一次编译，能拿到**精确的 `before/after` 截图 + `blk`**

**⇒ 而 `verify_changed.sh` 的 `CASES` 里已有 `Skyscrapers`，所以它会被自动对比。**

**⇒ 推荐：明晚改 `GSkyscrapers` 一处（`240 → 140`），编译，真机截图。
若盘面底如预测上移到 `~1386px` ⇒ 批量应用其余 `12` 处。**

## 六、这解决了「怎么证明改对了」

**预测（可证伪）：**
```
改后 GSkyscrapers 的 blk 应从 48px 变为... 
```
**⚠️ 等等 —— 这里有个陷阱：盘面缩小后，它的底部会**上移**，
而 `blk` 数的是「越过 1540px 的块」⇒ 盘面上移后**可能不再越过 1540** ⇒ `blk` 变成 `0`。

**⇒ 所以预测是：`blk` 从 `48px` 降到 `0`（或很小）。**
**⇒ 这是**可证伪的**：若改后 `blk` 仍 `48px` ⇒ 说明 `240 → 140` 没生效（那就要查为什么）。**

**⇒ 另一个可证伪的观测量：盘面底位置从 `1588px` 上移到 ~`1386px`。
这可以直接从新截图上量（用 `lowest` 的文字做参照物）。**
