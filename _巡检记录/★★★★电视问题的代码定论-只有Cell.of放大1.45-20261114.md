# ★★★★ 电视问题的代码定论：**只有 `Cell.of()` 放大 `1.45`，文字/间距/圆角全不放大**

> `2026-11-14 19:2x`。目标里那句「`Cell.of()` 乘 `1.45` 但 `FontSize/Space/Radius` 完全不放大」——**查代码确认，是对的。**

## 一、`Bp.scale()` 全项目只用在一处

```ts
// core/Design.ets:117
return Math.round(base * Cell.k * Bp.scale() * shrink);
```

**⇒ `grep "Bp.scale()" core/*.ets` 只有这一处「使用」（其余是注释）⇒ **`901` 处 `Cell.of()` 调用跟着放大**（`Diag.ets:84` 记录）。**

## 二、⇒ 而 `FontSize` / `Radius` 是**固定值**

```ts
FontSize.hero = 36   FontSize.xxl = 24   FontSize.xl = 20  …
Radius.xs = 8        Radius.sm = 12      Radius.md = 16    …
```

**⇒ 没有任何 `Bp.scale()` 参与 ⇒ **电视上文字与圆角与手机完全一样**。**

## 三、⇒ 所以电视上的真实比例

| 项 | 手机 | 电视 |
|---|---|---|
| 容器（`Cell.of`）| `×1.0` | **`×1.45`** |
| 文字（`FontSize`）| `×1.0` | **`×1.0`** |
| **文字/容器 比** | `1.00` | **`1/1.45 = 0.69`** |

**⇒ ⇒ 电视上**文字相对容器小了 `31%`**——而电视是「`3` 米视距、必须更大」的场景。**

**⇒ 所以 `1.45` 那个放大**没有达到目的**：框变大了、字没变大，视觉上字反而更小。**

## 四、⇒ 而 `shrink` 在电视上还**被跳过**

```ts
// Design.ets:112-113
// 电视不缩 —— 电视的 `Bp.scale()` 已是 `1.45`，
//   再乘 `0.85` 会把「3 米视距要更大」抵消掉一半（`1.45 × 0.85 = 1.23`）。
```

**⇒ 作者已经想到「别抵消放大」⇒ 但**抵消发生在文字上**（文字压根没放大），而不是在 `shrink` 上。**

## 五、⇒ 所以电视的正确修法方向

| 方案 | 改什么 | 代价 |
|---|---|---|
| **A** | `FontSize` 乘 `Bp.scale()` | 一处改动、`901` 处调用自动跟随 —— **但会影响手机**（`scale=1.0` 时无变化 ✅）|
| **B** | 只给电视加一个字号倍率 | 影响面小、但要逐处判断 |
| **C** | 反向：电视上 `Cell.of` **不放大** | 与设计意图相反 |

**⇒ `A` 最干净：`Bp.scale()` 在手机上是 `1.0` ⇒ 零回归（`Design.ets:97` 明确写了「手机上 `Bp.scale() = 1.0` ⇒ 结果与改造前逐像素一致（零回归的保证）」）。**

**⚠️ 但 `A` 会让**所有** `FontSize` 变大 `45%` ⇒ 手机上不变、但平板上会变 `1.06`、PC 上 `1.12` ⇒ **那正是想要的**。

## 六、⛔ 但现在**不许改**

**电视是最低优先项（目标说「第一件事是跑起来看 `3` 米效果」）⇒ 先看，再改。**
**⇒ 而且改 `FontSize` 会影响 `200,359` 条断言所依赖的布局 ⇒ 必须单独一夜做。**

## ⇒ 判据（`2322`）

**「放大容器」与「放大内容」是两件事；只放大容器会让内容**相对更小**。**
**⇒ 这次 `Cell.of` × `1.45` 而 `FontSize` × `1.0` ⇒ 文字/容器比从 `1.00` 降到 `0.69`。**

**⇒ 判据：做「放大」类改动时，要同时检查**容器与内容是否按同一比例放大**。
⇒ 只放大一方 ⇒ 视觉上可能比不改更糟。**

## ⇒ 判据（`2323`）

**作者注释里写「别让 `×0.85` 抵消放大」—— 说明他**意识到了抵消问题**，但**没意识到抵消发生在别处**（文字没放大）。**
**⇒ 判据：修「A 抵消 B」时，要检查**是否还有别的东西也在抵消**。
⇒ 这次抵消来自「文字没跟着放大」，不来自那个 `×0.85`。**
