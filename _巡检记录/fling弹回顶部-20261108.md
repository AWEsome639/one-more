## 0. 结论

**能稳定复现，而且不只在手势之后。**

| 试验 | 条件 | 弹回次数 |
|---|---|---|
| A | 冷启后**立刻**连续 fling ×10 | **2 / 10** |
| B | 同一会话里**静置 8 秒后**再 fling ×10 | **4 / 10** |
| **合计** | | **6 / 20 = 30%** |

另外还有一次**完全没有手势**的自发跳回：
滚到中段（首屏 `汉诺塔`）→ **静置 3 秒** → 再 dump 首屏已变回 `宝石迷阵`（连续 3 次 dump 都在顶部）。

⇒ **这是用户级问题**：用户快速滑动时约 **三成概率**被弹回第一屏；甚至不动也可能被弹回。

## 1. 复现步骤（最简）

```bash
HDC="/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains/hdc"; T="-t 127.0.0.1:5557"
$HDC $T shell "aa force-stop com.andrewoscar.onemore; aa start -b com.andrewoscar.onemore -a EntryAbility"
sleep 16
for i in $(seq 10); do
  $HDC $T shell "uitest uiInput fling 1280 1100 1280 600 1200 5"
  sleep 1.5
  # dump 看首屏第一张卡：是「宝石迷阵」= 被弹回顶部；否则说明前进成功
done
```
**判据（可观测状态）**：首屏第一张卡是不是 `宝石迷阵`（注册表第 1 款）。
⚠️ 注意 `fling` 的**第 5 个参数是 `stepLength`**（默认 = 距离/50），给 **5** 时一次约走 1~2 行；给默认值一次能走好几行。

## 2. 代码里三个"能把列表拽回顶部"的地方（按嫌疑排序）

### ① `source.reset()` → `onDataReloaded()`：**LazyForEach 整表重载**（嫌疑最大）
`components/GamesTab.ets:490` 起的 `list()` 带记忆化，缓存键 = `seg|category|picked|s:searchText`。
**键一变**就重算，然后：
```ts
this.listCache = this.watchFilter(this.computeList());
this.source.reset(this.listCache);      // ← reset 内部 onDataReloaded()
return this.listCache;
```
`LazyForEach` 的 `onDataReloaded()` 是**整表重载**语义，**滚动位置会归零**。
⇒ 只要有**任何**一次状态变化让键变了（哪怕结果集一模一样），列表就会跳回顶部。
**这与"静置 3 秒自己跳回"的现象吻合**（说明有不为人知的 rebuild 让 key 变了）。

### ② `resetGridScroll()`：`scrollEdge(Edge.Top)`（**8 处调用**）
`GamesTab.ets:468`：
```ts
private resetGridScroll(): void {
  setTimeout(() => { this.gridScroller.scrollEdge(Edge.Top); }, 0);
}
```
调用点：`picked` 变更（收藏/标签筛选 `:714`）、切分类（`:1049`）、清空筛选（`:2054/:2063`）、
切分段（`:2222/:2234`）、切视图模式（`:2419/:2439`）。
⇒ **这些是"按设计"要回顶部的**（切分类后必须回顶，否则停在列表底部 —— 有历史注释）。
⇒ 但**只要 fling 时手指路径上误触**这些控件中的任何一个，就会立刻被拉回顶部。
⚠️ 我用的 `fling` 是从 y=1100 到 y=600，**起点 y=1100 落在网格内的卡片上**，
理论上 fling 不该算点击；但 A/B 两组里弹回的时间点没有规律，**不排除误触分类条**。
（分类条在 y≈1237，起点 1100 在它上方 ⇒ 误触可能性不大。）

### ③ `onScrollIndex` 的折叠/展开动画
`GamesTab.ets:1340`：
```ts
if (first >= 2) { want = true; }        // 收起顶部
else if (first <= 1) { want = false; }  // 展开顶部
if (want !== this.topCollapsed) { this.lastToggle = now; animateTo({duration:520}, () => { this.topCollapsed = want; }); }
```
防抖 900ms、迟滞 1~2 行。
**今天上了 `effCollapsed() = topCollapsed || Bp.isShort()`（A 案）之后，矮屏上这个状态再怎么翻转都不会改布局** ⇒
**理论上不该再把列表顶回去**；但 `animateTo` 仍会跑，**若 ArkUI 在动画期间对 Grid 重新布局，仍可能复位滚动位置**（待验）。

## 3. 关键待验实验（需要改一行日志，**未做，等你批**）
在 `list()` 的缓存未命中分支打一行 hilog：
```ts
hilog.info(0x0001, 'perf', 'list miss key=%{public}s newLen=%{public}d', key, this.listCache.length);
```
再在 `resetGridScroll()` 里打一行。然后复现 20 次，看**跳回的那一刻**打印的是哪一类：
- 只有 `list miss` ⇒ 是 **LazyForEach 整表重载**（①）⇒ 修法：`reset()` 改成**增量**（`onDataChange`/`onDataAdd`）或**内容不变时不 reload**（`sameAs` 目前只比 id 顺序，结果集相同就当没变——**这条我已经做了**，所以若是它，说明 id 顺序真的变了）。
- 出现 `resetGridScroll` ⇒ 是**误触/程序调用**（②）⇒ 修法：fling 不应命中分类条，或给这些控件加 `hitTestBehavior`/防抖。

## 4. 影响面
- 用户快速滑到第 200 款，**30% 概率被打回第一屏** —— 这是"白滑了"的体感，比卡顿更劝退。
- 由于是**偶发**，用户不会认为是 bug，只会觉得"这 app 滑起来怪怪的"。
⇒ **建议按用户级 bug 排期**，优先级高于 `cachedCount` 一类优化。

### 6.1 怎么解读（三种可能，无法只靠现有证据区分）
1. **16:18 包里的其它改动顺手治好了**（这版还带了 `GKakuroMini`/`GShikaku` 棋盘限高等改动）。
2. **触发条件是有前提的，而我这次没造出来**：14:17 那天的弹回是在**长时间高强度使用之后**出现的
   （反复切语言 12 种、进出十几个游戏、AI 演示、内存涨到 400MB+）。
   这次 A/B/C 三组都是在"干净会话"里跑的，**没有一次是"用了半小时之后"**。
3. **偶发**，30 次的样本量还不足以排除（若真实概率 ≈10%，30 次全不中≈4%——偏小但可能）。

⇒ **结论：不能宣布已修复，只能说"当前包、当前条件下不可复现"。**

### 6.2 诊断日志先留着（成本几乎为零）
```
11-08 16:18:39.055 ... I A00001/com.andrewoscar.onemore/perf: list miss key=全部|全部||s: len=355
```
- 只在 **`list()` 缓存未命中** 和 **`resetGridScroll()`** 时各打一行，`info` 级，不刷屏
- 复现时的抓法（一条命令）：
```bash
hdc shell "hilog -x | grep -E 'perf.*(list miss|resetGridScroll)' | tail -20"
```
- 判读口径不变：**看"跳回那一刻"打印了什么**，不是"有没有打印过"（切分类/搜索本来就会打 `list miss`）

### 6.3 A-Z 对照没做成（受阻，不是结论）
`▦ / A-Z` 那对视图胶囊在**矮屏折叠态**下没被 dump 暴露（`find('A-Z')`、`find('🔤')`、`find('▦')` 都返回 None），
所以"网格 vs 列表"的控制变量法**没跑成**。要做得先把视图胶囊露出来（或改用一个能 dump 到的入口）。
