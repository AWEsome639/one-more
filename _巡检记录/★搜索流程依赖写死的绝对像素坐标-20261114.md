# ★ 搜索流程依赖**写死的绝对像素坐标** —— 换分辨率就静默失效

> `2026-11-14 11:4x`。审 `probe_no_card.sh` 时顺着查到的。**不是今晚的 bug，是个脆弱点。**

## 事实（`shot_game.py:628-630`）

```python
sh('uitest uiInput click 2276 264')    # 点搜索框
time.sleep(1.2)
sh('uitest uiInput click 1280 435')    # 点输入区
```

**⇒ 四个绝对像素，没有任何 `Bp.width` / `Bp.height` 参与计算。**

## 为什么在 `onemore7` 上是对的

设备 `2560×1600`：

| 坐标 | 位置 | 合理性 |
|---|---|---|
| `x=2276` | 距右边缘 `284px`（`89%` 宽）| 搜索框在右上 |
| `y=264` | 靠上（`16.5%` 高）| 顶栏下方 |
| `x=1280` | 正中（`50%` 宽）| 输入区居中 |
| `y=435` | 搜索框下方 | 输入区在框内 |

**⇒ 数值符合「搜索框在右上、输入区在其下方居中」的真实布局。**

## 风险

**若换成别的分辨率/密度（比如电视 `3840×2160`，或另一个模拟器实例）：**
- `2276, 264` 可能点到空白处或别的控件
- `1280, 435` 可能点到搜索框外

**⇒ 而且它不报错** —— `uitest uiInput click` 点哪儿都成功返回。
**⇒ 表现会是「`uinput` 打字没进去 ⇒ 搜不到 ⇒ 全部 `NO_CARD`」，看起来像「卡片定位坏了」。**

**⚠️ 这正是判据 `2073` 说的那类：精确匹配一个「假定不变」的东西（这次是坐标），环境一变就静默失效。**

## 今晚/明早不受影响

- **今晚**：`onemore7` 就是 `2560×1600`，且**今晚不改分辨率**
- **明早 `probe_no_card.sh`**：抄的是同两个值 ⇒ **同一设备上有效**

**⚠️ 但 `preflight_install.sh` 记录了设备 `updateTime`，却没记录「分辨率是不是我以为的那个」** ——
若哪天换实例，这个坐标会悄悄错。**⇒ 已在执行卡里写了 `实例 onemore7（2560x1600@480 ⇒ 853x533 vp）`，算是有记录。**

## 修法（记档，不做）

**把坐标改成按比例算**：
```python
# 假设搜索框固定在「宽 89%、高 16.5%」附近
W, H = Bp.width_px, Bp.height_px   # 需要 shot_game 拿到像素尺寸
sh('uitest uiInput click %d %d' % (int(W*0.889), int(H*0.165)))
```
**⚠️ 但这只是把「写死像素」换成「写死比例」—— 若布局本身变了（比如搜索框移到左边），一样错。**

**⇒ 真正稳的做法：从 dump 里找搜索框那个节点，点它的中心。**
**代价**：每次搜索多一次 dump（约 `2s` × `153` 款 = `5` 分钟）。
**⇒ 收益**：彻底摆脱坐标假设。
**⇒ 排期：等布局相关工作都清完之后再说，现在动它属于「用 5 分钟换一个还没出过问题的隐患」。**

## ⇒ 判据（`2088`）

**「绝对坐标点击」是自动化里第二脆的写法（第一是精确匹配 UI 文字，判据 `2073`）。**
两者共同的病根：**它们假定了一个「环境不会变」的真理，而这个假定没有写进任何检查里。**

**⇒ 判据：写绝对坐标的地方，必须同时记下「这个坐标是在什么分辨率下定的」。
否则半年后没人知道它为什么是 `2276`。**（这次至少能从 `2560×1600 → 89%` 反推出来。）
