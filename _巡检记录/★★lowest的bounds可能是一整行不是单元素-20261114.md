# ★★ `lowest` 的 `bounds` 可能是一整行，不是单个元素

> `2026-11-14 18:0x`。查「`PythagoreanTripleBuilder` 为什么不在 ③ 列表」时发现。

## 一、证据

```
lowest='⌫' [60,1521][861,1600]
```

**⇒ `x1=60`、`x2=861` ⇒ 宽 `801px` ⇒ **横跨整行**（屏宽 `2560px` 的 `31%`？不，是半个屏）
⇒ 所以 `lowest` 取到的是**那一行的文字**（`⌫` 是行里最左的键），而 `bounds` 是**整行**的范围。**

**⇒ ⇒ 于是「`y2 - y1 = 79px` 可见」这个数，是**那一行的可见高度**，不是单个键的。**

## 二、⇒ 而代码注释证实那一行确实被切

```ts
341|  // 2026-11-13 真机截图：数字键盘**最下排（⌫ / 0 / 确认）被切掉** ⇒ 点不到「确认」
312|  //   「0」与「确认」还在屏外 ⇒ 横屏再收一档：间距 md→sm（省 30）、键帽 48→46（省 7）。
```

**⇒ 开发者**自己记下了**这件事，并已调过两次（`48→46`、`md→sm`），但**没有记录「已修好」**。**

**⇒ 所以它的证据是**代码注释**，不是 `lowest` 的数值。**

## 三、⇒ 这解释了 ③ 节为什么只有 `6` 款

**`③` 的判据是「`lowest.y2 >= 1600` 且可见 `< 20px`」。**
**⇒ `PythagoreanTripleBuilder` 的可见是 `79px` ⇒ 不满足 `< 20px` ⇒ **被筛掉**。**
**⇒ 但那 `79px` 是**整行的**可见高度，而「确认」键可能在行内**更靠下**、已被切。**

**⇒ ⇒ 所以 `③` 那个判据**对「一行里只有部分元素可见」的情况会漏报**。**

## 四、⇒ 所以两个结论都成立，不矛盾

| 说法 | 依据 | 状态 |
|---|---|---|
| 「`③` 只筛出 `6` 款」 | `lowest` 可见 `< 20px` | ✅ 对该口径成立 |
| 「`PythagoreanTripleBuilder` 的确认键被切」 | 开发者注释（`11-13` 真机） | ⚠️ 但那是 `11-13` 的现象，`11-13` 之后又调过 |

**⇒ 两者不冲突：一个是「文字可见高度」口径，一个是「某行某键」口径。**

## ⇒ 判据（`2306`）

**`lowest` 的 `bounds` 可能是**一整行**（当那行的文字节点被合并时）⇒ 它的高度是「行」的，不是「元素」的。**
**⇒ 判据：看到 `bounds` 宽度接近屏宽 ⇒ 那是一条**行**，不是单个元素；
⇒ 此时「可见高度」只能说明「这一行露了多少」，不能说明「这一行里每个元素露了多少」。**

**⇒ 而若元素在行内垂直居中且行高 `>` 键高，行可见 `79px` 时键可能只露更少。**

## ⇒ 判据（`2307`）

**「代码注释里记着的问题」是**有效证据**，但必须看**日期**与**之后的改动**。**
**⇒ 这次注释是 `11-13` 写的，之后 `48→46`、`md→sm` 都改过 ⇒ 当前状态未知。**

**⇒ 判据：引用注释当证据时，同时列出「注释日期 + 之后有无改动」。
⇒ 有改动 ⇒ 标注「待复验」，不能当「当前状态」。**
