# `narrowScreen()` 阈值 420 → 460 评估 —— 2026-11-08

> 执行：verifier-eng2 ｜ **只读**（未改 .ets、未改 Bp 默认值）
> 问题：440×956 竖屏落在「两头不靠」区间（`tinyWatch`<210 ✗ / `tinyScreen`<340 ✗ / `narrowScreen`<420 ✗）
> 定义（`core/Bp.ets:243`）：`return Bp.height < 420 || Bp.width < 420;`

## 0. 结论：**改，但不要一刀切**（分成两档）

| 用法 | 建议 |
|---|---|
| **间距/字号收紧**（GameHost 顶栏间距、结算弹窗字号/内边距、DemoBar 文案） | ✅ **阈值改 460** —— 440 宽下这些收紧**明显更好**（把空间让给棋盘） |
| **隐藏 ☆ 收藏按钮**（`GameHost.ets:1115`） | ⚠️ **不要跟着改** —— 440 宽**放得下** 5 个按钮（‹ ☆ ? 普通 ↻ ≈ 200vp），隐藏它是**无谓的功能损失**；这一处建议用更严条件（如 `Bp.width < 300`）|

## 1. 调用点：**只有 2 处直接调用**（但影响面 33 个引用）

| 文件 | 行 | 形式 | 引用数 |
|---|---|---|---|

| `components/DemoBar.ets` | 48 | `private tiny(): boolean { return Bp.narrowScreen(); }` | **2** 处 `this.tiny()` |
| `core/Bp.ets` | 243 | 定义本身 | — |

**⇒ `games/` 里 0 处**：窄屏判据**只影响游戏页的 chrome（顶栏/演示条/结算弹窗）**，不影响任何游戏的棋盘布局。

## 2. 阈值改 460 后，谁会新进「窄屏分支」

- **440×956 竖屏**（今天的讨论对象）—— 现在走「正常大屏」，改后走窄屏；
- 420–460 宽之间的任何设备（480 宽的旧机不在内）；
- **853×533 横屏不变**（853 ≥ 460 且 533 ≥ 460 ⇒ 仍 false），**其它横屏（960/1280/2in1）也不变**。

## 3. 这些分支在 440 宽下是更好还是更差？（逐项）

| 分支 | 代码位置 | 440 宽下效果 | 判定 |
|---|---|---|---|
| 顶栏间距 `Space.sm → Space.xs` | GameHost:1033 | 5 个按钮在 440 上更松快 | ✅ 更好 |
| 顶栏左内边距 `Space.lg → Space.xs` | GameHost:1279 | 同上 | ✅ 更好 |
| 结算弹窗字号 `md→sm`、按钮高 `46→40`、内边距 `xxl→md` | GameHost:3612/3677/3681/3766-3769 | 440×956 下弹窗更矮，**少挤** | ✅ 更好（今晚「返回列表被切」那类问题会缓解） |
| 演示条文案 `演示中 ｜ 看这里：… → 演示中` | DemoBar:58/75 | **省 1–2 行**（竖屏垂直余量只有 ~35vp） | ✅ 更好 |
| **隐藏 ☆ 收藏** | GameHost:1115 | 440 宽 5 个按钮 ≈ 200vp，**根本放得下** | ❌ **无谓损失**（`?` 帮助已单独保留，见 2026-11-02 修） |
| 结果弹窗里三块统计的间距 `md→xs` | GameHost:3493 | 更好 | ✅ |

**⇒ 4 类「收紧」全部对 440 有利；唯一不该跟着变的是「隐藏 ☆」。**

## 4. 对 853×533 横屏的影响：**无**

`853 ≥ 460`、`533 ≥ 460` ⇒ `narrowScreen()` 仍 false，**一行分支都不会变**；
今天所有 853×533 的真机验收结论**不受影响**。960×540、1280×800 等横屏同理。

## 5. 「改/不改」结论

**改**（收益 > 成本），但按 §0 分两档：

```ts
// core/Bp.ets:243 —— 收紧类（间距/字号/文案）用 460
static narrowScreen(): boolean {
  return Bp.height < 460 || Bp.width < 460;
}

// pages/GameHost.ets:1115 —— 隐藏 ☆ 的那一处不要跟着 460，改用更严的条件
.visibility(Bp.width < 300 ? Visibility.None : Visibility.Visible)
//（或新增 Bp.hideFav()：Bp.width < 300 || Bp.height < 260）
```

**为什么值得改**：440×956 竖屏的垂直余量只有 **~35vp**（§上一条报告算过：chrome ≈240 + 盘 ≤596 + 底 85 ≈ 921 / 956）。
把顶栏间距、结算弹窗字号、演示条文案一起收紧，能**实打实多出 30–60vp**，比任何"改棋盘比例"都便宜，且**零风险**（只影响 chrome）。

**为什么别一刀切**：440 宽不是手表 —— 5 个按钮放得下，隐藏收藏纯属损失；
而且「隐藏控件」是不可逆体验损失，「收紧间距」只是视觉变化。

## 边界

- 只读；未改 .ets、未改 `Bp` 默认值；**没在 440 真机验过**（没有竖屏实例，见上一份报告 §1）。
- 「440 下 5 个按钮放得下」是按按钮 40vp × 5 = 200vp + 间距估算，**未真机测量**。
- `narrowScreen()` 在 `games/` 里 **0 处**，所以本评估**不涉及任何游戏的棋盘布局**。
