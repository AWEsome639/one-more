# 第 ② 项的产品设计：**统一语气，不是加个聊天框**

> `2026-11-16 06:55`。**「端侧 LLM」如果只做成「游戏里嵌个聊天框」，那是玩具。真正值钱的是下面这件事。**

## 一、⇒ 问题：`355` 款的文案是「一个人写的」，但读起来像「三百五十五个人写的」

**⇒ 现状（我从修 `9` 款时看到的真实差异）：**
- `Story Builder` 的开场是「主题：赶早八 / 把句子按时间顺序点出来」——**口语、亲切**
- `Base Conversion Run` 是「把进制换算对，答错扣 3 秒」——**说明书语气**
- `Skyscrapers` 底部就一个「`1`」——**几乎没有语气**
- `Triplets Logic` 是「从高到低排，谁在前？」——**命令式**

**⇒ 同一个 App，**四种人格**。这在「世界顶尖」的标准下是硬伤：玩家不会说「这个 App 有 355 款游戏」，他会说「这个 App 有点乱」。**

## 二、⇒ 端侧 LLM 的正确定位：**离线生成一套统一语气的文案，构建期一次性跑完**

**⇒ 不是运行时聊天，是**在构建机上生成一次、把结果固化进包**：**

```
[构建期 · 只在 Mac 上跑一次]
  ① 从 GameRegistry 导出 355 款的元信息
     （名字、玩法一句话、判定条件、失败代价、难度）
  ② 用固定 prompt 模板 + few-shot（挑 3 个最好的现存文案当范例）
  ③ 本地 Qwen2.5-0.5B 逐款生成：
     - 开场白（1 句，≤ 20 字）
     - 失败安慰（1 句，≤ 15 字）
     - 提示引导（1 句，≤ 25 字）
  ④ 人工过一遍（我过），把不合格的丢掉重跑
  ⑤ 产出 `entry/src/main/resources/rawfile/tone-pack.json`
[运行期 · 零 AI 依赖]
  游戏直接读 tone-pack.json 里的句子 ⇒ 首包不变大、耗电为零、离线可用
```

**⇒ 关键：**端侧模型的产物是「一份 JSON」，不是「一个运行时依赖」。**这样即使 `token/s` 只有 `3`，也完全不影响游戏。**

## 三、⇒ 为什么这比「接个聊天框」值钱

| 维度 | 聊天框 | 统一语气包 |
|---|---|---|
| 玩家感知 | 「哦，有 AI」 | 「这个 App 说话**像一个人**」 |
| 失败风险 | 运行时崩溃/卡顿/胡说 | **只是 JSON，不会崩** |
| 体积 | `+300 MB` 常驻 | **`~50 KB`** |
| 可复算 | 难（每次输出不同）| **易（JSON 就是证据，能 diff）** |
| 被抄走的难度 | 低（谁都能接 API）| **高（语气是一致性，不是单个句子）** |

## 四、⇒ 验收（不要「感觉好听」）

1. **一致性**：`355` 款的句子，**同一人格**（用固定 few-shot + 同一个 prompt 模板）
2. **长度**：每句 ≤ 现有该位置的行数容量（`≤ 20` 字，超了会被切 —— 这正是我昨夜修 `9` 款的原因）
3. **可 diff**：`tone-pack.json` 进 git，**每一句的变化都能 review**
4. **回退**：任何一款的文案不合格 ⇒ **保留旧文案**（JSON 里缺键就走默认值）

## 五、⇒ 与「世界顶尖」的关系

**⇒ 奥森的标准是「每一帧、每一处细节都值钱」。**
**⇒ `355` 款游戏里，**文案是唯一同时出现在每一款里的东西** —— 它的语气不一致，等于每一帧都差一点点。**

**⇒ 这一项做成了，是**玩家说不出为什么但就是觉得「顺」**的那种细节。**
