# ★ `Pattern Sequence Draw` 定案：**不需要改**

> `2026-11-14 14:1x`。这款我前后判过三次，现在用数字定案。

## 三次判断的历史

| 第几次 | 我说 | 依据 |
|---|---|---|
| ① | 「残留 `8vp`，倾向接受」 | 台账 `blk=24px` |
| ② | **「棋盘被三个统计卡挤到屏外，只露第二行」** | **看截图（错）** |
| ③ | **「不需要改」** | **算绝对位置（对）** |

## 数字定案

```
台账：blk = 2/24px
⇒ 最深块 y2 = 1540 + 24 = 1564px = 521.3vp
⇒ 屏高 1600px = 533.3vp
⇒ 距屏底 36px（12vp）⇒ **没有越过屏底**
```

**⇒ 而截图里看到的 `4` / `5` / `6` 是 `3×3` 网格的**第三行（最后一行）**——完整可见。**
**⇒ 我第 ② 次说「只露第二行」，是**又一次把完整棋盘读成被切**（与 `Skyscrapers` 同一个错）。**

## 结论

**不需要改。** 它的 `24px` 只是「最后一行压住手势线 `4px`」，与那 `19` 款同类。

**⇒ 若第二批 `240 → 140` 生效，它的盘面会从 `240vp` 缩到 `173vp`、底从上移 `67vp`
⇒ 压手势线的问题也一并消失。**

**⚠️ 但它**不在**那 `18` 处 `max(240, H−360)` 名单里**（清单里没有 `GPatternSequenceDraw`）。
**⇒ 所以第二批不会碰它。**

**⇒ 那它现在的限宽是什么？**

## 查它的限宽

**先前读到过：`GPatternSequenceDraw.ets` 的盘面是**
```ts
L331:  .width('100%').layoutWeight(1).padding({ bottom: Bp.isShort() ? 32 : 0 })
```
**⇒ 它走的是 `layoutWeight(1)`（弹性高度），**不是 `Math.max` 那套固定封顶**。**

**⇒ 所以它属于**另一种布局范式**（弹性 + `padding` 让位），
其行为由 `layoutWeight` 与 `padding` 决定，而不是限宽值。**

**⇒ 因此它本来就不该出现在「`240 → 140`」的名单里 —— 这也解释了为什么 `grep` 找不到它。**

## ⇒ 顺带确认它的状态

| 项 | 值 |
|---|---|
| `blk` | `24px`（`8vp`）|
| 最深块位置 | `1564px`（距屏底 `36px`）|
| 判定 | **贴手势条（`1584`）下方 `20px`** |
| 需要改吗 | **不需要** |
| 第二批会碰它吗 | **不会**（它不用 `Math.max(240, …)`）|

## ⇒ 判据（`2164`）

**同一款游戏被我判错两次（都是读图），而两次都是「把完整的内容读成被切的」。**
**⇒ 共同点：内容是**空的/无边框的网格**（`Skyscrapers` 的空棋盘、这里的空 3×3 格）。**

**⇒ 判据：凡「网格状且格子为空」的界面，看截图**不能**判断「被切还是在」。
必须用 `blk` 算绝对位置（`1540 + blk` 与 `1600` 比）。**

**⇒ 而这条我已经在 `2139` 写过一次了 —— 但当时没点明「空网格」这个具体特征。
⇒ 现在点明：**空网格是最容易误读的形态**，因为它没有内容来标出边界。**
