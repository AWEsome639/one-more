## 2.5 同族 bug 今天已经**真实发生过一次**（不是理论风险）

`entry/src/main/ets/components/GamesTab.ets:2840–2855`（**今天新加**，`verifier-eng2` 报、lead 批准）：
```ts
// ★ 2026-11-08 真机（853×533）：「找」按钮被挤成 **12vp 宽**贴在右边缘（x=841~853），点不到
//   ⇒ 输入框虽然有 layoutWeight(1)，但长 placeholder 按 min-content 撑住，按钮没有自己的宽度 ⇒ 被压到 12vp
.width(Cell.of(56))
.flexShrink(0)          // ← 全库唯一一处 flexShrink
```
**这和紫色 bug 是同一族**（`Row` 里固定尺寸元素没有 `flexShrink(0)` ⇒ 被压缩/拉伸），
只是表现形式一个是**背景铺满**、一个是**按钮被压到点不到**。
⇒ **判据 1829 应当扩写**：**`Row` 里任何"尺寸应当固定"的子元素，都要 `.flexShrink(0)`**（不只是 `SymbolGlyph`）。

## 3. 仍然存在的**同类风险面**（不是现存 bug，但是紫色 bug 的温床）

1. **`.flexShrink` 全库 0 处** ⇒ 默认 `flexShrink(1)`，`Row` 里**固定尺寸**的元素（圆点、图标、徽标）
   在空间不够时会被**压缩**（宽度变窄，背景随之变形）。今天那 22 个全圆元素里，**固定宽度的 5 个**就属于这一类。
2. **`Text(emoji)` 当图标用**：全库有大量 `Text('🎯')` 之类；一旦给它加 `backgroundColor` + 放在拥挤 `Row`，
   就会出现"背景比字形宽"的同款事故。**给图标加背景时，必须显式 `.width()/.height()` 或 `.flexShrink(0)`**。
3. **百分比宽度 + 圆角**：`width('78%')` 这类，父容器变窄时圆会缩小（本次 `GGomoku` 靠 `aspectRatio` 处理得当）。

## 4. 建议（若要把它变成闸门）

给 `tools/check_layout_overflow.py` 或 `code-linter` 加一条**第 5 类判据**：
```
若组件链同时满足：
  ① 有 .backgroundColor(
  ② 有 .borderRadius(Radius.full)   ← 全圆 = 期待是"点/胶囊"
  ③ 宽度可变：.width('xx%'|'100%') 或 .layoutWeight( 或父为 Row 且无宽度
  ④ 高度较小（< 20vp）或未设高度
⇒ 报「疑似背景拉伸」
```
本轮的 22 处里，用这条规则会**命中 7 处有意设计、0 处真 bug**（第 8 处 `GOrbitTap` 有固定宽高不会命中），
⇒ **规则本身需要再收紧**（例如要求"未设 aspectRatio 且未设 height"），否则误报率高。
