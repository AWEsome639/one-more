# 判据 1823（2026-11-08 立）

## 1823 · `position` 里的 `%` 是**设计选择**，不是语法限制

**来源**：`code-hunter` 复核 `GBreakout` 的 `position` 时，从文件头注释里挖出这个设计意图。

## 原文（`GBreakout:9-11`）

> 场地是正方形，**所有位置/尺寸都用百分比**，于是**物理与屏幕像素无关，任何机型手感一致**；
> **只有拖动挡板要把手指位移（vp）换成百分比，才需要 `onAreaChange` 量一下场地宽度**。

**⇒ `boardW` 的全部职责就是那一行拖拽换算（vp→%）** —— **不是给所有 `position` 用的**。

## 接上数值反而有害（三条）

1. **首帧全塌左上角**：`boardW` 初值 `0`，`onAreaChange` 是**布局完成之后**才触发
   ⇒ 第一帧 `x`/`y` 全是 `0`，球拍/球/40 块砖叠在 `(0,0)`，量到了才跳回来
2. **破坏「任何机型手感一致」**：百分比让物理与像素解耦，改 vp 就得重新校验球速/反弹角
3. **作者已经防过这个坑**：`:513` 那行 `if (!(this.boardW > 0)) return;`
   就是因为 `boardW` 可能为 `0` 才加的 —— 渲染路径若也用 `boardW`，得再写一套守卫，**比现在复杂且收益为零**

## 判据

**`position` 里的 `%` 是设计选择，不是语法限制**：
- **需要与设备尺寸解耦**（**物理/棋盘/粒子**）⇒ **优先 `%`**
- **只有必须从「用户输入（vp）」反推时** ⇒ **才引入 `onAreaChange` + 数值**

**⇒ 看到 `onAreaChange`，先问「它量的是给谁用的」，别假设它该给所有 `position` 用。**

## 全库核查（顺手做透）

**`x` 用 `%` 而 `y` 用数值的**：**全库只有 2 处，都在 `GFlappy`**
- `:580` `y: 0`（**管道贴上沿**）
- `:630` `x: 0`（**地面贴左沿**）

**⇒ 都是故意的「贴边」** ⇒ **全库没有真实的单位混用 bug**。

## 与判据 1821 的关系

**判据 1821（`position` 的 `%` 不生效）已于同日撤销。**
**1823 是它的「下半段」**：**1821 说「`%` 能用」，1823 说「`%` 该不该用」。**

## `code-hunter` 的自我认错（同样值钱）

**上一轮它写**：**「`GameHost:3801` 的 `y` 已是数值（`burstY()`），只有 `x: '50%'` 还是字符串 —— 同一行一半数值一半百分比，是明确遗漏」**

**这一轮它自己推翻了**：
```ts
private burstY(): string {        // ← 返回 string
  return y.toFixed(1) + '%';      // ← '56.0%'，带百分号
}
```
**`x` 和 `y` 都是百分比，完全一致，没有遗漏。**

**它的原话**：**「我错在只看函数名（`burstY` 看着像返 vp）和调用处，没点进函数体看 `return` —— 和 `playStyle` 那轮『看名字不看实现』是同一个坑。」**

**⇒ 判据 1824（新增）：判断一个函数的返回值类型，必须点进函数体看 `return`，不能只看函数名和调用处。**
