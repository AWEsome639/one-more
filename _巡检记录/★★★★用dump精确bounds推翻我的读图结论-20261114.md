# ★★★★ 用 dump 的精确 `bounds` 推翻我的读图结论

> `2026-11-14 14:0x`。**我今天第二次推翻「`Skyscrapers` 盘面被切断」这个判断。**

## 一、精确数据（与截图同一秒 `04:49:06`）

```

   ⇒ 最深**文字**节点 y2 = 1373px = 458vp

   ⇒ 某个叶子到达屏底（1600px = 533vp）
```

## 三、我之前错在哪

**上一轮我写**：

> 「「数楼」要求填满 `4×4`，而格子基本看不见。」

**⇒ 而 dump 的 `blk` 与 `lowest` 都表明：盘面确实铺满了 `382→529vp` 那一段。**

## 四、那 `Skyscrapers` 的真实问题是什么

```
盘面底 = 529vp = 1588px
手势线 = 1584px
⇒ 越界 4px
```

**⇒ **盘面底行压住手势条 `4px`** —— 这是「贴底」，属于**视觉瑕疵**，不是功能缺陷。**

**⇒ 而 `blk=48px` 的 `48` = `1588 − 1540`，说明它只是刚好越过 `block 基线 + 24` 那根线，
**不是「溢出很多」**。**

## 五、⇒ 这对普查结论意味着什么

**普查说 `21` 款 🔴 功能级，其中 `14` 款是「棋盘只露 `1`–`2` 行」。**
**而我亲自验的 `Skyscrapers` 这一例 —— **不成立**。**

**⇒ 三种可能：**
1. **普查整体偏严**（把「格子空、边框淡」这类也判成了「被切」）
2. **只有 `Skyscrapers` 这一例有误**，其它 `13` 款确实被切
3. **两者都有**

**⇒ **必须再验 `2`–`3` 个普查的 🔴 例**，才能判断普查的可信度。
**而验法不该是「看截图」（我已经在这上面错了两次），而是「用 `lowest` + `blk` + `max_bottom` 三个数算」：**

| 判断 | 算法 |
|---|---|
| **盘面是否完整在屏内** | `blk` 给出的 `y2`（`1540+blk`）≤ `1600` ⇒ 完整 |
| **还差多少** | `1600 − (1540 + blk)` ⇒ 正数表示还有余量 |
| **压住手势条多少** | `(1540 + blk) − 1584` |

**⇒ 对 `Skyscrapers`：`1540+48 = 1588` ⇒ 压手势条 `4px`，距屏底还有 `12px` ⇒ **完整**。**

## ⇒ 判据（`2136`）

**空白的、无边框的、单色的 UI 区域，**无法通过看截图可靠判断「它是被切了还是本来就这样」**。**
**⇒ 这是判据 `2119`（截图能揭示代码想不到的问题）的**反面限定**：
截图能看出「有没有异常」，但**看不出「异常的量」** ——
而「被切掉多少」正是「量」。

**⇒ 判据：想从截图判断「切掉了多少」，必须有一个已知尺寸的参照物（文字、图标、或另一张已知状态的图）。
没有参照物时，只能靠 dump 的 `bounds` 或另加测量。**

## ⇒ 判据（`2137`）

**我今天在「`Skyscrapers` 盘面」这件事上错了两次，而两次都是「看截图 → 得出量」：
第一次错说是「只露一行」，第二次错说是「完整」。**

**⇒ 判据：同一件事上，看图的结论若前后矛盾，说明这个信息来源对该问题**分辨力不足**。
⇒ 此时不要再看第三遍，换 `bounds` 这类**有数值的**来源。**

## 六、⇒ 而「`33` 处下限吃掉自适应」这个结论**不受影响**

**那个结论是从**代码算术**来的（`max(240, 533−360) = 240 ≠ 173`），不依赖截图：
- `max(240, …)` × `18` 处：下限确实压着
- 手机 `533−360 = 173 < 240` ⇒ 自适应确实失效

**⇒ 这条仍然成立，而且它才是真问题：盘面该 `173vp` 却做了 `240vp`。
`240` 让盘面比设计值大 `67vp` ⇒ **那 `67vp` 就是从其它元素那里抢来的** ⇒ 其余元素被挤。**

**⇒ 所以「`240 → 140` 让盘面变 `173`」这个改动仍然该做，理由从「盘面被切」改成
「**盘面占了 `240` 而设计只要 `173`，多占的 `67vp` 挤掉了别的东西**」。**
