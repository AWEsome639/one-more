# 间隙 `16 → 10` 的玩法影响（判据 1972 复验）

> 2026-11-13 00:5x ｜ **只读**：未改 `.ets`、未编译、未碰设备
> 对象：根容器 `Column({ space: Space.md(16) }) → Bp.isShort() ? Space.sm(10) : Space.md` 那一刀
> 覆盖款：**9 款**（= 当前仍溢出 且 根容器走 `Space.md`）+ **`Object Displacement`**（唯一保留的）

---

## 0 一句话结论

**9 款全部可以缩，0 款会因为「分组粘连」而受损；`Object Displacement` 也能缩，而且不影响「间隔感」这个玩法要素。**

理由一句话：**根 `space` 分隔的是「区块」（统计 / 棋盘 / 选项组 / 消息 / 按钮 / 规则），
而游戏内部真正的「分组间隙」是另外的常量**（`Grid.rowsGap/columnsGap`、选项容器的 `Space.sm`、格子 `Row` 的 `Space.xs`）——
**改根间距动不到它们**。

---

## 1 ⚠️ 先说测量：判据 1972 的「两个变差」数据点**不可比**

判据 1972 的依据是 `Object Displacement −90 / Base Shift +20 / Fraction Matcher +18`。
我把 `layout-canonical.tsv` 里的 **`lowest` 字段**拉出来对了一遍：

| 游戏 | 那次测量 | `max_bottom` | 当时「最低的那个节点」 |
|---|---|---:|---|
| Base Shift | 16:42 | 1569 | **`'121'`**（一个数字） |
| Base Shift | 00:39 | **1589** | **`'选出移位后的十进制值'`**（规则行） |
| Fraction Matcher | 15:04 | 1582 | **`'8/21'`**（统计卡） |
| Fraction Matcher | 00:40 | **1600** | **`'B'`**（选项字母） |

**⇒ 两次测的根本不是同一个节点。** `max_bottom` = 「所有可见节点的最低底边」，
一旦布局变好、**原来被顶出屏幕的规则行重新进入视野**，它就会成为新的「最低节点」，
读数**反而变大**。

**这正好解释了 `+20 / +18`**：间隙收紧后规则行**抬高进入了可见区**（原本在 1600 之外，压根没被量到）。
⇒ **那不是「内容更靠下」，而是「原本缺失的节点出现了」** —— 从玩法上看这是**改善**。

> 补充：Base Shift 在同一份代码下 16:17 / 16:29 / 16:31 三次测得 **1578 / 1578 / 1578**（完全一致）
> ⇒ 探针本身**很稳**，问题不在噪声，而在**「最低节点换人」**。

**⇒ 对判据 1972 的建议**：
- ✅ **保留**「先量一款再铺开」这条（它是对的，且成本低）
- ❌ **删掉**「省出来的空间被 `layoutWeight` 吸走 ⇒ 下方更靠下」这个**机制表述** —— 现有数据不支持
  （反例：`Object Displacement` 自己就有 **3 个 `layoutWeight(1)`**，照样 −90px 变好；
   因为那 3 个是**统计卡在 Row 里的横向**权重，只吃宽度、不吃竖直空间）
- 🔧 **要固定追踪同一个节点**再比（例如只量「底部按钮行的下沿」），否则读数会被节点增删污染

## 2 玩法视角：根 `space` 到底在分隔什么

以 `GNumericalEstimation` 为例（其余同构），根容器的直接子节点是：

```
DemoBar → HintBar → 统计三卡(Row) → 题面卡 → 选项组(Column, 内部 space=Space.sm)
        → 消息 Text → 重开 Button
```

- **根 `space` 只负责这 6~7 个「区块」之间的呼吸**
- **选项与选项之间**的间隙在 `Column({ space: Space.sm })` 里 —— **不受根间距影响**
- **格子与格子之间**在 `Grid(...).rowsGap(Space.sm).columnsGap(Space.sm)` 或 `Row({ space: Space.xs })` 里 —— **也不受影响**

⇒ **没有任何一款把「玩法分组」直接托付给根间距**（那会是糟糕的写法）。
⇒ 所以「缩根间距会不会让选项粘连 / 让棋盘格子看不清」——**答案是不会**，那两处是别的常量。

**真正取决于根间距的只有「视觉节奏」**：16vp → 10vp 会让整页更紧凑。对**信息密度高的文字/选项类**是加分；
对**只有 3~4 个区块的棋盘类**几乎无感。

| **Prime Hunter** | 统计 / 5×5 棋盘 / 按钮 | **更好** | 5×5 格 + 单个按钮，收紧没有副作用 |

## 4 专项：`Object Displacement` 能不能缩？——**能，而且不影响「间隔感」**

Lead 的担心很具体：它是**记忆物件位置**的游戏，**间隙会不会本身就是玩法要素**？

**看代码**（`GObjectDisplacement.ets`）：

```ts
Grid() { ForEach(CELLS, (i) => { GridItem() { Stack(){ … }.width('100%').aspectRatio(1) … } }) }
  .columnsTemplate('1fr 1fr 1fr')
  .rowsGap(Space.sm)        // ← 记忆格的行间隔 = 10vp，**独立常量**
  .columnsGap(Space.sm)     // ← 列间隔同上
  .width('100%')
  .height(Math.min(260, Bp.height * 0.35))   // ← 格阵高度**固定**，不吃弹性
```

- **记忆格的「间隔感」= `.rowsGap/columnsGap`**，与根容器 `space` **完全无关** ⇒ 缩根间距**一格都不会变**
- **格阵高度是 `min(260, 35% 屏高)`**，不是 `layoutWeight` ⇒ 省下的空间**不会被它吸走**，直接变成底部留白
  ⇒ 这正是它 −90px **真的变好**的机制原因

**玩法层面再确认一次**：这个游戏考的是「遮罩后哪个物件换了格」——
判据是**格子的相对位置**，不是「格子之间的留白宽度」；而格子本身 `aspectRatio(1)` 的边长由**格阵宽度**决定，
根间距不改格阵宽度 ⇒ **记忆难度不变**。

⇒ **可以缩，零玩法代价。**（唯一要守的是：格子别小于 44vp —— 3 列 + `Space.sm` 间距下仍然很大，安全）

## 5 建议

| # | 建议 | 依据 |
|---|---|---|
| 1 | **9 款都可以铺开「根间隙 16→10」** | §2：根间距不承载玩法分组；§3 逐款无风险 |
| 2 | **`Object Displacement` 保持现状**（已保留 ✓） | §4：−90px，且记忆格间隔不受影响 |
| 3 | **修正判据 1972 的机制表述** | §1：`+20/+18px` 是「最低节点换人」，不是「内容下移」 |
| 4 | **探针口径改一下**：固定追踪某个具体节点（如底部按钮行下沿） | 否则「布局变好」会被读成「变差」——这是**方向性错误**，比数值误差更危险 |

> 一句话给 Lead：**9 款该缩、0 款不能缩、`Object Displacement` 能缩（间隔感不受影响）；
> 但判据 1972 的「依据」要打折 —— 那两个 +20/+18 是**最低节点换人**，不是真的变差。**
