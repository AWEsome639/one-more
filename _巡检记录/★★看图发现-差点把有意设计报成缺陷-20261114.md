# ★★ 看图发现：差点把**有意设计**报成缺陷

> `2026-11-14 21:x`。用「当玩家看」的方式审 `Target Number` 的截图（台账判 `OK`）。

## 一、⇒ 看图结果：布局没问题

| 看什么 | 实测 |
|---|---|
| 提示行距屏底 | 约 `33px`（`1567` vs `1600`）⇒ **可见** ✅ |
| 四个选项 | 全部完整可见 ✅ |
| 题干/目标/三个数 | 全在屏内 ✅ |

**⇒ 所以台账判 `OK` 是对的。**

## 二、⚠️ 而我一度想报一个「跨游戏不一致」

**我说：`Base Conversion Run` 的选项有 `A 61`/`B 63` 字母，而 `Target Number` 没有 ⇒ 「选项标签不统一」。**

**⇒ 查了代码才知道**这是有意的**：**

```ts
// GTargetNumber.ets:216-217
// 屏幕上是 4 个算式 + 一个目标数 ⇒ 自己把每个式子算出来，等于目标的那个就是答案。
```

**⇒ 它的选项是**算式**（`3 × (2 + 8)`）⇒ **靠内容自己就能区分，不需要字母**。**
**⇒ 而 `Base Conversion Run` 是**裸数字**（`61`/`63`/`62`/`60`）⇒ 字母帮区分。**

**⇒ ⇒ 所以两者**都对**，差异是「内容是否自解释」决定的。**

## 三、⇒ 量化一下这个「差异」到底有多大

**全库 `355` 款里，`25` 款有字母常量（`LETTERS`）、`330` 款没有。**
**⇒ 但「有没有字母」取决于「选项是否自解释」，不是风格问题。**

## 四、⇒ 所以我撤回那个观察

**⛔ 我说「跨游戏不一致」是错的 —— 那只看了**两张图**就下结论，没查代码。**

**⇒ 而代价很低：一次 `grep` 就能查到注释。**

## ⇒ 判据（`2459`）

**「看起来不一致」只是一种**怀疑**，不是结论。**
**⇒ 报「不一致」之前，先查两边各自的**理由**（注释/文档/上下文）；有理由的差异是设计，不是缺陷。**

**⇒ 判据：报「不一致」的句式，必须带「我查过两边的理由了吗」这一问。**

## ⇒ 判据（`2460`）

**而这次之所以差点报错，是因为我在**看图的语境**里做**推断** —— 图只告诉我「长什么样」，不告诉我「为什么这样」。**
**⇒ 「为什么」只能从代码/注释里读。**

**⇒ 判据：图负责「发现问题」，代码负责「解释问题」；两者不能互相替代。**
