# `Stroop Test`：两次改动零效果 ⇒ 停手（判据 1970 又命中一次）

## 它的问题（`blk` 实测）

**全库 `blk` 数据里它最严重：`blk=3/72px`**（`3` 个块越界，共 `72px` = `24vp`）
`probe` 显示：选项按钮行 `Row h=129 y=[1471..1600]`，**底边正好到屏底**（游戏区只到 `1516`）

## 我试的两刀（都没效果）

| 改动 | 实测 |
|---|---|
| 选项 `Cell.of(62)` → 矮屏 `Cell.of(34)` | `1600`、`blk=3/72px`（**没变**）|
| 显示区 `.height(180)` → 矮屏 `.height(130)` | `1600`、`blk=3/72px`（**没变**）|

**⇒ 两刀都是「差 `160vp` 的改动」，结果一模一样 ⇒ 判据 1970 又命中：我改的不是撑高那个节点。**

## 为什么（代码读出来的）

```ts
Row({ space: Space.sm }) { this.opt(0) this.opt(1) }.width('100%')
Row({ space: Space.sm }) { this.opt(2) this.opt(3) }.width('100%')
```
**两行选项各 `2` 个按钮，每个按钮有 `.layoutWeight(1)`** ——
`layoutWeight` 会**吃掉显式 `height`**（判据 1895 说过「键高会被 `layoutWeight` 吃掉」）。

**⇒ 我改的 `Cell.of(62)` 被 `layoutWeight` 覆盖了；而 `blk` 的 `72px` 来自**两行按钮各越界 `24px`** +
一个 `24px` 的容器。**

**⇒ 真正的杠杆是「让两行选项各自变矮」** —— 要么去掉 `layoutWeight`（但那样按钮会塌），
要么**把 `opt` 包进一个有固定高度的 `Row`**，让 `layoutWeight` 在**那个固定高度内**分配。

## 明天怎么做（具体）

1. 给两行选项各加 `.height(Cell.of(40))`（在 `Row` 上，不是按钮上）
2. 按钮保留 `layoutWeight(1)` —— 它会在 `Row` 的固定高度里均分
3. 通过判据：`blk` 从 `3/72px` 降到 `0`

（前两次：`Kakuro` 的键盘、`Base Shift` 的选项）。

## 第三刀（`Row` 上加高度）**也零效果**，已回退

| # | 改动 | 结果 |
|---|---|---|
| ① | 选项 `Cell.of(62)` → 矮屏 `34` | `1600` / `blk=3/72px` |
| ② | 显示区 `height(180)` → 矮屏 `130` | `1600` / `blk=3/72px` |
| ③ | **两行选项 `Row` 加 `.height(Cell.of(40))`** | **`1600` / `blk=3/72px`** |

**⇒ 三刀（`Cell.of(62)` 的 `53vp` / 显示区 `30vp` / `Row` 的 `40vp`）全部零效果。
按钮在 `probe` 里始终是 `h=129 y=[1471..1600]`，**一个像素都没动**。**

## 这说明什么（判据 1987）

> **三刀零效果，且目标节点的 `bounds` 一个像素不变 ⇒ 我的改动**根本没作用到那个节点**。**
> **可能：① 改的是另一处同构代码 ② 这个节点的尺寸由**更高层**决定（例如根 `Column` 的剩余空间分配）③ 构建产物没带上这次改动**

**⇒ 遇到这种「怎么改都不动」的情况，别再换第三、第四种改法 ——
去确认「**这次改动到底进没进包里**」（例如在改动处加一行 `console.log` 看 `hilog`）。**

**这跟今晚 `Wordle` 那次一模一样**：前九刀全空，直到加了 `console.log` 才发现数据一直是对的。
