# ★ `19%` 失败率的两条根因：`NOT_HOME` 已修，`NO_CARD` 记档不动

> `2026-11-14 11:0x`。队友两份静态分析，我逐条验过。**结论与我原来的猜测全都不一样。**

## 一、`NOT_HOME`（`87` 次，`15.0%`）—— 已修

### 我原来的猜测：错
我以为「某些游戏的结算弹层没有可点关闭件，`Back` 永远被吃」。
**队友用结构性证据推翻了：**
- **`0` 款实现 `onBackPress`**（`GameHost.ets:502` 注释自己写「GameHost 没有 onBackPress」）
- **`0` 款有全屏结算遮罩**；`287/355` 款的结算态是 `Button(this.over ? '再来一局' : '重开')`，**有可点控件**

### 真因：同一文件里两条回首页路径，能力差 `3` 倍

| 路径 | 位置 | 做法 | 预算 |
|---|---|---|---|
| **A** | `shot_game.py:455-470` | `force-stop → start → sleep(25) → **再 start**（判据 1954）→ sleep(8)` | **`34s` + 双 start** ✅ |
| **C** | `shot_game.py:503-511` | `force-stop → start → 轮询 4×3s` | **`13s` + 单 start** ❌ |

**而 `NOT_HOME` 只有 `:514` 一个出口，只从路径 C 出来。**

**⇒ 判据 `1949`（冷启动 `30~60s`）与判据 `1954`（`force-stop` 后 `dumpLayout` 抓不到 App 窗口，需二次 `start`）
这两个修复，只应用在了路径 A，没应用在路径 C。**

### 已修（两步，逐行验证过）

1. **路径 C 对齐路径 A**：补 `sleep(25)` + 第二次 `aa start` + `sleep(8)`
2. **`NOT_HOME` 加诊断**：原来 `87` 条备注全是同一句 `could not reach home`，
   现在附上最后 `6` 个文本节点 ⇒ **一眼分出「dump 空（没渲染）」还是「卡在某个界面」**

**⚠️ 我第一版诊断写错了**：用了 `d2 if 'd2' in dir() else d`，但 `is_home()` 内部自己调 `dump('home')`、
**对象没传出来** ⇒ 那段会抛 `NameError` 被 `except` 吞掉、永远打印空。
已改成现 dump 一次（`dump('nothome')`）。`py_compile` 通过。

## 二、`NO_CARD`（`45` 次，`7.8%`）—— 记档，**今晚不动**

### 我给的假设：证伪
我猜「`tokens[:4]` 截断丢掉关键候选」。队友把 `24` 款逐款算了 token 表：
**只有 `Ab Reversal Oddball` 被截掉一个 `Ab`，而它在 `_base`/`name` 里都有 ⇒ 冗余。**
**⇒ A 假设贡献 `0` 行。**

### 但挖出一个更硬的结构性 bug

```python
# shot_game.py:602
hit = any(((want_zh and want_zh in (t or '')) or (name in (t or ''))) for t, _ in texts(d))
```

**⇒ 没有 y 过滤、没排除搜索框。而 `uinput` 刚打进去的词就是 dump 里的一个 text 节点
⇒ `hit=True` ⇒ 第一轮就 `break` ⇒ 多 token 策略在结构上是死的，也从没机会「等卡片渲染再来一轮」。**

### B 方向（占 `93%`）的四个具体环节

| # | 位置 | 问题 | 强度 |
|---|---|---|---|
| 1 | `L620` `if 560 < y1 < 1000` | 搜索框在 `y≈435`，首行结果标题很可能 `y1 ≤ 560` ⇒ **被滤掉** ⇒ `card=None`（屏幕上明明有卡）| 中（需 dump 确认 y）|
| 2 | `L620` `x2 > x1 + 100` | 窄标题（`蛇`/`Go`）直接跳过 | 中高 |
| 3 | `L597-599` 打字后 `sleep(2.4)` 只 dump 一次 | 这批失败耗时 `217`–`236s`（均值 `111s`）⇒ 设备慢，`2.4s` 可能没渲染完 | 中高 |
| 4 | `L344` `_find_text_node` 用 `==` 完全匹配 | 若标题被 dump 拆成 `时序`+`判断`，`L602` 子串也失败 | 中 |

### 为什么今晚不改

1. **`L602` 的修复（排除搜索框）会让每款多跑几轮重试** ⇒ 在 `6.6h` 窗口里可能吃不消
2. **`L620` 改 `560→480` 是没有 dump 支撑的猜测**
3. **今天已经动了 `shot_game.py` 两处**（路径 C、诊断），**首测前再动工作马，性价比是负的**

**⇒ 而且我刚加的诊断会让下一轮自动产出证据**：
`NOT_HOME` 现在会打印「最后 `6` 个文本」；`NO_CARD` 的失败耗时本身就暴露了「设备慢」这一层。

## 三、队友给的真机最小实验（明早一条命令就能定案）

在已连设备上：点搜索框 `(2276,264)` → 点输入区 `(1280,435)` → `uinput -K -t '时序判断'` → `sleep 3` → `dumpLayout` → 打印所有含 `时序/判断` 的节点与 bounds。

**判读表：**

| 看到什么 | 说明 | 改哪里 |
|---|---|---|
| 只有 `1` 个 `时序判断` 且 `y1 < 560` | **y 窗口是主因** | `L620` 的 `560` |
| 有 `时序判断`、`y1>560`、宽 `>100` | **时序**（`2.4s` 不够）| `L597` 改轮询 |
| 出现 `时序`/`判断` 两个节点 | **标题被拆** | `L602` 改匹配方式 |
| 只有输入框、没有结果卡 | 卡片没渲染 | 加等待 |
| 一条都没有 | `uinput` 没打进去 | 查输入路径 |

**⇒ 这个实验 `5` 分钟，比今晚盲改安全得多。**

## ⇒ 判据（`2068`）

**同一个文件里两条功能相近的路径，只要有一条先被修过，另一条就极可能还带着旧 bug。**
今天这个 `NOT_HOME` 就是：判据 `1949`/`1954` 的修复加在了路径 A，路径 C 原样不动。
**⇒ 修一个「回退/兜底」路径时，先搜同文件里有没有第二条同类路径 —— 有，就一起改。**
**⇒ 更一般的：`grep` 一下那个修复的关键词（这里是 `aa start`），看它在文件里出现几次。出现 `2` 次而只改了 `1` 次，就是漏了。**
