# 判据 3015：`check_ledger_freshness.py` 用 `mtime` 判「代码改过没有」—— `302/355` 款文件的时间是假的

## 一、怎么发现的

早报里一直写着「**`1` 款过期 —— `Odd Rotation`（量于 `11-17 17:14`，代码改于 `11-19 00:12`，滞后 `31h`）**」。
收尾前我决定核对这个数，用 `git log` 独立验一下：

```
$ git log -1 --format='%ad %s' --date=format:'%m-%d %H:%M' -- entry/src/main/ets/games/GOddRotation.ets
169db4f3 11-13 01:49 🚀 间隙收口全库铺开：**138 款**游戏矮屏根间距 16vp → 10vp
```

⇒ **最后提交是 `11-13 01:49`，不是 `11-19 00:12`。**

再看 `11-19 00:12` 那批提交是什么：

```
7ce011a1 11-19 00:22 判据 2961：系统提示的时钟与 shell date 差约 40 分钟…
29cc36be 11-19 00:20 第 ⑤ 项（电视）短板已用代码证实（判据 2960）…
22c3c116 11-19 00:19 第 ④ 项两条路已探明（判据 2959）…
```

⇒ **全是文档，没有一行游戏代码。**

## 二、根因：工具用的是文件 `mtime`

`check_ledger_freshness.py:96`（改前）：

```python
code_m = datetime.datetime.fromtimestamp(os.path.getmtime(p))
```

而 **`mtime` 会被 `git checkout` / `stash` / 批量脚本无内容变化地改掉**。

实测全库：

```
302 / 355 款 .ets 文件的 mtime 与 git 提交时间差 >10 分钟
```

| 文件 | `mtime` | git 最后提交 |
|---|---|---|
| `GOddRotation.ets` | `11-19 00:12` ← **假** | `11-13 01:49` ← **真** |
| `GWordle.ets` | `11-18 23:21` | `11-18 23:52` |
| `GCollatz.ets` | `11-15 17:13` | `11-15 17:13`（一致）|

⇒ **`Odd Rotation` 的「过期 `31h`」是假警报** —— 它的代码在 `11-13` 就定稿了，
   `11-17` 的测量是**在最终代码上做的**，完全有效。

## 三、修法

```python
_gt_cache = {}
def _git_time(path):
    """文件最后一次 git 提交时间；没有提交记录时退回 mtime（新文件/未跟踪）。"""
    ...
    out = subprocess.run(['git','log','-1','--format=%ct','--',path], ...)
    if out: return datetime.fromtimestamp(int(out))
    return datetime.fromtimestamp(os.path.getmtime(path))
```

带缓存（`355` 款约 `3s`），未跟踪文件退回 `mtime`。

## 四、★ 反向测试（不然这条修复没意义）

**改完变成 `0` —— 万一是把「真过期」也一起吞掉了呢？** 必须证伪。

### ① 先查有没有真过期被漏掉

逐款比「git 提交时间 vs 测量时间」：**`0` 款 git 提交晚于测量** ⇒ 与 `0 过期` 一致。

### ② 再注入一个假时间

`monkeypatch` 让 `Collatz` 的「提交时间」跳到 `2099-01-01`：

```
✅ 有效：358 款
⚠️ 过期：1 款
-- 过期清单 --
  Collatz   量于 11-19 04:00 ｜ 代码改于 01-01 00:00 ｜ 滞后 632180 h ｜ 末次 OK
```

⇒ **它正确报了。** 所以 `0` 是「真的没有过期」，不是「检查失效」。

## 五、判据

> **「代码有没有改过」是内容问题，只有版本控制能回答 —— 文件系统时间（`mtime`）不是内容证据。**

⇒ 三条：
1. **判「改没改」用 `git log -1 --format=%ct -- <file>`**；`mtime` 会被 `checkout`/`stash`/批量脚本无内容变化地改掉
2. **全库先量一次偏差**：这次是 `302/355`（`85%`）—— 这么高的比例说明它不是偶发
3. **改完必须做反向测试**：`1 → 0` 既可能是修对了，也可能是检查失效了；只有「注入假数据它仍报警」能区分
