# 判据 1970：**三档不同的封顶值给出同一个 `max_bottom` ⇒ 封顶没落到目标节点上**

## `Word Search` 的三次实验

| 封顶 | 理论板高 | 实测 `max_bottom` |
|---|---:|---:|
| `Bp.height - 200` | `333vp` | `1600` |
| `Bp.height - 290` | `243vp` | `1599` |
| `Bp.height - 360` | `173vp` | `1599` |

**⇒ 三个差 `160vp` 的封顶值，结果几乎一样 ⇒ 那个 `.width()` 根本没作用在撑高的节点上。**

## `probe` 给出的真相

```
h= 802 y=[ 798..1600] Column     ← 棋盘块 802px，直接到屏底
h=  38 y=[1562..1600] Text 'U'   ← 格子字母只剩 38px
```

**⇒ `802px` 与 `333vp(999px)` / `243vp(729px)` / `173vp(519px)` 都对不上**
**⇒ 撑高的是**内层**某个仍用 `width('100%')` 的节点。

## 判据 1970

> **同一款游戏，用几个差别很大的封顶值测出来 `max_bottom` 几乎不变 ⇒
> 停手，别试第四个值 —— 你的封顶没有作用于目标节点。**
>
> **⇒ 立刻 `probe`，看那个真正占高的节点的 `bounds`，然后按 1932 反查它的代码行。**

**⇒ 这是今晚第三次栽在「改错节点」上**（`Kakuro` 十次、`Base Shift` 一次、`Word Search` 三次），
**而每次「先 `probe` 再改」的那几款（`Kakurasu` / `Math Maze` / `Number Bonds` / `Tapa` / `Kurodoko` / `Pythagorean` / `Origin`）全部一次成。**

**⇒ 比分 `7 : 14`。判据 1932 是我今晚最该刻在脑子里的那一行。**
