# 按进程名统计模拟器：**不可靠，今天骗了我两次**

> `2026-11-16 10:35`。**今天两次「设备 0 / 残留 1」都是假的。**

## 一、⇒ 两次假结论

| 我的检查 | 输出 | 真相 |
|---|---|---|
| `pgrep -f qemu-system` | **`0`** | **折叠屏实例明明在跑** —— 它的进程形态不叫 `qemu-system` |
| `ps -eo command \| grep -c "[E]mulator -start"` | **`1`** | **没有残留** —— 那个 `1` 是我的 `bash -c` 命令行自己含了这个串 |

**⇒ 两次一正一反：一次漏报（以为没有、其实有 ⇒ 我又起了第二台 ⇒ 崩溃）、一次误报（以为有、其实没有）。**

## 二、⇒ 为什么按进程名不可靠

1. **同一个产品，不同 `deviceType` 的进程形态可能不同**（手机 vs 折叠屏）。
2. **任何 `grep`/`pgrep -f` 的匹配串都会出现在**执行它的那个 shell 的命令行里** ⇒ 自匹配。
3. **`nohup ... &` 再 `-start` 的链路上，真正的宿主进程可能换名。**

## 三、⇒ 改用工具自己的话

**⇒ 「有没有设备在跑」—— 问 `hdc list targets`（**连接状态**，不是进程表）。**
**⇒ 「停没停干净」—— 看 `Emulator -stop <name>` 的返回值（`Stop emulator <name> successfully`）。**
**⇒ 两者都改了：`test_nonshort.sh` 与 `dark_sample.sh` 的收尾现在打印 `hdc list targets`，不再数进程。**

## ⇒ 判据（`2818`）

**判断一个服务/设备的状态，优先问**它自己的接口**（`hdc list targets`、`-stop` 的返回值），而不是**数进程名**。**
**⇒ 数进程名有两个必踩的坑：不同实例进程名不同（漏报）、匹配串出现在自己的命令行里（误报）。**
**⇒ 今天这两次假结论，一次导致崩溃，一次让我差点去查「哪来的残留」。**
