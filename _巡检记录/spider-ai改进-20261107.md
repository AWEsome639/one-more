## 2. 改了什么 / 为什么

### 2.1 候选分抖动 — `SP_JITTER = 400`

- **位置**：`GSpiderSolitaire.ets` 常量区 + `spPick()` 里唯一的 `nSc.push(...)`。
- **代码**：候选分 = 状态评估 + 路径动作奖励 + `(Math.random() - 0.5) * SP_JITTER`。
  只影响「**同样好**的几步里挑哪一步」，不改评估函数本身。
- **为什么有用**：束搜索里大量候选的分数**几乎相等**（同一手的不同搬法），
  纯按分数取最大 ⇒ 每局都走同一条确定性路径，一旦钻进小循环就再也出不来。
  加一点噪声 = 在「差不多好」的走法之间换着试，能自然绕开死循环。
- **量级安全**：400 远小于「翻一张牌 +1000 / 收一组 +8000」，
  不会为了噪声牺牲真进度。
- **扫参**（同一批 200 局）：0 → 88.5%，150 → 93.0%，**400 → 93.0~93.5%**，
  800 → 92.0%，1600 → 85.5%（抖过头就乱走）。

### 2.2 死局兜底 — `spStep()` + 新 `spAnyMoveOf()`

- **现象（判据 1760 的冻结路径）**：`spPick` 只认「搬半段」的有效步，
  但游戏自己的 `hasMove()` 把「**整列搬到空列**」也算合法。
  只剩这种步时：`spPick` 返回 `<0` ⇒ 代打停手；
  而游戏既不结算也不结束 ⇒ 验证器只能 TIMEOUT。
- **兜底顺序**（`spPick < 0` 时）：
  ① 还能发牌 ⇒ 先 `deal()` 破局；
  ② 否则允许走一步「游戏认可的合法步」（`spAnyMoveOf`），**绝不先停**；
  ③ 真一步都没有才 `return false`（此时游戏会在 `afterMove()` 里判负、正常结算）。
- **离线数据**：200 局里 `stoppedEarly = 0`，即这条兜底从未被触发 —— 是纯保险，不影响正常对局。

## 3. 试过但没采用的（负结果，免得下次重踩）

| 方案 | 200 局胜率 | 结论 |
|---|---|---|
| 束搜索 3 层（现状基线） | 88.5% | — |
| 4 层 | 90.0% / 95.5%* / 91.0% | **纯噪声**：+1.5pp、+1.0pp、-1.0pp，且耗时 ~2x ⇒ 不采用（*这一行是“4 层+抖动”对“3 层+抖动”） |
| 5 层 | 84.0% | 明显更差 |
| 残局单独加深到 4 / 5 / 6 层 | 89.5% / 89.5% / 89.0% | 噪声内，成本更高 |
| 评估加「可翻牌数」（可翻牌列数） | 70.0% | 明显更差：AI 只顾翻牌 |
| 评估加「K 打头的链长」 | 78.5% | 更差 |
| 两者都加 | 74.0% | 更差 |
| 抖动 400 + `SP_STALL_LIMIT=45` | 92.0% | 不如抖动单独（93%） |
| 残局停滞时随机走一步 | 91.0% | 不如抖动（抖动更细、更连贯） |

> 观察：这些「加深/加特征」的方案在**输局重放**上能救回 13~14/23 局，
> 但同时在**原本赢的局**上丢分，总体打平或更差 —— 说明再加深同族评估**没有边际收益**。

## 4. 风险 / 待验证

- **非确定性**：同一副牌可能因为随机数不同而赢或输。这是「探索换总体胜率」的代价；
  三批各 200 局实测分布一致向上（+3~5pp）。
- **性能**：抖动只在每个候选多一次 `Math.random()`，不增加搜索量；
  死局兜底只在 `spPick < 0` 时进入。单拍耗时与改前同级（离线 0.6~0.8ms/步）。
- **未编译、未真机**：需统一编译 + 真机验证（本轮按纪律没编译）。
- **剩余 ~6% 失败局**：仍是「牌堆发完、反复倒牌也凑不齐 6 组」——
  游戏按规则不判负，这类局在真机上会一直倒到验证窗口结束。
  离线试过的 8 种加深/换评估方案都没能再提，判断是本策略族的上限。
