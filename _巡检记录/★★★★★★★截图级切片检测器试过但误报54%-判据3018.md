# 判据 3018：想在截图上做「底部被切」的批量检测 —— **第一次尝试失败，误报 `54%`**

## 一、为什么想做

`3017` 证明 `blk` 量不出「元素本该多高」：
`Simon Command` 的色块实际被切 **`71vp`**，`blk` 只报 **`8vp`**（差近 `9` 倍）。

⇒ 于是想造一把**截图级的尺子**：直接在 `797` 张截图上找「有一块颜色延伸到屏幕最底行」的签名。
   不用模拟器、能一次扫全库 —— 如果有第二款 `Simon Command`，这样就能找出来。

## 二、做了什么

`工具/detect_bottom_clip.py`：
1. 背景色 = 全图最常见颜色
2. 候选色 = 全图出现面积 ≥`5000px` 且与背景差 >`25` 的颜色
3. 看最后 `3` 行；若有 **连续 ≥`60px`** 的候选色像素段 ⇒ 判「有面板被下沿切了」
4. 量该颜色从底部往上连续多少行 = 「被切高度」

## 三、结果：**`190 / 355` 张（`54%`）被判「被切」**

```
占比     游戏                    被切高度
56.2%   Peripheral Focus        899px (300vp)
56.2%   Object Shuffle          899px (300vp)
54.7%   Double N Back           875px (292vp)
53.1%   Simon Says              850px (283vp)
52.8%   Mandelbrot              844px (281vp)
40.2%   Simon Command           643px (214vp)
27.0%   Wireframe 3D Rotation   432px (144vp)
```

⇒ **明显误报**，因为其中几款我已经独立验过是好的：

| 游戏 | 检测器判 | 实际 |
|---|---|---|
| `Mandelbrot` | `52.8%` | 精确严重度 **`2.8%`**，截图看过是好的 |
| `Wordle` | 也上榜 | `20.8%`，历史 `7` 次稳定 |
| `Magnets` | 也上榜 | `2.7%`，`6` 次历史一致 |

## 四、根因

它把「**满屏设计的背景面板延伸到下边**」当成了「卡片被切」。

两者在**颜色**上完全无法区分：
- 故意满屏的面板：从某行一直到 `y=1599`，没有底边圆角
- 被切掉的卡片：从某行一直到 `y=1599`，**底边圆角被切走了**

⇒ 区别只在**形状**（本来该不该有圆角/描边），不在颜色。
⇒ **要么加形状感知（检测底边有没有圆角/描边断口），要么人工看。**

## 五、处置：**不发布、进流程零次**

已在脚本头部写死警告：

```
⛔⛔⛔ 本脚本未校准，不要用它下结论（判据 3018）⛔⛔⛔
```

**理由：`54%` 的误报率比没有检测器更糟** ——
它会让人每天去核 `190` 张图，然后**连真的也不看了**（这正是 `3010` 说的报警疲劳）。

## 六、判据

> **一个检测器的价值 = 它抓到的真问题 ÷ 它报出的总数。误报率超过一半的检测器，等于把「有没有问题」这件事变成噪声。**

⇒ 三条：
1. **新写的检测器必须先拿「已知好的样本」验误报**：
   这次只要先跑 `Mandelbrot`/`Wordle`/`Magnets` 三款已知好的，立刻就会发现问题
2. **颜色类启发式区分不了「设计如此」与「被切」** —— 那需要形状/结构
3. **失败的检测器要留下并标明「试过、勿用」**，不要删 —— 否则下次有人会重写一遍

## 七、这次尝试的净收获

虽然检测器失败，但**顺带产出了三条可用结论**：

- `3016`：`5` 款缺 `blkh` 的用截图判掉了（`4` 好 `1` 坏）
- `3017`：`Simon Command` 横屏只有 `2/4` 色块可点（功能性损坏）
- **本条的副产品**：`aspectRatio` 影响面 **`515` 个文件 / `95` 处 `layoutWeight+aspectRatio`**
  ⇒ 但「哪几处在横屏真坏」这件事，**`blk` 判不了、颜色检测器也判不了**，
    只能逐款看截图 —— 这是今晚 `00:00` 窗口之后的活。
