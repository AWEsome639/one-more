# 静态审计：**`36` 款在横屏下「算式失效、下限生效」** —— 不是缺陷清单

## ⚠️ 先读这一句

**这份清单不是缺陷清单。**
「下限生效」只说明「按可用高度反推尺寸的公式在横屏没起作用」，**是否真的溢出要看实测**。

证据：名单里的 `G2048` / `GShikaku` / `GSudoku` **实测都是 `blk=0`**（布局是好的）。
⇒ 拿这份名单当「要修的 36 款」就是我今天犯了 `4` 次的那个错（`3063`/`3062`/`3067`/`3070`：**拿代理量当结论**）。

## 一、怎么算出来的

对所有 `entry/src/main/ets/games/G*.ets` 扫这个正则：
```
Math.max( <下限>, Bp.height - <N> )
```
分别代入横屏 `Bp.height = 533`、竖屏 `832`，比较「下限」与「算式结果」：
- 下限 > 算式 ⇒ **下限生效**（算式形同虚设）
- 下限 ≤ 算式 ⇒ 算式生效（正常）

## 三、这份清单的正确用法

**当一个游戏在横屏实测溢出（`blk > 0`）时，先查它在这份名单里吗：**
- **在** ⇒ 优先怀疑「下限顶住了、按高度反推没发生」⇒ 把下限降到算式之下（判据 `3054` 已证 `5` 次有效）
- **不在** ⇒ 说明算式生效了还溢出 ⇒ 是别的原因（兄弟不回流、`Stack` 里 margin、第二行没约束……）

⇒ 也就是说：**它是「排查优先级表」，不是「待办表」。**

有了这份表，明天实测出任何一款横屏溢出，**第一分钟就能定位到最可能的那一行**，而不是从 `355` 个文件里翻。

⇒ 这是「**把一次性的经验变成可复用的检索**」。
