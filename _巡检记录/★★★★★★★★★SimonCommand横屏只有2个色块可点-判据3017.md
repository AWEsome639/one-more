# 判据 3017：`Simon Command` 横屏下 **`4` 个色块只有 `2` 个可点** —— 布局把第二行推到屏外

## 一、截图量的（不是算的）

```
截图- Simon_Command-183835.jpeg  2560×1600

红块  y=956..1599   可见高 644px = 215vp   宽 1202px = 400vp
      底边 y=1599 ⇒ **正好压在屏幕底边**
```

`pad()` 的定义：`.layoutWeight(1).aspectRatio(1.4)` —— **高度由宽度推出来**：
`400vp ÷ 1.4 = 286vp` 应有高，**可见只有 `215vp` ⇒ 被切约 `71vp`**。

⇒ 而台账只报 `blk=3/72px`（`24px` = `8vp`）—— 又是 `3011` 那种**低估**，而且这次差近 `9` 倍。

## 二、更要紧的：只看到两种颜色

`PAD_COLORS` 有 4 色（红/蓝/绿/黄），版面是**两行 × 两个**：

```
Row { pad(0) pad(1) }     ← 红、蓝  ← 这一行被切掉底部 71vp
Row { pad(2) pad(3) }     ← 绿、黄  ← 整行在屏幕外
```

截图里**只有红和蓝** ⇒ **第二行完全不可见、点不到。**

⇒ 也就是说：**横屏下这款游戏有 `2/4` 的输入是够不着的。**
  这不是「底部压住手势条」，是**功能性损坏**。

## 三、算竖屏分支（判据 `3003`）

```
竖屏 360×780vp：每块宽 (360-20)/2 = 170vp ⇒ 高 170/1.4 = 121vp
两行 = 242vp + chrome ≈ 301vp ⇒ 合 543vp < 780vp  ✅ 装得下
```

⇒ **竖屏没问题。这是横屏专属。**

## 四、为什么比 `blk` 报的严重 9 倍

`blk` 只统计「`y2 > 1576` 的那部分」= `24px`。
但色块的真实问题是**它本该更高**（`286vp` 只给了 `215vp`）——
**而 `blk` 与 `blkh` 都不知道「本该多高」**（这正是 `3011` 的判据）。

⇒ 更根本的是：**`layoutWeight(1)` + `aspectRatio(1.4)` 这个组合在宽屏下会算出巨大的高度**
   （宽 `400vp` ⇒ 高 `286vp`），两行就 `572vp`，而横屏只有 `533vp` 总高。
   ⇒ **`aspectRatio` 是「按宽定高」，在宽屏上是放大器。**

## 五、如果以后要支持横屏，正解是什么（不是现在做）

不要用 `aspectRatio` 定高，改成**按高度预算反向算宽**，或者给 `pad()` 加高度上限：

```typescript
.height(Cell.of(90))            // 或
.constraintSize({ maxHeight: ... })
```

⇒ 但按 `3003` 的三道闸：**竖屏不触发 ⇒ 记录，不改。**
  而且 `2992`/`2994` 已定「横屏不是目标方向」。

## 六、判据

> **`aspectRatio` 是「按宽定高」—— 在横向空间充裕、纵向空间紧张的设备上，它会把内容撑出屏幕。**
> **凡是 `layoutWeight(1) + aspectRatio(N)` 的组合，都要在宽屏上验一次。**

⇒ 三条：
1. **`aspectRatio` + `layoutWeight` 的高度不受控** —— 它随宽度线性增长
2. **`blk` 量不出这类问题**（它只量「越过阈值的部分」，不知道元素本该多高）
3. **判「有没有坏」看截图里「该有的东西是不是都在」** —— 这次是「4 个色块只出现 2 个」

如果是共享写法，那横屏下可能不止这一款少内容。
