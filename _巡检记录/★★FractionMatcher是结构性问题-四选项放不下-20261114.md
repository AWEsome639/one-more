# ★★ `FractionMatcher` 是**结构性**问题，不是「缩一点就好」

> `2026-11-14 14:2x`。台账给出了精确位置，据此算清了缺口。

## 一、精确数据（`2026-11-14T05:50:28` 那行）

```
lowest='B'  bounds [108,1586][136,1600]
blk = 2/48px  ⇒ 最深块 1540+48 = 1588px
max_bottom = 1600
```

**⇒ 选项 `B` 的**标签**在 `y 1586–1600px`（`528.7`–`533.3vp`）——**贴在屏幕底边**。
⇒ 而 `C`/`D` 完全在 `1600` 以下（屏外）。**

## 二、四个选项需要多少

| 项 | 值 |
|---|---|
| 每槽 `Cell.of(48)` | `41vp = 123px` |
| `4` 槽 | `492px` |
| `3` 个 `Space.sm`（`8vp` = `24px`）| `72px` |
| **选项块总高** | **`564px` = `188vp`** |

**而可用空间：选项块从 A 的上沿开始，到屏底 `1600px`。
由 B 的位置（`1586–1600`）反推 B 行大约在 `1532–1654px`
⇒ A 行上沿约 `1532 − 123 − 24 = 1385px`
⇒ **可用 = `1600 − 1385 = 215px`**。**

## 三、⇒ 缺口

```
需要 564px，可用 215px
⇒ 必须缩到 38%
⇒ 每槽从 123px → 54px（约 18vp）
```

**⇒ 而 `18vp` 远低于 `touchMin 44`。**

**⇒ 也就是说：**四个选项 + 题目卡 + 统计 + 两个按钮，在 `533vp` 高的屏上**放不下**。**

## 四、这与 `Snake3D` 形成对比

| 款 | 我原以为 | 实际 |
|---|---|---|
| `GSnake3D` | 「需 `200vp` 放方向键，结构放不下」 | **它没有方向键（滑动手势）⇒ 只需缩 `12vp`** |
| **`FractionMatcher`** | 「缩到 `48→42` 就好」 | **真需要缩到每槽 `18vp` ⇒ 结构放不下** |

**⇒ 两款正好**反过来**：我担心的是前者（其实简单），忽略的是后者（其实严重）。**

## 五、⇒ `FractionMatcher` 的可行方向

**都得改结构，不是改数字：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A** | **选项 `2×2` 网格**（两行两列）| 高度减半到 `~282px`，**仍超 `215px`** ⇒ 还需再缩 |
| **B** | **题目卡缩小**（那个 `1/6 = ?` 的卡片很高）| 从截图看它占了约 `250px`，可压 |
| **C** | **去掉 `题号/答对/得分` 三统计中的一两个** | 省 `~185px` |
| **D** | **选项改为横向滑动的单行** | 只露一个，滑动看其余 |
| **E** | **矮屏隐藏「提示/AI 代打」两个大按钮** | 省 `~120px`（已有先例：很多款矮屏隐藏按钮）|

**⇒ 最可能的是 `B + E` 组合**：题目卡压一点 + 矮屏隐藏两个大按钮 ⇒ 省 `~250px`，够放四选项。

**⚠️ 但这仍需真机验（`B` 能压多少、`E` 是否影响可发现性）。**

## ⇒ 判据（`2165`）

**「需要缩到原尺寸的 38%」与「需要缩 10%」是两个完全不同的问题。**
**⇒ 判据：算「目标尺寸 / 当前尺寸」的比值。**
- `> 0.7` ⇒ 调参数可能够
- **`< 0.5` ⇒ 空间根本不够，必须改结构**

**⇒ 这次 `54/123 = 0.44` ⇒ 结构性。而 `GSnake3D` 的 `341/353 = 0.97` ⇒ 调参数即可。**
**⇒ 同一个「溢出」现象，比值把两者分开了。**

## ⇒ 判据（`2166`）

**我今天的注意力被「我之前担心过的」带偏了：**
- `GSnake3D` 我担心了一整天（实际简单）
- **`FractionMatcher` 我从没担心过（实际严重）**

**⇒ 判据：「担心程度」不能当作「严重程度」的代理。
⇒ 而唯一可靠的排序是**算出来的比值**（`目标 / 当前`）。
⇒ 所以每轮结束前，应该对所有已知溢出的款**都算一遍这个比值**，而不是按印象排。**
