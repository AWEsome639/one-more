# 中断的工具调用会带走后台跑批

> `2026-11-16 21:22`。**折叠屏跑批在 `198/323` 处死了，而 `trap` 表现正常（模拟器被优雅停掉）。**

## ⇒ 现象

- **21:21:17 日志最后一行 `[198/323] Reverse Stroop`**
- **21:22 检查：`pgrep sweep_nonshort.sh` = `0`、`hdc list targets` = `[Empty]`
- **我最后一次工具调用在 20:42 被 `Error: tool call aborted` 中断**

**⇒ 也就是说：我那条 `sleep 2400` 被中断时，**它所在的进程组（含 `nohup` 起的跑批）一起被收掉了**。**

## ⇒ 为什么会这样

**⇒ `nohup ... &` 只免疫「父 shell 退出时的 SIGHUP」，**不免疫进程组被整体 SIGKILL/SIGTERM**。**
**⇒ 工具被中断时，宿主通常会终止该次调用的整个进程树 ⇒ 后台任务跟着死。**
**⇒ 这与 AGENTS 里那条 `③ DSH 重启 ⇒ 后台进程全死` 是同一族：**后台任务的生命周期绑在「起它的那次调用」上，不是绑在机器上。**

## ⇒ 正确的做法（长期任务）

**⇒ 跑批这类要几小时的任务，应该走 `launchd`（或 `DSHRunner`），而不是 `nohup &`。**
**⇒ 已经这么做的：`ai.deepseek.onemore.nightrun`（手机跑批）—— 它就是 `launchd` 的，所以今晚不受影响。**
**⇒ 折叠屏跑批是临时的、用 `nohup` 起的 ⇒ 这次丢了 `1` 小时，但**进度在台账里、可续跑**，损失可控。**

## ⇒ 判据（`2834`）

**「后台」不等于「持久」。`nohup &` 只挡住 SIGHUP，挡不住进程组被收。**
**⇒ 判据：预计超过 `30` 分钟的任务 ⇒ 走 `launchd`；临时任务用 `nohup` ⇒ 必须**假设它随时会死**，并把进度落盘到可续跑的位置。**

---

# 【`21:26` 修正】改用 `launchd` 后果然活了

**⇒ `nohup` 版在 `21:24:38` 又被带走一次（睡了 `1.5` 分钟就没了）。**
**⇒ 换成 `launchd`：**

```bash
cat > ~/Library/LaunchAgents/ai.deepseek.onemore.nshortsweep.plist   # RunAtLoad=true, KeepAlive=false
launchctl load -w ~/Library/LaunchAgents/ai.deepseek.onemore.nshortsweep.plist
# 收工：launchctl unload ~/Library/LaunchAgents/ai.deepseek.onemore.nshortsweep.plist  ← SIGTERM ⇒ trap 优雅停模拟器
```

**⇒ 实测：`launchctl list` 显示 `pid=90184`、日志正常输出 `目标 137 款`。**

**⇒ 这就是判据 `2834` 的可操作版本：**超过 `30` 分钟的任务 ⇒ `launchd`；用 `nohup` 就必须假设它随时会死。**
