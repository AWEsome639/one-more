## 1. 新增判据 1810：`--active-pass`（ACTIVE 视为通过）

**为什么**：ACTIVE 这档**本来就是「AI 在工作、只是没有结算可等」**（实时/无尽/长局），
旧统计把它算成「未通过」⇒ 覆盖率被低估。verifier-dev 说的「缺 ACTIVE=通过的口径」就是这个。

**改了什么**

| 位置 | 改动 |
|---|---|
| 文件头文档 | 新增判据 1810 段：说明 ACTIVE 计入通过的条件与退出码变化 |
| 全局 | `ACTIVE_COUNTS_PASS = False`（默认关 ⇒ **344 WIN 基线不变**） |
| CLI | `--active-pass`（布尔开关，不吃值） |
| JSONL 记录 | 新增两个字段：**`active_ok`**（与开关无关，ACTIVE 恒 true）与 **`pass`**（受开关影响） |
| 汇总行 | 开关打开时追加 `｜ ACTIVE 计入通过 ⇒ 通过 N/M`（**明写**，防止看统计的人误以为 WIN 变多） |
| 退出码 | 开关打开时 `WIN+ACTIVE==total` ⇒ 0；**默认仍是有 ACTIVE 就返回 1** |

**「通过」的界定比 ACTIVE 更严**：只认**进度类**读数在动（步数/得分/接通/已描…），
**只涨失误计数的不算**（判据 1712 原有分类，本次未改）。

**实测（3 次运行，退出码与汇总行都对）**
```
WIN 1 · ACTIVE 0 · FAIL 1 · TIMEOUT 0 · ERROR 0 ｜ ACTIVE 计入通过 ⇒ 通过 1/2
WIN 0 · ACTIVE 0 · FAIL 0 · TIMEOUT 1 · ERROR 0 ｜ ACTIVE 计入通过 ⇒ 通过 0/1
```
JSONL 新字段样例（TIMEOUT 那条）：
```json
{"name":"井字棋","verdict":"TIMEOUT","detail":"…","active_ok":false,"pass":false,"ts":"2026-11-08T10:52:50"}
```

## 2. 两个 TIMEOUT 复核

### ② `井字棋`（`tic_tac_toe`）—— **TIMEOUT 复现** ✅

```
[1/1] 井字棋 => TIMEOUT（150.7s）
      读数={'得分': '8.2 秒', '步数': '9'} 步数历史=['9']
      页面(12): ‹|井字棋|三子连线|☆|?|普通|↻|提示|AI 代打|得分|40|步数
```
- **步数停在 9（棋盘下满）**、150 秒内**没有任何结算** ⇒ 与「满盘不结算」的判断吻合（真 bug，属游戏侧）。
- **附带抓到 readout 解析瑕疵**：`得分` 被抓成 **`8.2 秒`**（那是计时器）——`readout_sig()` 的「时钟排除」没覆盖「N 秒」这种写法 ⇒ 建议把 `\d+(\.\d+)?\s*秒` 也加进时钟/时间排除表（否则每款带计时器的游戏都可能把「得分」配错）。

### ③ `斐波那契合并`（`fibonacci_merge`）—— **本次 WIN，TIMEOUT 未复现**

```
[2/2] 斐波那契合并 => WIN（111.1s） 已返回列表（视作完成）
```
⇒ 「第 4 步后不动」**在这一版没重现**（结算出现了）。可能原因：修复已生效 / 触发条件偶发（取决于随机出的数列）。**建议**：把它加入「每轮必跑 5 款」的抽查名单，跑 3 轮再做结论。

## 3. ⚠️ 一个会污染统计的工程问题：**导航失败被算成「游戏 FAIL」**

本轮 5 次运行里 **4 次**卡在「进不去游戏」，全部被记成 `FAIL`：

| 运行 | 结果 | 真因 |
|---|---|---|
| 井字棋（第 1 次） | FAIL | `🔍 点不开搜索面板`（撞在别的游戏页上） |
| 井字棋（第 2 次） | **TIMEOUT** | ✅ 正常进游戏（有效数据） |
| 斐波那契合并 | WIN | ✅ 正常 |
| 乒乓 | FAIL | `搜索词输不进去` |
| 2048 | FAIL | `搜索词输不进去` |

⇒ **「进不去游戏」和「游戏打不通」在统计里无法区分**，这会让人误以为游戏有大面积缺陷。
**建议判据 1811**：导航/搜索失败单独记 `verdict='NAV'`（或 `ERROR`），
统计里单列、**不计入游戏失败**；批量扫时分母只算「真正进过游戏的」。
