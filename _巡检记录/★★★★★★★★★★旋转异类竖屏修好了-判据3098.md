
`288` 的来历（按实测 chrome 反推）：
```
上方 chrome ≈ 201.6vp（从截图量）

⇒ 网格可用 = 798.7 − 201.6 − 86 ≈ 511vp

⇒ 网格宽 = 3×163.7 + 20 = 511  ⇒  Bp.height − 287.6  ⇒  取 288
```

## 五、判据

> **同一个 bug 修到第四遍时，说明该写「检查器」而不是继续手修。**
> 手修的代价是每款都要「量 chrome → 算常数 → 构建 → 装包 → 看截图」，约 `15` 分钟；
> 而一个静态检查器可以在 1 秒内把剩下的 200+ 款筛一遍。

⇒ 三条：
1. **同类 bug ≥3 次就写检查器**（判据 `3094` 已提出，这里再次印证）
2. **检查器的判据要能从源码里读出来**：`aspectRatio(1)` ≥2 + 外层 `width('100%')` + 没有 `Bp.height` 限宽
3. **每一款的常数都不一样**（`424`/`288`/`536`），因为 chrome 不同 ⇒ 检查器只能「**筛**」，不能「**算**」
