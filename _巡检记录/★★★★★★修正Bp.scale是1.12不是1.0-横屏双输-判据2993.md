# 修正：`Bp.scale()` = **`1.12`**（不是 `1.0`）—— 横屏是**双输**

> `2026-11-19 01:58`。自查发现我好几处算术用错了 `Cell.of()` 的值。

## 一、⇒ 实际值

```ts
Bp.SM = 600, Bp.MD = 840
Bp.width = 853 (→ ≥ 840) ⇒ isLg() = true ⇒ Bp.scale() = 1.12
Cell.of(base) = round(base × 0.85 × 1.12)
```

| 表达式 | 我一直用的 | **实际** |
|---|---|---|
| `Cell.of(30)` | `26vp` | **`29vp`** |
| `Cell.of(46)` | `39vp` | **`44vp`** |
| `Cell.of(14)` | `12vp` | **`13vp`** |
| `FreeCell` `13` 张 | `362vp` | **`401vp`**（横屏）|

## 二、⇒ 但**竖屏会掉回 `1.0`**

**⇒ `Bp.width` 在竖屏是 `533`，而 `533 < SM(600)` ⇒ 既非 `md` 也非 `lg` ⇒ `Bp.scale() = 1.0`。**

| | 横屏 `853×533` | **竖屏 `533×853`** |
|---|---|---|
| 屏高 | `533` | **`853`（`+60%`）** |
| `Bp.scale()` | `1.12` | **`1.0`（元素 `−11%`）** |
| `Cell.of(30)` | `29vp` | **`26vp`** |
| `FreeCell` `13` 张 | `401vp` | **`362vp`** |

**⇒ ⇒ **竖屏是双赢：空间多 `60%`、元素还小 `11%`。横屏是双输。**
**⇒ ⇒ 这进一步解释了为什么 `4` 条 `blk` 全在横屏报 —— 横屏既要塞进更矮的屏、元素又大 `12%`。**

## 三、⇒ 我的修法是否受影响

| 修法 | 是否仍成立 |
|---|---|
| `FreeCell` `cardH()` | ✅ **成立**。它用 `Cell.of(30)`/`Cell.of(14)` 作上下界、`Bp.height` 作可用高 ⇒ **三个量都随环境自动变**。实测横屏 `13` 张 ⇒ `cardH=14vp` ⇒ 列高 `206 ≤ 224` ✅ |
| `Kakuro` `maxWidth` | ✅ **成立**。纯 `Bp.height`/`Bp.width` 的 vp 运算，不含 `Cell.of` |
| 那些「`26vp`」的引用 | ⚠️ **数值要读成 `29vp`（横屏）**，文档里我已标出错处 |

## ⇒ 判据 `2993`

**⇒ 报任何由 `Cell.of()` 算出来的数之前，先确认 `Bp.scale()` 在**当前环境**是多少 —— 它是 `1.0/1.06/1.12/1.45` 四档，按**窗口宽度**选，不按设备类型。**
**⇒ ⇒ 今晚我用了 `26vp`（`scale=1.0`）去算横屏（`scale=1.12`），差了 `12%`。**因为 `FreeCell` 的修法是自适应的，这个错没造成坏代码；但如果我按 `362vp` 去定 `maxHeight`，就会差 `39vp`。**
**⇒ 更值钱的一点：`Bp.scale()` 在竖屏会从 `1.12` 掉回 `1.0` ⇒ **方向一变，两个变量同时变好**。这是我今天第 `5` 次确认「方向」是主要矛盾。**
