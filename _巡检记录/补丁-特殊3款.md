## 1. `GBoxCompletion.ets` —— 卡在「4 行 × 53vp 的棋盘」+ 底部 44vp 按钮行

### 1.1 最底那块是什么
`build():348-400`：`Column({ space: Space.sm })` 依次是
`DemoBar(0)` → `HintBar(38)` → 状态 `Text`（`:361`，sm≈20）→ **棋盘 `ForEach(rowIdx())`（每格 `Cell.of(62)`=53vp，`.layoutWeight(1)` 只管宽）** → `Text(this.note)`（`:376`，≈20）→ **按钮行 `Row`（`:378`）**：`清空点亮` + `重开`，两个都是 `layoutWeight(1).height(Bp.isShort() ? Cell.of(34) : Cell.tap(38))`

### 1.2 为什么压不下去
- 棋盘**高度是固定值**（`Cell.of(62)` = 53vp/行 × `diffTotal`=4 行 = 212 + 3 间隙），**不受容器 `maxHeight` 约束** —— `constraintSize` 只压容器，不压固定尺寸子项（`Design.ets:104-106` 已写明这个坑）
- 底部按钮用 `Cell.tap(38)` ⇒ **被 44 抬回**，`isShort()` 又是 false ⇒ **拿不到 34→29 的矮屏档**
- 棋盘外层没有 `layoutWeight`，是**内容高驱动** ⇒ 上方/下方任何固定项都在往下顶

### 1.3 竖向预算账（343vp 可用）

### 1.4 精确补丁（原串 → 新串）

## 2. `GMentalMapping.ets` —— 卡在「地图 `maxHeight:'70%'`=240vp」+ 3 行 44vp 方向键

### 2.1 最底那块是什么
`build():351-...`：`DemoBar(0)` → `HintBar(38)` → 统计行 `Row`（3 列，lg+xxs≈34）→ 提示 `Text`（`:396`，sm≈20）→ **地图 `Column`（`:419`）`.aspectRatio(1)` + `.constraintSize({ maxHeight: '70%' })`（`:427`）** → **方向键盘 `Column`（`:432`）**：3 个 `Row`（`:434/:490/:546`）× 每行 2 个键，每个键 `.height(Bp.isShort() ? Cell.of(34) : Cell.tap(38))`

### 2.2 为什么压不下去
- **地图是 `aspectRatio(1)` + `maxHeight:'70%'`**：`70%` 是**容器百分比**（343×0.7 = **240vp**）。它**随容器等比缩、却不给别人让路** ⇒ 无论上面/下面怎么缩，地图**始终吃掉 240**（40% 的可用高）。
- 方向键是 `Cell.tap(38)` ⇒ **44**；`isShort()` false ⇒ 拿不到 29 的档。3 行 × 44 = **132 + 间隙**
- ⇒ **这是三款里最超的（≈157vp）**，且**缩小上方任何东西都没用**（地图是百分比上限，不是 `layoutWeight`，不会让位）

## 3. `GBubbleShooter.ets` —— 卡在「`cellPx()` 用 `Bp.height*0.30` 拍的」+ 底部未生效的重开门控

### 3.1 盘面到底怎么算的（lead 特别问的）
**不是固定行高表，也不是 `layoutWeight`**，而是**按 `Bp.height` 百分比反推格子边长**：
```ts
// GBubbleShooter.ets:438-443
private cellPx(): number {
  const gap: number = 2 * (ROWS - 1);                       // 9 行 ⇒ 16vp 间隙
  const avail: number = Math.max(120, Bp.height * 0.30);    // 533 ⇒ 159.9vp
  return Math.max(10, (avail - gap) / ROWS);                // ⇒ 15.99 ≈ 16vp/格
}
```
- `ROWS = COLS = 9`（`:24-25`）
- 盘面宽容器 `build():531-533`：`Math.min(Bp.width - 2*Space.lg, Math.max(140, Bp.height - 360))` ⇒ 533 时 `max(140,173)=173` ⇒ 宽 173
- ⇒ **盘面高 = 9 × 16 + 8 × 2 = 160vp**（正方形，1:1）
- **关键**：`0.30` 是**拍出来的比例**，它**不知道可用高只有 343**（343×0.30 ≈ 103 其实更接近真预算，但这里乘的是 `Bp.height`=533 ⇒ 160）

### 3.2 最底那块是什么
`build():445-602`：`HintBar(38)` → 统计行 `Row`（`:457`，≈34）→ **盘面**（`ForEach(rows)` × 盘宽 173，高 160）→ `Text(this.msg)`（`:560`，sm≈20）→ `Button(重开)`（`:576`，`Cell.of(46)`=39，**`visibility` 依赖 `isShort()` ⇒ 今天照常显示**）→ 底部提示 `Text(TG2('同色连 3 颗起炸…'))`（`:591`，xxs≈14）

### 3.3 竖向预算账（343vp）
| 项 | vp |
|---|---|
| HintBar | 38 |
| 统计行 | ~34 |
| **盘面 9×16 + 8×2** | **160** |
| `msg`(sm) | ~20 |
| **`重开` `Cell.of(46)`=39** | **39** |
| 底部提示(xxs) | ~14 |
| `Column` space ×5 (@8) | ~40 |
| **合计** | **≈345** ⇒ **超 ≈2~7vp（临界）** —— 与「接近达标」的观察一致 |

### 3.4 精确补丁（原串 → 新串）
**① `cellPx()` 短屏取 0.26（盘高 160 → 140，省 20vp，最稳）**
```diff
-    const avail: number = Math.max(120, Bp.height * 0.30);   // 横屏 533 ⇒ 160vp
+    // ★ 短屏（533）可用高只有 343，0.30 会占掉 160 ⇒ 取 0.26（⇒ 140vp，省 20）
+    const avail: number = Math.max(120, Bp.height * (Bp.height < 600 ? 0.26 : 0.30));
```
> 533 时：`avail = 138.6` ⇒ 每格 13.6 ⇒ 盘高 **138.6 ≈ 139**（省 21vp）⇒ 合计 ≈324vp ✓
> ⚠️ 每格 13.6vp 偏小（手指可点性差），但这一款本来就靠「列宽点射」，且页头有 ↻；**若嫌小，用 ② 代替**。

**② `重开` 门控换条件（省 39vp，但少一个入口）**
```diff
-      .visibility(Bp.isShort() ? Visibility.None : Visibility.Visible)
+      .visibility(Bp.height < 600 ? Visibility.None : Visibility.Visible)
```
> ①和②**二选一即可**（都能进预算）；**推荐 ①**（保留按钮，只缩盘面），因为 13.6vp 的球在 9 列里仍是这一款的核心可玩面。

## 4. 一句话结论

- **`GBoxCompletion`**：卡在「4 行 × 53vp 固定高棋盘 + 44vp 按钮行」⇒ 补 ①②③ **省 51vp > 超的 43** ⇒ **能修**（关键在把 `Cell.of(62)` 缩成 `Cell.of(52)`）。
- **`GMentalMapping`**：卡在「地图 `maxHeight:'70%'` 独占 240vp + 3 行 44vp 方向键」⇒ 若只缩上方/下方**永远修不好**；必须把地图上限降到 **120** 并把键换成 `Cell.of(34)` ⇒ **能修**（省 165 > 超的 157，但**余量只有 8vp，是这三款里最紧的**）。
- **`GBubbleShooter`**：盘面是 **`Bp.height × 0.30` 反推的格子边长**（9×16=160vp），只超 **2~7vp** ⇒ 把系数换成 **0.26** 就够 ⇒ **最容易修**。
- **⚠️ 三款共同前提**：`Bp.isShort()` 现在硬编码 `false`（未提交改动，434 处依赖）⇒ 所有「矮屏门控」今天都不生效。**先回退它可能一次救回多款**，比逐款打补丁更划算。
