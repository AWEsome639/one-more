## 1. 方法与可复现

```bash
# ① 全库分布（Cell.of / Cell.tap 的尺寸用法）
grep -oE "Cell\.(of|tap)\([0-9]+\)" -r entry/src/main/ets --include=*.ets | sort | uniq -c | sort -k2

# ② 今天动过哪些值（old → new）
git log --since="2026-11-10 00:00" -p --unified=0 -- entry/src/main/ets/games \
  | grep -E "^[-+].*Cell\.of"
```

**判定「可点」的规则**（脚本 `/tmp/touch-audit/scan2.py`）：

1. 只认**尺寸上下文**的 `Cell.of/tap`（`.width(` / `.height(` / `.size(` / `width:` / `height:`）——
   同一个函数也用来算字号/圆角，那些**不算触控尺寸**；
2. 判断这行是否落在**该组件自己的修饰链**上（向上只遇到 `.xxx(...)` 修饰行 ⇒ 自己的；
   跨过 `}` 或子块 ⇒ 只是祖先可点，**另算 C 类**）；
3. 链上有 `.onClick(` / `.focusable(Tv.on())` / `.onKeyEvent(` / `.gesture(` ⇒ 可点；
   或者组件类型本身就是 `Button` / `Toggle` / `Checkbox` / `Radio` ⇒ 可点。

**判据 1824**：判断"会不会违规"要读实现 —— `Cell.of` **无下限**（`Design.ets:100`），
`Cell.tap` **有下限**（`max(of, Layout.touchMin=44)`，`Design.ets:150`）。

## 2. 前提：`Cell.tap(N)` 永远不会违规（判据 1899）

```ts
static tap(base) { const v = Cell.of(base); return v < Layout.touchMin ? Layout.touchMin : v; }
```

⇒ `tap(32)` = **44**、`tap(38)` = **44**、`tap(44)` = 44（横屏 42 → 也抬到 44）。
⇒ **全库 169 处 `Cell.tap` 一律不算违规**，今天 `tap(38)` 那 33 处、`tap(32)` 那 2 处**不是问题**。
⇒ 全部违规只可能来自 **`Cell.of`**（685 处尺寸用法）。

## 4. 换算成真实 vp：同一行代码在五档设备上差多少

`Cell.of(N) = round(N × Cell.k × Bp.scale() × shrink)`，其中 `shrink = 0.85`（`Bp.height < 600`）、
`Cell.k` 由界面模式给（normal 1 / simple 0.9 / elder 1.33）、`Bp.scale()` 按设备（手机 1 / 平板 1.06~1.12 / 电视 1.45 / 手表 0.92）。

| base | 手机竖屏 normal | 手机 simple | 手机 elder | 横屏平板 853×533 | 电视 |
|---:|---:|---:|---:|---:|---:|
| 30 | **30** | **27** | **40** | **29** | 44 |
| 32 | **32** | **29** | **43** | **30** | 46 |
| 34 | **34** | **31** | 45 | **32** | 49 |
| 36 | **36** | **32** | 48 | **34** | 52 |
| 38 | **38** | **34** | 51 | **36** | 55 |
| 40 | **40** | **36** | 53 | **38** | 58 |
| 42 | **42** | **38** | 56 | **40** | 61 |
| 44 | 44 | **40** | 59 | **42** | 64 |

**读法**：

- `32` 在**五档里有四档**都 <44（只有电视 46 达标）⇒ 手机竖屏 32、simple 29、横屏平板 30、**连 elder 也才 43**
- `40` / `42` 在手机上刚好差 2~4vp，在横屏平板上更小（38 / 40）
- `44` 在横屏平板上被压成 42 ⇒ 这就是 `Cell.tap` 存在的理由

## 7. 建议（三条路，各有代价）

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A 全回退** | 把今天降的 138 处全部改回原值 | **必然重新溢出**——今天这批正是为了塞进 853×533 才降的 | ❌ 不可行 |
| **B 按设备分档（推荐）** | `.height(Bp.isShort() ? Cell.of(32) : Cell.tap(32))` | 竖屏手机拿回 44vp；横屏才用 32。**要复测竖屏是否溢出** | ✅ 竖屏用户（绝大多数）受益 |
| **C 保持现状** | 不改，记录为"已知触控不足" | 32vp 在手机上点边缘容易落空；读屏/无障碍不受影响（有 `accessibilityText`） | 若要保溢出指标 |

**为什么不推荐 `.responseRegion()` 扩热区**：`Design.ets:135` 已明确写 ——
网格相邻格子会重叠 ⇒ **点 A 触发 B**，比差点按更糟。

**B 方案的一处细节**：`Bp.isShort()` 是 `height < 690`（`Bp.ets:299`），
手机竖屏 744 ≥ 690 ⇒ 走 `Cell.tap` 拿 44；横屏 533 < 690 ⇒ 保持 `Cell.of(32)`。
正好是"有空间就用满、没空间才将就"。

**残余不确定**：

- 4 处 `dims=-`（`.size(...)` 或对象字面量）可能被重复/漏计；
- `ForEach` 那 3 处的"元素"是内联 `Text`，组件名不准但可点判定成立；
- 扫描器按行匹配，若同一行有多个 `Cell.of`（如 `width(32).height(32)`）会记 2 次 —— 本报告已注明。

## 9. 未验证

- **没有真机实测手指命中率**（本轮只读、不碰设备）：32vp 是否"真的点不到"取决于手指和握姿，
  业界通行判据是 44~48vp，本项目自己把 `Layout.touchMin` 定在 44。
- 没验证 B 方案改造后竖屏是否溢出（那要真机或模拟器量布局）。
- 没核对**手表档**（`Bp.scale=0.92`）：32 → 29vp，比手机更小，但手表本来靠"格少、圆屏大"，未展开。
