## 3. ③ Hanoi —— 失败的根因（bug2）

操作：开汉诺塔 → 点「升到 4 盘」→「升到 5 盘」→ prefs 确认 `hanoi: level=5` → 杀进程 → 重进 → 打开汉诺塔。
**期望**：盘数 5（按钮显示「回到 3 盘」）。
**实测**：按钮仍显示「**升到 4 盘**」（= 3 盘），且 prefs 里 `hanoi` 变成 **3**（at=02:44:37）。

根因（我上轮引入）：`GHanoi.aboutToAppear()` 里顺序是
```ts
this.reset(this.level);              // ← reset() 内部 saveLastWhere(n) ⇒ 把记录写成随机 3！
const lastLv = ProgressStore.lastLevel('hanoi');   // ← 这时读到的是 3
```
⇒ **写记录的动作发生在读记录之前**，上次的 5 盘被本轮随机值覆盖，恢复永久失效。
`GSokoban` 同样有（`load()` 里存档，`aboutToAppear` 先 `load(0)` 再读）。

## 4. 真机发现的 3 个问题（2 个已修，1 个是既有布局 bug）

### bug1（已修）`init()` 没把 `lastWhere` 装回 AppStorage — 数据丢失
- 现象 A：重启后 `lastWhere()` 永远 `undefined` ⇒ **退出恢复完全不生效**（③ 的第二个原因）
- 现象 B（更严重）：`saveLastWhere()` 从空 map 开始整体写回 ⇒ **一次存档把其他游戏的记录全冲掉**（实测 4 条 → 1 条）
- 修法：`ProgressStore.init()` 里补
  ```ts
  const lastWhereRaw: string = p.getSync(Keys.lastWhere, '{}') as string;
  AppStorage.setOrCreate(Keys.lastWhere, lastWhereRaw);
  ```
  并在注释里立判据：**凡是“读 AppStorage 再整体写回 JSON”的 key，必须在 init 里装回来**。

### bug2（已修）读/写顺序 —— 见 §3
- 修法：`GHanoi` / `GSokoban` 的 `aboutToAppear` 里**先读记录、再 reset/load**
- 回归测试：`node --experimental-strip-types /tmp/ps_test3.ts` ⇒ **8 通过 / 0 失败**
  （含“旧顺序复现 bug=3、新顺序=5”、“重启后新增不冲掉旧记录”、“闸门只放行一次”）

### bug3（既有布局，未修，建议单独立项）853×533 上多处底部控件被裁

## 5. ④「通关后重进 → 从头」不成立（设计缺口）

| 游戏 | 存档点 | 通关时会不会清记录 |
|---|---|---|
| `GSokoban` / `GHanoi` / `GBlockStackingPhysics` | `load()` / `reset(n)` 每次进关都写 | **从不清** ⇒ 打完最后一关重进仍停在该关 |
| `GShellGame` | 只在“过关且未通关”分支写 | **不清** ⇒ 通关后重进仍是最后一关 |
| `GArithmeticChain` / `GStaircaseMemory` / `GPythagoreanTripleBuilder` | `save(level < diffTotal ? level+1 : 0)` | **会清** ✓ |

⇒ ④ 只对后 3 款成立。若要对全部 10 款成立，需在“最后一关完成”处补一句 `saveLastWhere(id, 0, ...)`
（`GSokoban` 的「全部关卡通关」分支、`GShellGame` 的 `wins >= diffTotal` 分支等，各一行）。
