## 2 致命：选了这个档位，就永远赢不了

### 2.1 `GKlotski` —— 困难档上限 96 步，内置最短解 116 步 ★最严重

- **文件:行号**
  - `entry/src/main/ets/games/GKlotski.ets:25` `const MAX_MOVES: number = 160;`
  - `entry/src/main/ets/games/GKlotski.ets:40` `const KLO_STEPS: number = 116;`（注释原文：「最短解 116 步（单格推法）」，`KLO_MOVES[]` 直接把 116 步离线算好存成常量）
  - `entry/src/main/ets/games/GKlotski.ets:97` `@State private diffTotal: number = GameDiff.livesNow(MAX_MOVES);`
  - `entry/src/main/ets/games/GKlotski.ets:511` `if (this.moves >= this.diffTotal) { ... finish(false) }`
  - `entry/src/main/ets/core/GameDiff.ets:196` `v = Math.max(1, Math.floor(base * 0.6));`
- **问题**：`livesNow` 把「步数预算」当成「生命数」打折。困难档 = `floor(160×0.6) = 96`，而这一款的最优解就是 116 步 —— **困难档在数学上不可能通关**，不是“难”，是“不可能”。
- **实测数据**

  | 档 | 预算 `diffTotal` | 最短解 | 比值 | 结论 |
  |---|---|---|---|---|
  | 简单 | `ceil(160×1.5)` = 240 | 116 | 2.07 | 宽裕 |
  | 普通 | 160 | 116 | **1.38** | 只剩 44 步容错（人做不到 116 步零失误） |
  | 困难 | **96** | 116 | **0.83** | **0% 可通关** |

  > 这与昨晚刚修的 `GCompassMaze` 是同一个 bug 家族（`DMAX=20` 写死 vs 棋盘放大），但这款更硬：**最优解是常量，可直接相减**。
- **修法**（二选一，建议 A）
  - A：预算改成「最短解 × 档位倍率」——`private dmax(): number { return Math.ceil(KLO_STEPS * GameDiff.pick(1.6, 1.35, 1.15)); }`（→ 186 / 157 / 134，困难仍有 18 步容错）
  - B：保底 `Math.max(KLO_STEPS + 20, GameDiff.livesNow(MAX_MOVES))`（→ 136）
  - ⚠️ 别只把 `160` 调大：`livesNow` 会对任何 base 再砍 40%，调 base 只是把曲线整体平移。

### 2.2 `GMathGuess` —— 困难档 4 次猜 1–100，信息量不够

- **文件:行号**
  - `entry/src/main/ets/games/GMathGuess.ets:18-19` `const LO = 1; const HI = 100;`
  - `entry/src/main/ets/games/GMathGuess.ets:44` / `:63` `GameDiff.livesNow(7)`
  - `entry/src/main/ets/games/GMathGuess.ets:168` `this.guess = this.secret;`（顺带：AI 直接抄答案，见 §6.1）
- **问题**：本款是纯二分猜数（大了/小了），**1–100 的理论下限是 `ceil(log2 100) = 7` 次**。
- **实测数据**

  | 档 | 次数 | 二分能从 100 个数里区分出几种 | 结论 |
  |---|---|---|---|
  | 简单 | `ceil(7×1.5)` = 11 | 2¹¹ = 2048 | 宽裕 |
  | 普通 | 7 | 128 ≥ 100 | **刚好等于理论下限** —— 必须全程最优二分、一次都不能错 |
  | 困难 | `floor(7×0.6)` = 4 | **16** | **只能靠运气**（随机命中 4%） |

- **修法**：这款应该按「范围」分档而不是按「次数」——`pick(50, 100, 200)` 改 `HI`，次数固定 7；或者保底 `Math.max(7, GameDiff.livesNow(7))`。同类「猜测型」（`GWordle`/`GMastermind`）都要按这个口径审一遍。

### 2.4 `GCircuitConnect` —— 胜利格写死 15，棋盘 3×3 / 4×4 / 5×5

- **文件:行号**
  - `entry/src/main/ets/games/GCircuitConnect.ets:19` `const N = 4; const LAST = N * N - 1; const TURNS = 26;` ← `LAST = 15`
  - `entry/src/main/ets/games/GCircuitConnect.ets:48` `@State private diffTotal: number = GameDiff.sizeNow(4);`（→ 3 / 4 / 5）
  - `entry/src/main/ets/games/GCircuitConnect.ets:333` `const solved: boolean = lit[LAST] && has(this.maskAt(LAST), 1);`
  - `entry/src/main/ets/games/GCircuitConnect.ets:95` `const lit: boolean[] = new Array<boolean>(this.diffTotal * this.diffTotal).fill(false);`
- **问题**：`lit` 数组按实际棋盘开（9 / 16 / 25 项），胜利判定却永远读 `lit[15]`。
- **实测数据**

  | 档 | 棋盘 | `lit` 长度 | 读 `lit[15]` | 结果 |
  |---|---|---|---|---|

## 3 高：出生即死局 / 一次失误就结束

### 3.1 `GClassicMaze` —— 步数上限 `4n`，比迷宫最短解还短

- **文件:行号**
  - `entry/src/main/ets/games/GClassicMaze.ets:73` `GameDiff.sizeNow(9)`（→ 6 / 9 / 12）
  - `entry/src/main/ets/games/GClassicMaze.ets:103` `private dmax(): number { return this.diffTotal * 4; }`
  - `entry/src/main/ets/games/GClassicMaze.ets:312` 步数用尽 → `finish(false)`
- **问题**：DFS 完美迷宫（生成器 `:28-52` 递归回溯）里，左上→右下的树距离大约是 `n²` 量级，不是 `4n`。
- **实测数据**（复刻 `genWalls` 递归回溯 + BFS 最短解，每档 4000 局，种子固定）

  | 档 | n | 预算 `4n` | 最短解中位 | 均值 | P90 | 最大 | **超预算（开局死局）** | 比值 |
  |---|---|---|---|---|---|---|---|---|
  | 简单 | 6 | 24 | 18 | 18.7 | 26 | 34 | **16.1%** | 1.33 |
  | 普通 | 9 | 36 | **38** | 38.3 | 54 | 72 | **51.0%** | **0.95** |
  | 困难 | 12 | 48 | **62** | 62.7 | 90 | 118 | **71.5%** | **0.77** |

  > 比昨晚那款更需要修：`GCompassMaze` 困难档是“77% 死局”，这款**普通档就已经 51%**，玩家一进就撞上。
- **修法**：预算改成「按最短解算」——生成后跑一次 BFS（n ≤ 12，1225 格，成本可忽略），`dmax = Math.max(2.2 * shortest, 3 * n)`；或纯启发式 `dmax = n * n * 0.9`（12×12 → 130，实测 P90=90、最大 118，全部可解且有容错）。

### 3.2 `GMazeNav3d` —— 迷宫生成**不保证连通**，简单档 36.8% 出生死局

- **文件:行号**
  - `entry/src/main/ets/games/GMazeNav3d.ets:20` `GameDiff.pick(2, 3, 4)`（层数）
  - `entry/src/main/ets/games/GMazeNav3d.ets:81-117` `reset()`：每层挖一条 **22 步随机游走**，然后只把终点周围 3 格（`(W-1,H-1)`、`(W-2,H-1)`、`(W-1,H-2)`）**强行打通**，层间通道也只在游走终点开口
  - `entry/src/main/ets/games/GMazeNav3d.ets:142` `bfsStep()` 走不到终点就返回 `[]`
  - `entry/src/main/ets/games/GMazeNav3d.ets:290` `if (mv.length < 3) { return false; }` ← **代打第一拍就自我关闭**
- **问题**：`reset()` 的注释写着「保证连通」，但实际只保证终点**那 3 格自己连在一起**；它们和 (0,0) 的主干之间可能被墙完全隔开。层间通道也一样：在 z+1 层打开的那格不一定被 z+1 层的游走覆盖。
- **实测数据**（复刻 `reset()`，每档 4000 局，BFS 判 (0,0,0) → (4,4,L-1) 可达）

  | 档 | 层数 | **不可达（出生死局）** | 平均可达格数 |
  |---|---|---|---|
  | 简单 | 2 | **36.8%** | 24.6 / 50 |
  | 普通 | 3 | **22.9%** | 36.8 / 75 |
  | 困难 | 4 | **12.8%** | 49.3 / 100 |

  > **难度越高反而越不会死**（层数越多越容易连通）—— 曲线方向是反的；简单档给新手的死局率最高。
- **与昨晚 FAIL 的因果链**：`验收截图-v1.0.1/ai_win_verified.jsonl` 里 3D迷宫的最后一条是
  「代打启动后 1.5s 内自己就停了（autoStep 第一拍返回 false：多半是它算不出可动的一步），读数 步数=1/3」。
  `1/3` 正是 3 层 = 普通档 ⇒ 22.9% 的死局命中。**这不是“AI 太弱”，是迷宫本就无解**。
- **修法**：`reset()` 末尾加一次连通性校验（≤ 125 格，BFS 成本 < 1ms），不可达就重生成（最多 50 次）；更省事的做法是每层改用 DFS 生成 + 层间通道强制打通「同一 (x,y) 在两层都开」。

## 4 中：难度含义错位（不致命，但玩家一眼看出不对）

### 4.1 输一局比赢一局分还高 —— 5 款

- **共性公式**：`赢 = 基础分 + (上限 − 步数) × k`（步数越多分越少），`输 = 步数 × k2`（步数越多分越多）⇒ 撞满上限而输，分数反超“赢了但走得慢”。
- **文件:行号 + 代入实测**

  | 款 | 文件:行号 | 公式 | 困难档「赢」 | 困难档「输满」 | 结论 |
  |---|---|---|---|---|---|
  | `GClassicMaze` | `GClassicMaze.ets:322` | `solved ? 70+max(0,dmax-steps*3) : steps*3` | **70**（`48-62×3<0` 被夹） | **144**（48 步 ×3） | 输是赢的 **2.06 倍** |
  | `GCompassMaze` | `GCompassMaze.ets:414` | `solved ? 70+max(0,(dmax-steps)*2) : steps*4` | 128（dmax=45、16 步） | **180**（45×4） | 输是赢的 **1.4 倍** |
  | `GColorMazeNav` | `GColorMazeNav.ets:277` | `solved ? 70+max(0,(DMAX-steps)*3) : steps*3` | 148（最快）／**70**（26 步） | 78（26×3） | 慢赢 **输给**单纯输 |
  | `GChainReaction` | `GChainReaction.ets:511` | `solved ? 60+160*(limit-steps)/limit : steps*5` | 60（走满 limit） | `limit×5` = **50 / 130 / 250**（limit 按档 10/26/50，`:254` `limitOf()`） | 普通 130、困难 **250** 都 > 赢局下限 60 ⇒ **严重** |
  | ~~`GWordLadder`~~ | `GWordLadder.ets:325` | `solved ? (limit-steps+1)*100 : steps*10` | 100（走满） | `limit×10` ≤ **90**（`:72` `pick(9,6,4)`，最大 9） | **误报：90 < 100，不是 bug** —— 原判断用了 `Ladder.limit`（5~7），实际 `:72` 已覆盖成 9/6/4 |

### 4.2 难度越高分越少

- **`GRotatingMaze`**：`GRotatingMaze.ets:277` `80 + (DMAX - steps) * 2`，而 `DMAX` 写死 `64`（`:23`），棋盘随难度 `sizeNow(7)` → 5/7/9，最短解 8/12/16（4000 局 BFS，中位/P90/最大三者相等 = 曼哈顿距离 2(n-1)）。

- **`GClircuitConnect`**：`GCircuitConnect.ets:342` `60 + max(0,(TURNS-moves)*4)`，`TURNS=26` 写死而棋盘变大 ⇒ 困难档需要更多步数才能接通 ⇒ 同样的“赢”分更低（叠加 §2.4 的判负 bug）。

### 6.1 极端值的全量排查结果

Lead 问的两种极端，**一种没有、一种有变体**：

| 检查项 | 结果 | 明细 |
|---|---|---|
| 「赢 1 分 / 输扣 100 分」 | **不存在** | 355 款里赢局分支最小的是 `GTangram:352` `40 + ...`、`GGraphCoordinatePlot:262` `40 + ...`，没有 `solved ? 1` 这种 |
| 分数可为**负** | **8 款**（无 `Math.max` 兜底） | `GD2Attention:292` `hits*HIT - wrongTap*MISS`、`GMentalMapping:309` `right*60 - wrong*20`、`GOddOneOut:262` / `GOddRotation:287` `right*100+200-wrong*30`、`GTaskSwitching:262` `right*100-wrong*40`、`GTrailMaking:259` `step*40-mistakes*60`、`GVennNumbers:270` `placed*100-wrong*40`、`GVigilanceTask:271` `hit*120-fa*60-miss*30` |

- **负分的影响面（别夸大）**：`ProgressStore.recordPlay`（`:1367-1375`）只在 `score > prevBest` 时写最高分，负分永远进不去；`perfectCount` 门槛是 `score >= baseXp*10 = 120`（`ProgressStore.ets` 内）。所以负分**只影响结算页显示**。
- **修法**：8 款统一套 `Math.max(0, ...)`（`GGoNoGo:289` 已经是这个写法，照抄）。

### 6.2 一个附带发现：**输一局也能破纪录**

- `entry/src/main/ets/core/ProgressStore.ets:1372` `ProgressStore.lastWasBest = score > prevBest;`
- `recordPlay()` 对**每一局**都调用（`:343`，在 `if (!solved) return 0` **之前**），而很多款的输局也给分（`this.steps*3`、`this.bound()*12`…）。
  ⇒ **输局拿 60 分、上一把赢局只拿 40 分 ⇒ 结算页弹「🏆 新纪录」**，玩家会当场觉得系统坏了。
- **修法**：`ProgressStore.lastWasBest = solved && score > prevBest;`

### 6.3 顺带确认：分数**不影响** XP

- `ProgressStore.finishGame()`：`gained = Math.round(baseXp × difficultyFactor × streakBonus) + dailyBonus` —— **完全没有 score 项**。
  ⇒ 所以「难度越高分越少」不会让玩家少拿经验；它伤的是**最高分/新纪录/完美成就**这三块展示面。
  ⇒ 但也意味着：**现在“分数”这条曲线对玩家成长零影响**，把它做成“难度越高分越少”只是白让玩家膈应。
