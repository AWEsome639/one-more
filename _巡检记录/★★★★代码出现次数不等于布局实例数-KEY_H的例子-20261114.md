# ★★★★ 「代码出现次数」≠「布局实例数」——`KEY_H` 的例子

> `2026-11-14 21:x`。我一度把 `KEY_H` 的代码出现次数（`2` 次）当成布局实例数（`4` 个），差点改了计划。

## 一、⇒ 事实

```ts
// GWordle.ets:28
const KEY_H: number = 40;

// L518（换一题按钮）
.height(KEY_H)

// L594（在 ForEach 里，对每个键生效）
ForEach(KEY_CHARS, (row) => { … Text(ch).height(KEY_H) … })
```

**⇒ 代码里出现 `2` 次（`L518`、`L594`）。**
**⇒ 但 `L594` 在 `ForEach` 里 ⇒ **对每个键都生效**；而 `3` 行键盘各是一行 ⇒ `3 × KEY_H`。**
**⇒ 加上按钮 `1 × KEY_H` ⇒ **布局上共 `4` 个实例**。**

## 二、⇒ 所以两种「次数」

| 口径 | 数 |
|---|---|
| **代码出现次数** | `2` |
| **布局实例数** | **`4`**（`3` 行键盘 + `1` 按钮）|
| **改 `1vp` 的竖向影响** | **`4vp`**（按实例算）|

**⇒ ⇒ 我先前按「`4` 处」算省的量 ⇒ **对**；但用「代码出现 `2` 次」去否定它 ⇒ **错**。**

## 三、⇒ 而这为什么容易搞错

**`grep -c 'KEY_H'` 给 `3`（含定义行）⇒ 看着像「`2` 处用」。**
**⇒ 而真正的「几处」取决于**这些代码在几个实例上生效**（`ForEach` 会放大）。**

**⇒ ⇒ 判据（`2410`）：算「改一处常数影响多大」时，要数**布局实例**，不是数代码出现次数。
⇒ 尤其是 `ForEach`/`if` 里的用法，一处代码可能是 N 个实例。**

## 四、⇒ 而这对 `Wordle` 方案的意义

**`KEY_H 40 → 32` 省 `4 × 8 = 32vp = 96px`，需 `31vp` ⇒ **本来够**。**
**⇒ 但我后来改用 `Scroll`（判据 `2405`：有先例优先、且 `32vp` 低于触控下限）⇒ **仍然是对的**，只是理由不是「省不够」。**

**⇒ ⇒ 所以结论没变，但「为什么」变了：**
| 说法 | 对不对 |
|---|---|
| 「`KEY_H → 32` 省不够（我一度以为只省 `16vp`）」| ❌ 错（实际省 `32vp`）|
| 「`KEY_H → 32` 会让键小于触控下限、且有 `Scroll` 先例」| ✅ **对（这才是改用 `Scroll` 的理由）** |

## ⇒ 判据（`2411`）

**我这次是「刚纠正完又纠回来」——因为两次都只看了 `grep` 的输出、没看那个 `ForEach`。**
**⇒ 若第一次就点开 `L594` 看它在什么结构里，就不会有这两次来回。**

**⇒ 判据：`grep` 给出「在哪些行」，但**要不要打开看**取决于「那行在什么结构里」。
⇒ 而这一点只能打开看。**
