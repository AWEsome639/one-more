## 二、⇒ 改点（两处，都有先例）

### 改点 `A`：按钮行矮屏不渲染（第五批范式）

**现状**：`L535` 的 `Row({space: sm})` 里有三个 `Button`（提示/联机/重开）。

**改成**：用 `if (!Bp.isShort()) { … }` 包住整个 `Row`。

**先例（`5` 处，照抄）**：
```
GCompoundConnect.ets:698    if (!Bp.isShort()) { … }
GCryptoArithmetic.ets:518   if (!Bp.isShort()) { … }
GNumberBonds.ets:423        if (!Bp.isShort()) { … }
GNumberBondsAll.ets:413     if (!Bp.isShort()) { … }
GPeripheralFocus.ets:338    if (!Bp.isShort()) { … }
```

**省**：整行不渲染 ⇒ 按钮高度 + `Column` 的 `space`（`sm`）≈ **`39–47vp`**。

**⚠️ 但「提示」是功能按钮** ⇒ 矮屏下玩家失去提示能力。
**处理**：可接受（提示是辅助，不是必需）；或另把「提示」挪进头部圆钮（`L532` 之上）。
**⇒ 建议先只做「隐藏」，因为它是可逆的、且与其他款一致（很多款矮屏都藏按钮行）。**

### 改点 `B`：三张统计卡压成一行紧凑

**现状**（`L604-631`）：三个 `Column({space: 2})`，各带 `padding(Space.sm)` + `shadow(Shadow.card)`。

**改成**：`label` 与 `value` 同一 `Row`（`Text('步数')` + `Text(moves)` 并排），去掉上下 `padding`（保留左右）、去掉 `shadow`。
**⇒ 每张 `46vp → 26vp` ⇒ 省 `20vp`。**

**⚠️ 三张卡 + 容器 `Row` 的 `space` 都要跟着改（四处同步）。**

## ⇒ 判据（`2215`）

**「隐藏一个功能按钮」是可接受损失，但要区分「辅助按钮」与「必需按钮」。**
- `提示`（辅助）⇒ 可藏

**⇒ 判据：矮屏空间不够时，先藏「不用也能玩」的；「不用玩不了」的绝不能藏。
⇒ 而判断标准是：**藏了它，玩家还能不能完成一局**。**

## 五、估算校准（`13:5x`）

**我先前估「藏按钮行省 `39–47vp`」是凭「一个按钮约 `40vp`」。用全项目数据校准：**

| `Button` 高度写法 | 处数 | 折算 |
|---|---:|---:|
| `.height(Cell.of(46))` | `199` | **`39vp`** |
| `.height(Cell.tap(44))` | `134` | **`44vp`** |
| `.height(Cell.of(56))` | `46` | `48vp` |
| `.height(Cell.of(48))` | `45` | `41vp` |

**⇒ 主流是 `39`–`44vp` ⇒ 我估的 `39–47vp` 成立，且加上 `Column` 的 `space(sm = 8vp)`
⇒ 实际可省 **`47–52vp`**。**

**⇒ 所以余量从「`8–16vp`」变成「`16–29vp`」⇒ 更稳，可能不需要改点 `C`（题目区收字号）。**

**⚠️ 而 `GMagnets.ets:536` 的 `Button('提示')` **没有显式 `height`** ⇒ 走 `Button` 默认高度。
⇒ 但同一行的另外两个按钮、以及项目主流都约 `40vp` ⇒ 该行总高 `~40vp` 是合理估计。**

## ⇒ 判据（`2221`）

**估算一个元素的高度时，若它**没有显式 `height`**，就用**全项目同类元素的统计**来估。**
**⇒ 这次 `grep '.height(Cell.of(...))'` 一次就得到「`39`/`44`/`48`」三档主流值，
比凭印象估「约 40」可靠得多。**

**⇒ 判据：没有显式值的量，用「同类元素在全库的分布」估 —— 而那个分布往往一条 `grep | sort | uniq -c` 就能拿到。**
