# 三条环境锁 · 2026-11-08（只读调研）

> 目标里剩的三条「需要真机/环境」的锁：**fps 上限 / 电视 3 米观感 / 局域网真机对打**。
> 本轮只读探针，**没有改任何系统设置**（`wm size` 只去试了只读命令，发现模拟器根本没有 `wm`）。
> 每条给：**能不能解、怎么解、代价**。

---

## 0. 一页结论

| 锁 | 能不能解 | 怎么解（一句话） | 代价 |
|---|---|---|---|
| ① fps 上限 | **部分解（不能直读 GPU）** | GPU 频率/负载读不到（无 root）；用**开屏帧直方图 + 轻/重载对照 + 宿主机 CPU** 间接证明「47.7 是模拟器出帧上限，不是 app 上限」 | ~15 分钟，只读 |
| ② 电视观感 | **部分解（分辨率可模拟、视距不可）** | 模拟器没有 `wm`，但**改实例 config.ini** 的 `hw.lcd.*` 可模拟 1920×1080@320dpi；3 米视距/遥控器/overscan 只能真机 | ~20 分钟 + 真机 10 分钟 |
| ③ 局域网对打 | **能解（走手动 IP 直连，绕开 UDP 广播）** | 两台模拟器 NAT 下 `hdc fport` 只支持 tcp ⇒ 用 app 内置「手动输 IP」`10.0.2.2:<fport>` 连房主 TCP 41235；备选：host 侧扮演一方测协议 | ~10-15 分钟 / 备选 ~5 分钟 |

## ① fps 上限（判据 1511）

### 探针结果（实测）

| 探针 | 结果 | 说明 |
|---|---|---|
| `hdc -t 127.0.0.1:5557 shell "param get \| grep -i fps"` | **无输出**（只有 `const.SystemCapability.*` 噪音） | 模拟器没有 fps 相关 param |
| `ls /sys/class/devfreq` | **Permission denied** | shell 身份 `uid=2000(shell)`，无 root |
| `cat /proc/loadavg` | **Permission denied** | 同上 |
| `SP_daemon -f/-g/-c` | **无输出**（二进制存在，root:shell 755） | 需要更高权限/性能服务，shell 下不可用 |
| `hidumper -s RenderService -a fps/info/all` | 只有 5 行服务头，**无 dump 内容** | 模拟器 RenderService dump 未实现 |
| `param get \| grep -i gpu/egl` | 只有 `web.debug.eglSwapBuffersBackgroundColor` | 无 GPU 型号/频率 |
| 宿主机 Emulator 进程 | 空载 **CPU 9%**，RSS 295MB | 渲染时再测可判断是否单核打满（软件渲染瓶颈） |

> ⇒ **直接读 GPU 频率/负载：做不到**（模拟器无 root，devfreq/proc 被 SELinux 挡）。
> ⇒ 但 app **已经在日志里打帧直方图**（`Splash.ets:501`）：
> `finish: animMs=%d boosted=%s | frames fast=%d mid=%d slow=%d vslow=%d drop=%d`
> —— 47.7 这个数就是从这类直方图算出来的。

### 可执行方案（能证明「不是 app 上限」）

1. **采 app 帧直方图（n≥3，判据 1510）**
   ```bash
   HDC=~/Library/Huawei/command-line-tools/sdk/default/openharmony/toolchains/hdc
   $HDC -t 127.0.0.1:5557 shell 'aa force-stop com.andrewoscar.onemore'
   $HDC -t 127.0.0.1:5557 shell 'aa start -a EntryAbility -b com.andrewoscar.onemore'
   sleep 6
   $HDC -t 127.0.0.1:5557 shell 'hilog -x | grep "finish: animMs" | tail -5'
   ```
   由 `animMs / (fast+mid+slow+vslow)` 算 fps，跑 3 轮看极差（≤3fps 才算数）。
2. **对照「轻载」**：开屏动画本身是轻载（几十个矩形位移）。若轻载下 fps 也贴着 ~47.7，
   且**宿主机 Emulator 进程 CPU 未打满单核** ⇒ 这是**出帧上限**（模拟器 vsync/软件合成），不是 app 算得慢。
   ```bash
   ps aux | grep 'tools/emulator/Emulator' | grep -v grep | awk '{print $3, $6/1024}'
   ```
3. **反向对照（可选，重载）**：进一款 60fps 物理游戏（如 GPong/GBreakout 的 16ms tick）后再采一次；
   若重载 fps **不下降**（仍 47~48）⇒ 更坐实是模拟器上限（app 成本变化不影响出帧）。
4. 现有脚本可直接改设备参数复用：`工具/measure_splash_fps.sh`（里面写死 `127.0.0.1:5555`，
   当前设备是 **5557**，改 `DEV`/端口即可；`HC` 路径用的是 DevEco 内置 hdc）。

**代价**：~15 分钟；只读（`aa force-stop/start` 只切换前台，不改数据/设置）。
**边界**：这只证明「模拟器出帧上限 ≈ 47.7」；要拿到手机真实上限必须真机同法采一次（数据可比）。

## ② 电视 3 米视距观感

### 探针结果（实测）

| 探针 | 结果 |
|---|---|
| `wm size` / `wm density` | **`wm: inaccessible or not found`**（模拟器无 `wm` 工具） |
| `~/.Huawei/Emulator/deployed/*/config.ini` | **可配**：`hw.lcd.single.width/height`、`hw.lcd.density` |
| 现有实例分辨率 | onemore2 = 2400×3840、onemore3 = 1320×2232、onemore5 = 2880×1620（都是手机 6.39" / density 480） |

> ⇒ **分辨率/DPI 可模拟**（改 config.ini 后重启实例），**不能**模拟：3 米视距、遥控器焦点、overscan、TV 渲染差异。

### 可执行方案

**A. 模拟器近似（能做）**
1. 复制一个实例配置（`onemore4` 之类），把 `config.ini` 改为 TV 常用参数：
   `hw.lcd.single.width=1920`、`hw.lcd.single.height=1080`、`hw.lcd.density=320`、
   `hw.lcd.single.diagonalSize=55`（55 寸电视）、方向 landscape。
2. 重启该实例 → `hdc tconn 127.0.0.1:<port>` → 装当前 HAP 跑一遍。
3. 看：字号是否过小、按钮间距、9 宫格/棋盘是否被裁、横向滚动是否出现。
**代价**：~20 分钟（复制/改配置/重启），只改模拟器实例配置（不改系统设置、不改 .ets）。

**B. 真机清单（奥森有电视时照着做，10 分钟）**
- [ ] 装 release HAP（确认 `bm dump updateTime ≥ HAP 构建时间`，判据 1794）
- [ ] 3 米外看：主标题/按钮文字是否可读（判据：不用眯眼）
- [ ] 遥控器**方向键**遍历：首页 → 游戏卡 → 进游戏 → 返回，焦点框全程可见
- [ ] 遥控器**确认键**：能进游戏、能暂停、能退出
- [ ] 四角是否被 overscan 切掉（TV 常见 3~5% 裁边）
- [ ] 结算弹窗在电视上是否完整（按钮不被切）
- [ ] 横屏棋盘：进一款棋盘游戏看是否溢出（判据 1799）
- [ ] 局域网对打：两台设备（一台电视 + 一台手机）同 Wi-Fi
- [ ] 语音/读屏：TV 无障碍朗读是否触发（可选）
- [ ] 帧率观感：快速滑动列表是否明显卡顿（对比手机）

**结论**：**部分可解**。分辨率近似可做，**3 米视距的「观感」只能真机**；清单已备。

## ③ 局域网真机对打

### 探针结果（实测）

| 项 | 结果 |
|---|---|
| 两台模拟器 IP | 都是 `10.0.2.15`（QEMU user-mode NAT，彼此不可见） |
| 当前在线设备 | **只有一台**（127.0.0.1:5557）；实例目录有 onemore/2/3/4/5 |
| `hdc fport` 支持的 schema | `tcp:<port>`、unix domain socket、`dev:`、`jdwp:`、`ark:` —— **没有 udp** |
| app 的 LAN 协议（`core/Lan.ets`） | UDP **41234** 广播 `YIJU/1 DISCOVER` → 房主回 `YIJU/1 HOST <port> <name>`；对局走 **TCP 41235**，一行一条 JSON |
| app 是否支持手动 IP | **支持**：`pages/LanLobby.ets:427 manualJoin()` —— 「扫不到？直接输房主 IP」，默认端口 41235 |

> ⇒ UDP 广播发现（41234）在 NAT 下**桥不过去**（fport 只转 TCP）。
> ⇒ 但**对局本身是 TCP**，且 app 有**手动 IP 直连**入口 ⇒ 可以绕开广播，直接测 TCP 对局！

### 可执行方案

**A. 两模拟器 + fport（真·两机对打，~15 分钟）**
1. 启动第二台模拟器（`onemore2` 已部署）：`/Applications/DevEco-Studio.app/Contents/tools/emulator/Emulator -start onemore2`
   （启动后 `hdc tconn 127.0.0.1:<实际端口>`；**不要 pkill**，只能 `-stop`）
2. A 机（房主）建房 → app 监听 **TCP 41235**。
3. Mac 上把 A 机的 TCP 端口映到 host：
   ```bash
   HDC=~/Library/Huawei/command-line-tools/sdk/default/openharmony/toolchains/hdc
   $HDC -t 127.0.0.1:5557 fport tcp:44135 tcp:41235
   ```
4. B 机：局域网大厅 → 「扫不到？直接输房主 IP」→ 填 **`10.0.2.2:44135`**
   （QEMU user-mode NAT 里 `10.0.2.2` = 宿主机；fport 把 host:44135 → A机:41235）。
5. 验证：连上后落子/走棋是否同步、断线是否提示、结算是否同步。

**代价**：~10-15 分钟；风险：两台模拟器吃 CPU/RAM（当前空载 Emulator ~9% CPU / 295MB，两台可接受），端口冲突需换 44136 之类。
**注意**：UDP 广播发现仍不可用（fport 不支持 udp）——这一步是**用「手动 IP」绕开发现**，不是修好广播。

**B. 只测协议逻辑（host 扮演一方，~5 分钟，不用第二台模拟器）**
1. A 机建房 → 同 A 方案第 3 步做 fport。
2. Mac 上用 `nc` 或 node 连 `127.0.0.1:44135`，按协议发一行 JSON：
   `{"t":"move","d":...}`（格式见 `core/Lan.ets` 的 `LanMsg`），收房主回包。
3. 验证：协议解析、非法包是否崩、断线重连、结算包。
**代价**：~5 分钟；只测协议逻辑，不测真实网络（NAT/丢包/时延）。
**可写成脚本**（`node` 或 `nc` + 超时），放进 `_巡检记录/` 备查。

**C. `hdc file send` 为什么不适用**：LAN 对局是 **TCP 行 JSON 流**，不是文件传输；file send 只能核对文件，测不了协议。⇒ 用 A/B。

**结论**：**能解**（用手动 IP 直连绕开 NAT 的广播问题），代价 ~15 分钟；真机验证仍建议一台电视+一台手机（同 Wi-Fi，走真实广播）。
