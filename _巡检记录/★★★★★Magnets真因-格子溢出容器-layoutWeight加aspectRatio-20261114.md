# ★★★★★ `Magnets` 真因：格子**溢出了容器**（`layoutWeight(1)` + `aspectRatio(1)`）

> `2026-11-14 19:4x`。今天修好 `5` 款（`2048`/`Shikaku`/`Kakuro Mini`/`Fraction Matcher`/`Percentage Shopping`），`Magnets` 查明机制、留给明天。

## 一、⇒ 事实

**实测（`18:52`）：**
```
Magnets  OK  lowest='现 0' [2371,1589][2438,1600]  blk=2/48px  board=544x544@90,750  max=24
```

**截图（`截图-Magnets-185229.jpeg`）：`4` 列 × `4` 行棋盘只看到约 `2.8` 行；`4` 个格子横跨约 `87%` 屏宽。**

### 代码事实

- **`L701`：网格 `Column` 有 `.width(Math.min(Bp.width - 2*Space.lg, Math.max(140, Bp.height - 375)))`**
  - `533vp` 屏上 = `min(813, max(140,158)) = 158vp` = `474px`
- **`board=544x544` = `181vp`** ⇒ **容器确实是 `158vp` + padding `sm×2` = `178vp` ≈ `544px`** ✅ **限制生效了**
- **但截图里格子横跨 `~742vp`** ⇒ **格子超出了父容器**

### 为什么

**格子是 `.layoutWeight(1).aspectRatio(1)`（`L645-646`、`L693-694`），没有固定尺寸。**
**⇒ 在 ArkUI 里，`layoutWeight` 分配的是**主轴**空间；`aspectRatio(1)` 再用宽度定高度。当外层高度无界（本作的 `Column` 无 `.height`），格子会按自然尺寸绘制，**超出 `158vp` 的父容器，且父容器没有 `clip` ⇒ 溢出可见、不被裁**。**

**⇒ 所以 `blk=48px` 只是「容器底边超出 48px」；真正的问题是**格子在水平方向就溢出了 3 倍多**。**

## 二、⇒ 明天怎么修（三条路，按风险升序）

1. **给格子一个显式宽度**（最稳）：把 `.layoutWeight(1)` 换成 `.width(w)`，其中 `w` 由可用宽算出
   （参考 `GGo9.boardMax()` 的算法：`(可用宽 - 线索宽×份数 - 间隙) / N`）。
2. **给网格 `Column` 加 `.clip(true)`**：能立刻止住溢出，但会**切掉内容** ⇒ 不解决「看不到」的问题，只是把溢出藏起来。**不建议**（等于今天 `Scroll` 的错误重演）。
3. **给格子加 `.constraintSize({ maxWidth: ... })`**：折中，需实测确认 `aspectRatio` 是否尊重它。

**⇒ 首选第 `1` 条：与 `Shikaku` 的 `240→200` 同源 —— 把尺寸算出来，而不是靠弹性分配。**

## ⇒ 判据（`2619`）

**`layoutWeight(1)` 只负责主轴分配，`aspectRatio(1)` 再用宽度定高度；**两者组合在「容器高度无界」时会画出比容器大的元素**。**
**⇒ 判据：看到「容器宽度正确、内容却超出」时，先查子元素是不是 `layoutWeight`（弹性）而不是算出来的绝对尺寸。**

## ⇒ 判据（`2620`）

**而 `.clip(true)` 是**把溢出藏起来**，与今天 `Scroll` 的错误同型（都是「让指标好看、问题没解决」）。**
**⇒ 判据：修布局溢出只能「算小到装下」或「改结构」，不能用裁切/滚动把溢出藏起来 —— 除非产品语义就是可滚列表。**
