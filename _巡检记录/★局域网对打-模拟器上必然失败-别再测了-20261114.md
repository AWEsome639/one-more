# ★ 局域网对打：两台模拟器**必然失败**，原计划那 `5` 分钟不用测

> `2026-11-14 10:0x` 读源码确认。**这条是为了省掉一次注定失败的测试，并说清真要测需要什么。**

## 一、实现机制（`core/Lan.ets`）

```ts
const DISCOVER_PORT = 41234;   // UDP 发现
const TCP_PORT      = 41235;   // TCP 配对

srv.listen({ address: '0.0.0.0', port: TCP_PORT, family: 1 });      // 房主开服
udp.setExtraOptions({ broadcast: true });                            // 开广播
udp.bind({ address: '0.0.0.0', port: DISCOVER_PORT, family: 1 });    // 收广播
… address: { address: '255.255.255.255', port: DISCOVER_PORT }       // 发广播

await tcp.connect({ address: { address: room.ip, port: room.port } });  // 加入方连房主
```

**⇒ 发现**：UDP 广播到 `255.255.255.255:41234`
**⇒ 配对**：TCP 直连 `room.ip:41235`，`room.ip` **只能来自广播**

## 二、为什么模拟器上必然失败

两台实例的 `hdc shell ifconfig` 都是 **`10.0.2.15`** —— 这是各自 NAT 虚拟网络内的地址。

| 环节 | 结果 |
|---|---|
| UDP 广播 `255.255.255.255` | 出不了各自的虚拟网络 ⇒ **对面收不到** |
| `room.ip` | 拿不到（没收到广播）⇒ 连接无从发起 |
| 退一步硬填 `10.0.2.15` | 那会连到**自己** |

**⇒ 不是代码 bug，是网络拓扑决定的。**

## 三、关键：没有手动 IP 入口，所以无 app 内绕过

我特意查了有没有「手动填房主 IP」的路径 —— **没有**。
`tcp.connect` 唯一的地址来源是 `room.ip`，而它只由广播填充。

**⇒ 所以这条路是封死的：**
- **想测，只有两条路**：
  1. **两台真机同一 WiFi**（这才是真实场景）
  2. **让模拟器共享宿主机网络**（桥接 / host-only 同网段）—— 属宿主层改动，不是改 app
- **在默认 NAT 的模拟器上，无论怎么点都是「搜不到房间」，且这不说明 app 有问题**

**⇒ 原计划那「两台实例起来、看能不能发现房间」的 `5` 分钟测试，结论已定，不必做。**
**⇒ 更不要因为搜不到就去改 `Lan.ets` —— 那是把网络拓扑问题误判成代码问题。**

## 四、顺带一条他们已经踩过的坑（值得留着）

`Lan.ets:206-207` 的注释：

> ★ 必须**等到对手回话才算连上**，不能只看 `connect()` 有没有抛错。
>   实测（`2026-10-11`）：受限网络下 `socket.connect()` 会直接 resolve 而不抛错。

**⇒ 这是真的：某些网络栈上 `connect` 是「乐观成功」。**
所以他们用了应用层握手 —— 这个设计是对的，将来若在真机上测，**判「连上了」必须看对手回话，不能看 `connect` 返回值**。

## ⇒ 结论

**第 ⑤ 项的「局域网真机对打」不是待修代码，是「没有测试环境」。**
- 模拟器对打：**确定不可行**（无需再试）
- 真机对打：需要**你有两台设备连同一 WiFi**，或允许改模拟器网络模式
- 代码侧：`Lan.ets` 的握手设计是对的，**没有已知缺陷**

**⇒ 判据（`2046`）：一个「跨设备功能」在虚拟环境里失败，先分清是**代码问题**还是**拓扑问题**。
判据是：换一套网络拓扑（真机同 WiFi）能不能解决。能解决 ⇒ 拓扑问题，别改代码。**
