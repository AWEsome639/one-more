# 判据 3033：审计器**没有时间上界会随新数据漂移** —— 差点让早报的数悄悄脱钩

## 一、怎么发现的

`3031` 修完竖屏口径后我往早报加了一节（㉓），顺手跑审计 —— **它报了 `5` 项不符**：

```
单实例后 条数      实测 216   早报 174    ❌
单实例后 OK 数     实测 201   早报 168    ❌
单实例后 通过率 %   实测 93.1  早报 96.6   ❌
blk>0 款数         实测 29    早报 18     ❌
2048               实测 OK_NOSHOT  期望 OK  ❌
```

## 二、真因：**报告写的是哪一段，审计就得按哪一段算**

早报那组数（`174` 条 / `96.6%`）**说的是「`02:33–06:46` 那一轮跑批」** ——
而我后来为了竖屏验证又追加了约 `40` 条记录，落在同一个台账里。

⇒ 审计器的过滤只有**下界**（`>= 02:33`）、**没有上界** ⇒ 把这些新记录算进了「那一轮跑批」。
⇒ `174 → 216`、`96.6% → 93.1%`、`blk>0` 的 `18 → 29`。

**⇒ 五个不符里，没有一个是真的数据错误，全都是「统计窗口不一致」。**

## 三、修法

```python
'bounds': ('02:33', '06:46'),   # 下界 + 上界
...
day_rows = [r for r in rows if r[0][:10] == day and r[0][11:16] <= upper]
```

再加一处：`returns`（回滚款末次状态）那段原来用的是**全台账** `rows`，
`2048` 那条窗口外的 `OK_NOSHOT`（`07:57`）就把断言顶掉了 ⇒ 改成用 `day_rows`。

### 修后
```
✅ 早报每一个数都能从台账重算出来（不符项 0）
```

### 反向测试（`3013` 的纪律：校验器必须能失败）
故意把 `blk_gt0` 从 `18` 改成 `17` ⇒ **立刻报 `1` 项不符** ⇒ 还原后 `0`。

## 四、判据

> **审计器的统计窗口必须和报告声明的窗口一致。**
> 只写「从某时刻起」而不写「到某时刻止」，等于让报告偷偷覆盖之后所有数据 ——
> **新数据一进来，昨天还对的数就变成错的了。**

⇒ 三条：
1. **报告里凡是写了时间段的数，审计器就必须同时记下界和上界**
2. **同一段断言里，所有子检查都要用同一个过滤后的集合** ——
   这次 `returns` 用了全台账、其它用了窗口 ⇒ 只错一项，最难发现
3. **修完仍要做反向测试** —— `0` 项不符可能是「都对」，也可能是「过滤太松把检查关掉了」

## 五、这条的价值

**这是我第一次被自己的审计器抓住。**
`3013` 建它的时候期望是「挡抄写错」，结果它先挡住的是一类我当时没想到的错：
**口径漂移** —— 报告没改、台账没改，但两者「对同一段时间」的定义不同。

⇒ 所以 `3013` 说的「两类错两套办法」要补第三类：

| 错的类型 | 例子 | 靠什么挡 |
|---|---|---|
| 抄写错 | 把 `96.2%` 写成 `95.6%` | 审计器 |
| 口径错（指标本身）| 用 `lowh` 当分母 | 判据（`3005`/`3010`）|
| **窗口错（同一指标、不同区间）** | **本条** | **审计器 + 显式上下界** |
