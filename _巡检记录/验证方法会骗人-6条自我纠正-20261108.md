# 验证方法会骗人：6 条自我纠正（2026-11-08，perf-hunter）

> **为什么单独写这一份**：今天有 6 次，我"以为"的量法和"真实"的情况不是一回事。
> 每一次都不是代码 bug，而是**尺子坏了** —— 量出来的东西看起来像结论，实际是测量工具/观测口径的产物。
> 下次谁去验同类东西，先读这一份，能省掉这 6 个坑。

**共同结构**：`我以为的` → `实测` → **为什么会骗人** → **以后怎么量**。

---

## 1. `cachedCount`：Grid 与 List 语义完全不同

- **我以为的**：`GamesTab` 里两处 `.cachedCount(20)` 都是"预加载 20 张卡"；既然网格是 `ForEach`，那它大概是**没生效**，两处都是死配置。
- **实测**：
  - **Grid + ForEach**：`.cachedCount()` 是**死配置**。SDK `grid.d.ts:563` 原文：
    `"It works only in LazyForEach and Repeat with the virtualScroll option enabled."`
  - **List + ForEach**（A-Z 视图那处）：**是活的**。SDK `list.d.ts:769–773` 写的是"预布局"语义，
    `ForEach` 下**依然生效**。
- **为什么会骗人**：同一个 API 名字，**Grid 和 List 的语义不同**。凭"名字一样 ⇒ 行为一样"下结论，
  会得出"两处都白写"的错误结论，进而**把一处本来有用的配置删掉**。
- **以后怎么量**：**去 SDK 的 `.d.ts` 里逐字读那句注释，并看清楚是哪个组件的**。同名参数在不同组件里语义可以相反。

---

## 2. `LazyForEach` 首帧拿不到预填数据（而 `aboutToAppear` 看起来"已经填好了"）

- **我以为的**：在 `aboutToAppear` 里 `source.reset(this.list())` 把 355 条灌进 `IDataSource`，
  `LazyForEach` 挂上来就能直接渲染第一帧。
- **实测**：**首屏空白**，`dumpLayout` 里**连 `Grid` 节点都没有**（不是"卡片少"，是整个网格不渲染）。
  补了"挂载后 `setTimeout(0)` 再 `onDataReloaded()` 一次"仍然不稳定；
  最后只能上**闸门**：第一帧用 `ForEach` 直出，挂载后再切 `LazyForEach`（`gridReady`）。
- **为什么会骗人**：`aboutToAppear` 里数据**确实是对的**（`items.length === 355` 可断言），
  但 `LazyForEach` 的**首次取数时机**在它注册 listener 之前，框架首帧拿到的是一份**空快照**。
  ⇒ "数据准备好了" ≠ "组件拿到了数据"。**这是两个不同的时刻。**
- **以后怎么量**：验 `LazyForEach` 不要只看"列表里有没有内容"，要 dump **节点类型**：
  `Grid` 在不在、`GridItem` 有几个。**节点类型比文本更早暴露真相。**

## 3. 「今天这一局」在**收起态也渲染** ⇒ 不能用它判断"顶部是否展开"

- **我以为的**：dump 里出现「今天这一局」= 顶部展开块被渲染了 ⇒ 顶部处于展开态。
- **实测**：**收起态也会渲染它**。`GamesTab.ets:1150`：
  `if (this.effCollapsed() && !Bp.tinyScreen() && !Bp.isWatch() && !this.searchOpen) { this.dailyStrip() }`
  —— 收起态用**紧凑版**的今日卡（`dailyStrip()`）。
  ⇒ 我据此把一次"正常收起态"误读成"顶部展开没恢复"，白查了一轮。
- **为什么会骗人**：**同一个视觉元素在两种状态下都出现**，只是形态不同。用"某个元素在不在"当状态判据，
  必须确认它**只在一种状态下出现**。
- **以后怎么量**：判断"顶部整块展开"要看 **「随机来一局」或「🎮 全部」分段行** ——
  这两块**只在展开态渲染**（`effCollapsed()` 为 false 时才有）。

## 4. 设备被切成**阿拉伯语 + RTL + 停在设置页**

- **我以为的**：设备归我独占，上一轮验完就复位了，这一轮直接开跑就行。
- **实测**：一进页面 dump 出来全是 `بنفسجي / أرجواني / نيلي`（阿拉伯语的配色名）+ 底部 tab 文字为
  `الألعاب / إحصائيات / الإعدادات`，而且**停在设置页** ⇒ 前一个人的 i18n/RTL 验证没复位。
  我的脚本按中文文案找控件（`'🔍'、'经典 46'`）**全部找不到** ⇒ 报"控件不存在"，其实是**语言不对**。
- **为什么会骗人**：**设备是共享资源，上一次的"临时状态"就是下一次的"初始状态"**。
  而且 RTL 会**镜像布局**（设置 tab 从左跑到右），坐标全变。
- **以后怎么量**（已立判据 1814）：**每次验前先 dump 一次**，确认三件事：
  **语言 = 中文、页面 = 游戏页、筛选面板 = 收起态**。对不上就先复位再验。

## 5. `dumpLayout -p <固定路径>` 在超时会让我读到**上一次的旧文件**

- **我以为的**：`uitest dumpLayout -p /data/local/tmp/x.json` 之后 `cat` 那个文件，拿到的就是当前页面。
- **实测**：这台机器 `dumpLayout` **经常超时**（返回里没有 `saved`，但也没报错）。
  我的代码 `cat` 了**上一次留下的同名文件** ⇒ 拿到的是**几分钟前的页面**。
  表现就是"点进去又回到首页""明明进了游戏却又显示首页"这种**自相矛盾的观测**，
  我一度以为是 app 崩了/被重启，其实是**读到了旧快照**。
- **为什么会骗人**：**失败是静默的**。命令没报错，文件存在，内容是 JSON —— 一切看起来都正常。
- **以后怎么量**：
  1. **每次 dump 用唯一路径**（`uuid` 后缀），读完 `rm`；
  2. **连拍两次比对文本集合**（我封装成 `dump_stable()`，两次一致才认）；
  3. 关键结论永远**用两个独立观测交叉**（dump + hilog/playlog/preferences）。

## 6. 点卡片**中心**会落到软键盘上

- **我以为的**：卡片 bounds 的中心点就是最安全的点击点。
- **实测**：搜过东西之后**软键盘**从 y≈960 开始占屏，而卡片 `[60,828][634,1206]` 的中心 y≈1017
  **正好在键盘里** ⇒ 点了个键盘按键 ⇒ "点了卡片但没进游戏"。
  我一开始以为是 `GridItem` 的点击事件坏了 / 共享元素转场崩了。
- **为什么会骗人**：**无障碍坐标是全屏坐标**，而**可点区域被软键盘遮住了**。
  bounds 中心 ≠ 可点区域中心。
- **以后怎么量**：**点卡片的"上部 1/5"**（`y = top + (bottom-top)*0.2`），永远在键盘之上；
  或者先按一次返回把键盘收掉再点。

## 7.（补充，不是"自我纠正"）`Bp` 读的是**【窗口】**，不是"死读屏幕"

> 这一条是我今天为了验"非矮屏有没有被误伤"去查源码查出来的。它不是踩坑，是**一个一直被猜来猜去的事实**，
> 而且它决定了"以后怎么验响应式"。所以附在这里。

- **大家一直猜的**：`Bp.width / Bp.height` 到底是**窗口**尺寸，还是**物理屏幕**尺寸？
  （这决定了"把模拟器窗口拖小/拖大，能不能验断点"）
- **事实（`entryability/EntryAbility.ets:146–154`）**：
```ts
const wVp: number = px2vp(prop.windowRect.width);    // ← 窗口 rect，不是屏幕
const hVp: number = px2vp(prop.windowRect.height);   //   且 windowRect 给的是 px，必须 px2vp
Bp.update(wVp, hVp, dev);
mainWin.on('windowSizeChange', (sz: window.Size) => {  // ← 还监听了窗口变化
  Bp.update(px2vp(sz.width), px2vp(sz.height));
});
```
  ⇒ **`Bp` 跟的是应用窗口，且窗口一变就会重算**。
- **推论（很重要）**：**改窗口大小确实会改 `Bp.height`** ⇒ 断点/`isShort()`/列数都会跟着变。
  ⇒ **以后验"响应式"不用瞎猜**：改窗口 = 改 `Bp`。
  （历史证据：`EntryAbility.ets:140` 那段注释就是踩过 `windowRect` 给 **px** 的坑 ——
   1320×2232px 的手机（440×744vp）曾被误判成 lg ⇒ 排 4 列 + 放大 1.12 倍。）
- **本机的现实限制**（我三条路都试过，全堵死，所以"拖窗口"这条路在这台机器上用不了）：
  | 路径 | 结果 |
  |---|---|
  | `desktop_*`（窗口控制工具） | **`Platform not supported`** |
  | 设备 shell 的 `wm` | **不存在**（`/bin/sh: wm: inaccessible or not found`） |
  | 转屏 | 应用 `orientation: "portrait"` 锁定，且模拟器实际横屏 ⇒ 不改变窗口尺寸 |
- **怎么验（替代方案）**：既然是纯函数关系，**代码证明比实测更严格**：
  `Bp.isShort()` = `Bp.height < 690`，不依赖其它状态 ⇒ 任何 `height ≥ 690vp` 的窗口，结果为 `false`。
  （实测只能验一个尺寸；代码证明覆盖全部尺寸。）

## 8.（验证技巧，也是判据）「甩了 ≠ 到了」：**动作不等于状态**

> 这条不完全是"自我纠正"，但它属于同一类毛病：**拿"我做了什么"当"现在是什么状态"**。

- **我以为的**：为了回到列表顶部，我**快速回甩 14 次**，然后 dump —— 看到 `Grid` 在、卡片 8 张，就认为"已经回到顶部了"。
- **实测**：那一次卡片是 **根式化简 / 罗马数字算术 / 数列侦探 / 数列堆叠** —— 这是列表**中段**，离顶部还远。
  高速甩动的惯性/阻尼会让它停在半路，**甩的次数根本不等于位置**。又补了两轮（20 次）才真正到顶：
  首屏变成 **宝石迷阵 / 打砖块 / 弹珠消 / 跳棋**。
- **为什么会骗人**：**「甩 14 次」是动作，不是状态**。动作成功 ≠ 目标达成。
  更阴的是：**中间的 dump 看起来完全正常**（有 `Grid`、有 8 张卡、没有报错）——
  只有当你认识"顶部应该长什么样"时，才发现它不对。
- **正确的判据（可观测状态）**：**首屏第一张必须是「宝石迷阵」**（`GameRegistry` 的第一款）。
  ⇒ 回甩后要**轮询**：一直甩 + dump，直到 `cards[0] == '宝石迷阵'` 或**连续两轮内容不再变化**才停。
- **推广（这条比顶部更重要）**：**凡是"做一次动作就可能停在半路"的操作，判据都要写成状态，不能写成动作次数**。
  例：滚动到顶/到底（看首尾元素）、切分类（看计数行「经典 · 46 款」）、搜索（看「全部 · 3 款」）。
  ⇒ **动作只是手段，判据永远是"屏幕上出现了什么"。**
