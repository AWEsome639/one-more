# ⛔ `Fraction Matcher` 的 `padding lg→md` 修法**可能不够**：实省 `24px`、需要约 `109px`

> `2026-11-14 15:4x`。核 A 批算术时顺手验 A 档的省量，发现这个数是按错的 `Space.lg` 估的。

## 一、⇒ 实测

| 项 | 值 | 依据 |
|---|---|---|
| 选项 `B` 可见 | **`14px`** | 台账 `lowest='B' [108,1586][136,1600]` ⇒ `1600-1586` |
| 选项行高 | **`123px`** | `.height(Cell.of(48))` ⇒ `48 × 0.85 = 40.8vp × 3 = 122.4px` |
| **要整行露出需要** | **约 `109px`（`36vp`）** | `123 - 14` |
| **`padding lg→md` 实省** | **`8vp = 24px`** | **`Space.lg = 20`、`Space.md = 16` ⇒ `4vp`/边、两边共 `8vp`** |

**⚠️ 而 `add_check_entries.py` 的 `NEW_CASES` 里写的是 **`16vp`** ⇒ 那是按「`lg = 24`」估的，实际 `lg = 20`。**

## 二、⇒ 所以修完仍不够

**`24px` 只能让 `B` 从 `14px` 露到 `38px`，而整行 `123px`。**
**⇒ 仍然只露 `31%` ⇒ **仍属功能级**（选项被切到看不清）。**

## 三、⇒ 那什么才够

| 候选 | 省量 | 够不够（需 `109px`）|
|---|---:|---|
| 题卡 `padding lg→md` | `24px` | ❌ |
| **`HintBar` 隐藏**（`GGo9` 已验证模板）| **约 `90px`**（`30vp`）| **接近、可能仍差一点** |
| 两处叠加 | `114px` | ✅ **够** |
| 缩选项行高 `48→44` | `5 × 4 × 0.85 × 3 = 51px` | 单独不够 |

**⇒ 所以 `Fraction Matcher` 的正确修法是**「缩题卡 padding + 隐藏 HintBar」**，或**缩上方 + 缩选项行**组合。**

**⚠️ 而这需要重新推算，不是照 `apply_fixes.sh` 里那一行改完就能好。**

## 四、⇒ 这不是「白改」——但预期要下调

**`padding lg→md` 仍是正确的第一步（`24px` 是实的），只是**不足以单独解决**。**

**⇒ 所以明天的验收标准要改：**
- **原来预期「选项行露出 `37%→76%`」** ⇒ 那个数是按 `16vp` 算的，**不成立**
- **实际预期：「露出 `14px → 38px`（`11% → 31%`）」** ⇒ **仍不达标**

**⇒ 明天的判断要改成「改完若仍 `<50%` 露，就再叠加 `HintBar` 隐藏」。**

## ⇒ 判据（`2559`）

**验「省多少」时要**取代码里的实际常量**，不要用记忆里的值。**
**⇒ 我这里把 `Space.lg` 记成 `24`（实际 `20`）⇒ 省量估成 `16vp`（实际 `8vp`）⇒ 差一倍。**

**⇒ 判据：任何「改完省 N vp」的算式，每一项常量都要当场 `grep` 出来；记忆里的设计 token 值不可信。**

## ⇒ 判据（`2560`）

**而「省量是否够」要用「需要多少」去比，不能只说「省了一些」。**
**⇒ 这里 `24px < 109px` ⇒ 明确不够；若只报「省 `24px`」会让人以为改完即好。**

**⇒ 判据：报改动收益时，必须同时报「需求缺口」与「满足比例」；只报收益等于没报。**
