# 判据 `3095`：**`258 / 356` 款竖屏一次都没测过** —— 「过期」名单看不见「从未测过」

## 一、怎么发现的

抓到第三款同类缺陷（`Odd Rotation`，判据 `3094`）后，我按「结构模式」扫全库，
发现 `Shape Shifter` / `Navon Hierarchical` 两个候选，然后查台账 ——

```
Shape Shifter       竖屏条数 0 / 横屏条数 3
Navon Hierarchical  竖屏条数 0 / 横屏条数 1
```

它们**从来没在竖屏下被量过**，而且不在竖屏待测名单里。

## 二、缺口有多大

```
横屏测过          356 款
竖屏测过           98 款
★ 竖屏一次没测过   258 款（72%）
```

⇒ **七成的游戏从没在竖屏下被看过一眼**，而 `2.0.0` 的 `deviceTypes` 里有 `tablet` ——
竖屏是**承诺过的形态**。

## 三、为什么名单里没有它们

`check_ledger_freshness.py --nonshort` 判的是「**过期**」=「量过，但代码改动晚于测量」。
⇒ **没有竖屏记录的款压根不参与比较**，所以既不算新鲜、也不算过期，**直接消失**。

⇒ 这是「判据只覆盖有数据的那部分」的经典漏洞（和 `3088` 的 `blk` 同构）。

## 四、按结构风险排序（把 258 压成 6）

风险分 = 正方形格子(`aspectRatio(1)`≥2) 且未做宽度限高 **+3**；`ForEach`≥3 **+1**；横屏本来就溢 **+2**。

```
★ 风险 ≥4（最该先测）6 款：
  Color Flood          AR 3  ForEach 3
  Dual Mirror          AR 7  ForEach 4
  Mirror Tracing       AR 3  ForEach 4
  Navon Hierarchical   AR 2  ForEach 4
  Shape Shifter        AR 5  ForEach 11
  Sudoku Hex           AR 2  ForEach 3
```

⇒ 名单已落盘：`_巡检记录/待测-竖屏从未测-高风险6款.txt`（全量 258 款在同目录另一份）。

## 五、判据

> **「过期」和「从未测过」是两种不同的缺口，报表只报前者，后者会静默消失。**
> 覆盖率的分母要用「**该测的款数**」，不是「有这个方向记录的款数」。

⇒ 四条：
1. **任何「新鲜度/过期」类报表，都要同时报「从未测过」的数量** —— 否则覆盖率会被高估
2. **`2.0.0` 声明了 `tablet`（竖屏形态），就必须有竖屏覆盖证据**；72% 没测过 = 声明与证据不符
3. **把「未知」按结构风险排序**，比逐个测更省时间（258 → 6）
4. **同一类缺陷出现 3 次就该做全库静态扫描**（`3094`）—— 这次扫出来 6 个新候选
