## 根因（读代码）

**`GYajilin.ets:452`**：
```ts
.constraintSize({ maxHeight: Math.max(140, Bp.height - 360) })
```

**⇒ `Bp.height - 360 = 533 - 360 = 173`** ⇒ **`Math.max(140, 173) = 173`**

**⚠️ 而「`-360` 只限制了「棋盘的 `maxHeight`」」** —— **「没有算「HUD 行 + 玩法说明 + 提示行 + 按钮行」的高度」。**

**⇒ 这是「判据 1826」的又一次应用**：
> **「游戏区可用高」的账要先减「`GameHost` 的 `-190`」再减「页头 `253`」**
> **⇒ 「而 `Yajilin` 又在这之上「减 `360`」，但「减的是「棋盘」不是「总高」」。**

## 修法（明早落，今晚先记）

**「`-360` → `-400`」**（**`Bp.height - 400 = 133`，`Math.max(140, 133) = 140`**）

**⚠️ 但「`Math.max(140, ...)` 的下限 `140` 会「反噬」」**：
- **`133 < 140`** ⇒ **「`maxHeight` 还是 `140`」**
- **⇒ 「减 `400` 没用，要减到「`140` 以下」才有用」**
- **⇒ 「真正要改的是「`140` 下限」→ 「`120`」」**

**⚠️ 而「这正是「聪明格」的同一个坑」**：
- **`GKenken` 的「`Math.max(200, …)` 下限反噬」**（**今晚早些时候修的**）
- **⇒ 「`Yajilin` 的「`Math.max(140, …)`」是同一类**

**⇒ 修法（两条一起）**：
1. **`-360` → `-380`**（**让「棋盘」更小**）
2. **`Math.max(140, …)` → `Math.max(120, …)`**（**让「下限」不反噬**）

## 而这条也值得记

**「`Math.max(下限, 屏高 - N)`」这种写法有「隐性反噬」**：
- **当「屏高 - N < 下限」时，实际用的「下限」**
- **⇒ 「减 N 减再多也没用」**
- **⇒ 「这是「下限」不是「上限」」**

**⇒ 判据 1848（候选）**：
> **看到 `Math.max(下限, Bp.height - N)` 时，先算「`Bp.height - N` 是否 < 下限」。**
> **是 ⇒ 「减 N 无效」，真正要改的是「下限」。**
