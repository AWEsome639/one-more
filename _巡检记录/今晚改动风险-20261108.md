## ① `Cell.of ×0.85` 的几何裁字风险

### 口径（比上次“232 处”严格得多）

上次的 232 处是**宽口径**：只要「固定高块里有 Text」就算，含大量单行标签 ⇒ 基本不成立。
本次按**真会裁**的三条同时满足来判定：
1. 高度由 `.height(Cell.of(N))` 决定，且 `N ∈ [36, 54]`（HUD 标签/按钮那档）；
2. 块内有 `maxLines(2)` 或 `maxLines(3)`（**只有多行才会被 0.85 裁掉第二行**）；
3. **没有** `minFontSize(...)`（有自适应字号就安全）。

### 结果：**0 处硬裁**

| 类别 | 处数 | 说明 |
|---|---|---|
| 有 `textOverflow`（省略号） | **11 处 / 9 款**（严口径：`maxLines` 在同一元素链上）<br>宽松口径（14 行窗口内出现 `maxLines`，多数属于相邻元素）为 **248 处** | 最坏是“少显示一行 + …”，不会出现半个字 |
| **无 `textOverflow`（硬裁）** | **0 处**（严/宽两种口径都是 0） | — |

11 处清单（`Cell.of(基准) → 0.85 后`）：

若要彻底消除：给这 11 处加 `minFontSize(10).maxFontSize(...)`（`GRuleSwitcher` 已示范）。

## ② `parseNumMap` 按原始字符串缓存 —— 失效风险

### 机制（`ProgressStore.ets:909-926`）

```ts
private static mapCacheRaw: string = '';
private static mapCacheVal: Record<string, number> | undefined = undefined;
private static parseNumMap(raw: string) {
  if (raw === mapCacheRaw && mapCacheVal !== undefined) return mapCacheVal;  // 只比字符串
  …JSON.parse…
}
```

Lead 的担心「字符串不变但内容该变」—— **核对结论：不会发生**，因为：

| 写入点 | 是否产生**新字符串** |
|---|---|
| `:242-243` init 从盘读入 | 是（读到的串） |
| `:1334-1339` perGamePlays 自增 | 是（`JSON.parse` → 改 → `JSON.stringify` → `setOrCreate`） |
| `:1347-1356` perGameBest 破纪录时 | 是（同上） |
| `:1220-1221` reset 写 `'{}'` | 是 |

- 全部写点都用 **`JSON.parse` 直接解析**（**不是** `parseNumMap`）⇒ 不会拿到缓存对象去改。
- 3 个读点（`:522 playsOf`、`:529 bestOf`、`:536 playedKinds`）**只读**，不写回。
- 破纪录才写 `perGameBest`；不破纪录时字符串不变 ⇒ 缓存命中是对的（best 本来就不该变）。

### 3 个隐患（都不影响当前正确性，建议加固）

| # | 位置 | 风险 | 触发条件 | 修法 |
|---|---|---|---|---|
| 1 | `:913-926` `parseNumMap` **返回缓存对象本体** | 将来任何调用方就地改它（`m[k]=v`）⇒ **raw 不变、内容变** ⇒ 缓存污染（正是 Lead 担心的那种） | 出现新的写调用方时 | 返回前 `return JSON.parse(raw)` 或返回浅拷贝；或加注释「返回值只读」 |
| 2 | `:909-910` 缓存**全局单条**、跨 key 共用 | `bestOf`/`playsOf`/`diffOf` 交替读会互相踢缓存（**纯性能**，无正确性问题） | 每次交替读 | 改成 `Map<string, Record<string,number>>`（按 key 分槽） |
| 3 | `:914` 只比字符串 | 两个不同 key 恰好同串（都 `'{}'`）会共享同一对象 | 同时为空时 | 无害（内容相同）；与 #1 一起修更稳 |

## ③ `constraintSize`（游戏区上限 343vp）对 355 款的副作用

### 先明确语义：`maxHeight` **只压超限内容**

`maxHeight` 不改变小于上限的尺寸 ⇒ **本来就不超高的款零变化**（没有“本来不大、加了反而变小”这种情况）。

### 逐类核对「依赖全屏」的款

| 依赖类型 | 款数 | 名单（抽样） | 结论 |
|---|---|---|---|
| `Canvas` 全屏绘制 | **0** | — | 不涉及 |
| 读触摸坐标 `touches[0]/offsetX/offsetY` | **8** | `G2048` `GBreakout` `GDoodleJump` `GKlotski` `GPong` `GSnake` `GSnake3D` `GSokoban` | **安全**：其中 4 款只用**方向**（offsetX 差值）；`GBreakout` 的分母 `boardW` 是 `onAreaChange` 实测的（`:128`/`:621`）⇒ 缩板自动跟随 ✓ |
| 用 `.position({...})` 绝对定位 | **9** | `GBreakout` `GDoodleJump` `GFlappy` `GKlotski` `GOrbitTap` `GPong` `GSolitaire` `GSpiderSolitaire` `GVennNumbers` | **安全**：`GOrbitTap` 完全不用 Bp 宽高；`GKlotski` 只用 `Bp.width <= Bp.height` 判横竖（不拿它当坐标）；其余按**自身容器**百分比 |
| 把 `Bp.height` 当固定高度 | **4**（15 处） | `GChangeBlindness:50` `GObjectDisplacement:47` `GPeripheralFocus:42`（都是 `Bp.height*0.35` 且 ≤260）+ 我刚改的 `GPythagoreanTripleBuilder` | **安全**：533×0.35≈187vp < 343 上限 |
| 源码里对 Bp 宽高做四则运算 | **65** | `GAkari` `GBejeweled` `GFutoshiki` … | 多数用于**尺寸微调/分支判断**（如 `Bp.width > Bp.height` 横竖），不构成“必须是全屏”的强依赖 |

### 结论

**没有一款是“棋盘必须占满全屏否则算错坐标”**（唯一像的 `GBreakout` 已用 `onAreaChange` 自适应）。
⇒ ③ 不存在需要回滚/补丁的副作用。
