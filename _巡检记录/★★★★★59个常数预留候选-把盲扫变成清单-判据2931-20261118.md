# 把「盲扫」变成「清单」：`59` 个「按高度限宽」候选（判据 `2931`）

> `2026-11-18 21:04`。今天抽 `20` 款发现 `2` 个缺陷后，我没有继续盲抽，而是**用代码把所有同型点找了出来**。

## 一、⇒ 发现

**⇒ 全库 `grep 'Bp.height - <常数>'` ⇒ `128` 款**在用它。**
**⇒ 其中**「按高度限宽」型**（`.width(Math.min(Bp.width - X, Bp.height - N))`，与 `Crossword`/`Word Search` 一字不差的写法）⇒ **`59` 款**。**
**⇒ 而 `N = 360` 占了绝大多数（约 `50` 款）—— **同一个常数被复制到了几十处**。**

## 二、⇒ 为什么 `-360` 在折叠屏上不够（算式）

| 设备 | `Bp.height` | 网格宽 = `h-360` | 屏高 | 网格占高比 | 剩余给 chrome |
|---|---|---|---|---|---|
| 手机 | `533vp` | `173vp = 519px` | `1600px` | `32%` | `1081px` ✅ |
| 折叠屏 | `832vp` | **`472vp = 1416px`** | `2496px` | **`57%`** | `1080px` ⚠️ |

**⇒ 关键：两种屏的「剩余空间」几乎一样（`1081` vs `1080px`），但网格占高比从 `32%` 涨到 `57%`。**
**⇒ 而 chrome（头部/提示/按钮）是**固定 vp**，在折叠屏上换算成 px 后占比更小，但网格**按 vp 减常数**、在更高屏上按比例放得更大 ⇒ **网格吃掉了 chrome 该有的空间**。**

## 三、⇒ 所以真正的问题不是「常数太小」，而是**公式形状错了**

**⇒ `Bp.height - 360` 隐含假设「chrome 固定 `360vp`」。手机成立，折叠屏不成立。**
**⇒ 正确的形状应该让 chrome 按 **px 或按屏高的比例** 预留，而不是按 vp 常数：**

```ts
// 候选公式（未验证，需要真机对比后再用）
const chrome: number = Math.max(360, Bp.height * 0.42);   // 手机 533*0.42=224 → 仍取 360
const byH: number = Bp.height - chrome;                    // 折叠屏 832*0.42=349 → 仍取 360?
```
**⇒ ⚠️ 上式在折叠屏上仍得 `472vp` ⇒ **说明 `0.42` 这个比例也不对**。必须**先在折叠屏上量出真实 chrome 高度**（dump 里「网格上边界」到「顶部」的距离），再用实测值定公式。**
