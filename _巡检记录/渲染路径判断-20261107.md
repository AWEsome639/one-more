# 渲染路径判断扫描 · 2026-11-07

> 只读审计，**未改任何 `.ets`**（本轮写域只有 `_巡检记录/`）。
> 判据背景：`this.t(zh, en)` / `TG(...)` 的返回值有**三条渲染路径** ——
> **zh 返回原词 / en 返回入参 / 其余 10 种查字典**。
> 任何「拿这个返回值做字符串判断」的地方，都可能**随语言变**：
> 中文 4 个字、英文 20 个字符、某语言首字符少了 emoji —— 判断结果就跟着变。

---

## 0. 一页结论

| 类 | 命中 | 真问题 | 脆弱但当前安全 |
|---|---|---|---|
| 内容判断（`startsWith` / `includes` / `indexOf` / 切片） | **4 处** | **1 处**（且是**死分支**） | 3 处（依赖译文保留标记） |
| 裸调用丢赋值（判断对象根本没被赋值） | **3 处 / 2 个文件** | **2 处**（1 重 1 轻） | — |
| 长度判断（`length > N`） | **2 处** | **1 处**（与卡片高度耦合） | 1 处（presence 判断） |
| 与字面量相等（`=== '某个值'`） | **0 处** | — | — |
| 取首字符（`[0]` / `charAt(0)`） | **0 处** | — | — |

**一句话**：lead 最担心的「`xxx === '某个值'`」**全仓 0 处**；
真正咬人的是 **`GAlgebraicBalance` 的裸 `TG2(...)` 丢赋值** ——
它让 `tip.startsWith('✓')` 成为**永远为假**的分支（对错反馈文字不显示、颜色永远不绿）；
另有 3 处前缀判断**依赖译者保留 emoji**（今天 12 条渲染路径都保留，明天就可能断）。

---

## 1. 为什么「三条路径」会不一致（判据口径）

| 路径 | 取到的值 | 典型差异 |
|---|---|---|
| zh | `L()` 对 `Lang.ZH` 直接返回 **zh 参数原文** | 短（2~4 个汉字）、带全角标点、**原词里可能没有 emoji** |
| en | 直接返回 **en 参数** | 长（英文平均比中文长 2~4 倍）、用 ASCII 标点 |
| 其余 10 种 | 查 `EXTRA` / `GameI18n.DICT` | 长度浮动、**译者可能保留/丢弃首尾 emoji**、阿语会镜像箭头 |

⇒ 任何 `startsWith / includes / length / === / slice` 都在**赌这三条路径长得一样**。

---

## 2. 扫描方法（四类 + 收敛规则）

1. **直接式**：`this.t(...)` / `TG(...)` 之后**同一行**紧跟 `.length/.startsWith/...` 或与字面量比较。
2. **变量中转**：`const/let x = <含 t()/TG() 的表达式>`，之后 60 行内出现 `x.<判断>`（且中间没有重新赋值）。
3. **成员字段**：`this.x = <含 t()/TG() 的表达式>`，之后**全文件**出现 `this.x.<判断>`。
4. **长度阈值**：`length > N`（N>0），并额外检查本地化 helper（`taglineText()/displayTagline()/displayName()`）。

**收敛规则**（避免假阳性）：
- `.length > 0`、`=== ''`、与自身比较 ⇒ **presence 判断**，单独归类（不当作危险）；
- 数组的 `.length/.slice/.indexOf` ⇒ 排除（不是译文）；
- 注释/字符串先做**等长掩码**，避免把注释里的例子当成代码；
- 正则里的 `|` 必须先包 `(?:…)`（本轮踩过：`DEC` 的交替把整条正则拆成三个分支，差点报出 2977 条假命中）。

## 3. 命中清单（按「能不能碰到 / 多严重」排序）

### A1 【真 bug · 用户可见】`GAlgebraicBalance.ets:246/248` —— 裸 `TG2(...)` 丢赋值，判断变成死分支

```ts
241:  private answer(v: number): void {
242:    if (this.over || this.lockTap) { return; }
243:    const good: boolean = v === this.eq.answer;
244:    if (good) {
245:      this.right++;
246:      TG2('✓ 平衡了，x = {0}', String(this.eq.answer))     // ← 值被丢弃，本该 this.tip = …
247:    } else {
248:      TG2('✗ 正确答案 x = {0}', String(this.eq.answer))    // ← 同上
249:    }
...
348:      Text(this.tip).fontSize(FontSize.sm).fontColor(this.tip.startsWith('✓') ? Palette.emerald : this.theme.inkSoft)
```

**证据链**：
1. 全文件 `this.tip =` 只有 3 处（`123 / 256 / 262`），**没有一处**是 ✓/✗ 文案；
2. 所以 `startsWith('✓')` **永远为假** ⇒ 颜色永远是 `inkSoft`（中性灰）；
3. 玩家答对/答错都**看不到任何对错反馈**（tip 停在「点一个候选值」或「共答对 N/M 题」）。

**为什么会不一致**：严格说这条**与语言无关**（是丢赋值），但它**正是「拿译文做判断」这一类的最坏形态** ——
判断对象根本没被赋过值 ⇒ 分支恒假。和 2026-11-07 早先修的 `GActionSequenceRecall.deal()`（我的 S-01）是同一类。

**能不能碰到**：**100%**（每次答对/答错都走这条路），只是不报错、不崩，只是「什么都没发生」。

**修法**：`this.tip = TG2('✓ 平衡了，x = {0}', String(this.eq.answer));`（另一支同理）。
**更稳的做法**：颜色别依赖译文首字符 —— 用状态字段 `this.lastRight: boolean`，
文案只负责显示。这样即使译者改了 emoji、或以后加语言，行为也不变。

### A2 【同类 · 较轻】`GActionSequenceRecall.ets:244` —— 裸 `TG2(...)` 丢了「过关」提示

```ts
241:    if (this.cursor >= this.seq.length) {
242:      if (this.level >= this.diffTotal) { this.end(true); return; }
243:      this.level = this.level + 1; this.deal();
244:      TG2('✅ 过关！第 {0} 关：{1} 个动作', Digits(String(this.level), ...), this.len())   // ← 丢弃
```

**影响**：升级时本应显示「✅ 过关！第 N 关」，实际 `deal()` 刚把 msg 设成「看好机器人做 N 个动作…」⇒
玩家看到的是下一关的引导语，**少了「过关」这一下正反馈**（不崩、不卡，只是少了反馈）。
**修法**：`this.msg = TG2(...)`（注意 `deal()` 在它前面已经设置过 msg，赋值顺序要让「过关」后写）。

> 这个文件里我上次报的 `deal()` 那处**已修**（注释里写着 verifier-dev S-01）；这是**同一文件的第二处**，上一轮漏了。

### B1-B3 【脆弱 · 当前安全】三处 `tip.startsWith('✓')` 依赖译文保留 ✓

| 文件:行 | 判断 | 赋值的 key | 当前 11 语言是否都以 ✓ 开头 |
|---|---|---|---|
| `GAlgebraicBalance.ets:348` | `tip.startsWith('✓')` | **无**（见 A1，赋值被丢） | — （死分支） |
| `GAlgebraicInequalitySolver.ets:336` | `tip.startsWith('✓')` | `this.tip = TG2('✓ 解集就是 {0}', …)`（269 行） | ✅ **12/12**（10 字典列 + zh 原文 + 繁体 toTrad）保留 ✓ |
| `GDivisibilityDash.ets:362` | `tip.startsWith('✓')` | `this.tip = TG2('✓ 对了，连击 {0}', …)`（278 行） | ✅ **12/12** 保留 ✓ |

**实测**（直接解析 `GameI18n.DICT`）：

```
「✓ 对了，连击 {0}」   en '✓ Right, combo {0}'  de '✓ Richtig, Combo {0}'  ar '✓ صحيح، تتابع {0}' …   → 12/12 带 ✓
「✓ 解集就是 {0}」     en '✓ The solution set is {0}'  ja '✓ 解集合は {0}' …                         → 12/12 带 ✓
```

**为什么仍然报**：这是**用内容当状态**的写法 —— 一旦某语言把 ✓ 去掉（或加一个空格、换成 √），
颜色判断就静默失效（答对也不绿），而且**没有任何测试会发现**。
**能不能碰到**：今天碰不到（11 语言都对）；**新加语言 / 译者改文案时就会**。
**建议**：与 A1 同样改成 `this.lastRight` 状态字段。

### C1 【脆弱 · 当前安全】`GSentenceUnscramble.ets:234` —— `msg.indexOf('❌') === 0` 当「上一步错了」的标志

```ts
233:  private pick(i: number): void {
234:    if (this.over || this.usedAt(i) || this.msg.indexOf('❌') === 0) { return; }
...
241:      this.lives = this.lives - 1; this.msg = TG2('❌ 正确语序：{0}', this.plan[this.qi]);
254:    this.feed = setTimeout(() => { this.feed = -1; this.next(); }, GAP_MS);
```

**行为**：答错后 msg 以 ❌ 开头 ⇒ 在 `GAP_MS` 内**锁住输入**（等动画/展示正确答案），`next()` 后恢复正常。
**实测**：`「❌ 正确语序：{0}」` 的 **12 条渲染路径**（10 字典列 + zh 原文 + 繁体 toTrad）**全部**以 ❌ 开头 ⇒ 今天行为一致。
**能不能碰到**：今天不会出错；但若某语言去掉 ❌，**该语言下答错后不会锁输入**（可以连点）——
是行为性差异，比 B 类更隐蔽。
**建议**：用 `this.lastWrong: boolean` 或 `this.lockUntil: number` 代替对 msg 内容的判断。

### D1 【真耦合】`Common.ets:1303` —— 用**译文长度**决定行数，而卡高是单值

```ts
1303:          .maxLines(this.taglineText().length > 24 ? 3 : 2)
```

**为什么会不一致**：`taglineText()` → `displayTagline()` → `GAME_TAGLINE` 字典（zh 原词 / en `enTagline` / 10 语言）。
中文 tagline 约 9 字（≤24 ⇒ 2 行）；**英文 355 款里有 226 款的 `enTagline` > 24 字符**（⇒ 3 行）。
⇒ **同一张卡，在中文下需要 2 行高度，在英文下需要 3 行**；而卡片高度 `cardH()` 是**单一数值**。

**能不能碰到**：`440×744` 这类手机（`cardH=84`）切英文 **必然**：3 行内容 ≈ 98.8vp > 84vp ⇒ 溢出/被裁。
这正是我上一份报告里的 **S-07b**，这里补上它的**根因归属**：根因是「长度判断 + 单值卡高」，不是单独某一方。

**建议**：二选一 ——
① 卡高按「当前语言 tagline 是否 >24」分档（96/84）；
② 或者 maxLines 恒 2（英文吃省略号，判据 932 的取舍）——但要接受英文副标题看不全。
（lead 在 S-07b 里已在处理，本条目作为根因记录。）

### E1 【安全 · presence 判断】`StatsTab.ets:631` —— `this.t(unitZh, unitEn).length > 0`

```ts
630:        if (this.t(unitZh, unitEn).length > 0) {   // 有单位才画单位
```

**为什么安全**：调用点里 `unitZh/unitEn` **要么都空、要么都非空**（`''/''`、`'局'/'rounds'`、`'款'/'games'`），
字典对这两个键也有译文；所以三条路径给的都是「空」或「非空」。
**风险**：契约脆弱 —— 若以后有人写 `statCell(..., '款', '', ...)`（中文有单位、英文传空），
中英文就会一个显示单位、一个不显示。
**建议**：改签名收 `unitZh/unitEn` 时用 `if (unitZh.length > 0)` 之类的**非语言相关**输入判断，
或干脆用两个可选参数。

## 5. 已知边界（别把「0 处」当全清）

1. 静态数据流只覆盖「直接 / 变量 / 成员」一层；**函数参数传递、数组聚合、`@Builder` 参数**没覆盖
   （例如 `foo(this.t(...))` 里 foo 内部判断）。
2. 无法判断**运行时生命周期**（如 `msg` 被 `setTimeout` 清掉、被其它分支覆盖）—— A1 的死分支是静态推出来的，
   已用「全文件 `this.tip =` 只有 3 处」证明。
3. `displayName()` / `displayTagline()` 走的是 `GAME_NAME` / `GAME_TAGLINE` 字典（另一套路径），
   只覆盖了「长度判断」这一类，没做全量三路径展开。
4. 「译文是否保留标记」是 **2026-11-07 的字典快照**；字典一改，B/C 类结论就要重跑。
