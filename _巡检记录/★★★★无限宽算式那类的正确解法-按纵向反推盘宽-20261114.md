# ★★★★ 「无限宽算式」那类的正确解法：**按纵向反推盘宽**

> `2026-11-14 15:2x`。查 `Mandelbrot`（`A 档不在清单里` 的 `3` 款之一）时找到的。

## 一、`Mandelbrot` 的现状

```ts
387|      .width('100%')                     ← 只有这个，**没有任何 constraintSize**
390|        ForEach([0..11], (r) => {        ← 12 行
392|            ForEach([0..15], (c) => {    ← 16 列
```

**⇒ 盘宽 = 屏宽 `821vp` ⇒ 格宽 `821/16 = 51vp` ⇒ `aspectRatio(1)` ⇒ 行高 `51vp`
⇒ `12 行 × 51 = 612vp` 高。**

**⇒ 而内容区只有 `401vp` ⇒ **被切 `211vp`**。**
**⇒ 这与台账 `blk=48`、`max_bottom=1600` 吻合。**

## 二、⇒ 与「下限太大」那类**完全不同的病因**

| 类 | 病因 | 解法 |
|---|---|---|
| 那 `15` 款（有限宽算式）| 下限 `240` 让盘面**该缩不能缩** | 换 `44 * N` |
| **`Mandelbrot` 等（无限宽算式）** | **`.width('100%')` 让盘面撑满宽度** ⇒ 高度失控 | **按纵向反推宽度上限** |

**⇒ `layout_guard` 的 docstring 说的正是这一类：「宽驱动必须配高度上限」。**
**⇒ 而这些款**完全没有上限** ⇒ 它们本该被 `layout_guard` 抓到，但断言是 `0`。**

**⚠️ 所以 `layout_guard` 的检测可能只覆盖 `width('100%') + aspectRatio` 同时出现在**同一元素**上的情况，
而 `Mandelbrot` 是「行 `.width('100%')` + 格 `.aspectRatio(1)`」分开写的 ⇒ 漏检。**

## 三、⇒ 正确解法

**约束方向反过来：先定「纵向能放多少」，再反推盘宽。**

```
内容区高 401vp ÷ 行数 12 = 33.4vp（每行）
⇒ 格宽（=行高）33.4vp × 列数 16 = 534vp（盘宽上限）
⇒ .constraintSize({ maxWidth: Math.min(Bp.width - 2*Space.lg,
                                       (内容区高 / 12) * 16) })
```

**⇒ 通用式：`maxWidth = (可用高度 / 行数) * 列数`**

**⚠️ 但 `33.4vp < 44vp` ⇒ 触控不达标。**
**⇒ 这类「行×列乘积超出预算」的盘面，**要么缩小格子**（触控不达标）、**要么滚动/缩放**（保持 `44vp`）。**

**⇒ `Mandelbrot` 已确定属「需滚动/缩放」类。**

## ⇒ 判据（`2279`）

**「宽度撑满」和「高度失控」是一对：只要 `aspectRatio(1)`，宽度越大高度越大。**
**⇒ 而解法有两个方向：**
- **限宽**（让高度可控）⇒ 格子变小
- **限高 + 滚动**（保持格子尺寸）⇒ 交互变复杂

**⇒ 判据：遇到「宽驱动高度」的盘面，先算「按纵向预算反推的格宽」；
⇒ 若那个格宽 `< 44vp` ⇒ 触控与「全部可见」不可兼得 ⇒ 必须在两者中选一个并明确说选哪个。**

## ⇒ 判据（`2280`）

**`layout_guard` 断言为 `0` 但 `Mandelbrot` 明显违规 ⇒ 说明断言有**漏检模式**。**
**⇒ 它的规则是「`width('100%')` 与 `aspectRatio` 同时出现」，而 `Mandelbrot` 把两者拆在**父与子**两个元素上。**

**⇒ 判据：断言为 `0` 时，若肉眼/数据能看到违规，先怀疑断言的**匹配模式**太窄（跨元素的组合它抓不到）。**
