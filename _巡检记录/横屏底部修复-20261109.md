## 0 值不值得：**修 2 款，不是 165 款**

perf-hunter 的原话是「**棋盘本身全部在屏内**」—— 即 165 款里**棋盘**没问题，问题只在**底部控制区**（按钮行 / 数字键盘）。
而且「棋盘超高」这一类，`GShikaku`(−260) / `GKakuro`(−310) / `GKakuroMini`(−280) 已经用同一套修法收过一轮（判据 1802）。
⇒ 本轮只修抽检点名的 2 款，**不做 165 款全量改造**（收益不足以支撑 165 次编译回归）。

## 1 两个**不同**的根因（这是本轮最有价值的部分）

### 1.1 数独：`boardPx()` 的 `0.44` 没把 chrome 算进去

```ts
// 改前
const h: number = Math.max(160, Bp.height * 0.44);   // 533 × 0.44 = 234vp
```
`0.44 × 屏高` 只管「棋盘够大」，**没算「按钮行 + 信息行 + 键盘 + 状态行」这层 chrome**。
棋盘已经按 0.44 占满，剩给底部的空间不够 ⇒ 末两行被顶出内容区。

**实测对账**：内容区到 `1516px`，按钮/键盘行尾到 `1600px` ⇒ **越界 84px ≈ 29vp**；
棋盘 234 → 193vp 正好让出 **41vp ≈ 120px** > 84px ✓

### 1.2 聪明格：`Math.max(200, …)` 的下限**反噬** + 默认 `flexShrink(1)` 把键位行压扁

```ts
// 改前
.width(Math.min(Bp.width - 2 * Space.lg, Math.max(200, Bp.height - 360)))
```
屏高 533 时 `533 − 360 = 173`，但 **`Math.max(200, 173)` = 200** —— 下限把棋盘**撑回去**，
多出的 **27vp ≈ 79px** 正好把数字键盘顶出屏幕（实测裁掉约 80px，**数字对得上**）。

**第二个机制**：根容器是 `Column().height('100%').justifyContent(Start)`，
子节点默认 **`flexShrink(1)`** ⇒ 内容一超高，框架**先压可压缩的子节点** ——
键位行就从正常的 ~130px 被压到 **51px**（不是"被裁"，是**被压缩**）。
⇒ 这与判据 1829 是同一件事，只是 **1829 写的是 Row 的横向，这里发生在 Column 的纵向**。

## 2 修法（3 类改动，全部落在「容器 / 控件行」上）

| 文件 | 改动 | 数值 |
|---|---|---|
| `GSudoku.ets` | `boardPx()` 矮屏分支：`Bp.height − 340` | 234 → **193vp**（让出 120px）|
| `GSudoku.ets` | 按钮行 + 数字键盘行 **`.flexShrink(0)`** | 防被压扁 |
| `GKenken.ets` | 棋盘宽度：矮屏下限 `200→150`、留白 `360→380` | 200 → **153vp**（让出 138px）|
| `GKenken.ets` | 按钮行 + 数字键盘行 **`.flexShrink(0)`** | 防被压扁 |

**为什么两处都加 `flexShrink(0)`**：尺寸修法依赖「`Bp.height` 是真实窗口高」；
`flexShrink(0)` 是**机制性兜底** —— 即便空间仍不够，框架也只能去挤别的元素（棋盘/文字），
**不允许把控件压成点不到的 51px**。
