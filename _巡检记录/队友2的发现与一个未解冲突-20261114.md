# 队友 `2` 的五款大盘分析：**三条可用，但有一处冲突必须今晚定**

> 产出：`_巡检记录/五款大盘-列数能否减-20261114.md`（`99` 行，只读）

## 一、它的结论（三条我认为成立）

| 游戏 | 判定 | 依据 |
|---|---|---|
| **`GFindWord`** | ✅ **`6 → 4`（`43.2vp`）** | `L20 N=6` 硬编码；词库全 **`3` 字母**；判定 `path.length>=3` **与 `N` 无关** |
| `GLetterCancellation` | ✅ `6 → 4` **+ `TARGETS 8→4`** | `TARGETS=8`，`N=4` 只有 `16` 格 ⇒ `8` 目标占 `50%` ⇒ 必须同步减 |
| `GVisualSearch` | ✅ `6 → 4`（**难度会降**）| `36` 格里 `1` 目标 ⇒ `N=4` 只剩 `15` 干扰项；**⚠️ 它有两处宽度公式：`L288 -360` 与 `L311 -400`，要一起改** |
| **`GWordSearch`** | 🔴 **减列救不了** | 词库全 **`5` 字母**，放置用 `N-w.length+1` ⇒ **`N≥5`**；减到 `6` 也只有 `28.8vp` |
| `GWordSnakeTrail` | 🟡 `8 → 6` 折中 | 词库 `3` 字母，`N` 只用于坐标换算 ⇒ 减列几乎无风险；但 `6` 列只到 `28.8vp` |

**⇒ 最该先做 `GFindWord` —— 五款里唯一「达标且不伤玩法」的。**

## 二、但它的一个前提我不同意（**这是今天最后一个未解问题**）

**它写：**
> 「`6 列 × 44vp = 264vp < **352vp 可用高**` ⇒ 只把上限提上去就够，不用加滚动」

**它的 `352vp` 与我算的 `233vp` 冲突：**

| 来源 | 可用高 | 怎么来的 |
|---|---:|---|
| **它** | **`352vp`** | 未说明推导 |
| **我** | **`233vp`** | `533 − 头部(300)` |
| 我的头部 `300` | — | **从三款 `max` 反推**（`Hitori All 1499` / `Norinori 1487` / `Pipes 1508`）|

**⚠️ 而我那个反推有**已知缺陷**：那三款当时**还没被我限宽**（`Hitori All` `04:09` 测的，我的改动是后来的）**
**⇒ 它们的 `max` 里含的盘面高**不是 `173vp`** ⇒ **我的「头部 `300`」很可能不准。**

**⇒ 所以这一处**两个人都可能错**。**

## 三、今晚数据能一次定死它

**装包后，任取一款 `-360` 的已改游戏（如 `Hitori` / `Shikaku` / `Crown`），看它的 `max`：**
```
max_px = 头部_px + 盘面_px(519) + 底部_px
⇒ 头部 + 底部 = max_px − 519
```
**⇒ 若 `max ≈ 960~1000px` ⇒ 头部 `~300vp`（我的对）**
**⇒ 若 `max ≈ 1180~1250px` ⇒ 头部 `~352vp`（它对）**

**⇒ 这个数一出来，明天「能不能把 `X` 从 `360` 调到 `340`（甚至 `300`）」就有了确定答案。**

## 四、所以明天做什么（等今晚定）

| 今晚结果 | 明天动作 |
|---|---|
| **`max` 小（头部 `~300`）** | `X` 只能到 `340`；`FitWord`/`LetterCancellation`/`VisualSearch` 减列照做 |
| **`max` 大（头部 `~352`）** | `X` 可以大胆降到 `300`，甚至 `-260`；五款的格子会显著变大 |

**⇒ 无论哪种，**列数那三条都成立**（它们与可用高无关，只与「列数 × 44 是否装得下」有关）**
**⇒ 而 `44vp` 本身也不是硬指标（判据：本项目实际下限 `~30vp`）**

**⇒ 所以最稳的第一刀仍是：`GFindWord` `6 → 4`（`43.2vp`，与可用高无关，纯减列）**
