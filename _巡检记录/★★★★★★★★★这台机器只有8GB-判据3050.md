# 判据 3050：**这台 Mac 只有 `8 GB` 内存** —— 今天所有不稳的最终解释

## 一、决定性数字

```
hw.memsize         :  8.0 GB          ← 总内存
vm.swapusage       :  6.4 GB / 7 GB 已用
memory_pressure    :  29% 可用  ≈ 2.3 GB
```

⇒ 而常驻的两块：
| 进程 | 占用 |
|---|---|
| 鸿蒙模拟器（`onemore_fold` / `onemore7`）| **`~1.3 GB`** |
| DSH 宿主（Electron + 本会话）| `~0.6 GB` |
| `WindowServer` + 系统 | `~0.6 GB` |

⇒ **`1.3 + 0.6 + 0.6 ≈ 2.5 GB`，可用只有 `2.3 GB`** —— 从开机那一刻起就是负余量，
   全靠 `swap` 顶，而 `swap` 也已经用掉 `6.4/7 GB`。

## 二、所以今天所有「故障」都是同一条

`3046` 我记了六个症状、`3047` 我把指标从 `Pages free` 换成 `memory_pressure` ——
**但两条都没说到「绝对量」：这台机器只有 `8 GB`。**

⇒ 补上这一条，全部现象都有确切解释，而且**不用再逐个排查**：

| 现象 | 8 GB 够吗 |
|---|---|
| 模拟器 `etime` 只有 `00:15`（刚崩完自动重启）| ❌ |
| `hdc` 反复 `need connect-key` | ❌ |
| `bundle manager service is died` | ❌ |
| `aa start` 报 `successfully` 但截图全黑 | ❌ |
| 一次测量 `70s` 变 `130s`/`300s` | ❌ |
| 系统整体卡（奥森原话「好卡」）| ❌ |

## 三、这条改变「怎么在这台机器上干活」

| 做法 | 以前 | **现在（8 GB 的现实）** |
|---|---|---|
| 开模拟器 | 随时可开 | **只在 DSH 刚重启、没别的活时开** |
| 并行 | 「不并行」 | **绝对不并行**，连 `grep` 大批量都算负载 |
| 全库扫描 `7.4` 小时 | 一晚能跑 | **不现实** —— 每崩一次就要重解四层 |
| 编译 + 测量 | 串行即可 | 串行也紧张：编译峰值会先把 `swap` 顶满 |
| 一次测多少 | 30 款一批 | **10 款一批**，每批前查 `memory_pressure` |

⇒ **真正稳的路只有两条**：
1. **真机测**（奥森自己的设备）—— 不占 Mac 内存
2. **DSH 重启后立刻测**（宿主最小时占 `~0.2 GB`），用完立刻关模拟器

## 四、判据

> **判断「能不能跑重活」要看绝对值，不只百分比。**
> `8 GB` 总内存跑「DSH + 鸿蒙模拟器」是**结构性不足**，不是「清理一下就行」；
> 百分比会随系统波动给出虚假希望（今天我看到过 `29%`、`30%`、`21%`、`6%`、`47%`，最误导的是 `47%`）。

⇒ 四条：
1. **先看 `hw.memsize`** —— `8 GB` 与 `16 GB` 的可用策略完全不同
2. **模拟器门槛**：`8 GB` 机器上**只在宿主最小、无其它活时**开，且**一次只测一小批**
3. **`memory_pressure` 的百分比会骗人** —— 它算进了可压缩内存，而模拟器要的是**连续可用**
4. **别再在 `8 GB` 机器上规划「跑一夜」** —— 那是为 `16 GB+` 设计的方案

## 五、给奥森的一句

今天卡，不是谁的错，是**这台 Mac 就这么大**：
`8 GB` 同时扛「DSH + 鸿蒙模拟器」，我每开一次模拟器就把它推到 `swap` 极限。

⇒ **要提速的话，最省事的一步是关掉 DSH 重开**（把一天的历史还回去）；
   **要根治的话，测版面这类活应该在真机上做**，不该占这台机器。
