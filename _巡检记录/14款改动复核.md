## 2. 回答 Lead 的三个具体问题

### Q1：`height(N)` 到底是谁的高度？—— 10/11 改对了，1 个改了内层

判断口径（判据 1895 的正确用法）：

- ✅ **改容器**（外面那层 `.width('100%').height(N)`）⇒ 有效，因为容器不在 `layoutWeight` 分配链上；
- ✅ **容器内的元素写 `layoutWeight(1).height('100%')`** ⇒ 它们跟随父级，**改父级就是对的**；
- ❌ **改被父级写死高度的内层** ⇒ 空操作。`GVennNumbers` 就是这一种。

逐款核对：

```
改【外层容器】且父级无固定高：AbReversalOddball / ActionSequenceRecall / BlinkDetector /
  ChoiceReactionTime / StopSignal / StroopNumberSize / CardCountingMemory(Grid 自身即块)
改【外层 Row】、内层卡 layoutWeight+height100%：SpatialConflict / TemporalOrderJudgment / Topology
改【内层】但外层写死 150：VennNumbers  ← 唯一空操作
```

### Q2：`GGeometricVision` 两块各 173vp 会不会太小 / 会不会超宽？

| 项 | 数值 | 结论 |
|---|---|---|
| 单块封顶 | `min(853-40, max(140, 533-360))` = **173vp** | 计算正确 |
| 两块并排 | 2×173 + `Space.sm`(10) + 「VS」文字 ≈ **376vp** | **远小于 853vp，不会超宽** ✅ |
| 游戏区高度 | 约 **343vp**（533 − 顶栏/间距） | 173/343 ≈ **50%**，方块在区内占比 **不小** ✅ |
| **但** | `gridB` 没改 ⇒ **A=173、B=槽宽(~398)** | 🔴 **不对称**，比"小"严重得多 |

⇒ **大小不是问题，不对称才是问题。** 两块都改 173 后，A/B 各占 Row 的一半宽、居中显示，视觉上是一致的。
