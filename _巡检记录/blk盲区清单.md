## 0. 最严重的一条：**它并不比 `max_bottom` 更稳，反而更抖**

Lead 的假设是「`max_bottom` 抖 ±250px，`blk` 稳」。但把这 14 条实测按游戏排开：

| 游戏 | `max_bottom` | `blk` 序列（同一款、20 分钟内） |
|---|---|---|
| **Wordle** | 1600 → 1600 → 1600 → 1600 | **1/60 → 0 → 0 → 2/48** |
| **Nonogram** | 1365 → 1323 → 1323 → 1323 | **1/60 → 1/24 → 0 → 0** |
| **Kakurasu Sums** | 1464 → 1464 | **1/24 → 0** |
| **Magnets** | 1600 → 1600 | **0 → 2/48** |

**`max_bottom` 在这 23 分钟里一个像素没动，`blk` 却 0↔2 来回跳。**
这与「`blk` 抗抖动」的前提**正好相反**：

- `blk` 数的是**容器块**，而容器块会随**浮层/键盘/提示条的生灭**出现或消失；
- 被 `SKIP` 掉的 `Stack`/`Flex` 只挡住了一部分，没挡住 `Column`/`Row` 形态的临时块；
- 于是 `blk` 把「状态抖动」从**叶子层**搬到了**块层**，抖动**没有消失，只是换了个位置**。

> ⚠️ 校准表里 `Nonogram(1323)→0`、`Wordle(1600)→2/48` 都能复现，但**同款的下一次运行就是 0 或 1** —— 
> 单次采样当成"已校准"是**幸存者偏差**：5 款各跑 1 次都"对上了"，但同款多跑几次就对不上。

## 1.5 装饰类会不会被误判？（Lead 的问题 ④）

**分两种，结论不同：**

| 装饰类型 | 会不会被 `blk` 算进越界 | 依据 |
|---|---|---|
| `shadow()` / 阴影、光晕（绘制效果，不改布局盒） | **不会** | ArkUI 的 `shadow` 是**绘制属性**，不改节点 `bounds`；dump 取的是布局盒 |
| `Path` / `Image`（手绘光晕、背景纹理） | **不会**（被 SKIP） | `shot_game.py:546` |
| **被拉伸到全屏的容器**（`height('100%')` / `layoutWeight(1)` 的 Column/Row） | **会** ✅ 这是真误报 | 见下 |

**实证（比推理硬）**：
```
Nonogram   max_bottom=1323（所有文字都在屏内）  blk=1/24px
Kakurasu   max_bottom=1464（同上，屏内）        blk=1/24px
```
`blk=1/24px` 意味着有一个块 `y2=1600`（=1516+60+24），可**所有内容都结束在 1323/1464**。
⇒ 那个"越界块"就是**撑到屏幕底的布局容器**（`height('100%')` 或 `layoutWeight(1)` 吃满剩余空间），
**它里面什么都没画**。这类容器在 355 款里普遍存在（撑满剩余高度的写法是项目里到处用的）。

**⇒ 这是"误报"的主要来源**：`blk` 把"容器几何上到屏底"当成了"内容越界"。

**建议**：统计块时排除「`y1` 之后没有叶子子节点」的容器，或改成「只数**叶子节点**的 `y2`，但按**根的直接子块**分组取每组的最大 `y2`」——
这样既保住"按块分组"的稳定性，又不会把空容器算进来。

## 3. 建议的最小改动（不动 `.py`，给 Lead 拍板）

1. **`Text` 单独一档**：`blkText` = 文字节点里 `y2 > 1600` 的个数。这条能救 **215 款**的文字越界。
2. **滚动页豁免**：扫描时若块的祖先链有 `Scroll`，跳过（救 10 款误报）。
3. **阈值改 1584**（手势条顶），而不是 `1516+60=1576`。
4. **`root is None` 输出 `NA`**，不要静默 0。
5. **每款采 3 次**，报 `blk` 的中位数与 min–max —— 单次 `blk` 不可作判据（§0 已证）。
