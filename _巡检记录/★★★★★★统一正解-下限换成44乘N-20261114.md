# ★★★★★★ 统一正解：把下限换成 **`44 × N`**

> `2026-11-14 13:3x`。今天所有关于「限宽下限」的思路，到这里收敛成一个公式。

## 一、公式

```ts
// 现在（随意定的下限）
.width(Math.min(Bp.width - 2 * Space.lg, Math.max(240, Bp.height - 360)))

// 正解（下限 = 触控下限 × 格子数）
.width(Math.min(Bp.width - 2 * Space.lg, Math.max(44 * N, Bp.height - 360)))
```

**⇒ 那个 `240`（以及 `200`/`140`/`160`）是**猜的常数**；
而 `44 * N` 是「每格至少 `44vp` 触控下限」的**直接推导**。**

## 三、⇒ 为什么这是「有依据」而不是「又一个猜的数」

**`44vp` 是项目的触控下限（`Layout.touchMin`、`Cell.tap` 保证 `>= 44`）。**
**⇒ 所以 `44 * N` 不是估计值，是「`N` 个格子并排时的**最小可行宽度**」。
⇒ 它随 `N` 自动变化，不需要为每款游戏单独猜。

**⚠️ 而 `3×3` 的 `max(132, 173) = 173` ⇒ 仍由高度决定（比触控下限宽），这是对的：
⇒ 高度富余时就该按高度撑满，而不是按触控下限。**

## 四、⇒ 所以「`240 → 140`」与「`44N`」的区别

| 方案 | `6×6` 结果 | 每格 |
|---|---|---:|
| `240 → 140` | `173vp` | `28.8vp` ❌ |
| **`44 × N`** | **`264vp`** | **`44.0vp`** ✅ |

**⇒ 「`240 → 140`」是**朝反方向走**（把盘面缩到更小），
⇒ 而 `44N` 是**按需给足**（`6×6` 反而要**变大** `24vp`）。**

## 五、⇒ 而这需要配合「藏上方元素」

| `N×N` | 盘面变化 | 需腾 | 藏 `HintBar`+统计卡（`~90vp`）够吗 |
|---|---:|---:|---|
| `4×4` | `240 → 176`（**小 `64`**）| — | ✅ 不需要藏 |
| `5×5` | `240 → 220`（**小 `20`**）| — | ✅ 不需要藏 |
| `6×6` | `240 → 264`（**大 `24`**）| `24vp` | ✅ 藏了有 `90vp` |
| `8×8` | `240 → 352`（**大 `112`**）| `112vp` | ✅ 藏 `90` + 缩其他 `22` |

**⇒ 所以：`4×4`/`5×5` 只需改下限（盘面自动变小、格子反而变大）；
`6×6`/`8×8` 要改下限 **+** 藏上方元素。**

## ⇒ 判据（`2263`）

**一个「猜的常数」（`240`）被 `N` 个副本复制时，正解往往不是「换一个更好的常数」，
而是「把那个常数换成**能从约束推出来的表达式**」。**
**⇒ 这次 `240` → `44 * N`：同一个公式对 `3×3` 到 `15×15` 都成立（只是大棋盘受纵向限制）。**

**⇒ 判据：看到同一常数在 N 处出现，先问「它是不是某条约束的近似值」。
⇒ 是 ⇒ 写成表达式（`44*N`）；不是 ⇒ 才需要一个更好的常数。**

**我今天在「下限该是多少」上绕了 `3` 次：`240→140`（错）、`240→173`（错）、最后 `44×N`（对）。
前两次错在**都在「猜一个数」的框架里**，第三次才跳出框架。**

**⇒ 判据：同一个问题改了两版还不对时，别改第三版 —— 先问「这个问题的正确形式是什么」。
⇒ 形式错了，任何数值都不会对。**
