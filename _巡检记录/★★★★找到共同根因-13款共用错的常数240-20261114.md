# ★★★★ 找到共同根因：**`13` 款共用 `Math.max(240, …)` 这个错的下限** —— 自适应算法从未生效

> `2026-11-14 13:2x`。从「`14` 款棋盘只露 `1`–`2` 行」追到一行代码。**这可能是今天最有价值的一个发现。**

## 一、怎么找到的

1. 普查发现 `14` 款「棋盘只露 `1`–`2` 行」（`Crown` / `Skyscrapers` / `Hitori` …）
2. 问「它们有几款**已经有**封顶而没生效」⇒ **`14/14` 全都有**（各 `1` 处 `Math.min(Bp.width…Bp.height…)`）
3. ⇒ 不是 `14` 个独立问题，是**一个共同根因**
4. 读 `GSkyscrapers.ets:749`：
   ```ts
   .width(Math.min(Bp.width - 2 * Space.lg, Math.max(240, Bp.height - 360)))
   ```
5. **`max(240, …)` 的 `240` 是下限** ⇒ 在这块屏上它把计算结果顶掉了

## 二、算术

```
Bp.height = 533vp
Bp.height - 360 = 173vp        ← 「按可用高度算」的正确值
Math.max(240, 173) = 240vp     ← 下限把它顶成了 240
Math.min(853 - 40, 240) = 240  ← 宽度没超，所以取 240
⇒ 盘面 = 240vp
```

**⇒ 也就是说：那个「按高度自适应」的算法，**在这块 `533vp` 的屏上从未生效过**。
它只在 `Bp.height - 360 ≥ 240`（即 `Bp.height ≥ 600vp`）时才起作用 —— **而手机是 `533vp`。**

**⇒ 这是个「在高屏上验证、在矮屏上退化」的典型：下限 `240` 是为「别太小」设的，
但它同时**取消了「放不下就更小」的能力**。**

**⇒ 这些款写成了 `240`。**

## 四、为什么 `240` 一定错（不需要真机就能断定）

**判据 `2044`（先算比值）：**

```
盘面预算 = 533 - 104(头部) = 429vp
而「头部 104 + 统计/按钮/线索 ≈ 200 + 盘面 240」= 544vp > 533vp
⇒ 必然溢出
```

**⇒ 更直接的：`max(240, …)` 意味着**盘面永远 ≥ 240vp**，
而 `240 + 104 = 344vp`，只剩 `189vp` 给其余所有元素。
`Skyscrapers` 还有：`AI 代打` 按钮 + 三个统计 + 顶部线索行 + 侧边线索 ⇒ **`189vp` 不够。**

**⇒ 所以`240` 这个下限本身就不成立，不是「稍微大一点」。**

## 五、修法（一行，但值要定）

**形态：`Math.max(240, Bp.height - 360)` → `Math.max(<新值>, Bp.height - 360)`**

| 候选新值 | 手机上的结果 | 判断 |
|---|---|---|
| **`140`** | `max(140,173) = 173vp` ⇒ 盘面 `173vp` | ✅ **与已验证样板一致** |
| `120` | `173vp`（同样被 `173` 主导）| ✅ 效果同 `140` |
| `0` | `173vp` | ⚠️ 极小屏会过小 |

**⇒ 在手机上，只要新值 ≤ `173`，结果都是 `173vp`。
⇒ 所以改 `140`（样板值）在这一代手机上与改 `0` 等效，但保留了「极小屏别太小」的保护。**

**⚠️ 但「`173vp` 够不够」还要真机验：**
`Skyscrapers` 有额外的顶部线索行 + 侧边线索列 ⇒ 它的盘面可能该比 `173` 更小。
**⇒ 而那需要看「线索占多少」，只能真机量。**

## ⇒ 判据（`2129`）

**「下限」（clamp floor）是一种**隐藏的自适应杀手**：
它平时看不出来，只在「算出值 < 下限」时默默顶掉正确结果 —— **而那恰好是「空间不够」的时候，
也就是最需要自适应的时候。**

**⇒ 判据：写 `Math.max(下限, 自适应计算)` 之前，问「下限会不会正好吃掉自适应」。
若下限比典型自适应值还大，那这条自适应就是死的。
⇒ 附带做法：把下限设成「明显小于任何可能算出的值」（如 `140` vs `173`），
这样它只在极端情况下生效。**

## ⇒ 判据（`2130`）

**「`14` 个问题」和「`1` 个问题出现 `14` 次」在表面上完全一样。**
**区分它们的唯一办法：去找那 `14` 个实例的**代码**是否同源（这次 `grep` 一个模式就找到了）。**

**⇒ 判据：面对「一批同现象」，先 `grep` 它们的关键写法是否一致。
若一致 ⇒ 是一个 bug 的 `N` 次复制，修一处、验一处、再批量。
若不一致 ⇒ 才是 `N` 个独立问题。**
