# ★★ 重启占掉 `44%` 的窗口；把 `--every 8` 改成 `12` 能省 `42` 分钟 = 多跑 `16` 款

> `2026-11-14 10:4x`。**代码已冻结，只记不改。** 这是明天（或下一轮）最便宜的一项优化。

## 一、两个「重启」是分开的，之前我只算了一个

| 重启类型 | 位置 | 频率 | 单次成本 |
|---|---|---|---|
| **App 重启**（`force-stop` + 双 `start`）| `shot_game.py:449-472` | **每款一次** | **`34.8s`** |
| **模拟器重启**（`-stop` / `-start`）| `verify_layout.py:restart_emu` | **批内每 `--every` 款 + 每批边界** | **约 `2` 分钟** |

## 二、模拟器重启次数的算式

```
总重启 = 批数 × (批内重启 + 1)
        批数     = ceil(245 / 批大小)
        批内重启 = floor((批大小 − 1) / every)
```

| 批大小 | `every` | 批数 | 批内重启 | **总重启** | **耗时** |
|---:|---:|---:|---:|---:|---:|
| `40` | `8` | `7` | `4` | `35` | `70` 分钟 |
| **`12`** | **`8`（当前）** | `21` | `1` | **`42`** | **`84` 分钟** |
| **`12`** | **`12`** | `21` | **`0`** | **`21`** | **`42` 分钟** |
| `8` | `8` | `31` | `0` | `31` | `62` 分钟 |
| `16` | `16` | `16` | `0` | `16` | `32` 分钟 |

**⇒ 我先前把批 `40→12` 的代价估成「多 `14` 次重启 ≈ `28` 分钟」；实际是多 `7` 次 ≈ `14` 分钟。**

## 三、当前配置下，重启总共吃掉多少

| 项 | 分钟 | 占 `6.6h` 窗口 |
|---|---:|---:|
| App 重启（`153 × 34.8s`）| **`88.7`** | **`37%`** |
| 模拟器重启（`42 × 2min`）| **`84`** | **`35%`** |
| **合计** | **`173`** | **`72%`** |

**⚠️ 但两者部分重叠**：模拟器重启的那段时间里，App 不必重启（批内第一款的 App 重启发生在模拟器就绪后）。
**⇒ 保守估计：重启相关开销占窗口 `40%`–`50%`，即 `2.6`–`3.3` 小时。**

## 四、最便宜的优化：`--every 8` → `--every 12`

**改动**：`sweep_all.sh` 里 `python3 工具/verify_layout.py --every 8` → `--every 12`。

**效果**：批内不再重启（`12` 款一批、`every 12` ⇒ `floor(11/12)=0`），
**只剩批边界** ⇒ 总重启 `42 → 21`，**省 `42` 分钟 ≈ 多跑 `16` 款**。

**风险**：`every 8` 是判据 `1923b` 定的「每 `8` 款重启一次」。放宽到 `12` 会拉长两次重启的间隔。
**⚠️ 但 `verify_layout.py` 还有一条「连续 `2` 款失败立刻换设备」的**症状触发重启**（`:107-112`）
⇒ 真出问题时不用等节拍到 `12` 款。**
**⇒ 所以 `12` 是安全的：症状兜底还在。**

**⚠️ 为什么不用 `16`**：批 `16` 虽然只要 `32` 分钟重启，但 `06:45` 检查的越界粒度变成 `16 × 155s = 41` 分钟（现在是 `31` 分钟）。
**⇒ 用 `42` 分钟换 `10` 分钟更准的收工，不值。**

## 五、什么时候改

**今晚不改**（判据 `2079`/`2080`：代码冻结，保持可复算）。
**⇒ 明晚窗口一起改**（它和那 `11` 处编辑不冲突：一个是工具参数、一个是游戏代码）。

**验证方式**：改完跑 `--dry` 看批数与执行顺序不变，且 `grep -c "every 12"` 命中 `1` 处。

## ⇒ 判据（`2081`）

**「有几种开销」要分开数，别把它们混成一个「固定开销」。**
今天我先只看到 App 重启（`34.8s/款`），后来才看到模拟器重启（`2min × 42`）——
**两者加起来接近窗口的一半，而任何一项单独看都不刺眼。**

**⇒ 判据（`2082`）：一个「参数」改动（这里是批大小）会连带改变**别的计数**（这里是重启次数）。
改之前把「依赖这个参数的所有计数」列出来，逐个算新值 —— 否则会像我今天这样，
把「省 `70` 分钟越界」的收益，配上一个「多 `14` 分钟重启」的代价，却只估对了其中一半。**

# 六、复核「模拟器重启约 `2` 分钟」这个数，并做整体交叉验证

## 代码粒度：`15s`

```python
subprocess.run('-stop …', timeout=90); time.sleep(5)
Popen('-start …')
for _ in range(24):
    time.sleep(15)          # ← 先睡 15s 再查
    if _dev(): return       # ← 一活立刻返回
```

**⇒ 单次耗时 = `5 + 15k` 秒（`k` = 第几次轮询才发现活着）。**
**`2` 分钟 = `5 + 15×8 = 125s` ⇒ 与注释的估计一致。**
**上限是 `5 + 15×24 = 365s ≈ 6` 分钟（设备一直起不来时）。**

## 交叉验证：把两项重启代进昨夜实测

昨天（`11-14`）的配置是 **批 `40` + `every 8`** ⇒ 按前面的算式 **`35` 次模拟器重启**。

| 项 | 分钟 |
|---|---:|
| App 重启（`153 款 × 34.8s`）| **`88.7`** |
| 模拟器重启（`35 次 × 125s`）| **`72.9`** |
| **合计** | **`161.6` = `2.69` 小时** |
| 昨夜墙钟跨度 | `6.59` 小时 |
| **⇒ 扣掉重启后的「真实干活」** | **`3.90` 小时 ÷ `153` 款 = `92` 秒/款** |

**⇒ `92s` 用于「dump + 搜索 + 点击 + 读图」，量级合理。**

**⇒ 这说明整个时间模型是自洽的：`155s/款 = 34.8s App重启 + 约 27s 均摊的模拟器重启 + 92s 干活`
（`34.8 + 27 + 92 ≈ 154`，与 `155` 差 `1s`）。**

**⇒ 顺带确认：`every 12` 那项优化（`42 → 21` 次重启）在昨夜配置下等价于
「`35` 次 → `7` 次」，能省 `28 × 125s = 58` 分钟 —— 比我先前说的 `42` 分钟还多。
（因为昨夜是批 `40`，现在是批 `12`，两者基准不同，比较时要看清。）**

## 一个次要优化（记档，不做）

**`15s` 的轮询粒度本身有浪费**：设备若在第 `16` 秒活，要等到第 `30` 秒才发现。
**改成 `3s` 轮询** ⇒ 每次最多省 `12s` × `42` 次 ≈ **`8` 分钟**。
**⇒ 收益只有 `every 12` 那项的 `1/5`，不值得为它改代码。**

## ⇒ 判据（`2083`）

**验证一个「耗时估计」最好的办法，不是重读代码，而是**把它代进一次真实测量里看是否闭合**。**
这次：`34.8 + 27 + 92 = 154 ≈ 155`，三个独立来源的数能对上，说明模型没有大漏洞。
**⇒ 反过来说：如果代进去差得远（比如算出 `200s` 或 `80s`），那一定是某一段被漏算了 —— 
这比逐个校验每个数快得多。**

# 七、第二个优化候选：把 `sleep(25)` 改成「轮询到就绪」

**⚠️ 今晚不改、明天也先不改 —— 这条风险明显高于 `every 12`。记档是因为它是剩下最大的一个杠杆。**

## 现状（`shot_game.py:462-469`）

```python
sh('aa start -a EntryAbility -b com.andrewoscar.onemore')
time.sleep(25.0)                                            # ← 固定 25s
sh('aa start -a EntryAbility -b com.andrewoscar.onemore')   # 判据 1954：第二次 start
time.sleep(8.0)                                             # ← 固定 8s
```

**⇒ 每款固定 `33s`，不管 App 起得快不快。**

## 为什么 `25` 和 `8` 是这两个数

- **`25`**：判据 `1949` 原文「App 冷启动要 **30~60s**」—— 原来 `6×3s=18s` 不够，
  `dump` 只拿到状态栏 `['03:11','100']` ⇒ 误报 `NOT_HOME`。**⇒ `25` 是「比 `18` 稳」的经验值。**
- **`8`**：判据 `1954` —— `force-stop` 后 `dumpLayout` 会抓不到 App 窗口，
  **必须再发一次 `aa start`**。那 `8s` 是给第二次 `start` 之后留的余量。

## 若改成轮询，能省多少

**做法**：把 `sleep(25)` 换成「每 `3s` dump 一次，看到 App 窗口就继续；最多 `25s`」。

| 假设冷启动实际耗时 | 每款省 | 一夜（`153` 款）|
|---|---:|---:|
| `10s` | `15s` | **`38` 分钟** |
| `15s` | `10s` | `26` 分钟 |
| `20s` | `5s` | `13` 分钟 |
| `≥25s` | **`0`** | **`0`** |

**⇒ 收益完全取决于「冷启动实际有多快」，而这个数**我没有**（`elapsed_s` 是整款耗时，不含分段）。**

## 为什么它比 `every 12` 危险

1. **`every 12` 只改一个「多久重启一次」的节拍**，重启动作本身不变，且还有「连续 `2` 款失败立刻换设备」兜底
2. **这条改的是「App 起没起好」的判定**。若判定错了（比如 dump 抓到了状态栏就当成起了），
   后面所有步骤都在半启动的 App 上跑 ⇒ **`CANNOT` 类型的大面积失败**，而且**看起来像「游戏有问题」**
3. **判据 `1954` 的「第二次 `start`」依赖「第一次已经起完」这个前提**。轮询若在「半起」时就认为好了，
   第二次 `start` 可能变成「对已经在跑的 App 再 start 一次」—— 行为未知

## ⇒ 要做它，必须先拿到「冷启动分段耗时」

**最小的取证方法**（下次有真机时，`5` 分钟）：
```bash
# 计时：从 aa start 到 dump 能拿到 App 窗口
T0=$(date +%s); aa start -a EntryAbility -b com.andrewoscar.onemore
while :; do
  if dump 里出现 'One More' 或 'All'; then echo "$(( $(date +%s) - T0 ))s"; break; fi
  sleep 1
done
```
**⇒ 跑 `10` 次取分布，才敢把 `sleep(25)` 换成轮询。**

## 两个优化候选的优先级

| # | 优化 | 省 | 风险 | 何时做 |
|---|---|---:|---|---|
| **1** | **`--every 8` → `12`** | **`42` 分钟** | **低**（有症状兜底）| **明晚** |
| 2 | `sleep(25)` → 轮询 | `0`–`38` 分钟（取决于冷启动）| **高**（判定错误会大面积假失败）| **拿到分段数据后** |

## ⇒ 判据（`2084`）

**优化一个「等待」之前，先分清它是「等一个已知会完成的事」还是「等一个可能不完成的事」。**
- `25s` 等的是**确定会起来的 App** ⇒ 可以用轮询替代（只要判定可靠）
- 但**判定「起来了」比「等够时间」难得多** —— 后者只是慢，前者错了会静默地把后续步骤放在错的状态上跑

**⇒ 判据（`2085`）：一个保守的固定等待，本质上是「用可预测的慢，换掉不可预测的错」。
要动它，先证明「判定就绪」这件事有可靠的信号，而不是先算它能省多少时间。**
