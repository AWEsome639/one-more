# 判据 `3092`：**这台机器内存极小，`nohup … &` 起的构建会被 jetsam 杀掉**

## 一、实测内存

```
free      4701 pages  ≈ 0.07 GiB
wired   129395 pages  ≈ 2.0 GiB
active  126070 pages  ≈ 1.9 GiB
RSS 合计      4.0 G     进程 454 个
swap      2893M / 4096M 已用
```

⇒ **`wired` 一项就吃掉 `2.0 GiB`，整机 RSS 才 `4.0 G`。** 这台机器长期在 swap 里挣扎。

## 二、三个后台任务全被 `SIGKILL`

```
bash-4f58655… finished [killed, SIGKILL]
bash-e5ecb82… finished [killed, SIGKILL]
bash-df4e758… finished [killed, SIGKILL]
```

⇒ 全部是 `nohup … &` 起的构建/测量链。**内存一紧就被系统杀。**

## 三、今晚被这条解释掉的所有怪事

| 现象 | 我当时的判断 | 真相 |
|---|---|---|
| `BUILD SUCCESSFUL in 1 s` 但 HAP 没变 | 「构建缓存没失效」 | **构建被杀，旧包留着**（`3089`）|
| `clean` 重建后字节完全一样 | 「改动没进源码」 | **那次 clean 构建根本没跑完** |
| 改完常数一测毫无变化（`230→561→577`）| 「那个 `.width()` 不是约束」| **改动没进包**（判据 `3091` 的结论要打折）|
| 一次构建 `12`–`35` 分钟 | 「机器慢」 | swap 抖动 |

## 四、怎么办

1. **构建必须前台跑**（带 `timeout`），⛔ 不要 `nohup … &`
2. **每次构建后核对 HAP 字节 + mtime** —— 两者都没变就是没构建
3. **构建前先停模拟器**（省 `2`–`3 GiB`），构完再起
4. **不要同时跑两个重活**（一个构建 + 一个测量就会互相挤死）
5. 内存紧时优先怀疑**机器**，不要怀疑代码

## 五、判据

> **「改动没生效」先分三种：没改上（编辑丢了）、没编译（构建被杀）、没生效（逻辑不对）。**
> 今晚我三次都直接跳到第三种去改逻辑，浪费了三个构建周期。

⇒ 四条：
1. **改完立刻 `grep`/`git diff` 确认落盘**（这次就是这一步没做，被 background kill 吞了）
2. **构建必须前台**；后台构建在这台机器上不可靠
3. **构建结果以 HAP 字节 + mtime 为准**，不以日志里的 `BUILD SUCCESSFUL` 为准
4. **先排除机器因素**（内存/swap/进程被杀）再怀疑代码
