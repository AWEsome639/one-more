# ★★ 最大单项时间成本：**每款开工前重启 App，纯等待 `34.8s`** —— 一整夜 `1.48` 小时

> `2026-11-14 11:2x`。读 `shot_game.py:449-472` 发现。**这是整条管线里最贵的一段，之前所有时间估算都没把它单列。**

## 一、事实

`_body(name, t0)` 的**开头**就是（每款都跑）：

```python
sh('uitest uiInput keyEvent Home'); time.sleep(0.8)
sh('aa force-stop com.andrewoscar.onemore'); time.sleep(1.0)
sh('aa start -a EntryAbility -b com.andrewoscar.onemore')
time.sleep(25.0)                       # 判据 1949：冷启动 30~60s
sh('aa start -a EntryAbility -b com.andrewoscar.onemore')   # 判据 1954：二次 start
time.sleep(8.0)
```

**⇒ 纯等待 `0.8 + 1.0 + 25 + 8 = 34.8s`，不含 `aa start` 本身的耗时。**

## 二、为什么这样做（不是随便加的）

代码注释写清了，是三次踩坑换来的：
- **判据 `1920`**：结算弹层没有可点关闭件时 `Back` 永远被吃 ⇒ **只有重启能回初始态**
- **判据 `1921`**：`Back` 会把 App 退到系统、把「设置」拉到前台 ⇒ 之后 `is_home()` 永远假
- **判据 `1949`**：冷启动要 `30~60s`，原来 `6×3s=18s` 不够 ⇒ `dump` 只拿到状态栏 ⇒ 误报 `NOT_HOME`
- **判据 `1954`**：`force-stop` 后 `dump` 抓不到 App 窗口 ⇒ **必须二次 `aa start`**

**⇒ 这是「用时间换确定性」的刻意设计，不是浪费。**

## 三、但它占了多少

| 项 | 值 |
|---|---:|
| 每款重启等待 | **`34.8s`** |
| 一夜 `153` 款 | **`88.7` 分钟 = `1.48` 小时** |
| 占 `6.6h` 窗口 | **`22%`** |
| 相对单款 `155s` 墙钟 | **`34.8 / 155 = 22.5%`** |

**⇒ 单款 `111s` 的构成大致是：`35s` 重启 + `76s` 读图/搜索/点击/dump。**

## 四、能优化吗（今晚不做，给出量化前景）

**当前**：无条件重启 —— 每款都付 `35s`。

**可能的优化**：**先试 `Back` 回到首页；回到了就跳过重启。**
- 若 `60%` 的款能靠 `Back` 回首页 ⇒ 省 `0.6 × 153 × 35s = 53` 分钟/夜
- **⇒ 按 `155s/款` 折，多跑约 `20` 款/夜**

**⚠️ 但风险是实打实的**：`NOT_HOME`（`15%` 失败率的**主因**，今天刚定位到路径 C 弱于 A）**正是「`Back` 回不去」造成的**。
**⇒ 把兜底从「无条件重启」改成「先试 `Back`」，等于把失败率重新引回来。**

**⇒ 正确的做法不是「跳过重启」，而是「缩短重启」**：
- `sleep(25)` 是「冷启动最坏情况」的保守值。**若实测大多在 `10s` 内起好，可改成「轮询 `is_home()`，最多 `25s`」** ⇒ 多数款可能只等 `10s`，省 `15s/款` = `38` 分钟/夜
- 这需要真机数据（冷启动实际分布），**明早从新台账的 `elapsed_s` 能反推一部分**

## 五、对今晚的影响

**今晚不改。** 但**知道这一项存在，今晚看 `elapsed_s` 时分得清**：
- 若某款 `elapsed_s` 只有 `40s` ⇒ 说明它**很早就失败了**（重启后就挂了）
- 若某款 `elapsed_s` 接近 `260`（`BUDGET_S`）⇒ 它在搜索/点击环节耗尽了预算
- **若整轮 `elapsed_s` 中位数远高于 `104`（历史中位）⇒ 说明重启段变慢了**（设备慢或负载高）

**⇒ 判据（`2075`）：一个管线里最贵的那一段，往往不在「算法」里，而在「为了确定性而加的等待」里。
先量清它占多少（这次 `22%`），再决定动它 —— 而且要先想清「它当初是为了防什么」。**
