# ★ 我今天的推送纪律偏差：`109` 次用 `git push` 而没核对

> `2026-11-14 12:2x`。**目标文本明写「`push_and_verify.sh` 推送」，我整天用的是裸 `git push` 并只看回显。**

## 一、`push_and_verify.sh` 存在，且它不是画蛇添足

它的文件头（判据 `625`，第 `1230` 轮）写着：

> 本机 SSH 到 GitHub 是**间歇性**的：实测直连 `10` 次 ✅`7` / ❌`2` / ⚪`1`
> （`Permission denied (publickey)` 与空输出交替出现）
> ⇒ 两个坑：
> ① **`git push` 失败时可能也返回 `0`**（连接中途断开但已传完对象）
> ② `git ls-remote` 失败时返回**空字符串** ⇒ 老判定 `[ "$LOCAL" = "$REMOTE" ]` 里 `$REMOTE` 为空 ⇒ 误判「没推送」
> ⇒ 正确做法：**重试到拿到非空 SHA**，再与之比较

**⇒ 也就是说：`git push` 的退出码与回显，**都不足以证明同步**。
而我这 `109` 次提交，每次都是看「`To github-awasome:...` + 分支范围」就当成功了。**

## 二、实际核对结果：**这次真的同步了**

```
本地 HEAD: 39f7e3164080d05202ab7434e132e71b2e6575e3
远端 main: 39f7e3164080d05202ab7434e132e71b2e6575e3
✅ 真同步
```

**⇒ `ls-remote` 拿到的是分支尖端；尖端一致 + 历史线性追加 ⇒ `109` 次提交都在远端。**

**⇒ 这次没出事，但**是运气**，不是流程。**

## 三、正确的做法（从下一次起）

```bash
LOCAL=$(git rev-parse HEAD)
REM=""
for i in 1 2 3 4 5; do
  REM=$(git ls-remote origin refs/heads/main 2>/dev/null | awk '{print $1}')
  [ -n "$REM" ] && break
  sleep 2
done
[ -n "$REM" ] && [ "$LOCAL" = "$REM" ] && echo "✅ 真同步" || echo "❌ 未同步"
```

**或者直接用 `bash 工具/push_and_verify.sh`（它就是干这个的，`15` 次重试）。**

## ⇒ 判据（`2095`）

**「命令返回 `0`」与「结果真的发生了」是两件事，凡是**跨网络**的操作都必须分开验证。**
- `git push` 返回 `0` ⇒ 可能只是「对象传完了但引用没更新」
- `git ls-remote` 返回空 ⇒ 可能是**查询失败**而不是「远端没有」

**⇒ 判据：跨网络的操作，验证方式必须是「再去读一次对方的状态」，
而不是「看这次命令自己说什么」。**（这与判据 `2040`「找唯一出口」是同一类：
**别信过程的自述，去读结果的实体。**）
