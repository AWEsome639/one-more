## 0 一句话

**不是「3 个弱 tag」的问题，是整套 tag 系统只有 ~1.5 个独立维度。**
25 个 tag 里有 **3 对完全重复**（`pausable≡untimed` / `focus≡memory` / `brainy≡hard`）、**4 个是类别的别名**（`calc`=MATH 100%、`word`=WORD 100%、`space`=SPATIAL 100%、`memory`=MEMORY 100%）、**时长/难度/脑力三组直接按类别生成**。
⇒ **355 款在筛选器眼里只剩 62 种不同的样子，最大的一组 54 款完全不可区分**（三消、发射消泡、三连是同一组）。
⇒ 所以 ChatFinder 的天花板不是“某几个 tag 太肥”，而是**tag 本身的信息量 ≈ 类别字段**，而类别本来就已经 +40 直接用了。

## 5 结构性冗余（根因：`tools/gen_tags.py` 的生成规则）

### 5.1 三对 tag **完全相同**（不是“相似”，是同一批游戏）

| 对 | 款数 | 生成原因（代码） |
|---|---|---|
| `pausable` ≡ `untimed` | 323 | `gen_tags.py:183-184` 同一个 `else` 分支里**连续 add** ⇒ 必然相同 |
| `focus` ≡ `memory` | 74 | `gen_tags.py:69-77` `CAT_ATTR['MEMORY'] = ['memory','focus']` ⇒ 必然相同 |
| `brainy` ≡ `hard` | 58 | `gen_tags.py:193-194` `if 'hard' in t: t.add('brainy')` ⇒ 必然相同 |

### 5.2 九个「子集」关系（一方完全包含另一方 ⇒ 等于白加）

`calc ⊂ normal`(59/249)、`word ⊂ normal`(53/249)、`speed ⊂ normal`(22/249)、
`cozy ⊂ pausable`(18/323)、`drag ⊂ pausable`(15/323)、`zen ⊂ pausable`(14/323)、
`cozy ⊂ untimed`、`drag ⊂ untimed`、`zen ⊂ untimed`（后三对同前，因 pausable≡untimed）。
⇒ **场景组里有 2 个（`cozy` 18、`zen` 14）是 `pausable` 的子集** —— 选它永远不会筛掉任何「可暂停」的款；
> 另外 `speed`(22)、`calc`(59)、`word`(53) 是 `normal` 的子集 ⇒ 同理，「普通难度」这条也筛不掉它们。

### 5.3 三组 tag **直接由类别生成**（等于类别字段的复述）

| 组 | 生成规则 | 后果 |
|---|---|---|
| 时长 | `gen_tags.py:145` `cat=='LOGIC'`→long；`:148` `cat in (MATH,MEMORY,WORD)`→short；`:150` else→medium | **时长 = f(类别)**，6 类映射到 4 档 |
| 难度 | `:158` `cat=='LOGIC'`→hard；`:160` `cat in (MATH,MEMORY)`→normal；`:164` `cat=='CLASSIC'`→easy | **难度 = f(类别)**，`normal` 自然吃到 70% |
| 脑力 | `:69-77` `CAT_ATTR[类别]` | 5 个 tag 是类别的 1:1 别名（`calc`/`word`/`space`/`memory` 各 100% 落在单类） |

⇒ 这就是「时长×脑力交叉表」里 `short` 与 `logic` 共现 **0 款**的原因（不是设计，是**两个 tag 都从类别推出来的**，互斥是构造出来的）。

### 5.4 三个「死查表」（ChatFinder 引用了数据里不存在的 tag）

| 查表 | 数据里存在吗 | 后果 |
|---|---|---|
| `g.tags.indexOf('multiplayer')` | **0 款**（25 个 tag 里没有它） | 「联机/对打/朋友」**永远返回 0 个结果** |
| `g.tags.indexOf('board')` | **0 款** | 靠后面的「名字含棋/牌」兜底（13 款），但这条永远不生效 |
| `g.tags.indexOf('quick')` | **0 款** | 已被 `short|timed` 兜住（`ChatFinder.ets:213` 的 `quick` 分支永远不命中，代码注释 `:210-212` 也承认了） |

## 7 `playStyle` 可行性：**现有 tag 推不出来**，必须人工建表

### 7.1 从现有 tag 推：**不可能**
25 个 tag 覆盖 6 个维度 —— 时长 / 难度 / 操作（**输入方式**）/ 节奏 / 脑力（**能力**）/ 场景（**氛围**）。
**没有任何一个描述“玩法动词”**。`tap` 是“怎么点”，不是“点了会怎样”。
§6 的 62 个签名已经把上限摆在明面上：**同签名 = 推不出区别**。

### 7.2 从代码自动推：**不可靠**（我试过）
用 11 个机制正则扫 355 个文件：

| 正则 | 命中 | 说明 |
|---|---|---|
| `setInterval\|requestAnimationFrame\|tick(` | **354/355** | 每个游戏都用了定时器 ⇒ 完全无区分度 |
| `push(` | **298/355** | 多数是数组 `push` ⇒ 误报 |
| `matchAt\|findMatch\|hasMatch` | **1/355** | 三消类根本不用这套命名 ⇒ 漏报 |
| `shoot\|fire\|bullet\|aim` | 4/355 | 同上 |

⇒ **正则级别的手段分不开“玩法机制”和“实现细节”**，因为 355 款是 8 个 agent 分头写的，命名没有共识。

### 7.3 从 id/名称关键词粗分：**最多覆盖 51%**
我按 10 个拟定的 playStyle 类，用 id+英文名关键词跑了一遍：

| 拟 playStyle | 粗分命中 | 例 |
|---|---|---|
| `fill-grid` 填格谜题 | 32 | kakuro / sudoku / akari / bridges |
| `word` 文字 | 37 | wordle / anagram / cryptogram |
| `memory` 记忆 | 35 | memory / n_back / corsi |
| `maze/path` 走格 | 23 | maze / path_finder / pipes |
| `match` 消除配对 | 11 | bejeweled / match3 / mahjong |
| `merge` 合并收敛 | 11 | 2048 / fibonacci_merge / collatz |
| `push/slide` 挪块 | 11 | sokoban / klotski / slide15 / hanoi |
| `reaction` 反应限时 | 15 | blink / go_no_go / stop_signal |
| `quiz/estimation` 估算答题 | 11 | fraction_match / angle_finder |
| `board` 棋类对抗 | 9 | gomoku / checkers / go9 |

**命中 182/355（51%），173 款这 10 类都不沾**（而且多类互相覆盖，实际可分性更差）。

### 7.4 结论与成本
**必须新增一组 `玩法`（playStyle）tag，人工建表。**
- 建议 **10 类**（上表），每款打 **恰好 1 个**（和 时长/难度/操作 一样是划分，不再是多标签）。
- 成本：`gen_tags.py` 加 10 条规则可自动覆盖 ~51%，剩下 **173 款**需人工过（按每款 5 秒 ≈ 15 分钟）。
- 收益：**62 个签名 → 62 × 10 ≈ 数百种**，ChatFinder 才第一次有能力回答「有没有像 2048 那样合并的」「三消类有哪些」。
