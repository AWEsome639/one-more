# 判据 3076：**交付完整性核查** —— 台账不记「代码里还剩什么」

## 一、为什么需要它

昨晚修了 `9` 款，每处都是**一行两行的常量改动**：
```typescript
Math.max(240, …)  →  Math.max(160, …)
'72%'             →  '32%'
34                →  24
```
这类改动的特点：
- **很容易被后来的回滚 / 批量替换 / cherry-pick 静默抹掉**
- **台账不会告诉你** —— 台账只记「量过什么」，不记「代码里还有什么」
- 一旦被抹掉，台账还会显示「已修好」（因为最后一次测量是在修好之后）

⇒ 所以需要一份**独立的、按特征串验证的**清单。

## 二、工具：`工具/check_deliverables.py`

`20` 条检查，每条是 `(标签, 文件, 必须出现的特征串, 判据号)`：

| 类别 | 条数 | 例子 |
|---|---|---|
| `2026-11-19` 修好的 `9` 款 | `12` | `Simon Command` 的 `1.4 * (Bp.height - 400) + 10` |


## 三、反向测试（`AGENTS.md` 的硬要求）

> **改完必须做反向测试 —— `1→0` 既可能是修对，也可能是检查失效。**

⇒ 把 `Kakuro` 那条的特征串故意改成 `Bp.height - 99999`：
```
退出码: 1（期望 1）
❌ 交付完整性：1/20 项缺失 —— 有改动被回滚或替换掉了
```
⇒ **它真的会报错**，不是「永远绿」的摆设。

## 四、当前结果

```
✅ 交付完整性：20 项全部在位
```

## 五、用法位置

1. **发布前**跑一次（比断言更直接：断言查「有没有破坏规范」，它查「改动还在不在」）
2. **回滚任何东西之后**跑一次（确认没连带抹掉别的）
3. **接手时**跑一次（快速了解「这版到底包含哪些修复」）

## 六、判据

> **「台账说修好了」与「代码里还是修好的」是两件事。**
> 前者靠测量，后者得靠特征串。

⇒ 三条：
1. **每一处交付都留一个「可搜索的特征串」** —— 注释里带上判据号，修 bug 时顺手加一条
2. **这类脚本必须做反向测试** —— 否则它可能一直在骗你
3. **它查的是「存在」，不查「正确」** —— 正确性仍归实测/截图；两者互补，谁都替代不了谁
