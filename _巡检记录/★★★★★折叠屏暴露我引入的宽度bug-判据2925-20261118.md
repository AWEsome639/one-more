# 折叠屏暴露了一个**我自己引入的**宽度 bug（判据 `2925`）

> `2026-11-18 19:32`。**工具修好后第一次在折叠屏上测，立刻抓出我 `gs()` 修复的缺陷。**

## 一、⇒ 我错在哪

**⇒ 我的 `gs()` 只按**高度**算格子：`(Bp.height - 预留) / 行数`。**
**⇒ 但格子是**方形**、一行有 `COLUMNS` 个 ⇒ 格子边长还必须满足 `边长 × 列数 ≤ 屏宽`。**

| 设备 | `byH` | 列数 | 实际占宽 | 屏宽 | 结果 |
|---|---|---|---|---|---|
| 手机 `2560×1600` | `84vp=252px` | 6 | `1512px` | `2560` | ✅ 一直没事 |
| **折叠屏 `2224×2496`** | **`184vp=552px`** | 6 | **`3312px`** | `2224` | ❌ **横向爆掉** |

**⇒ 修法：取「高度预算」与「宽度预算」的**较小者**：**
```ts
const byH = Math.floor((Bp.height - 280) / ROWS.length);
const byW = Math.floor((Bp.width - 80) / CELLS.length);
return Math.max(36, Math.min(byH, byW));
```

## 二、⇒ 证据（折叠屏 `2224×2496`）

| 指标 | 修前 | 修后 |
|---|---|---|
| `lowest` | 到屏底 `2496` | **`重开` `[62,1944][2162,2097]`** ⇒ 离屏底 `399px` |
| 格子宽 | 约 `540px`（6 列 = `3312px`，超出屏宽）| **约 `120px`（6 列正好铺满）** |
| 裁图 | 格子巨大、横向溢出 | **`6` 列完整铺满、纵向也在屏内** |

**⇒ 截图：`截图-折叠屏-TripleSequence-修好-1932.jpeg`。**

## 三、⇒ 手机侧**不需要重测**（算式可证）

**⇒ 手机上 `byH=84vp`、`byW=(853-80)/6≈128vp` ⇒ `min=84` ⇒ **与改前逐字相同** ⇒ 手机行为不变。**
**⇒ 这是「改一处、用算式证明另一处不受影响」的例子 —— 比再跑一次设备更快且更可靠。**

## 四、⇒ 同一修复已同步到另外三款

**⇒ `Trace Path`（`5` 列）、`Silhouette Match`（`gs` 与 `go`）、`Chimp Test`（`5` 列）都加上了宽度封顶 —— 它们目前在各设备上都放得下，但**统一加上防止将来再犯**。**

## ⇒ 判据 `2925`

**⇒ 「按高度算尺寸」只对**单列**元素成立。**多列方形元素必须同时按宽度封顶：**
```
边长 = min( (可用高 - 余量) / 行数,  (可用宽 - 余量) / 列数 )
```
**⇒ 而且**必须在至少两种宽高比的设备上验证** —— 手机（`1.6:1`）上永远发现不了，折叠屏（`0.89:1`）一测就爆。**

## 五、⇒ 顺带澄清：`blk` 在非手机屏上是**假阳性**

**⇒ 折叠屏上 `blk=6/3140px`，但 `lowest` 只到 `2097`、裁图也完整。**
**⇒ 原因：`blk` 的阈值 `GAME_BOTTOM+SLACK = 1516+24 = 1576` 是**按 `1600` 高的手机定死的** ⇒ 在 `2496` 高的折叠屏上，任何延伸到 `1576` 以下的元素都被算「溢出」。**

**⇒ ⇒ **`blk` 只在手机（`2560×1600`）上有意义**；换屏后必须改用「`lowest.y2` vs 屏高」或直接裁图判断（`2899` 的延伸）。**
