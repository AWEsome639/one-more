# 判据 3039：两款竖屏修复**横屏零退化**（配对数值，逐字相同）

## 一、为什么要做这件事

`Gravity Sort`（`3035`）与 `Perspective Shift View`（`3038`）的修法都是**只动非矮屏分支**：
- `Gravity Sort`：`Bp.isShort() ? 360 : 410` —— 只改了 `false` 那一支
- `Perspective Shift View`：新增 `maxWidth: Bp.height − (Bp.isShort() ? 200 : 600)` —— 横屏算出来 `333vp`

⇒ **两句都是「算出来安全」，但「算出来安全」不是证据。**
   奥森的标准是「真机截图 / **配对前后数值** / 换一台设备也成立」之一 ⇒ 必须实测。

## 二、怎么测

```
$ Emulator -stop onemore_fold
$ Emulator -start onemore7 -noWindow      # 2560×1600 = 853×533vp 横屏
$ hdc kill && hdc start && hdc tconn 127.0.0.1:5555
$ hdc install -r entry-default-signed.hap  # 含两处修复的同一个 HAP
$ DSH_EMU_INST=onemore7 python3 工具/verify_layout.py --names-file /tmp/land2.txt
```
⇒ **注意不设** `SHOT_SCREEN_*`（横屏用默认 `1600 / 1516 / 1584`）。

## 五、判据

> **「只改了 A 分支 ⇒ B 分支不受影响」是**推理**，不是**证据**。
> 交一次 `B` 分支的实测数值，成本只有一次测量（`~2` 分钟），但它是「换一台设备也成立」那条标准的唯一兑现方式。**

⇒ 三条：
1. **凡是用 `isShort() ? A : B` 写的改动，两个分支都要量** —— 哪怕数学上讲得通
2. **回归验证要对比 `lowest` 坐标，不只对比 `blk`** —— `blk=0` 可能掩盖版面位移；
   坐标逐字相同才能说「没动」
3. **横屏测量不要设 `SHOT_SCREEN_*`** —— 默认值就是横屏（`1600/1516/1584`）；
   设成竖屏常量会得出一堆假数据（`3031` 的坑）
