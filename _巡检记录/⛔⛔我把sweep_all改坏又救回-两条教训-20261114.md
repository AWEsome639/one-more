# ⛔⛔ 我把 `sweep_all.sh` 改坏又救回 —— 两条教训

> `2026-11-14 15:0x`。为了给「空基线静默跑 0 款」加守卫，我直接改了那个 `197` 行的编排脚本，改出了语法错。

## 一、⇒ 发生了什么

**`sweep_all.sh` 里 `except Exception: BASELINE = ''` ⇒ 空基线让 `if BASELINE and …` 短路 ⇒ 所有行都算「已测」⇒ 待测 `0` 款、脚本正常退出（静默跑 0 款）。**

**⇒ 我想在里面加 `sys.exit(3)` + bash 侧检查 `$?`。**
**⇒ 结果：插入点落进了 heredoc 里面 ⇒ 第 `198` 行 `unexpected end of file`。**

**⚠️ 而更危险的是：我用 `bash -n "$f" && echo "✅"` 这种写法核对，失败时「✅」不打印、但**后续步骤继续跑**，我差点没注意到脚本已经坏了。**

## 二、⇒ 怎么救回来的

**`git checkout -- 工具/sweep_all.sh` ⇒ `bash -n` 过、干跑恢复「已测 144 / 待测 245」。**

**⇒ 然后改用**不动那个脚本**的办法：在 `run_tonight.sh` 的第 `5` 步之前加**
```bash
[ -f "$HAP" ] || fail 5 "HAP 不见了 ⇒ sweep_all 会空基线、静默跑 0 款 ⇒ 拒绝进入跑批"
```
**⇒ 复杂脚本一字未动（`git status` 里 `sweep_all` 改动数 `0`）。**

## 三、⇒ 全量复核（改完之后必做）

| 检查 | 结果 |
|---|---|
| **`10` 个 shell 脚本 `bash -n`** | **全 ✅** |
| **`8` 个 Python 工具 `py_compile`** | **全 ✅** |
| **① `final_check`** | **退出码 `0`、「全部就绪」** |
| **② `sweep_all --dry`** | **已测 `144` / 待测 `245`** |
| **③ `apply_a_batch --dry`** | **成功 `10` / 失败 `0`** |

## ⇒ 判据（`2553`）

**改一个几十行以上的编排脚本，优先考虑「能不能不改它」——**
**⇒ 在调用方加一道检查，往往比在被调用方内部插逻辑更安全（调用方的结构简单、插入点明确）。**

**⇒ 判据：修 bug 先找**最外层的能拦住它的地方**，而不是最贴近出错点的地方。**

## ⇒ 判据（`2554`）

**`bash -n "$f" && echo "✅"` 这种写法，失败时只是不打印 ✅、**不会中断后续命令**。**
**⇒ 我差点因此漏掉「脚本已坏」。**

**⇒ 判据：验语法要用 `if bash -n "$f"; then …; else …; fi`，让失败走显式分支；不要用 `&&` 链 + 只打印成功。**

## ⇒ 判据（`2555`）

**而这次能救回来，是因为**改动前脚本已在 git 里、且改动后立刻发现问题**。**
**⇒ 若当时还叠着别的未提交改动，`git checkout` 就会把那些也一起丢掉。**

**⇒ 判据：动关键脚本前先确认工作树干净（或只改那一个文件），这样回滚是精确的。**
