# 📏 反向证伪测试的结果：模型精确命中，但暴露一条判读校准（`09:5x`）

**测法**：那 `33` 款走死码分支的（封顶固定 `140`–`240vp`），按模型「`104+cap+底部 ≤ 533`」**应该装得下**。
若它们在台账里 `blk>0`，模型即被证伪。

**结果**：`30` 款有台账数据，其中 **`19` 款 `blk>0`** —— 但**值全是 `1`–`3px`**：

| `blk` | 款数 | 例子 |
|---|---|---|
| `3px` | `4` | `Hitori` / `2048` / `Shikaku` / `Matrix Reasoning` |
| `2px` | `10` | `Gomoku` / `Crown` / `Dominosa` / `Gokigen Naname` / `Heyawake` / `Hitori All` / `Norinori` / `Path Intersect` / `Pipes` / `Skyscrapers` |
| `1px` | `5` | `Number Bonds All` / `Factor Finder` / `Memory` / `Countdown Math` / `Modulo Path` |

**⇒ 这不是证伪，是精确命中**：
模型说「封顶 `240` ⇒ 底部拿 `189vp`」（`533 − 104 − 240`），
而数据说「它们正好需要 `189`–`190vp`，于是超出 `1`–`3px`」。
**两边算的是同一件事，误差在 `3px` 内。**

且内容底边落在 `1577`–`1579`，**手势线在 `1584`** ⇒ 视觉上完全安全。

## ⇒ 今晚判读必须加这条校准

**`blk = 1`–`3px` 是噪声级（抗锯齿 / 整数取整），不是缺陷。**
真溢出是 `blk = 24` 以上那几个量级（`Snake3D 96px = 32vp`、`2048 曾 72px`…）。

**⇒ 若今晚看到 19 款 `blk=1~3px`，不要当成「19 款还没修好」。**
**它们的正确读法是：`cap 240` 这一族的底部预算已经用尽（`189/189`），再接任何内容就会真溢出。**

## ⇒ 顺带把 `A` 类的结论改精确

原来写「`A` 类 `33` 款全部装得下」——**更准确的说法是**：
「`A` 类封顶 `140`–`240vp`，底部预算 `189`–`289vp`；其中 `cap=240` 这一族已把预算用到 `189/189`，
表现为 `1`–`3px` 的噪声级超出；**功能上安全，但已无余量**」。

**⇒ 判据（`2037`）：`blk` 不是布尔值，是量级。`1~3px` 与 `24~96px` 是两类东西，
用同一个 `>0` 判据会把 `19` 款误判成没修好。**

**⇒ 这条预测的价值最高 —— 它检验的不是「某一款改得对不对」，是「`isShort` 这个机制本身在横屏下是否工作」。**

**补充（口径核对）**：`Bp.isShort()` 定义在 `Bp.ets:296` 是 `Bp.height < 420`，

**这与「矮屏」这个词的直觉相反 —— 横屏的 `533` 不是「矮」，但可用的垂直空间确实被头部吃掉。**

**⚠️ 这条必须今晚验：若 `8` 款仍 `≥1584`，则全库 `isShort` 降档都需要重新审视判据**

# ⛔ 撤回预测⑤的「机制空转」那半 —— `isShort()` 是 `< 690`，横屏生效

**我写「`Bp.isShort()` 是 `Bp.height < 420`，横屏 `533 > 420` ⇒ 全部空转」——错的，撤回。**

**错因**：`Bp.ets:296` 那个 `< 420` 是 **`narrowHeight()`**，**不是 `isShort()`**。
`isShort()` 在 `Bp.ets:299`，真实定义：

```ts
static isShort(): boolean {
  // ★★★ 2026-11-03（第 935 轮）620 → 690
  return Bp.height < 690 && !Bp.isTv();
}
```

**⇒ 横屏 `Bp.height = 533 < 690` ⇒ `isShort()` 为真 ⇒ `738` 处降档（涉 `334` 款）在横屏下是生效的。**

**⇒ 预测⑤的结论保留：那 `8` 款今晚应当过关。但理由改回原来那个**（它们早已有降档，台账数据是改动前的），
**不是「机制空转」。**

**⇒ 判据（`2038`）：同一个类里相邻的函数（`narrowHeight` / `isShort` / `isSm`）判据各不相同，
按名字猜语义必错 —— 我读的 `< 420` 是「只关心高度」的窄判据，`isShort` 用的是 `690`。**
**这是我今天第三次因「没读到定义就推断行为」而错**（前两次：`cov` 可信度、`@since` 版本号）。

## ✅ 但那段注释里有一条对目标第 ⑤ 项有用的真东西

`isShort()` 的实现里带着 `2026-11-13` 的一次修正记录：

> ★★★ **电视不该进「矮屏」分支** —— `1080p` 电视 `@dens2.0` ⇒ `px2vp(1080) = 540vp`
> ⇒ 原来会判成矮屏，于是**隐藏说明行、棋盘封顶、`Cell.of ×0.85` 整套「矮屏减法」都在电视上生效**
> ⇒ **越修越小，而 `10-foot UI` 恰恰相反（3 米视距需要更大）**

**⇒ 这就是目标「电视 `3` 米观感」的病根：电视被当成了矮屏，全套「减法」反着用。**

**而且它已经修了** —— 判据里加了 `&& !Bp.isTv()`。

**⇒ 所以第 ⑤ 项的电视一条，代码侧已完成，只差真机验证**（跑 `onemore_tv`、爬 3 米看观感）。
**⇒ 这也解释了为什么电视那项一直「看着像没做」：它是「做了但没验」，不是「没做」。**

**⚠️ 附带一个待验点**：`px2vp(1080) = 540vp` 这个数意味着电视横屏可用高度只有 `540vp`，
和手机横屏的 `533vp` 几乎一样 —— **两者可用垂直空间其实接近，差别在物理尺寸（3 米视距）。**
所以电视该做的是「放大元素」而不是「加更多内容」，这条与 `!isTv()` 的修法一致。
