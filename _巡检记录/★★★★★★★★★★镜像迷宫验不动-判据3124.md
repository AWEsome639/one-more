# 判据 `3124`：`镜像迷宫` 现在**测不动**（`TIMEOUT`），而它 `07:27` 刚测成功过

## 一、事实

```
07:27:28  Mirror Maze  OK  69.9s  lowest='◀' [62,2378][564,2496]  blk=1/24px blkh=118px
```

⇒ 那时是**正常测出来的**（`blkh=118px` 就是「四个方向按钮被切」的证据）。

改完 `360 → 380` 之后：

```
13:08  镜像迷宫  TIMEOUT  400.1s shot_game 超时

```

⇒ 试了两次（`400s` 与 `240s`、`--no-retry`），都是**导航阶段**超时，不是测量阶段。

## 二、最可能的原因（不是游戏坏了）

「`镜像`」**本身是一款游戏**（`Mirror Image`），而且它是「`镜像迷宫`」的**前缀**：

```
镜像        → Mirror Image
镜像迷宫    → Mirror Maze      ← 我要的
镜像描线    → Mirror Tracing
```

⇒ 测量工具是「在搜索框输名字 → 点匹配到的卡片」。
**如果它取的是「第一个包含该字符串的卡片」，就会打开 `镜像` 而不是 `镜像迷宫`**，
然后在错误页面上等一个永远不出现的标题 ⇒ `TIMEOUT`。

⇒ 这与判据 `2603` 同类：**「失败备注里含本该匹配的标题」⇒ 是测量判据的问题、不是游戏的问题**。

## 四、判据

> **名字是前缀关系时，「搜索 + 点第一个」会静默打开错的那款，而失败表现是「超时」——看起来像游戏坏了。**

⇒ 四条：
1. **`TIMEOUT` 不等于「游戏慢」**：可能根本没进对页面
2. **中文游戏名有大量前缀关系**（`镜像` / `镜像迷宫` / `镜像描线`；`西蒙` / `西蒙说` / `西蒙指令`）
   ⇒ 名单驱动的脚本必须**精确匹配**，不能用 `startswith` / `includes`
3. **同一款「以前能测、现在不能测」**，先怀疑**测量路径**变了（名字冲突、卡片排序、UI 改版），别先怀疑被测对象
4. **失败时要把当时的屏幕文字打进日志**（工具已有 `last texts`）—— 这次我没去读它，
   否则一眼就能看出「打开的是 `镜像` 而不是 `镜像迷宫`」
