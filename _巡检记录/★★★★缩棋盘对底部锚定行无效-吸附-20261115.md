# ★★★★ `Magnets`：缩棋盘**不会**把底部线索行推上来 —— 高度被布局吸收

> `2026-11-15 08:44–08:52` 真机三个档位实测。

## 一、⇒ 三档实测

| `MAG_CELL` | 棋盘高 | `lowest`（底部线索行）| `y2` | `blk` |
|---:|---:|---|---:|---|
| `52` | `211vp` | **不出现**（在屏外）| — | `2/48px` |
| `48` | `195vp` | `现 0`（右线索列）| `1355` | `2/48px` |
| `44` | `179vp` | **`4＋`**（底部线索行出现）| **`1600`** | `2/48px` |
| `40` | `163vp` | `3＋` | **`1597`** | `2/48px` |

**⇒ 从 `44` 到 `40`，棋盘少了 `16vp`（`48px`），而底部线索行只上移 **`3px`**。**

**⇒ 结论：缩棋盘省下的高度**被布局吸收了**，底部线索行**钉在屏底**。**

## 二、⇒ 为什么（与 `2599` 同构，只是竖着发生）

**`2599` 说的是「`layoutWeight` 会把父级 `space`/`padding` 的吸收掉」；这次是反过来：
外层 `Column` 按剩余空间分配，剩下的高度被某个 `layoutWeight`／`FlexAlign` 元素重新占满 ⇒ 线索行位置不变。**

**⇒ 所以对**底部锚定**的行，缩上方内容**不解决问题**；必须：**
1. **缩那一行自己的高度**（`CLUE_W = 44` 是它宽度与高度的共同常量 ⇒ 要拆开）
2. **或给父容器加 `padding({ bottom: N })`**（但今天在 `Factor Finder` 证明过：有 `layoutWeight` 子元素时父 padding 会被吸收）
3. **或把那行改成 `if (!Bp.isShort())` 隐藏**（若它只是辅助信息）

## ⇒ 判据（`2684`）

**「缩上方内容让下方内容上移」**只在下方内容不是底部锚定时成立**。**
**⇒ 判据：改之前先看「缩上方 N px 后，下方元素实际移动了多少」—— 若远小于 N，说明它被锚定/吸收，
    再缩只是白改（今天 `Magnets`：缩 `48px`、只移 `3px`，第 `4` 次白改）。**

## 三、⇒ `Magnets` 现状（诚实）

- **棋盘**：`4×4` 四行 + 右侧线索四格**全在**（`MAG_CELL` `52` 那版已截图验证；`44`/`40` 同样四行齐）
- **底部线索行**：`44` 起开始渲染、但**被切**（`y2` `1600`/`1597`）
- **`blk`**：始终 `2/48px`
- **代码**：`MAG_CELL = 40` + 父 Column 居中；HAP `46553112` 对齐

**⇒ 下次：改 `CLUE_W` 的**高度用法**（或给底部线索行单独一个更小的高度常量），**别再缩棋盘**。**

## 四、⇒ 又发现一层：那个 Row 的 `.height()` **也被忽略**

**后来我给棋盘 `Row` 加 `.height(4 * MAG_CELL + 3 + 24)`（`235vp`，把每列顶上的两行线索文字也算进去），
理论上有 `58vp` 余量。实测：**

```
MAG_CELL=52 + height 235vp ⇒ board=156x156、lowest='现 0' [819,1355][886,1397]、blk=2/48px
```

**⇒ 与「`MAG_CELL=52` + `height 211vp`」**一模一样**（`blk`/`lowest`/`board` 三项全同）。**

**⇒ 结论：这个 `Row` 的 `.height()` **也被忽略** —— 它的实际高度由**子元素**决定（4 个格子 + 每列顶上两行线索文字）。**

## ⇒ 判据（`2685`）

**`layoutWeight` 之外，还有一种情况让显式尺寸失效：**容器的尺寸由子元素内容撑开**（`Column`/`Row` 默认 `wrapContent`）。**
**⇒ 判据：`.height()`/`.width()` 无效时，先确认容器是否 `wrapContent`；若是，唯一杠杆是**改子元素的尺寸**，
    或给容器换一个不受子元素影响的定位（如绝对定位 / 外层再套一层固定尺寸）。**
**⇒ 今天 `Magnets` 三层同因：`layoutWeight`（子元素覆盖父级）→ 底部锚定（上方缩小不传导）→ `wrapContent`（显式高度被忽略）。**

## 八、⇒ 用 `path` 建树后：那 `48px` 是「贴边」，很可能不是真溢出

**按判据 `2686` 把 `/tmp/nodes-Magnets.tsv` 按 `path` 建树，`y2 > 1576` 的只有两个块：**

```
▼ Column  y2=1600  h=880  x=60-2500    ← 棋盘区容器（y=720 → 1600）
  父链：Column(2560x1399@0,117) → Column(2560x1030@0,381) → Column(2440x970@60,381) → Column(2440x880@60,720)
▼ Row     y2=1600  h=202  x=890-1670   ← 底部线索行（y=1398 → 1600）
  父链：同上的三个 Column → Row(780x202@890,1398)
```

**⇒ 两块底边都**正好 `1600`**（屏幕最底边）⇒ `blk` 的 `48px` = `(1600-1576) × 2`。**

**⇒ 这正是判据 `2639` 说的「`max=24` 有两种含义：贴边 / 真溢出被裁到 1600」——这里是**贴边**。**

**⇒ 也就是说：棋盘区被 `layoutWeight` 吃满剩余高度、底边钉在 `1600`；
   我缩棋盘省下的高度被它重新吃掉 ⇒ 底边永远回到 `1600` ⇒ `blk` 永远 `48px`。**
**（与判据 `2684` 同一件事：底部锚定的容器不会因为上方变小而让出空间。）**

## 九、⇒ 所以 `Magnets` 的真正修法只有两条

| 方案 | 做法 | 风险 |
|---|---|---|
| **A. 给棋盘区留底部留白** | 外层 `Column` 加 `.padding({bottom: 8})` | **`Factor Finder` 证明过：有 `layoutWeight` 子元素时父 padding 会被吸收 ⇒ 可能无效** |
| **B. 把棋盘区从 `layoutWeight` 改成固定高度** | `.height(...)` 显式 | **判据 `2685`：`wrapContent` 容器忽略显式高度；但这里是 `layoutWeight` 吃满，改成固定高度**可能**有效** |

**⇒ 下次先试 B（显式高度），因为它绕开了「父 padding 被吸收」的问题。**
