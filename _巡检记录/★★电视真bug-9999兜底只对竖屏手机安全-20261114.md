# ★★ 电视真 bug：`9999` 封顶兜底只在「竖屏手机」下安全

> `2026-11-14 10:2x`。**这是「换一台设备就破功」的典型，比 `1:11` 缩放失衡严重得多。**
> 起因：队友 `82fcab75` 把 `84` 处按可机械性分桶，B 类里 3 处 `: 9999` 哨兵被我抽查到。

## 一、现场（三处，原文）

```ts
// GKakuro:632       （注释自己写着「aspectRatio(1) 的棋盘」）
.constraintSize({ maxWidth: Bp.height < 600 ? Math.min(Bp.width - 2 * Space.lg, Math.max(140, Bp.height - 360)) : 9999 })

// GKakuroMini:562
.constraintSize({ maxWidth: Bp.height < 600 ? Math.min(Bp.width - 2 * Space.lg, Math.max(120, Bp.height - 360)) : 9999 })

// GShikaku:787
.constraintSize({ maxHeight: Bp.height < 600 ? Bp.height - 260 : 9999 })
```

## 二、`9999` 这个兜底为什么当年是安全的

设计意图显然是：**「矮屏才需要封顶；高屏（竖屏手机）让盘面自然铺满宽度就好。」**

竖屏手机：`360vp` 宽 × `780vp` 高。
**不封顶 ⇒ `aspectRatio(1)` 取可用宽度 `360vp` ⇒ 盘面 `360×360vp` ⇒ 完全放得下。**
（宽度本身就是天然约束，`9999` 等于「不管」但也不出事。）

## 三、电视上为什么炸

电视实例：**`1280vp` 宽 × `720vp` 高**（`4K@3840×2160 @density480 ⇒ ÷3`）。

| 判据 | 竖屏手机 `360×780` | **电视 `1280×720`** |
|---|---|---|
| `Bp.height < 600` | `780 < 600` = **假** | `720 < 600` = **假** |
| 走哪一支 | `9999`（不封顶） | **`9999`（不封顶）** |
| `aspectRatio(1)` 盘面边长 | 受宽度约束 = **`360vp`** | 受宽度约束 = **`1280vp`** |
| 屏幕高度 | `780vp` | **`720vp`** |
| 结果 | `360 ≤ 780` ✅ | **`1280 > 720` ⇒ 炸穿** |

**⇒ 根因一句话：`9999` 兜底隐含假设「高屏必然窄」，而电视是「又高又宽」。**
**⇒ 这个假设在 `355` 款里只在电视上破功 —— 正是「换一台设备也成立」这条证据要求要抓的东西。**

## 四、影响范围（精确）

**只有这 `3` 处**（`games/` 口径，模式 `Bp.height < 600 ? … : 9999`）。
其余 `81` 处是「矮屏小二选一」，最坏只是不够大，**不会炸**。

| 款 | 分支 | 电视上预期 |
|---|---|---|
| `GKakuro` | `maxWidth: … : 9999` | 盘面 `1280vp` 见方 ⇒ **严重溢出** |
| `GKakuroMini` | `maxWidth: … : 9999` | 同上，且它基线已收到 `120` ⇒ 更说明作者知道它大 |
| `GShikaku` | `maxHeight: … : 9999` | **更糟**：注释（判据 `1928`）明说 `aspectRatio(1)` 的棋盘 `maxHeight` **只裁不缩** ⇒ 连「裁」都没有 |

**⚠️ 未验**：`aspectRatio(1)` 是否真的作用在 `constraintSize` 的那个节点上。
`GKakuro` 的注释说它是，但**注释不等于代码**（今天第 `6` 次教训）。**⇒ 真机第一眼就该看这三款。**

## 五、修法（等真机确认后再动）

原则：**把「矮屏才封顶」改成「除竖屏手机外都封顶」，或干脆一律封顶。**

```diff
- maxWidth: Bp.height < 600 ? Math.min(Bp.width - 2*Space.lg, Math.max(140, Bp.height - 360)) : 9999
+ maxWidth: Math.min(Bp.width - 2*Space.lg, Math.max(140, Bp.height - 360))
```

**⇒ 直接去掉三元**：因为 `Math.max(140, Bp.height - 360)` 本身在竖屏手机上也是合理值
（手机竖屏 `780` 高 ⇒ `420`；`min(360-40, 420) = 320` ⇒ 盘面 `320vp`，比原来的「不封顶铺满 `360`」略小但正常）。

**⚠️ 但那会改动竖屏手机的观感** —— 所以更保守的写法是只在电视上走封顶：

```diff
- const maxW = Bp.height < 600 ? Math.min(...) : 9999;
+ const maxW = (Bp.height < 600 || Bp.isTv()) ? Math.min(...) : 9999;
```

**⇒ 这条要奥森或真机数据来定，我不擅自选。**

## ⇒ 判据（`2050`）

**三元表达式的兜底分支（`9999` / `Infinity` / 「不限制」）隐含一个「另一侧不会发生」的假设。
跨设备时先问：**这个兜底在另一台设备上还安全吗？**
`9999` 在竖屏手机上安全，是因为「高屏必然窄」；电视推翻了这个前提，
于是同一个兜底从「不限制」变成「炸穿」。**
