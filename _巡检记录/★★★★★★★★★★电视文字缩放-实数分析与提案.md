# 电视（`onemore_tv`）文字偏小：**实数分析 + 提案**（未实施）

## 一、三个缩放源，只有 `Cell` 会放大

| 常量 | 定义处 | 电视下的值 | 有没有 `scale()` / `isTv()` |
|---|---|---|---|
| **`Cell.of(base)`** | `Design.ets:100` | `base × Cell.k ×` **`1.45`** `× 1.0` | ✅ 有 |
| **`FontSize.*`** | `Design.ets:24` | **原值**（如 `md = 16`）| ❌ **没有** |
| **`Space.*`** | `Design.ets:39` | **原值** | ❌ 没有（待逐一核）|
| **`Radius.*`** | `Design.ets:143` | **原值** | ❌ 没有（待逐一核）|

`Cell.of` 的实现（`Design.ets:100-117`）：
```typescript
return Math.round(base * Cell.k * Bp.scale() * shrink);
```
⇒ `Bp.scale()` 在电视上是 **`1.45`**（`Bp.ets:98`，注释原文「3 米视距，必须大」）；
⇒ `shrink` 对电视**故意不缩**（`:112-113` 注释：`1.45 × 0.85 = 1.23` 会把「要更大」抵消一半）。

## 二、所以「文字相对小多少」是可以算的，不是感觉

```
格子相对大小 = 1.45
文字相对大小 = 1.00
⇒ 文字 / 格子 = 1 / 1.45 = 0.690
⇒ 文字相对小 31.0%
```

⇒ 这是**按构造算出来的系统性比例**，与具体游戏无关。
⇒ 之前记的「相对小 `34%–48%`」如果是指某些具体字形，那是在 `31%` 的系统性差距之上又叠加了游戏自己的因素；**底数是 `31%`**。

## 三、为什么这是「提案级」而不是「顺手改」

1. **`FontSize` 是全项目共享常量** —— `355` 款游戏、`43` 处在位，一处改动全库生效
2. **`AGENTS.md` 的硬规则**：动共享组件前要能同时说清「好了哪一好、坏了哪两坏」；
   作者的 `HintBar` 先例就是「一好两坏、证据混合 ⇒ 回退」
3. **我今晚没有电视设备可验** —— `onemore_tv` 已部署，但夜间扫描正占着模拟器与 `hdc`

⇒ 只在一台设备上「看起来更大」不算证据，得**两张 TV 截图对比 + 至少两款不同形态的游戏**。

## 四、提案（三个选项，按风险排）

### A. 只在电视上放大文字（最小风险）
新增 `Bp.textScale()`：
```typescript
static textScale(): number {
  return Bp.isTv() ? 1.45 : 1.0;   // 与 Cell 同步，手机恒为 1.0 ⇒ 零回归
}
```
然后把 `FontSize` 从「静态数值」改成「按 `textScale()` 计算」。
- ✅ 手机零影响（`1.0`）
- ⚠️ `FontSize.xx` 目前是 `static` 常量，被 `300+` 处直接读 ⇒ 改动面大
- ⚠️ 但**只影响电视** ⇒ 手机端风险 = 零（可静态证明）

### B. 只给「电视专用布局」放大（更稳）
不动 `FontSize`，而是在 `GameHost` 里加一个 `tvTextScale` 的 `@StorageProp`，
TV 竖起来的那个窗口单独设 `1.45`。风险更低但**改动分散**。

### C. 不改字号，改电视的 `Cell` 再大一点（最省事但方向错）
把电视的 `1.45` 提到 `2.0` ⇒ 格子更大、文字相对更小 ⇒ **方向反了，否决**。

⇒ **推荐 A**：目标单一（「电视上文字与格子同比例」）、手机端可证明零回归（`isTv()` 之外恒 `1.0`）。

## 五、验收方案（要做这个改动必须先准备好）

1. **两张 TV 截图**：改前 / 改后，同一款游戏、同一状态
2. **两款不同形态**：一款网格类（如 `Kakuro`）+ 一款文字类（如 `Word Mastermind`）
3. **手机端回归**：`onemore7` 与 `onemore_fold` 各测 `3` 款，`blk` 与截图都必须与今天的结果一致
4. **断言**：`200359/0`

## 六、判据

> **「文字相对小」是可以算的：`文字缩放 ÷ 格子缩放`。**
> 今天算出来是 `1 / 1.45 = 0.690`（小 `31%`）——比凭感觉的「34–48%」更硬，也更可复算。

⇒ 三条：
1. **先算，再说** —— 三个常量里只有 `Cell` 有 `scale()`，这就是全部原因
2. **共享组件的改动要能静态证明「另一端零回归」** —— 这次靠 `isTv() ? 1.45 : 1.0`
3. **没有设备就不要动它** —— 这类改动只在 TV 上生效，没有 TV 就无法验
