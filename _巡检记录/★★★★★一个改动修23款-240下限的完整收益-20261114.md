## 三、`Snake 3D` 单独看：它的自适应**没坏**，是偏移量给大了

**`max(300, 533−180) = max(300, 353) = 353vp`** ⇒ 自适应**生效**，但结果是 `353vp`。

**核对账：**
```
盘面 353 + 头部 104 = 457vp
剩 533 − 457 = 76vp 给底部
```
**⇒ 而目标文本早就记着「`GSnake3D` 是典型：底部需 `≈200vp`、只剩 `76vp`」** —— **逐字对上。**

**⇒ 所以它的问题不是 `max()` 用错，是 `-180` 这个偏移量低估了底部需求。
若底部真需 `200vp`：盘面应 ≤ `533 − 104 − 200 = 229vp` ⇒ 偏移量应 ≥ `-304`。**

**⇒ 候选：`max(300, Bp.height - 304)` 在手机上 = `max(300, 229) = 300`（下限又顶掉）
⇒ 得同时把下限降到 `≤229`，如 `max(200, Bp.height - 304)` = `max(200,229) = 229vp`。**

**⇒ 也就是说 `Snake 3D` 需要**同时**改下限和偏移量 —— 正是判据 `2133`（先解 clamp 再调参数）的场景。**

## 五、⇒ 为什么这个「一批 + 一款 + 一款」的顺序是对的

**判据 `2135`（无条件正确的先做、依赖测量的后做）：**

| 改动 | 依赖测量吗 | 依据 |
|---|---|---|
| `240 → 140` | **不依赖** | `140` 是全库主导值（`73` 处）、真机收敛值；且 `173 > 140` ⇒ 下限不生效 |
| `GSnake3D` 的 `-180 → -304` | **依赖** | `-304` 是从「底部需 `200vp`」推的，而那个 `200vp` 来自旧记录、未在当前包上复验 |

**⇒ 所以 `Snake 3D` 排在第三批，且它自己也要单独验。**

## ⇒ 判据（`2143`）

**「同一个 bug 的 N 次复制」修完之后，要专门检查「**看起来同类但机制不同**」的那几个。**
这次 `5` 款真溢出里，`4` 款是「下限顶掉自适应」，`1` 款（`Snake 3D`）是「自适应正常但参数太大」。

**⇒ 若不区分，把 `Snake 3D` 也塞进「`240 → 140`」那一批 ⇒ 它的下限是 `300` 不是 `240`，
改了也白改（`max(140, 353) = 353` 仍然 `353`）。**

**⇒ 判据：批量修一类问题时，逐个确认「它是不是真的同类」——
标准是「同一条代码形态 + 同一个失效机制」，缺一不可。
`240 → 140` 只对「下限压着」的有效；对「下限没压着但值太大」的无效。**
