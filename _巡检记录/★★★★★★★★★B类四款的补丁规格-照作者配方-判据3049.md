## 一、配方出处（作者的，不是我推的）

`GCrossword.ets:334-341`

```typescript
// ★ 2026-11-15（判据 2759/2762）：格子是 `layoutWeight(1)+aspectRatio(1)`、容器 `.width('100%')`
//   ⇒ 五列各 ~480px、五行需 ~2400px ≫ 屏高 ⇒ 只显示第一行五个巨大橙块（截图实证）
//   ⇒ **按可用高度限宽（aspectRatio 会让格子高度跟着降）**
.width(Math.min(Bp.width - 2 * Space.lg,
                Math.max(200, Bp.height - (Bp.isShort() ? 360 : 500))))
```

⇒ 作用链：**容器窄 ⇒ `layoutWeight` 分到的格子窄 ⇒ `aspectRatio(1)` 让高跟着降 ⇒ 整块变矮。**

### `Shadow Pivot` 的完整改法（唯一算完的）

```typescript
// 现在（约 line 295 附近，答案格那个）
}.width('100%') }.width(104)        // ← .width(104) 是「原形」预览，别动
// 答案格的那个容器，加：
.width(Math.min(Bp.width - 2 * Space.lg,
                Math.max(120, Bp.height - (Bp.isShort() ? 360 : 643))))
```

- **横屏**：`533 − 360 = 173vp`（与作者 `Crossword` 的矮屏取值一致）
- **竖屏**：`832 − 643 = 189vp` ⇒ 格子 `232vp → 189vp` ⇒ 两行省 `258px ≈ 缺口 260px`
- **下限 `120`** 而不是作者的 `200`：因为 `Shadow Pivot` 竖屏只能到 `189`，`200` 的下限会盖掉它

⇒ ⚠️ **`Math.max` 的下限必须小于目标值**，否则算式被下限吃掉（今天在 `constraintSize` 上栽过一次：
   上限 `332vp` 比实际 `232vp` 还大 ⇒ 摆设）。

## 五、判据

> **照抄已验证的配方时，只有「算式里的常量」需要重算，**结构**一点都不该动。**
> 如果发现必须动结构才能套用，说明这款不属于这类，别硬套。

⇒ 四条：
1. **`Math.max` 的下限必须小于目标值** —— 否则算式被下限吃掉（今天栽过）
2. **改的是「包住 `layoutWeight` 那层的容器」** —— 不是 `layoutWeight` 那层本身
3. **一次只改一款、走完五步** —— 今天的 `Shadow Pivot` 就是因为五步没走完就接着改
4. **`blk` 归零要同时看 `blkh`** —— 压扁元素也能让 `blk` 归零
