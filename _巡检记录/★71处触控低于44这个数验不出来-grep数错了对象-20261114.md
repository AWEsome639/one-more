# ★ 「`71` 处基线 `< 44`」这个数**验不出来** —— 我的 `grep` 数错了对象

> `2026-11-14 13:1x`。判据 `2152`（旧数字可能根本是错的）用在「`71` 处」这个计数上。**结果：验法本身错了。**

## 一、我先前的想法

**目标写**：「已知 `71` 处基线 `< 44` 是**故意**的（塞进 `533`），`2026-11-08` 决定接受现状」
⇒ 我想「数一下现在有多少处 `< 44` 的触控基线，看还是不是 `71`」。

## 二、数出来两个数

```
Cell.tap(30-43)  ⇒ 145 处（全在 games/）
Cell.of(30-43)   ⇒ 216 处（games/）
```

**⇒ 而我准备把 `145` 当成「触控基线 < 44 的数量」⇒ 那是 `71` 的两倍。**

## 三、⛔ 但 `Cell.tap` 的语义让这个数**毫无意义**

```ts
static tap(base: number): number {
  const v: number = Cell.of(base);
  return v < Layout.touchMin ? Layout.touchMin : v;   // ← 保底 44
}
```

**⇒ **任何 `Cell.tap(x)` 返回值都 ≥ `44vp`**，无论 `x` 多小。**

**⇒ 所以 `Cell.tap(30)` 渲染出来**就是 `44`**，它不是「低于 `44` 的触控目标」，
而是「**设计值低于 `44`、但被抬到 `44` 的触控目标**」。**

**⇒ 那 `145` 处**全部满足 `≥ 44`**，一个都不违反触控下限。**

## 四、那「`71` 处基线 < 44」到底是什么

**唯一可能的含义：**不经 `Cell.tap`、直接用 `Cell.of(base)` 当可点元素尺寸的那些地方。**
（因为 `Cell.of(30)` 返回 `26vp`，那才是真的低于 `44`。）

**⇒ 而这样的地方**数不出来**，因为：**
- `grep "Cell.of(3x)"` 会同时匹配「尺寸」（不是触控）与「触控」（该抬没抬）
- **区分它们需要看每个调用点是不是 `onClick`/`Button` 的尺寸** ⇒ 那是**逐处判断**，不是计数

**⇒ 所以「`71`」这个数我**无法用 `grep` 验证**。**
**⇒ 它要么需要一个专门的扫描器（解析调用点上下文），要么就仍是未验证状态。**

## 五、⇒ 这一轮的收获是**负结果**，但它有价值

| 我做了什么 | 结果 |
|---|---|
| 数 `Cell.tap(30-43)` | `145` —— **但全部 ≥ 44，与「低于 44」无关** |
| 数 `Cell.of(30-43)` | `216` —— **尺寸与触控混在一起，无法区分** |
| 想验「`71` 处」 | **验不出来** |

**⇒ 结论：`71` 仍是**未验证**的旧数字。而我的第一次尝试（数 `Cell.tap`）是**数错了对象**。**

## ⇒ 判据（`2156`）

**数一个「违规数」之前，先确认「这个数对应的代码形态在计数时能被唯一识别」。**
- `Cell.tap(x)` 里 `x < 44` ⇒ **不是违规**（它会被抬到 `44`）
- 违规只可能是「该用 `Cell.tap` 却用了 `Cell.of`」⇒ **那是「用错函数」，不是「参数小」**

**⇒ 判据：「参数值」与「实际效果」之间若有转换（`Cell.of`/`Cell.tap`/`Math.max` 下限），
就不能用参数值去数「效果违规」。必须先过一遍转换。**

**⇒ 这与判据 `2040`（找唯一出口）是同一件事的另一面：
`2040` 说「看尺寸要看出口」；这条说「**数违规也要看出口**」。**

**负结果也是结果，但要写清「为什么验不出来」，否则下一个人（或下一轮的我）会再试一次。**
**⇒ 这次写清了：`Cell.tap` 会抬到 `44` ⇒ 数它无意义；`Cell.of` 分不出触控与否 ⇒ 数它不可靠。**
