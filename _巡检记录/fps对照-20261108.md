## 0. 结论先说

| 条件 | animMs（3 次） | 总帧 | **实测 fps** |
|---|---|---|---|
| **轻载**（冷启后立刻） | 2238 / 2244 / 2241 | 114 / 111 / 109 | 50.9 / 49.5 / 48.6 ⇒ **均值 49.7** |
| **重载**（连续操作 5 分钟后，33 轮甩动+进出游戏） | 2230 / 2242 / 2239 | 120 / 123 / 119 | 53.8 / 54.9 / 53.1 ⇒ **均值 53.9** |

1. **`animMs` 恒定 ≈ 2237–2244ms**（设计值 `TOTAL=1660` + `HOLD=2230` 兜底）
   ⇒ **动画按时间轴播放，不按帧数** ⇒ 帧率高低**不会改变**开屏时长。
2. **重载反而更快（53.9 > 49.7）** ⇒ **帧率与 CPU/负载无关** ⇒ 不是"app 忙不过来"。
3. **今天的实测区间是 48.6–54.9fps，6 次采样里一次都没有 47.7。**
4. ⇒ **「47.7 是模拟器出帧上限」这句话，用现有数据既不能证实、也不必再沿用**——
   更准确的说法是：**splash 实测 ~50–55fps，与负载无关、与动画时长无关。**

## 1. 为什么说"不是 app 的性能极限"

| 证据 | 说明 |
|---|---|
| **负载加重 fps 反升** | 5 分钟连续操作（33 轮甩动 + 每 8 轮进出一次游戏）之后测，**53.9 > 49.7** ⇒ 若瓶颈在 app/CPU，重载只会更慢 |
| **animMs 6 次全部落在 2230–2244** | 抖动 < 0.6% ⇒ 动画由**时间轴**驱动（`此版让推出动画跑完再硬跳`），帧数只是被动记录 |
| **帧桶分布** | fast(≤20ms) 占 **85–95%**、mid(21–33) 占 5–13%、slow 以上 ≤2% ⇒ **绝大多数帧落在 ≤20ms**（60Hz 的 16.7ms 也在这个桶里），均值只是被**少量掉帧**拉高 |
| 均值反算 | 轻载 2241/111 = **20.2ms/帧**；重载 2237/121 = **18.5ms/帧** ⇒ 夹在 50–55fps 之间，**到不了 60fps（16.7ms）** |

⇒ **更像"60Hz 上限 + 少量掉帧"，而不是"硬卡在 47.7"**。

## 2. 为什么**不能**直接下"模拟器上限"的结论

想要证明"这是模拟器出帧上限"，需要**一个不经过本 app 的参照系**（系统 UI 动画 / RenderService 帧统计 / 显示刷新率）。本机三条都取不到：

| 尝试 | 结果 |
|---|---|
| `hidumper -s 4353`（DisplayManagerService）grep `refresh/fps/rate` | **无输出** |
| `hidumper -s 4606`（WindowManagerService）同上 | **无输出** |
| `hidumper -s RenderService` / `param get persist.sys.display.refresh_rate` | 前者只打印服务标题；后者 **`errNum 1002`（不存在）** |

⇒ 只能说「**负载无关**」这一半（这是 app 不是瓶颈的证据），**不能说**「已经证明是模拟器上限」。

## 3. 建议怎么改写这条"环境锁"

**旧口径**（建议废弃）：「splash 上限 47.7fps = 模拟器出帧上限」。
**新口径**（今天 6 次采样支持）：
> **Splash 实测 48.6–54.9fps（轻载均值 49.7 / 重载均值 53.9），与负载无关；
> 开屏时长由时间轴固定 ≈ 2240ms，帧率不影响时长。**
> 凡"要和 60fps 做对比"的性能结论，**都应注明本机基线是 ~50fps、而非 60fps**。

**如果需要最终钉死"模拟器上限"**，下一步只有两条路（都不在本机能力范围）：
1. 换一台**真机**量同一个 splash（真机 60Hz/120Hz 差异会立刻暴露）；
2. 用**系统级帧统计**（RenderService 的 jank/fps 接口，本机 dump 不出来）

```bash

$HDC $T shell "hilog -x | grep 'finish: animMs'"
# fps = (fast+mid+slow+vslow+drop) / (animMs/1000)
```
