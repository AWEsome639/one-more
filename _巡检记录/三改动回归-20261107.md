## P1-1 窄屏副标题被整片藏掉（我引入的回归）

- **位置**：`components/Common.ets:1157`
  `.visibility((Bp.tinyWatch() || (this.hasBadge() && Bp.width < 420)) ? None : Visible)`
- **问题**：11-07 之前这个条件只看 `streak > 0`（少数卡）；我把它扩成了 `hasBadge()` = **通关 🏆 / 最高分 / 连胜 任一**。
  而「玩过一局就有最高分」⇒ **一旦玩过，'best > 0' 恒真** ⇒ 在 360–419vp 宽的手机上，**几乎所有玩过的卡都没有副标题**。
- **触发条件**：手机宽 < 420vp（360×800 这类很常见）＋ 玩过任意一局。**每台窄屏手机都能碰到。**
- **一句话修法**：窄屏只保留**一个**角标（优先级 🏆 > 分数 > 连胜文字），`badgePadRight()` 自然回落到 ≤48，副标题就不必藏；
  或最省事：把条件改回只按「角标真的很宽」算 —— `(this.badgePadRight() > 48 && Bp.width < 420)`。

## P1-2 角标胶囊比预留空间宽 ~12–16vp

- **位置**：`components/Common.ets:1037–1049`（`badgePadRight()`，上限 72）
- **问题**：按 `FontSize.micro = 10vp` 逐项估（与仓库里「🔥 徽章实测 47vp」这条旧结论互校过，模型误差 ±3vp）：

  | 组成 | 宽（vp） |
  |---|---|
  | 🏆 emoji | ~11 |
  | `1,470`（5 字符，bold 10vp） | ~24.5 |
  | 🔥 emoji | ~11 |
  | `3 天` | ~18 |
  | Row space 3 × 3 段 | 9 |
  | 胶囊左右 padding 7+7 | 14 |
  | **合计（不含右边距 6）** | **~87.5** |

  ⇒ 要让副标题不被压住，右内边距至少要 **≈84**（87.5 − 卡片内边距 10 + 右边距 6 的换算差），而代码把上限**卡在 72** ⇒ **差 12–16vp**。
- **触发条件**：卡片**同时**有连胜 + 最高分（老玩家常见），且 `Bp.width ≥ 420`（这一档副标题是**可见**的，才会被压）。
  表现 = 副标题第二行的末尾被半透明胶囊盖住 —— 与判据 268 同一类毛病。
  加分项：分数 5 位（`12,470`）时差得更多，约 **18vp**。
- **一句话修法**：上限提到 **84**；或三样同时亮时把「N 天」压成只剩 🔥（省 ~18vp，正好补上缺口）；或把分数从「永不缩写」改成 ≥10000 就缩写（`12k`）。

## P1-3 `maxLines(3)→2` 让英文长 tagline 更早被截

- **位置**：`components/Common.ets:1169`
- **问题**：为修「竖排」改成 2 行是**对的**（3 行在 30vp 宽里确实逐字换行），但代价是**英文副标题更早截**。实测 355 款数据（`GameRegistry.ets` 的 `enTagline`）：

  | 指标 | 值 |
  |---|---|
  | 长度 中位数 | **28 字符** |
  | > 24 字符 | **226 款** |
  | > 32 字符 | 109 款 |
  | 最长 | 53（`yajilin`/`tapa`/`shikaku` 等「A grid logic puzzle — read the clues, deduce the rest」） |

  估算：440vp 手机 2 列卡片，副标题区 ≈130vp；三标签全亮时只剩 **~58vp**，`minFontSize 8` 下约 **12 字符/行 × 2 行 ≈ 24 字符**
  ⇒ **226 款英文副标题会吃到省略号**（改前 3 行约 36 字符，约 100 款）。
- **触发条件**：英文界面 + 该卡有角标（几乎=玩过）。
- **一句话修法**：按长度决定行数 —— `this.taglineText().length > 24 ? 3 : 2`（中文 9 字仍走 2 行，竖排问题不复发），
  或把角标从「与副标题同层」挪到卡片**右上角**（那里现在只有 ✓，且 tinyWatch 下图标隐藏时是空的）。

## P2-4 `nextGameId()` 的热路径：710 次 `hasCleared()`

- **位置**：`pages/GameHost.ets:762–803`
- **问题**：函数里两个循环各遍历一遍 355 款，每次都调 `ProgressStore.hasCleared(id)`；而
  `hasCleared()` = `AppStorage.get(cleared) → split(',') → indexOf`（**没有缓存**，我核过 `ProgressStore.ets`）。
  ⇒ 每次点「下一款」做 **最多 710 次** 全串 split（已通关 N 款时每次分配 N 个字符串）。
- **触发条件**：点「下一款」（一次性，非每帧）。低端机/手表上可能 10–50ms 抖动。
- **一句话修法**：进循环前 `const cl: Set<string> = new Set(ProgressStore.clearedGames());`，之后 `cl.has(id)`。

## P2-5 `weekStat()` 一次重绘算 6 遍

- **位置**：`components/StatsTab.ets:300`（实现）；调用点 `749 / 750 / 768 / 772 / 775 / 776`
- **实测调用次数**：有数据时 **6 次**（`749` 一次、`750` 一次、`768` 一次、`todayPlaytimeText` 一次、`weekRateText` 一次、`weekTopText` 一次）；空态 4 次；极小屏 2–3 次。**与你记的「6 次」一致。**
- **每次的代价**：`GameLog.recent(800)` —— ★ 好消息：它是**内存数组切片**（`GameLog.mem` 尾部 800 条），**不 JSON.parse、不碰磁盘**（我核过实现）；
  但每次都要复制 800 个引用 + 再全表循环一遍 ⇒ 一次重绘 ≈ **4,800 次记录遍历 + 4 次 Map 构造**。
- **会不会在 355 款列表页被误调**：**不会**。`Index.ets:436–448` 里 `StatsTab` 与 `GamesTab` 是两个**互相独立的 `TabContent`**，
  只有当前页签的内容会被构建；而且本板块外层还有 `if (GameLog.count() > 0 || this.plays > 0)` 兜底。
  （唯一无法纯静态证明的是「ArkUI TabContent 是否预建」——即使预建，也只是首次构建调一次，不是每帧。）
- **一句话修法**：`recentStats()` 里算一次 `const st = this.weekStat();` 然后传给三个取数方法（把 `weekStat()` 改成 `weekStatOf(st)`），6 次变 1 次。

## P3-7 「下一款」与「演示态」：不是新 bug，但会更常撞上

- **机制**：进了新游戏，`aboutToAppear` 里 `Hint.demoOnce(key)` 为真 ⇒ `setTimeout(demoStart, 3000)`。`demoOnce` 是 **AppStorage 进程级标记**（每个游戏每次 App 生命周期只演一次）。
- **会不会「进去直接是演示态」**：**不会直接进** —— 有 3 秒延迟，且 `gotoNext` 里已经 `Demo.stopAll()` 停掉上一局的演示。但「下一款」**偏向挑没通关的**（也就是可能从没打开过的）⇒ 落到「首次打开」的游戏概率大幅上升 ⇒ **演出的次数会明显变多**（演示期 HintBar `disabled`，一碰才停）。
- **一句话修法（可选）**：`gotoNext()` 里对新游戏先 `AppStorage.setOrCreate('demo_seen_' + next, true)` 再切 ⇒ 「下一款」进来就是干净开局，不再放演示。
- **边缘（P4）**：若一局在 **3 秒内**打完就点「下一款」，旧组件的 `setTimeout(demoStart, 3000)` **没有在 `aboutToDisappear` 里清**（355 款通用写法）⇒ 会对**已销毁组件**启一个演示 interval（判据 557 那类“后台空跑 + 潜在崩溃”）。这是老问题，只是「下一款」让它更容易被触发。
