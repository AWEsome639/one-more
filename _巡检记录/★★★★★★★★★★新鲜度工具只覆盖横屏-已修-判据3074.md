# 判据 3074：**新鲜度工具只看横屏台账** —— 修好了，而且它自己暴露了 `42` 款过期

## 一、怎么发现的

我想验证「预测器 A 在竖屏是否也成立」（`3072` 只在横屏验过）。
把 `layout-nonshort.tsv` 接进同一套算法，得到：

```
无高度反推（高风险）: 1/15 = 6.7%
有高度反推（对照）  : 22/133 = 16.5%
⇒ 0.4×（反向）
```

**差点当成结论写下来。** 然后按 `2613` 查数据新鲜度：

```
竖屏 OK 记录按日期：11-16 → 409 条 ｜ 11-17 → 42 条 ｜ 11-19 → 1 条 ｜ 今日 → 4 条
```

⇒ **`409` 条来自 `11-16`（四天前）**，那之后修过很多东西。这个对照**被污染，不能用**。

## 二、顺着查出一个真工具缺陷

`工具/check_ledger_freshness.py:25`：
```python
LEDGER = os.path.join(ROOT, '_巡检记录', 'layout-canonical.tsv')
```

⇒ **它只读横屏台账。** 竖屏台账**完全不受监控**。
⇒ 而它每天报的「`359` 款有效」是**横屏口径** —— 这句会让人以为「全库都新鲜」。

## 三、修了三处

1. **`--nonshort` 开关**（默认仍是横屏，不破坏现有用法）
2. **报「台账名 + 记录条数 + 时间跨度」**，跨度 `≥2` 天就加一条警告：
   > ⚠️ **这份台账跨 N 天**：靠前的记录可能已被之后的改动作废（判据 `2613`）
   > 拿它做「某特征能否预测缺陷」这类统计前，先确认数据新鲜度
3. **`errors='replace'` 读台账** —— `layout-nonshort.tsv` 不是纯 UTF-8（含 `0xe9` 孤立字节），
   不加这参数 `--nonshort` 直接抛 `UnicodeDecodeError`

## 四、修完立刻拿到两个新数字

```
layout-canonical.tsv  2779 条 · 11-12 → 11-20（跨 7 天）· 有效 359 · 过期 0
layout-nonshort.tsv    762 条 · 11-16 → 11-19（跨 3 天）· 有效 315 · 过期 42
```

⇒ **竖屏有 `42` 款过期** —— 这就是我刚才那个 `0.4×` 里藏着的噪声。

## 五、所以「预测器 A 是否在竖屏成立」的正确答案是

**不知道** —— 现有数据不足以回答。

⇒ 要做这个验证，得先**重测那 `42` 款竖屏**（或至少重测其中落在两组里的那些）。
⇒ 在那之前，「A 是横屏专属还是通用特征」**仍待定**。

## 六、判据

> **工具报「多少款有效」而不报「数据有多旧」，本身就是一种误导。**
> 有效性与新鲜度是两个维度：`359` 款「有效」的台账，可能整体是七天前开始累积的。

⇒ 四条：
1. **凡是「覆盖率/有效性」类报告，必须同时报「时间跨度」**
2. **跨度大的台账，做统计前先确认它有没有过期项** —— 这次竖屏有 `42` 款
3. **一个验证被污染时，正确动作是「宣布不知道」，不是「报那个反向倍数」**
4. **`errors='replace'`**：老台账可能不是纯 UTF-8，读之前先假设它不是
