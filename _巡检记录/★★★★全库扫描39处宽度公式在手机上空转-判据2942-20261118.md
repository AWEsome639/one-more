# 全库扫描：**`39` 处宽度公式在手机上「空转」** —— 但不预测折叠屏缺陷

> `2026-11-18 23:02`。由 `2941`（`Math.max` 下限吃掉了缩减）延伸出的全库检查。

## 一、⇒ 扫描方法与结果

**⇒ 匹配 `.width(Math.min(..., Math.max(<下限>, Bp.height - N)))` 这类写法，共 `121` 处。**
**⇒ 逐处算 `max(下限, 533 - N)`（手机 `Bp.height = 533vp`）：**

| 类别 | 处数 | 含义 |
|---|---|---|
| **下限 ≥ 高度算式** | **`39`** | 手机上**恒取上限** ⇒ `N` 改多少都无效（**空转**）|
| 下限 < 高度算式 | `82` | 公式生效 |

**⇒ 空转的 `39` 处涉及 `38` 款**，例如：
`2048`（floor `200` / N `360`）、`Memory` / `Hitori` / `Dominosa` / `Kenken` / `Crown` / `Pipes` / `Shikaku`（floor `240`）、`MatrixReasoning`（floor `140` / N `520` ⇒ `533-520 = 13`，**公式实际是荒谬的 13vp，永远取 140**）、`ConnectFour` / `Tangram` / `MathMaze` / `NegativeSpaceDetection`（N `420`）。

**⇒ 最极端 `MatrixReasoning`：`Bp.height - 520 = 13vp`（`39px`）—— 这个算式在任何设备上都不可能被采用。**

## 三、⇒ 那它揭示的是什么

**⇒ 同一款在两台设备上**走两套不同的尺寸机制**：**
- 手机：`max(下限, 173)` = **下限**（硬编码 vp，作者调过好看；
- 折叠屏：`max(下限, 472)` = **`472vp`**（高度算式）。

**⇒ 这意味着：**手机上的观感由那个「下限」决定，折叠屏上由「`Bp.height - N`」决定** ⇒ 两个数字之间没有任何关系 ⇒ 改一个不会影响另一个，**也很难一通百通**。**

**⇒ 这是**设计层面的气味**，不是 bug：它让「一次修好、两屏都对」变得不现实，今天 `6` 款折叠屏修复都要单独处理手机侧，就是这个原因。**

## ⇒ 判据 `2942`
