# 判据 `3091`：`Simon Says` 竖屏 **C/D 两块被切** —— 确认是真缺陷，但我两次改常数都没效果，**已回滚**

## 一、缺陷（真机截图确认）

`onemore_fold` `2224×2496`（竖屏），`blk=2/48px`。
截图 `截图-Simon_Says-224823.jpeg` 清楚显示：**下面两块（C 蓝、D 橙）只露出上半截**。
和 `Simon Command`（判据 `3089`）是同一类问题：纵向堆两行方块、行宽按整屏算、没算两行总高。

## 二、我试了什么（都没效果）

改 `GSimonSays.ets` 的两处：
```typescript
.width(Math.min(Bp.width - 2 * Space.lg, 2 * Math.max(125, Bp.height - (Bp.isShort() ? 410 : 230))))
```

| 竖屏常数 | HAP 变化 | 实测 `blk` | 截图 |
|---|---|---|---|
| `230`（原）| — | `2/48px` | C/D 各切一半 |
| `561` | `53,502,882`（clean 重建）| `2/48px` | **完全没变** |
| `577` | `53,502,883` | `2/48px` | **完全没变** |

⇒ 三次测量 `blk` 一模一样、截图一模一样 ⇒ **那个 `.width()` 的第二项根本不是约束**。

## 三、我能确定的推断

面板宽约 `345vp` ⇒ 行宽约 `701vp` = `Bp.width(741) − 2×Space.lg(20)`。
⇒ 说明这个式子的结果一直等于**第一项**，也就是 `2 × max(125, Bp.height − N) ≥ 701` 恒成立。
⇒ 反推：`Bp.height − N ≥ 350`。代入 `N=577` ⇒ **`Bp.height ≥ 927`**。

⇒ 也就是说：**这台设备上 `Bp.height` 不是我一直以为的 `832`**（`2496px ÷ 3`）。
   真实值我没取到（诊断日志那次构建没产出新包就中断了），所以**这一条还是推断、不是实测**。

## 四、为什么回滚

1. 改动**没有任何可观测效果**（`blk` 与截图三次全同）
2. 我没有拿到 `Bp.height` 的真值，继续调常数就是**盲拟**
3. 判据 `2605`/`3089`：**没验过的改动不能留**

⇒ 代码已 `git checkout` 回滚（`git status` 零改动），`2.0.1` 里**不含** `Simon Says` 的改动。

## 五、下一步该怎么做（写在前面，接手的人照这个走）

1. **先取 `Bp.height` 的真值** —— 在 `GSimonSays.build()` 里加一行 `console.info('BPDIAG h=' + String(Bp.height) ...)`，
   构建后 `hdc hilog | grep BPDIAG`。**这一步不做，后面全是猜。**
2. 拿到 `Bp.height` 后，按「两行方块总高 = 行宽」这个几何关系反推：
   `行宽 + chrome ≤ Bp.height`（chrome 在竖屏约 `290–330`）
3. 改完**必须 clean 重建**（判据 `3089`：增量构建会「成功但不重建」），核对 HAP 字节数
4. 装包、量 `blk`、**看截图** —— 三样齐了才算修好

## 六、判据

> **改一个常数没反应，先怀疑「我改的那一项不是约束」，再怀疑「改动没进包」。**
> 这次两种情况可能是叠加的（既不是约束项、诊断构建又没产出），所以三次测量全同。

⇒ 四条：
1. **连续两次改常数、指标一模一样 ⇒ 立刻停手**，先证明「改动真的进了包」+「改的那一项真的被用到」
2. **`Bp.height` / `Bp.width` 这类全局量不要凭屏幕分辨率除密度去推** —— 直接打日志取真值
3. **诊断用的构建必须核对 HAP 字节与 mtime**（判据 `3089`），否则会以为「没效果」其实是「没编译」
4. **没验过的改动一律回滚**，把「真缺陷 + 试过什么 + 下一步」写进判据，比留个半成品强
