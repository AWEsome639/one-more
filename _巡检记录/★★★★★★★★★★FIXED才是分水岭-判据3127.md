# 判据 `3127`：`(Bp.height − FIXED) × 系数` 这一族，**分水岭是 `FIXED` 分不分形态，不是系数**

## 一、族谱（`grep` 一次全部找出来）

```bash
grep -rn "Bp.height - FIXED" entry/src/main/ets/games/*.ets
```

| 游戏 | `FIXED` | 横屏边长 `(533−FIXED)×0.70` | 横屏实测 |
|---|---|---|---|
| `GReversi`（黑白棋）| **`isShort() ? 320 : 200`** | `149` | ✅ 底 `1331`，屏内 |
| `GSlidePuzzle`（数字华容道）| **`isShort() ? 260 : 200`** | `191` | ✅ 底 `1461`，屏内 |
| `GCompoundConnect`（复合连线）| `260` | `191` | ✅ 底 `1372`，屏内 |
| `GSlitherlink`（数回环）| `200` | `233` | ✅ 底 `1408`（**例外**，见下）|
| `GCheckers`（跳棋）| `200` | `233` | ❌ **被切** |
| `GBejeweled`（宝石迷阵）| `200` | `233` | ❌ **被切** |

⇒ **系数 `0.70` 六款全一样，但只有两款坏。** 差别在 `FIXED`。

## 二、正确范式仓库里早就有

`GReversi` / `GSlidePuzzle` 写的是：

```typescript
const FIXED: number = Bp.isShort() ? 320 : 200;   // ← 横屏多留 120
```

⇒ 这才是 idiomatic 修法：**横屏把固定部分算大一点**，而不是去改系数。
⇒ `Checkers` / `Bejeweled` 漏了这一步 ⇒ `FIXED` 仍是 `200` ⇒ 横屏多出 `120vp` 没人预留。

## 三、我实际用的修法（已验证但**不是**最优雅的）

我把系数从 `0.70` 改成 `Bp.isShort() ? 0.60 : 0.70`：

```
(533 − 200) × 0.60 = 200   ← 与我需要的 200 一致
```

⇒ **数值等价**（`(533-200)*0.60 = 200` vs `(533-320)*0.70 = 149`，都 ≤ 可用），
两款都已真机验证通过（`blk=0/0px` + 截图完整）。

⇒ 但**下次再遇到这一族，优先改 `FIXED`**：它与同族其它款一致，读代码的人一眼能懂。

## 四、`GSlitherlink` 是例外（同样 `FIXED=200` 却没事）

实测横屏 `OK`、最低点 `1408`。原因推测：它的棋盘不是严格 `aspectRatio(1)` 撑满，
而是另有宽度上限（`:532` 附近还有别的约束）。

⇒ **这正是否证「同算式必同病」的直接反例。**

## 五、判据

> **「同算式」不等于「同病」。要看那个算式里的每个变量在这款里取什么值。**

⇒ 五条：
1. **`grep` 同款算式是找嫌疑的最快办法**，但**只能缩小范围，不能直接批量改**（判据 `3104` 再次被证实）
2. **找差异要逐变量比**：这次 `系数` 六款相同、`FIXED` 两款不同 ⇒ 一列就看出分水岭
3. **仓库里往往已经有正确范式**（`Reversi`/`SlidePuzzle` 的 `isShort() ? 320 : 200`）——
   改之前先看同族别的款怎么写的
4. **例外必须记下来**（`Slitherlink`）—— 它是「同算式必同病」这个推论的唯一反例，
   有它在，下次就不会盲目套
5. **一次 `grep` + 一次批量横屏测量（`4` 款 `5` 分钟）就否掉了 `3` 个不必要改动** ——
   比改完再回滚便宜得多
