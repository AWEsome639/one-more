# `Magnets` 根因：`MAG_CELL=52` **只按高度算、没按宽度算** ⇒ 棋盘只占宽度 `56%`

> `2026-11-19 00:56`。不看新截图，**只读作者自己的注释 + 算术**就能定案。

## 一、⇒ 作者已经算过了，但只算了一个方向

`GMagnets.ets:716-720` 原文：
> 「`2026-11-15` dump：Row 宽对了（`276vp`）但**高度没设** ⇒ 只拿到 `154px`…补上高度。
> **`4×52+3+24 = 235vp < 可用 293vp` ✅ ⇒ 格子还能用回作者原本的 `52`。**」

**⇒ 这是**高度**方向的不等式：`4 × 52 + 线索 27 ≤ 293` ✅**
**⇒ 但**宽度**方向从没算过：**

| 方向 | 算式 | 结果 | 可用 | 占比 |
|---|---|---|---|---|
| 宽 | `4×52 + CLUE_W(44) + 4×Space.xs(24)` | **`276vp`** | `533 − 40 = 493vp` | **`56%`** |
| 高 | `4×52 + 3 + 24` | `235vp` | `293vp` | `80%` |

**⇒ ⇒ 高度用掉 `80%`、宽度只用 `56%` ⇒ 屏幕上就是「棋盘缩在中间偏左、右侧一大片空」。**
**⇒ 这正是我 `01:08` 那张截图看到的样子 —— 不是渲染 bug，是**常数取值只优化了一个方向**。**

## 二、⇒ 最优值可以算出来（`2974` 的做法）

**⇒ 两个约束同时满足时的最大边长：**
```
宽约束：4·c + 44 + 24 ≤ 493  ⇒  c ≤ 106.2
高约束：4·c + 3 + 24  ≤ 293  ⇒  c ≤ 66.5      ← 这个更紧
⇒ c_max = 66
```
**⇒ ⇒ 现在是 `52`，**可以安全取到 `64`**（留 `2` 的余量）：**
| | 现在 | 改成 `64` | 变化 |
|---|---|---|---|
| 格子 | `52vp` | `64vp` | **`+23%`** |
| 棋盘宽 | `276vp` | **`324vp`** | `56% → 66%` |
| 棋盘高 | `235vp` | `283vp` | `80% → 97%`（`< 293` ✅）|

## ⇒ 判据 `2976`

**⇒ 一个「尺寸常数」如果同时受宽高两个方向约束，**必须把两个不等式都写出来**；只算一边（今天作者只算了高度）就会在另一边留下大片空白，而代码看起来「已经修过了」。**
**⇒ ⇒ 复查任何「已经修好」的布局常数时，先问：**另一边算过没有？**
