# 大屏的真问题，可能是「浪费空间」而不是「切内容」

> `2026-11-16 13:27`。**看了 `Binomial Match` 在折叠屏上的截图（`截图-Binomial_Match-125033.jpeg`）之后的判断。**

## 一、⇒ 那款其实是好的

**⇒ 手机上它的 `lowest` 是 `换一组` 按钮（`114px`），折叠屏变成提示行（`44px`）⇒ 配对比较器把它列进「元素变了，需复核」。**
**⇒ 看图：**`换一组` 按钮完整地在**（绿色整条），只是它**下面**还有一行提示 ⇒ `lowest` 自然变成提示行。**

**⇒ 所以这是**误报**，不是缺陷。**

## 二、⇒ 但图上暴露了另一件事

**⇒ 整个游戏内容（标题 / 提示+AI 代打 / 三个统计 / 题目卡 / 两组选项 / 换一组 / 提示行）**全部挤在屏幕上半部**，下半部是**一大片空白**。**

**⇒ 在 `2224×2496` 的竖屏上，这不算「坏了」，但离「每一帧、每一处细节都值钱」差得远：**
**⇒ 大屏给了你 `798vp` 的高度，而界面只用了一半 —— 那另一半**没有承担任何信息**。**

## 三、⇒ 这改变了接下来的判据

**⇒ 之前我盯的是「有没有东西被切」（`blk` / `lowh` / 配对比较）。**
**⇒ 现在要加一条：**大屏下内容有没有**利用**多出来的空间。**

**⇒ 两种坏法：**
1. **被切**（`Mental Mapping` 的方向键）—— 已抓到 `1` 例、已修
2. **浪费**（`Binomial Match` 只占上半屏）—— 可能**很多款**都是这样，因为布局大多是 `Column` 自上而下堆

## 四、⇒ 怎么量「浪费」

**⇒ 现成的数：`dump` 里所有带 bounds 的节点，算 `y2` 的最大值 ⇒ 就是「内容实际占用了多少高度」。**
**⇒ 判据：内容底 `y2 / 屏高 < 0.75` ⇒ **浪费**（超过 `1/4` 的屏高没有内容）。**
**⇒ `shot_game.py` 已经打了 `lowest` 的 `y2`（如 `[477,2327][1748,2474]` ⇒ 内容底 `2474 / 2496 = 0.99`）—— 对 `Binomial Match` 而言 `lowest` 是提示行、到底了。**

**⚠️ 但「内容到底了」不等于「内容填满了」：中间可能有大量空白。**
**⇒ 更准的量法：统计**纵向空白段**的总高度（相邻节点 `y` 区间之间的空隙）。**

**⇒ 这条先记下，等跑批结束、有全量数据再设计指标 —— 不要在只有 `1` 个样本时就定阈值。**
