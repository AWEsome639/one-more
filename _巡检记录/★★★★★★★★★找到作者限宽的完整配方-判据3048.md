# 判据 3048：**作者的完整配方找到了** —— 限「容器宽度」，不是限元素

## 一、我之前错在哪

`Shadow Pivot` 五次尝试，用的都是「直接约束那个 `aspectRatio` 元素」：
`padding` / `margin` / `Stack` 的 `constraintSize(maxHeight)` / `Stack` 的 `maxWidth` —— 全败。

⇒ 结论写成「`layoutWeight` 定宽时 `constraintSize` 拦不住」（`3030` §十九）。**这句是对的，但只对了一半。**

## 二、`GCrossword.ets:334-341` 里作者写完了整套做法

```typescript
// ★ 2026-11-15（判据 2759/2762）：格子是 `layoutWeight(1)+aspectRatio(1)`、容器 `.width('100%')`
//   ⇒ 五列各 ~480px、五行需 ~2400px ≫ 屏高
//   ⇒ 只显示第一行五个巨大橙块、线索与输入区全被挤出屏外（截图实证）
//   ⇒ **按可用高度限宽（aspectRatio 会让格子高度跟着降）**
.width(Math.min(Bp.width - 2 * Space.lg,
                Math.max(200, Bp.height - (Bp.isShort() ? 360 : 500))))

// ★ 2026-11-18（判据 2911/2926）：折叠屏上 `-360` 不够 ⇒ 下方两行选项被切（截图实证）
//   矮屏（手机 533）保持 `-360`（它已经 blk=24 勉强通过、不动它）
//   非矮屏（折叠屏 832）用 `-500` ⇒ 网格窄一点、给下方两行选项让出空间
```

⇒ **修的是「容器的 `width`」，不是格子的 `constraintSize`。**
   容器变窄 ⇒ `layoutWeight(1)` 分配到的格子也变窄 ⇒ `aspectRatio(1)` 让高跟着降 ⇒ 整块变小。

⇒ 这解释了为什么我那五次全败：**我一直在约束「被分配宽度的那一层」，而作者约束的是「分配者的宽度」。**

## 六、判据

> **元素被 `layoutWeight` 分配宽度时，约束它自己无效 —— 要约束「分配宽度的那一层」（容器）的 `width`。
> 容器变窄 ⇒ 分配到的宽度变小 ⇒ `aspectRatio` 让高跟着变小。**

⇒ 四条：
1. **看到 `layoutWeight(n) + aspectRatio(x)`，改它的**父容器** `.width(...)`** —— 不是改元素
2. **`width` 用「按可用高度算」的表达式**（作者的原式）：
   `.width(Math.min(Bp.width - 2 * Space.lg, Math.max(200, Bp.height - (Bp.isShort() ? 360 : 500))))`
3. **「不可约束」不等于「必须动结构」** —— 今天我把 `4` 个 B 类判成「要人眼」，是过早放弃；
   **动手前先 `grep` 整个库看有没有人已经解过这个题**（`3044` 的扫描就是被这条救回来的）
4. **作者的注释里常写着「已知并接受」的取舍** —— `Crossword` 的 `blk=24` 就是，
   **别把它当缺陷再「修」一遍**
