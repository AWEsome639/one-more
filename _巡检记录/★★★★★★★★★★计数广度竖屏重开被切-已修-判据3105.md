# 判据 `3105`：`Counting Span`（计数广度）竖屏 `重开` 被切 —— `360 → 430`

## 一、发现的

`detect_bottom_clip.py --today`（`85` 款新鲜截图）里唯一被标的一款：`cov=0.94`。
截图：底部 `重开` 只露出文字上半。

## 二、根因

`GCountingSpan.ets:375` —— 又是 `Bp.height - 360`（第四个 `- 360` 家族）。

## 三、三档实测（这次两档都不够，值得记）

| 竖屏 reserve | `blk` | `cov` | `重开` 块高 | 判读 |
|---|---|---|---|---|
| `360`（原）| `1/24px` | `0.94` | 只露文字上半 | 被切 |
| `406` | `1/24px` | `0.94` | **`109px`**（完整应 `137px`）| **仍被切 `28px`** |
| **`430`** | **`0/0px`** | **`0.00`** ✅ | 收进来 + 下方提示行可见 | **完整 + 留边** |

### ⚠️ `406` 这一档是关键证据

按截图算出的 reserve 是 `367`，我按判据 `3104` 的经验加了 `39` 得到 `406`，
结果 `重开` 块只有 `109px`（完整 `137px`）⇒ **还缺 `28px`**。

⇒ 说明「按截图估算 + 经验补偿」这条路**不可靠** —— 两次都是先差一点。

## 四、更可靠的做法（下次直接用）

**不要先算，先看「底部块的完整高度」**：
```
完整按钮高 = Cell.of(44) ≈ 44vp ≈ 137px（在 3.125 密度下）
若 lowest 块高 < 完整高度 ⇒ 还缺 差值
```
⇒ 这次 `109px` vs `137px` ⇒ 缺 `28px` = `9vp` ⇒ 再加边距 `10vp` ⇒ `406 + 19 = 425`，取 `430` 一次到位。

⇒ 比「按上方 chrome 估算」快一档：**估算需要两轮，量块高只需要一轮。**

## 五、判据

> **`lowest` 块的「高度」比「它的 y2」更有信息量** —— `y2` 只告诉你它贴不贴底，
> `高度`直接告诉你「它被切掉了多少」。

⇒ 四条：
1. **判断「按钮有没有被切」，量块高**（`blkh` 字段），不是量 `y2`
2. **`blkh` < 控件应有高度 ⇒ 被切**，差值就是还要收多少
3. **`blk=1/24px` + `cov≈0.94`** 是「贴边或被切」的通用信号，两者必须靠 `blkh` 或截图区分
4. **修完要三样归零**：`blk=0` + `cov=0.00` + 截图里控件完整且留边
