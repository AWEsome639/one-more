# 判据 `3106`：`Bp.height - 360` 家族全景 —— **`10` 款实测，只有 `5` 款坏**

## 一、为什么写这个

`grep -rl 'Bp.height - 360' games/*.ets | wc -l` ⇒ **`73` 个文件**。
但今天实测下来，这一族里**坏的只有一部分** —— 把已知数据列全，好让下次一眼判断。

## 三、⚠️ 一个反直觉的事实：**没有简单公式**

`Memory Palace` 和 `Memory Matrix` 结构几乎一样（网格 + 提示 + 一个按钮），
但一个需要 `388`、另一个需要 **`454`** —— 差 `66vp`。

⇒ 原因：网格**上方**的 chrome 不同（`Memory Palace` 多一行「找出 🗿 的位置」大字）。
⇒ 所以「按下方内容估算」永远算不准，**因为上方也在变**。

## 四、唯一可靠的做法（照这个来，别算）

```
① 先把 reserve 设成一个明显偏大的值（比如 480），量一次 → 拿到「底盘」
② 看 blkh：完整按钮 ≈ Cell.of(44) ≈ 137px（密度 3.125）
③ blkh < 137 ⇒ 缺 (137 − blkh)px，换算成 vp（÷3.125），加 10vp 边距
④ 一次性加减到位
```

⇒ 或者更快：**直接从截图量棋盘上下两段 chrome**（上段从屏顶到棋盘上沿、下段从棋盘下沿到屏底）。

## 五、判据

> **同一个魔数在 `73` 个文件里，坏的只有 `5` 个 —— 而坏的那 `5` 个，原因各不相同。**
> **不要试图找一个统一公式；要找一个统一的「测量流程」。**

⇒ 四条：
1. **批量改魔数前先抽样**（`73` → 实测 `5` 坏）—— 判据 `3104`
2. **别按 chrome 估**（估了两次都差一轮）—— 量 `blkh` 差值更快
3. **同一结构不同游戏可能差 `66vp`** —— 因为上方 chrome 也在变
4. **每次修完必须 `blk=0` + `cov=0.00` + 截图三样归零**，否则下一款还会踩同一个坑
