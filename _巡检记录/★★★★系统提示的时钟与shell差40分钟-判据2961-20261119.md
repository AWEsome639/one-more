# 系统提示的时钟与 `date` 差约 `40` 分钟 ⇒ 一律以 `date` 为准

> `2026-11-19 00:24`。**今天被这个坑了两次。**

## 一、⇒ 现象

| 来源 | 显示 |
|---|---|
| **系统提示（每轮附带）** | `2026-11-19T01:04` |
| **shell `date`（真实）** | **`00:24`** |
| 差 | **约 `40` 分钟** |

**⇒ 二次确认：`ps` 的 `etime` 也对得上 `date`（看门狗 `etime=04:33` 时 `date` 是 `00:17`）。**

## 二、⇒ 今天被坑的两次

1. **以为看门狗 `10` 分钟没记日志（卡住了）** ⇒ 实际只过了 `4.5` 分钟，第 `2` 条还没到；
2. **以为跑批 `10` 分钟没进展（卡住了）** ⇒ 实际台账最后一行在 `33` 秒前。

**⇒ 两次都差点去「修」一个正常在跑的东西。**

## ⇒ 判据 `2961`

**⇒ 所有时间判断（多久没动、跑了多少、还剩多少）**一律用 shell `date` 与文件 `mtime`**，不用对话里附带的时间戳。**
**⇒ 判别方法：`ls -l <log>` 的 `mtime` 与 `date` 对比 —— 这两个同源，能互相印证；对话时间戳是第三方，可能与宿主时钟不同步。**

**⇒ 推论：判断「进程卡住」的正确姿势不是看「我感觉过了多久」，而是**
```bash
date +%s                      # 现在
stat -f %m <日志或台账>        # 最后写入
```
**⇒ 差值 > 单款平均耗时 × 2 才算可疑（今天 `~170s` ⇒ 超过 `6` 分钟才算）。**
