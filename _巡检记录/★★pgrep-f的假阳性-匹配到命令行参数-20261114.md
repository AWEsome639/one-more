# ★★ `pgrep -f` 的假阳性：匹配到了命令行**参数**

> `2026-11-14 13:50`。查 Colima 是否重启时，被自己的 `pgrep` 骗了一次。

## 一、⇒ 发生了什么

**我用这个判断 Colima 是否回来了：**
```bash
pgrep -f qemu        # 返回 1 ⇒ 我以为 qemu 又起来了
```

**⇒ 而真相：那个 `1` 是 `limactl usernet` 的网络助手进程，它的命令行里有：**
```
--listen-qemu /Users/a0000/.colima/_lima/_networks/user-v2/user-v2_qemu.sock
```

**⇒ `pgrep -f` 匹配**整条命令行**（含参数）⇒ 把 `--listen-qemu` 里的 `qemu` 也算进来了。**

**⇒ 而 `ps -p $(pgrep -f "qemu-system")` 返回**空** ⇒ 真正的 `qemu-system-x86_64` 确实不在了。**

## 二、⇒ 所以「Colima 重启了」是我的误判

**实际状态：**
| 检查 | 结果 |
|---|---|
| `qemu-system-x86_64` | **不存在**（`ps -p` 查不到）|
| `limactl usernet` | 仍在（`0.0%` CPU、`4MB`）⇒ **无害的网络助手** |
| 磁盘 | `17 GiB`（仍是停 Colima 后的值 ⇒ 证明 VM 没重启）|

**⇒ 磁盘 `17 GiB` 是铁证：若 VM 重启，那个 `5 GiB` 会重新被占。**

## 三、⇒ 而那个 `189%` 的 WebKit 是瞬时尖峰

**`ps` 抓到它 `189.1%`，`2` 分钟后查是 `18.0%`。**
**⇒ 页面渲染/图片解码的瞬时峰值 ⇒ 不是持续负载。**

## 四、⇒ 所以负载 `6.73` 的构成

**当时：`WebKit 189%` + `DeepSeek 61%` + `SkyLight 30%` + `DeepSeek 18%` + `DeepSeek 14%` ≈ `312%`**
**⇒ 而 `6.73` 的 1 分钟负载 ≈ `6.7` 核 ⇒ 与 `312%` 不符（负载还含「等待」的进程）**
**⇒ 无论哪种，那个峰值是我**自己**（DSH + 它开的网页）造成的，不是外来重活。**

## ⇒ 判据（`2428`）

**`pgrep -f X` 会把**参数里含 X** 的进程也算进来 ⇒ 判断「某进程在不在」要用 `ps -p` 或 `pgrep -x`，不要用 `pgrep -f`。**
**⇒ 这次 `--listen-qemu` 就骗了我。**

**⇒ 判据：`pgrep -f` 适合「按命令行找」，不适合「判断某程序是否在跑」。
⇒ 后者要用 `pgrep -x <exact-name>` 或 `ps -p`。**

## ⇒ 判据（`2429`）

**而「Colima 是否重启」这件事，**磁盘可用量**比进程列表更可靠。**
**⇒ 停了它少 `5 GiB`；若重启那 `5 GiB` 会回去 ⇒ 我看磁盘还是 `17 GiB` ⇒ 一眼就知道没重启。**

**⇒ 判据：判断「某服务是否在跑」时，找一个**它有而别人没有的副作用**（这里是磁盘占用）去查，比查进程可靠。**
