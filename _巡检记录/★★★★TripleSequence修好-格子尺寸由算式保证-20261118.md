# `Triple Sequence` 底行被切 —— **修好了**（格子尺寸由算式保证，判据 `2907`）

> `2026-11-18 11:52`。**这是本族第三款修好的，也是第一款用「结构性方案」而不是「调参数」修好的。**

## 一、⇒ 为什么之前七种处方都不行

**⇒ 它是 `3 行 × 6 列`，格子 `layoutWeight(1) + aspectRatio(1)` ⇒ **宽度驱动**：格子宽度 = 网格宽 / 6，高度**跟着宽度走**。**
**⇒ 网格 `width('100%')` ⇒ 每格约 `420px` ⇒ 3 行 `1260px` ⇒ 必然超出可用高（约 `860px`）。**
**⇒ 所以「加约束」「缩间距」「收窄百分比」全都在跟 `layoutWeight` 的再分配打架（`2599`/`2904`）。**

## 二、⇒ 正确做法：**让高度由算式保证**

```ts
private cp(): number {
  return Math.max(36, Math.floor((Bp.height - 280) / ROWS.length));   // 余量 280vp
}
// 格子上：
.width(this.cp()).height(this.cp())        // 取代 .layoutWeight(1).aspectRatio(1)
// 行上：
.width('100%').justifyContent(FlexAlign.Center)   // 固定宽度后居中
```

**⇒ `Bp.height=533`、`ROWS=3` ⇒ `cp()=84vp=252px` ⇒ 3 行共 `756px` ⇒ 稳稳装进可用高。**
**⇒ 格子不再「铺满宽度」，而是**固定大小居中** —— 视觉上小一点，但**一行都不会缺**。**

## ⇒ 判据 `2907`

**⇒ 「宽度驱动」的网格（`layoutWeight + aspectRatio`）在矮屏上，**唯一可靠的解法是把格子尺寸算出来写死**：**
```ts
cell = Math.max(下限, (可用高 - 余量) / 行数)
```
**⇒ 不要试图靠「加约束 / 缩间距 / 收窄百分比」去间接影响它 —— 那些都会被 `layoutWeight` 的再分配吸收（本族七个处方里五个是这么死的）。**
**⇒ 代价是格子不再铺满宽度，要配一个 `justifyContent(FlexAlign.Center)` 让它们居中。**
