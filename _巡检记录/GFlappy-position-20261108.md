## ① 四处 `position` 分别是什么

| 行 | 元素 | 代码 | 作用 |
|---|---|---|---|
| `:580` | **上管道** | `.width(PIPE_W+'%').height(pipeTop(k)+'%')`<br>`.position({ x: pipeX(k)+'%', y: 0 })` | 从顶部垂下来的管，高度 = 空隙上沿 |
| `:586` | **下管道** | `.width(PIPE_W+'%').height((GROUND-top-PIPE_GAP)+'%')`<br>`.position({ x: pipeX(k)+'%', y: (top+PIPE_GAP)+'%' })` | 从空隙下沿一直铺到地面 |
| `:622` | **小鸟** | `.width(34).height(26)`<br>`.position({ x: BX+'%', y: this.py+'%' })` | 玩家角色 |
| `:630` | **地面** | `.width('100%').height((100-GROUND)+'%')`<br>`.position({ x: 0, y: GROUND+'%' })` | 底部 8% 高的地面 |

**更正一处口径**：你在消息里列的第四项是「间隙」，但代码里**没有间隙元素** ——
间隙是上管 `y+height` 与下管 `y` 之间的**空白**（上下两根管拼出 `PIPE_GAP=30%` 的空档）。

---

## ② 是不是全用 `%`？—— 坐标是，**尺寸不是**

### 坐标：全部 `%` ✓（两处 `0` 是有意的）

| 位置 | 写法 | 判定 |
|---|---|---|
| `:580` | `x: pipeX(k)+'%'`, `y: 0` | `y:0` = **管道贴上沿**，`0` 是无单位贴边 ✓ |
| `:586` | `x: …+'%'`, `y: …+'%'` | 全 `%` ✓ |
| `:622` | `x: BX+'%'`, `y: py+'%'` | 全 `%` ✓ |
| `:630` | `x: 0`, `y: GROUND+'%'` | `x:0` = **地面贴左沿**，铺满整宽 ✓ |

**这四处坐标没有一个是真的单位混用** —— 和我上一轮报告里说的「都是故意的贴边」一致。

### 🔴 但尺寸口径不一致：**小鸟是固定 vp，其它全是 `%`**

| 元素 | 尺寸写法 | 口径 |
|---|---|---|
| 上/下管道 | `.width(PIPE_W + '%')`、`.height(… + '%')` | **%** ✓ |
| 地面 | `.width('100%')`、`.height(… + '%')` | **%** ✓ |
| **小鸟** | **`.width(34).height(26)`** | **固定 vp** ✗ |

**而判定盒用的是 `%`**：

```ts
const BW: number = 10, BH: number = 6;          // 判定盒（% 口径）
const overlapX = BX + BW > p.x && BX < p.x + PIPE_W;      // 水平：%W
const inGap = this.py > p.top && this.py + BH < p.top + PIPE_GAP;  // 垂直：%H
```

⇒ **视觉是小鸟 34vp 宽，判定是 10% 场地宽** —— 两者只在特定屏宽上相等。

## ③ 容器是什么

```ts
Stack() { 管道 / 小鸟 / 地面 }
  .width('100%')
  .layoutWeight(1)          // ← 高度 = 剩余空间，动态
  .backgroundColor(...)
  .borderRadius(Radius.lg)
  .clip(true)
  .direction(Direction.Ltr) // RTL 下把飞行区钉成 Ltr（position 不镜像）
  .shadow(Shadow.card)
```

**没有 `aspectRatio`、没有 `constraintSize`/`maxWidth`** ⇒ 场地宽高比**完全由设备与界面模式决定**。
（对比：`GBreakout` 用 `aspectRatio(1)` 锁成正方形，所以它的 `boardW` 一个值就够宽高都用。）

## ④ 首帧 `boardW = 0` 的隐患？—— **没有，也不需要**

```
grep -E "onAreaChange|boardW|fieldW|fieldH|this.w|this.h"  GFlappy.ets  →  0 命中
```

- 全文件**没有任何测量变量** ⇒ 不存在「首帧测得 0」的问题
- 也**不需要**引入：坐标全是 `%`，根本不用知道容器是多少 vp

> 判据 1823 的正面例子：**GFlappy 用 `%` 是对的**（物理与像素解耦，和 `GBreakout` 同一个设计思路）。
> 它的问题不在「该不该用 %」，在「**有一处尺寸没用 %**」。

## ⑤ 量纲问题：**管道间距 vs 球速没问题，小鸟才是**

### 5.1 管道间距 vs 球速：**自洽，且与设备无关** ✓

```
PIPE_SPACING = 42 (%)     每两根管的水平间距
PIPE_SPEED   = 1.5 (%)/tick
⇒ 28 tick ≈ 0.92 s 一根，与屏幕尺寸无关 ✓
```

因为**间距和速度都是 `%W`**，比值恒定 ⇒ 无论多宽的屏，管道到来的**时间节奏都一样**。
纵向同理：`PIPE_GAP=30 %H`、`GRAVITY=0.48 %H/tick²` 都是 `%H`，自成一体 ✓

**⇒ 不存在 `GPong` 那种「水平/垂直两套单位打架」的问题。**

### 5.2 🔴 真正的问题：**小鸟视觉固定 vp vs 判定盒 `%`**

判定盒宽 = `BW(10%) × 场地宽`，视觉宽 = **固定 34 vp** ⇒ 两者只在 **340 vp** 时相等：

| 场地宽 (vp) | 判定盒宽 | 视觉宽 | **多出** | 倍数 |
|---:|---:|---:|---:|---:|
| 320 | 32.0 | 34 | −2.0 | 0.94×（判定略小，宽容）|
| **340** | 34.0 | 34 | **0.0** | **1.00×** ← 设计原点 |
| 360 | 36.0 | 34 | +2.0 | 1.06× |
| 420 | 42.0 | 34 | +8.0 | 1.24× |
| 533 | 53.3 | 34 | +19.3 | 1.57× |
| **853** | **85.3** | **34** | **+51.3** | **2.51×** |
| 1280 | 128.0 | 34 | +94.0 | 3.76× |

**验证机就是 853vp**（`onemore` 2560×1600 @480 ⇒ 853×533vp）
⇒ **在验证机上，小鸟右边有 51vp 的“看不见的判定盒”**（比小鸟本身还宽 1.5 倍）。

**玩家感受**：「明明看着还有缝，怎么就撞死了」。

### 5.3 这和奥森 2026-10-13 报的「边缘判定太大」是**同一个病根**

代码里留着这条记录：

```ts
const BH: number = 6;   // ★ 2026-10-13：原 8 ⇒ 判定盒比鸟视觉大 ~30%，奥森报「边缘判定太大」
```

当时**只改了 `BH`（纵向 8→6）**，`BW`（横向 10%）一直没动。
而**纵向其实是安全的**：`BH=6%H` 在 433vp 高的场地上才等于 26vp 视觉高，
场地更矮时判定盒反而**比视觉小**（宽容）⇒ 纵向不会误判。
**真正会误判的是横向**，恰恰是没改的那一维。

## ⑥ 建议（只提不改）

### 方案 A（推荐，最便宜）：**给场地加宽度上限**

```ts
.width('100%')
.layoutWeight(1)
.constraintSize({ maxWidth: 420 })   // ← 加这一行
```

- 420vp 时判定 42 / 视觉 34 = **1.24×**（可接受，且与手机观感接近）
- **物理一行不用改**（全是 `%`），只是场地不再在平板上被拉到 853 宽
- **有先例**：`GGo9` 就有 `.constraintSize({ maxWidth: this.boardMax() })`，
  且注释记录了「按横屏 533 高算」的真机收敛过程（`boardMax()` 用 `Bp.width`/`Bp.height` 两个分支）
- 副作用：平板上场地变成居中一列 —— 但这**更像真·像素鸟**，不是缺点

### 方案 B：把小鸟也改成 `%`

```ts
.width(BW + '%').aspectRatio(34 / 26)
```

- 判定盒与视觉**从此永远一致** ✓
- 但 853vp 时小鸟会变成 **85vp 宽**——**视觉上过大**，得同时把 `BW` 调小（会改变难度）
- ⇒ 要动玩法参数，不如 A 便宜

### 方案 C：`onAreaChange` 量宽度再换算

- **不推荐**：这是 GFlappy 刻意避免的（它全用 `%` 就是为了不依赖像素），
  引进来会破坏「任何机型手感一致」，而且引入首帧 0 的风险

| 场地宽 | 横向判定盒 | 视觉 34 | 横向倍数 | 纵向判定盒(6%×135) | 视觉 26 | **纵向倍数** |

**纵向判定盒只有视觉的 0.31×** —— 玩家「看着撞上了却没死」。
**这个数在任何 `maxWidth` 下都不变**（因为 maxWidth 不改高度）。

⇒ **420 vs 380 的差别（1.24 vs 1.12，12 个百分点）被纵向 0.31× 的失真盖过去了**，

## 为什么不用像 `GGo9.boardMax()` 那样按朝向算

`maxWidth` **只在宽屏生效**：

| 设备 | `width('100%')` | `maxWidth: 420` 是否生效 |
|---|---|---|
| 手机竖 360 | 360 | **否**（360 < 420）⇒ 零影响 |
| 手机竖 440 | 440 | **否**（440 > 420，会裁到 420 ⚠️ 见下）|
| 平板横 853 | 853 | **是** ⇒ 裁到 420 |

**一个常量就够，不需要朝向分支。**

⚠️ 一个边界：**440vp 的手机**（部分大屏手机竖屏）会被裁到 420 —— 影响很小（4.5%），
但如果要绝对零回归，可以把常量提到 **460**（此时 460 宽下横向倍数 = 1.35×，仍远好于 2.51×）。

## 玩法节奏不受影响（这次是纯视觉修复）

```

PIPE_SPEED   = 1.5 (%W)/tick
⇒ 无论场地多宽，都是 42 / 1.5 = 28 tick ≈ 0.92s 一根  ← 与 W 无关
```

纵向同理（`PIPE_GAP` 与 `GRAVITY` 都是 `%H`）⇒ **限宽只改“看起来多大”，不改“多久来一根”**。
