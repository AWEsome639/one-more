# 端侧 LLM：**`@since 10` 的 MindSpore Lite 就在 SDK 里** ⇒ 不必等 API 20

## objective 里的卡点

> **端侧 LLM（第八个想法 v2）：仍卡在 API 20，需换路线验证**

**现状**：`core/LocalLLM.ets`（`230` 行）用的是
`localChatModel` from `@kit.DataAugmentationKit`（**API 20+**），
而项目 `compatibleSdkVersion` 是 **`5.0.0(12)`** ⇒ **大部分设备用不了**。

## 今天的发现（换路线的验证结果）

**扫本机 SDK（`apiVersion 26`）找到：**

```
/Applications/DevEco-Studio.app/.../ets/api/@ohos.ai.mindSporeLite.d.ts   986 行
/Applications/DevEco-Studio.app/.../ets/kits/@kit.MindSporeLiteKit.d.ts
```

**而它的 `@since` 是 `10`（第 `24`/`35`/`45` 行）—— **远低于 `compatibleSdkVersion 12`**。**

**⇒ 结论：`MindSpore Lite` 在**当前 SDK 上就能用**，**不需要 API 20**。**

## 能力（从 `.d.ts` 读出的）

```ts
loadModelFromFile(model: string, context?: Context): Promise<Model>
loadModelFromBuffer(model: ArrayBuffer, context?: Context): Promise<Model>
// … predict 等（共 986 行 API）
```

**⇒ 可以「从文件」或「从 buffer」加载模型 ⇒ **模型可以放在 `resources/rawfile`**（打进包）。**

## 这把「不可行」变成了「可行，但有工程量」

| 路线 | API 要求 | 现状 |
|---|---|---|
| `@kit.DataAugmentationKit` 的 `localChatModel` | **API 20+** | 已实现（`LocalLLM.ets` 230 行），但多数设备用不了 |
| **`@ohos.ai.mindSporeLite`** | **`@since 10`** | **可用**；需要：① 一个量化小模型（`0.5B~1.5B`）② 转换/量化 ③ 首启加载策略 |

## 下一步（按代价从小到大）

1. **先验证「能加载并跑通任意模型」**（最小可复现）：
   用个极小的模型（比如几 MB 的分类模型）走通 `loadModelFromFile` + `predict` ⇒ 证明链路通
2. **再评估模型体积**：`0.5B` int4 量化约 `300~400MB` —— 奥森说过「大一点没关系」
3. **首启加载策略**：`rawfile` 拷到沙箱再 `loadModelFromFile`（`rawfile` 不能直接给路径）
4. **回落策略不变**：`LocalLLM` 现有的「拿不到就用规则版」的铁律照旧 ——
   `ChatFinder.parse()` 是保底，模型是锦上添花
