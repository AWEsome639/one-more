# 端侧 LLM：**`@since 10` 的 MindSpore Lite 就在 SDK 里** ⇒ 不必等 API 20

## objective 里的卡点

> **端侧 LLM（第八个想法 v2）：仍卡在 API 20，需换路线验证**

**现状**：`core/LocalLLM.ets`（`230` 行）用的是
`localChatModel` from `@kit.DataAugmentationKit`（**API 20+**），
而项目 `compatibleSdkVersion` 是 **`5.0.0(12)`** ⇒ **大部分设备用不了**。

## 今天的发现（换路线的验证结果）

**扫本机 SDK（`apiVersion 26`）找到：**

```
/Applications/DevEco-Studio.app/.../ets/api/@ohos.ai.mindSporeLite.d.ts   986 行
/Applications/DevEco-Studio.app/.../ets/kits/@kit.MindSporeLiteKit.d.ts
```

**而它的 `@since` 是 `10`（第 `24`/`35`/`45` 行）—— **远低于 `compatibleSdkVersion 12`**。**

**⇒ 结论：`MindSpore Lite` 在**当前 SDK 上就能用**，**不需要 API 20**。**

## 能力（从 `.d.ts` 读出的）

```ts
loadModelFromFile(model: string, context?: Context): Promise<Model>
loadModelFromBuffer(model: ArrayBuffer, context?: Context): Promise<Model>
// … predict 等（共 986 行 API）
```

**⇒ 可以「从文件」或「从 buffer」加载模型 ⇒ **模型可以放在 `resources/rawfile`**（打进包）。**

## 这把「不可行」变成了「可行，但有工程量」

| 路线 | API 要求 | 现状 |
|---|---|---|
| `@kit.DataAugmentationKit` 的 `localChatModel` | **API 20+** | 已实现（`LocalLLM.ets` 230 行），但多数设备用不了 |
| **`@ohos.ai.mindSporeLite`** | **`@since 10`** | **可用**；需要：① 一个量化小模型（`0.5B~1.5B`）② 转换/量化 ③ 首启加载策略 |

## 下一步（按代价从小到大）

1. **先验证「能加载并跑通任意模型」**（最小可复现）：
   用个极小的模型（比如几 MB 的分类模型）走通 `loadModelFromFile` + `predict` ⇒ 证明链路通
2. **再评估模型体积**：`0.5B` int4 量化约 `300~400MB` —— 奥森说过「大一点没关系」
3. **首启加载策略**：`rawfile` 拷到沙箱再 `loadModelFromFile`（`rawfile` 不能直接给路径）
4. **回落策略不变**：`LocalLLM` 现有的「拿不到就用规则版」的铁律照旧 ——
   `ChatFinder.parse()` 是保底，模型是锦上添花

## 附：`mindSporeLite` 的准确 API（从 `.d.ts` 抄的，可直接照写）

```ts
import { mindSporeLite } from '@kit.MindSporeLiteKit';

// ① 从 buffer 加载（rawfile 读出来的 ArrayBuffer）
const model: mindSporeLite.Model =
  await mindSporeLite.loadModelFromBuffer(buf, context);

// ② 拿输入张量
const inputs: mindSporeLite.MSTensor[] = model.getInputs();

// ③ 填数据 + 推理
inputs[0].setData(inputArrayBuffer);          // 例如 Float32 的 token ids
const outputs: mindSporeLite.MSTensor[] = await model.predict(inputs);

// ④ 读结果
const out: ArrayBuffer = outputs[0].getData();  // Float32 概率/ids
```

**关键点（今晚实测时要验证的）：**
1. **`rawfile` 不能直接给路径** ⇒ 先用 `resourceManager.getRawFileContent()` 拿 `Uint8Array`
   ，`.buffer` 就是 `ArrayBuffer`
2. **`setData` 要 `ArrayBuffer`**，不是普通数组 ⇒ 用 `new Float32Array([...]).buffer`
3. **`context`** 可省（用默认 CPU）
4. **模型必须真的存在**，否则 `loadModelFromBuffer` 抛 —— **今晚先用**任意**小模型打通链路**

## 今晚的最小验证（不需要 LLM，任何小模型都行）

**目标：证明「读 rawfile → 加载 → predict → 读输出」这条链通。**

**若手边没有模型**：可以先用一个**几十 KB 的 dummy**（比如 `[1,2,3]` → `[6]` 的乘法图）
或者直接从 OpenHarmony 示例里拿一个 `.ms` 模型。

**⇒ 通了之后，再换 `0.5B` 量化模型才是「工程」而不是「冒险」。**

## 今晚的链路测试（具体到步骤）

1. **把这个 `.ms` 放进 `entry/src/main/resources/rawfile/`**（先临时放，测完删）
2. 写一个**最小测试入口**（比如 `ChatFinder` 里加个 `debugSelfTest()`，或临时页面）：
   ```ts
   const rm = getContext().resourceManager;
   const buf = await rm.getRawFileContent('mobilenetv2.ms');      // Uint8Array
   const model = await mindSporeLite.loadModelFromBuffer(buf.buffer);
   const inputs = model.getInputs();
   // MobileNetV2 输入 1×224×224×3 float32
   const data = new Float32Array(1 * 224 * 224 * 3);
   inputs[0].setData(data.buffer);
   const outputs = await model.predict(inputs);
   hilog.info(0x0001, 'LLMTEST', 'outputs=' + outputs.length + ' bytes=' + outputs[0].getData().byteLength);
   ```
3. **通过判据**：`hilog` 里出现 `LLMTEST outputs=1 bytes=1000`（MobileNetV2 输出 `1×1000` 类别概率）
4. **链路通了之后**，再换 `0.5B` 量化 LLM 才是「工程」

**⚠️ 注意**：`11 MB` 放进 `rawfile` 会让 HAP 变大 `11 MB` —— **测完要删掉**，或改用「首启下载到沙箱」。
