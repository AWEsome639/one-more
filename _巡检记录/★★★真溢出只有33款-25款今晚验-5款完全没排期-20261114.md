# 五、那 `4` 款「完全没排期」的根因**已定性**（读代码，不需设备）

## 共同壳结构

四款都是同一套壳：
```ts
Column({ space: Bp.isShort() ? Space.sm : Space.md }) {
  …头部…
  Column({ space: 2 }) { …内容… }.layoutWeight(1)   // 弹性
  …底部…
}
```
**⇒ 所以溢出来自「弹性内容里的固定尺寸」或「盘面按宽度撑高」。**

## 逐款定性

| 游戏 | 关键代码 | 根因类 | 估算 |
|---|---|---|---|
| **`GPatternSequenceDraw`** | `:316` `.layoutWeight(1).aspectRatio(1)`（格子网格）| **① 盘面按宽度撑高** | 限宽即限高（标准一刀）|
| **`GBlockCount3D`** | `:340` `.height(Cell.of(56))` + `:359` `.height(Cell.of(46))` | **② 固定高** | `56+46 = 102vp` |
| **`GFractionMatcher`** | `:347` `.height(Cell.of(48))` + `:364` `.height(Cell.of(46))` | **② 固定高** | `48+46 = 94vp` |
| **`GPythagoreanTripleBuilder`** | `:357/368/379/392` **四个按钮**各 `.height(Cell.of(Bp.height<600 ? 46 : 48))` | **③ 底部按钮行** | **`4 × 48 = 192vp`** |

## 修法方向（尚未写代码，先记录）

### ① `GPatternSequenceDraw` —— 最直接，用库内标准一刀
```ts
// 找到包 aspectRatio(1) 那个容器的 width，加封顶
.width(Math.min(Bp.width - 2 * Space.lg, Math.max(140, Bp.height - 360)))
```
**⇒ 与 `GGo9.boardMax()` / `9` 款 `Nonogram` 类同一范式，已验证 `4/4` 达标。**

### ② `GBlockCount3D` / `GFractionMatcher` —— 降低固定高
**两款都是「两个固定高的块堆叠」**：
- `BlockCount3D`：`56 + 46 = 102vp`
- `FractionMatcher`：`48 + 46 = 94vp`

**⇒ 修法：短屏侧降一档**（`Bp.isShort() ? 44 : 56` / `Bp.isShort() ? 38 : 46`）。
**⚠️ 但先要量清「底部还剩多少」—— 这需要今晚的 `board=` 数据（首次产出）。
⇒ 所以这两款**排在今晚之后**，不是现在能定的。**

### ③ `GPythagoreanTripleBuilder` —— 四个按钮要 `192vp`，这是硬约束
**和 `GSnake3D` 同一类：底部需求远超预算。**
**⇒ 只能三选一**：
1. **把四个按钮改成两行两列**（`2×2` 网格，高度减半到 `~96vp`）
2. **缩短文案让按钮变矮**
3. **降难度/删按钮**

**⇒ 这是产品级取舍，不是纯布局问题。写进「待奥森定」清单。**

## ⇒ 排期结论

| 游戏 | 何时能做 | 前置条件 |
|---|---|---|
| `GPatternSequenceDraw` | **随时**（标准一刀，不需数据）| 无 |

## ⇒ 判据（`2105`）

**说「还有 N 款要修」之前，先按「现在能不能动手」分组**：

# 六、⛔ 自我更正：`GPatternSequenceDraw` 的「标准一刀」**不能照下**

## 我先前写的

> `GPatternSequenceDraw`：`:316` `.aspectRatio(1)` 格子 ⇒ **① 盘面按宽度撑高** ⇒
> **随时可做**，用库内标准一刀 `.width(min(W-2*Space.lg, max(140, H-360)))`

## 为什么这条站不住

**查了实际参数**：`SIDE = 3`（`:23`，`const SIDE: number = 3`）。

**按静态布局推算**：
```

⇒ 每格 ≈ 266vp
⇒ 3 行 ⇒ 盘面 ≈ 798vp
⇒ 而盘面预算只有 343vp ⇒ 应溢出 ≈ 265vp
```

**而实测 `blk = 24px = 8vp`。**

**⇒ 相差 `33` 倍。我的模型一定有错。**

## 可能的解释（都不能确定，需要真机 dump）

| 猜测 | 说明 |
|---|---|
| **ArkUI 裁剪** | 溢出的节点被裁到视口内 ⇒ `bounds` 报的是裁剪后的值 ⇒ `blk` 只数到少量越界 |
| **`aspectRatio` 由高度驱动** | 若父容器给了高度约束，格子可能按高度定尺寸而非宽度 |
| **Shell 有 `layoutWeight`** | 外层 `Column` 可能是弹性的，盘面被压缩 |

**⇒ 判据：拿不出「为什么实测与推算一致」的解释之前，不要基于推算改代码。**
**⇒ 而这类矛盾最有价值的地方：它指出了「我以为是 A 机制、实际是 B 机制」——

# 九、⛔ 第八节的算数**用错了单位** —— `Cell.of` 才是真高度（判据 `2040` 又栽一次）

## 错在哪

**我在第八节把 `88` 当成了实际高度：`3 × 88 = 264vp`。**

**但 `Cell.of(88)` = `round(88 × Cell.k × Bp.scale() × shrink)`：
手机 `Bp.height=533 < 600` ⇒ `shrink = 0.85`、`Cell.k = 1`、`Bp.scale() = 1.0`
⇒ **`Cell.of(88) = round(74.8) = 75vp`**（不是 `88`）。**

**⇒ 也就是说：`3 × 88 = 264` 应为 `3 × 75 = 225vp`，我多算了 `39vp`。**

## 而这条语义，`Design.ets:100-112` 的注释里写得非常清楚

> ★★★ `2026-11-08` **矮屏压缩**：`GameHost` 的 `.constraintSize({maxHeight: Bp.height - 190})` 只能压**容器**，
> **不会让容器里固定尺寸的子项缩小** ⇒
