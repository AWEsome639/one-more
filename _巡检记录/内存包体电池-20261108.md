### 1.4 `GameSource` 会不会攒 listener？（lead 点名的问题）—— **不会**

代码层面（`core/GameSource.ets`）：
```ts
registerDataChangeListener(l) { if (this.listeners.indexOf(l) < 0) { this.listeners.push(l); } }  // ★ 去重
unregisterDataChangeListener(l) { const i = this.listeners.indexOf(l); if (i >= 0) { this.listeners.splice(i, 1); } }
reset(next) { if (this.sameAs(next)) return; this.items = next; /* 通知 */ }
```
- **注册去重**、**注销真删** ⇒ 同一个 listener 最多一份；
- `reset()` 每次只**换数组引用 + 通知**，不新建 listener、不累积字符串；
- **实测佐证**：9 分钟里共触发 **26 轮**列表变化（滚动 + 每 6 轮进游戏返回一次 ⇒ 列表反复重建），RSS 在第 200 秒后**没有继续上涨** ⇒ 与"listener 越攒越多"的形态不符。

## 4. 方法与坑（判据级）

1. **`VmSize` 不能当内存用**：46.6 GB 是虚拟地址空间；**RSS/PSS 才是真占用**。（我第一次看 `/proc/status` 就被 46 GB 吓了一跳。）
2. **RSS ≠ PSS**：RSS 含共享页（`.so`/`.abc` 的 mmap 会被多进程共享），PSS 按比例折算。做"应用占多少"的口径时用 PSS，做"系统还剩多少"时用 RSS。
3. **`hidumper -s <数字>` 的 SA 号是猜不得的**：`-s 1901` 实际打印的是 `ResourceSched`，不是内存；**`hidumper --mem <pid>` 才是内存分类**。
4. **判泄漏要看"平台期"，不是看"涨没涨"**：预热阶段涨 80 MB 很正常；关键是**后 5 分钟是否还在单调上升**。
5. **包体必须区分 debug/release**：`module.json` 的 `app.debug` 是唯一可信判据；`sourceMaps.map` 在不在可以直接说明问题。

## 5. 复现命令

```bash

# 内存：三时点

# 包体构成

import zipfile,os,collections

c=collections.Counter()
for i in z.infolist(): c[os.path.splitext(i.filename)[1]]+=i.file_size
for e,s in c.most_common(): print(f'{s/1048576:7.2f} MB  {e}')"
```
