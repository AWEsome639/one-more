### 1.3 有没有泄漏？—— **没有证据**

把 26 次采样按时间排开（RSS，kB）：

```
 16s  362,152   121s 431,412   221s 411,840   392s 403,276   500s 403,720
```

- **上涨只在前 200 秒**（362 → 442 MB），之后**回落到 400–405 MB 并且横向不动**（后 5 分钟波动 < 5 MB）。
- ⇒ 典型形态是**首屏/缓存预热的"涨到平台期"**，不是线性泄漏。
- 切后台 90s 只掉 15 MB（ArkUI 不主动释放渲染缓存），回前台不再涨。

### 1.4 `GameSource` 会不会攒 listener？（lead 点名的问题）—— **不会**

代码层面（`core/GameSource.ets`）：
```ts
registerDataChangeListener(l) { if (this.listeners.indexOf(l) < 0) { this.listeners.push(l); } }  // ★ 去重
unregisterDataChangeListener(l) { const i = this.listeners.indexOf(l); if (i >= 0) { this.listeners.splice(i, 1); } }
reset(next) { if (this.sameAs(next)) return; this.items = next; /* 通知 */ }
```
- **注册去重**、**注销真删** ⇒ 同一个 listener 最多一份；
- `reset()` 每次只**换数组引用 + 通知**，不新建 listener、不累积字符串；
- **实测佐证**：9 分钟里共触发 **26 轮**列表变化（滚动 + 每 6 轮进游戏返回一次 ⇒ 列表反复重建），RSS 在第 200 秒后**没有继续上涨** ⇒ 与"listener 越攒越多"的形态不符。

## 3. 电池

### 3.1 结论：**这台模拟器上测不了**（三条路都堵死，如实记录）

| 路径 | 结果 |
|---|---|
| `hidumper -s 3301`（PowerManagerService）/ `-s BatteryService` | 只打印**服务标题**，**没有任何数据行**（模拟器不透出） |
| `battery_stats` | **命令不存在**（`inaccessible or not found`） |
| `/sys/class/power_supply/` | **Permission denied**（shell uid 2000 读不到） |

⇒ **模拟器没有真实电池**，"mAh / 掉电速率"这一层**在本机不可测**，要么真机，要么不做。

### 3.2 能测的替代指标：**CPU 占用**（耗电的主要驱动）

| 场景 | 实测 | 方法 |
|---|---|---|
| **前台交互**（滚动 355 款网格 + 进出游戏） | **≈ 18.7%**（10s 窗口，utime+stime 增量 / 壁钟） | `/proc/<pid>/stat` 第 14+15 字段差分 |
| **切后台 90s 期间** | **≈ 0.10%**（30s 采样，只涨 3 ticks） | 同上 |

**判读**：
- **后台几乎不耗电**（0.1% ≈ 空转）⇒ 没有后台定时器/唤醒在偷偷跑（与之前"定时器泄漏"的巡检结论一致）。
- 前台 18.7% 是**我制造的负载**（每 0.2 秒一次全屏滑动），**不代表用户常态**；常态应远低于此。
- ⇒ **功耗方向没有发现异常**；真要出报告得在真机上跑（且需要电池统计权限）。

## 4. 方法与坑（判据级）

1. **`VmSize` 不能当内存用**：46.6 GB 是虚拟地址空间；**RSS/PSS 才是真占用**。（我第一次看 `/proc/status` 就被 46 GB 吓了一跳。）
2. **RSS ≠ PSS**：RSS 含共享页（`.so`/`.abc` 的 mmap 会被多进程共享），PSS 按比例折算。做"应用占多少"的口径时用 PSS，做"系统还剩多少"时用 RSS。
3. **`hidumper -s <数字>` 的 SA 号是猜不得的**：`-s 1901` 实际打印的是 `ResourceSched`，不是内存；**`hidumper --mem <pid>` 才是内存分类**。
4. **判泄漏要看"平台期"，不是看"涨没涨"**：预热阶段涨 80 MB 很正常；关键是**后 5 分钟是否还在单调上升**。
5. **包体必须区分 debug/release**：`module.json` 的 `app.debug` 是唯一可信判据；`sourceMaps.map` 在不在可以直接说明问题。

## 5. 复现命令

```bash
HDC="/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains/hdc"; T="-t 127.0.0.1:5557"

# 内存：三时点
PID=$($HDC $T shell "pidof com.andrewoscar.onemore" | tr -d '\r\n ')
$HDC $T shell "grep VmRSS /proc/$PID/status"

# 内存分类（Pss Total + 各类别）
$HDC $T shell "hidumper --mem $PID" | head -25

# CPU（前后台各测一次，30s 窗口）
A=$($HDC $T shell "cat /proc/$PID/stat" | awk '{print $14+$15}'); sleep 30
B=$($HDC $T shell "cat /proc/$PID/stat" | awk '{print $14+$15}')
echo "CPU = $(( (B-A) / 30 ))%"      # 单位：ticks/100 ⇒ 百分比

# 包体构成
python3 -c "
import zipfile,os,collections
z=zipfile.ZipFile('entry/build/default/outputs/default/entry-default-signed.hap')
c=collections.Counter()
for i in z.infolist(): c[os.path.splitext(i.filename)[1]]+=i.file_size
for e,s in c.most_common(): print(f'{s/1048576:7.2f} MB  {e}')"
```
