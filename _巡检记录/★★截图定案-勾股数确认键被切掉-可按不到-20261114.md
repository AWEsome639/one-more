| 我说 | 实际 |
|---|---|

而 `L357/368/379/392` 是**四个** `.height(Cell.of(...))` —— 每个 `Row` 一行。**
**⇒ 判据 `2111` 说「错两次就别猜第三次」——这次**又错**，因为我看的还是代码片段而不是整段。**

## 三、预算（`工具/budget.py` 算，非手算）

```

内容区 429vp ⇒ 余 273vp 给「题目卡 + 统计 + 提示按钮 + 间距」

⇒ 最小可行 base = 41（Cell.of=35vp，省 16vp，余量 0）

```

## 四、取舍：这次可以自己拍板

| 方案 | 触控 | 可玩性 |
|---|---|---|
| 现在（`base 46` ⇒ `39vp`）| 已 `< 44` | **「确认」按不到 ⇒ 不可玩** |
| `base 40`（`34vp`）| 更小 | **「确认」回来了** |

**⇒ 与 `Fraction Matcher` 的取舍**性质不同**：那边是「触控差 vs 布局好看」，
这边是「触控差 vs 功能不可用」。**

**⇒ 后者优先。而且 `34vp` 仍远大于手指误触的临界（一般 `28vp` 以上可点），

## 五、改法（三件套）


## ⇒ 判据（`2119`）

**「看截图」不只是「确认观感」，它能揭示**静态分析根本想不到的**问题类型。**
**这次静态分析只关心「超了多少 px」，而截图显示的是「某个按钮完全不可达」。**
**⇒ 前者是布局问题，后者是功能问题 —— 严重程度差一个量级。**

**⇒ 判据：`blk>=24` 的款，除了量「超多少」，还要看截图回答「**超出去的那部分是什么**」。
若是一个可点控件被切掉 ⇒ 那是功能缺陷，优先级高于所有「压住手势条」类问题。**

而第二个 `Row` 在 `L387` 之后 —— 我看到了它，但没意识到还有第三、第四个。
