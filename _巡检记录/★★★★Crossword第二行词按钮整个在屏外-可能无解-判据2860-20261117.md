# `Crossword`：第二行词按钮**整个在屏外** ⇒ 4 个候选词不可达（可能无解）

> `2026-11-17 21:30`。**用完整 UI 树量出来的，不是推的。前四次修法全错在这里。**

## 一、⇒ UI 树实测（`uitest dumpLayout` + 解析全宽元素）

```
y  117- 381  h= 264  Row          ← 头部
y  381-1351  h= 970  Column       ← 主内容（含网格 600×600 @980,725）
y  411- 525  h= 114  Row          ← 线索面板 1
y  555- 695  h= 140  Row          ← 线索面板 2
y 1355-1404  h=  49  Text         1 行：胸腔里日夜跳动的器官（5 字母）
y 1434-1476  h=  42  Text         从词库里挑一个词，填进这一行
y 1506-1600  h=  94  Row          ← 第一行词按钮（唯一渲染出来的那行）
```

**⇒ **树里只有一行词按钮**。代码里明明有两行（词 0–3 与词 4–7），第二行**完全不在树里** ⇒ 它在 `y>1600` 的屏外。**

## 二、⇒ 这带来一个**功能性问题**，比外观严重

**⇒ 候选词库 8 个词，屏幕只显示前 4 个。**
**⇒ **如果正确答案落在后 4 个里，这一局无解** —— 玩家看不见、点不到。**

**⇒ 这才是这款真正的缺陷；之前我盯着的「圆角被切」只是表象。**

## 三、⇒ 同时纠正我自己的一个误判

**⇒ 我一直以为按钮「被压到 `94px`（应 `108px`）」。实际算一遍 `Cell.of`：**

```
Cell.of(base) = round(base × Cell.k × Bp.scale() × shrink)
shrink = 0.85 当 Bp.height < 600 且非 TV（手机 533 < 600 ⇒ 生效）
⇒ Cell.of(42) = round(42 × 0.85 × 1.0 × 0.85) ≈ 30vp ≈ 90px
```

**⇒ 实测 `94px` ≈ 设计值 `90px` ⇒ **按钮从来没有被压缩**，它一直是全高、只是**底边齐着屏底**（圆角被屏幕边缘切掉几个像素）。**

**⇒ 判据 `2860`：**`Cell.of` 在手机上已经有 `×0.85` 的矮屏压缩**（`Bp.height<600`），所以「`Cell.of(42)` 应当是 `108px`」这种换算**是错的**。用错尺子 ⇒ 四轮改动全打在空气上。**

## 四、⇒ 下一轮的正确方向

**⇒ 修**数据/结构**，不是修像素：**
1. **保证正确答案一定落在可见的前 4 个**（洗牌时把答案放进 `bank[0..3]`）
2. **或者**把 8 个词改成「一行 4 个 + 换一批按钮」两页
3. **或者**把网格从 600px 压到 ~440px（腾出 `160px` 放第二行）—— 但要先确认网格缩了之后**不会**被 `layoutWeight` 吃掉（判据 `2599`）

**⇒ 三条里第 1 条最便宜、也最对症（它直接消灭「无解」这个功能问题）；第 3 条要再量一轮。**

## 【`21:37` 决定性发现】词按钮行是**贴底锚定**的 ⇒ 上面缩多少都不动

**⇒ 第 `5` 次尝试：网格 `200vp→150vp`（`600px→450px`，实测 `board=450x450` 确认已生效）。**
**⇒ 结果：`lowest='EMBER'` 仍在 `[60,1506][861,1600]`（`94px`）—— **词按钮行一动不动**。**

**⇒ 网格从 `600` 缩到 `450`（省 `150px`），词按钮行**连一个像素都没上移**。**
**⇒ 这说明：这行是被**贴底**钉住的（父容器 `layoutWeight` 撑满 + 内容靠底 / 或行在容器底边），所以「缩上面的东西」永远换不来它的位移。**

## ⇒ 五次尝试的总表（同一款）

| # | 改法 | 结果 |
|---|---|---|
| 1 | 缩网格 `-360→-390` | 首行 `94→34px` ❌ |
| 2 | `constraintSize({minHeight})` | 无变化 ❌ |
| 3 | 1+2 | `94→34px` ❌ |
| 4 | 根列 `space` 降档 | `94→28px` ❌ |
| 5 | **网格 `200→150`（省 `150px`）** | **`94px` 不动** ❌ |

**⇒ 判据 `2860` 补完：**
- **先确认**尺子**（`Cell.of` 自带矮屏 `×0.85`，别按名义值算）**
- **再确认**锚点**（贴底/`layoutWeight` 撑满的元素，缩上面的内容不会让它上移）**
- **这两条都没确认就改，等于对着空气打五拳**

## ⇒ 真正的修法（下一轮）

**⇒ 不是调数，是改**锚点**：把词按钮区从「贴底」改成「跟在网格后面」，或给它**固定的两行高度**（`2 × Cell.of(42) + gap`），让容器按内容排。**
**⇒ 动之前先量一次**父容器的 `layoutWeight`/`justifyContent`**（这次我不再猜了）。**

## 【`21:45` 祖链实测】词按钮 `Row` **超出父 `Column` `249px`**

```
(0,0,2560,1600)                        h=1600
  root        (0,117,2560,1600)        h=1483
    Stack     (0,117,2560,1600)        h=1483
      Column  (0,117,2560,1444)        h=1327
        Column (0,381,2560,1411)       h=1030
          Column (60,381,2500,1351)    h=970     ← 父容器，底边在 1351
            Row (60,1506,2500,1600)    h=94      ← 词按钮行，y 从 1506 开始
              Text (60,1506,657,1600)  h=94  EMBER
```

**⇒ 关键：父 `Column` 的底边是 **`1351`**，而词按钮 `Row` 从 **`1506`** 开始 ⇒ **超出父容器 `155px`**（行底 `1600` 超出 `249px`）。**
**⇒ `Column` 默认**不裁剪**（`Cell.of` 那段注释里就写着）⇒ 它画到了父亲外面、也画到了屏幕外面。**

**⇒ 所以这不是「没空间」，而是**父容器高度算小了、子元素硬撑着画出去**。**
**⇒ 这解释了为什么缩网格无效：网格缩了，父 `Column` 的高度（`970`）没跟着变（它是被更外层分配的），于是超出的部分照旧超。**

## ⇒ 下一轮的正确入口（已量到、不用再猜）

**⇒ 从外往里数第二层那个 `Column (0,381,2560,1411)` 与第三层 `Column (60,381,2500,1351)` —— **它们的高度是被外层分配的**。要找的是**谁给它分配了 `970`**（`layoutWeight`？`height('100%')`？），把那个分配改成「按内容」。**
**⇒ 具体做法：`grep -n "layoutWeight" GCrossword.ets` 逐个核对，并看 build 根 `Column` 的修饰符（`L423` 已知是 `justifyContent(Start)`）。**

## 【`21:52` 第 `6` 次尝试】整页包 `Scroll` —— **首屏变成什么都看不见，更糟**

**⇒ 改：根 `Column` 外包一层 `Scroll`，并去掉 `Column` 的 `height('100%')`（让它按内容排）。**
**⇒ 实测：`lowest='0/5'` 在 `[417,621][496,677]` —— 内容底只到 **`677`**（屏幕中上部），`blk=0`、`max=0`。**
**⇒ 也就是：首屏只剩头部 + 网格上半，**线索、提示、两行词按钮全在视口之外**（`Scroll` 的初始位置在顶部）。**

**⇒ 比原来更糟（原来至少能看到 4 个词）⇒ 已回滚、已重编。**

## ⇒ 六次尝试的最终结论

| # | 改法 | 类别 | 结果 |
|---|---|---|---|
| 1–5 | 缩网格 / `minHeight` / 组合 / 降间距 / 再缩网格 | 调参 | 全部无效或更糟 |
| 6 | 整页包 `Scroll` | 结构 | **首屏什么都看不见，更糟** |

**⇒ 判据 `2861`（新）：**`Scroll` 不是「内容超框」的通用解** —— 它的初始位置在顶部，会把本来还能看到的内容推出视口；`blk=0` 还被它变成恒真（判据 `2605`）。**
**⇒ 换 `Scroll` 前先问：**滚动之后，用户第一眼看到的是不是还是「该看的东西」？** 不是就别换。**

## ⇒ `Crossword` 的正解（留给下次，方法已明确）

**⇒ 问题不是「空间不够」，而是**父容器高度被外层分配、子元素硬撑出去**（祖链实测：父底边 `1351`、行从 `1506` 起）。**
**⇒ 唯一干净的路：**把词按钮区从「跟在网格后」改成「独立的一行固定高度区」**（例如放进根 `Column` 的**第一个**子元素位置、紧跟头部），让它永远在首屏；网格再按剩余高度自适应。**
**⇒ 这需要改 `build()` 的子元素顺序，是一次真正的重构（不是改一个数），应在一个上下文充裕的会话里做，并配 `uitest dumpLayout` 逐步验收。**
