## 2. 被推翻/修正的三条 & 为什么当初会错

### ① `1961` → `1962`：「想当然的机制」+「单次观察」

我把 ArkUI 的 `ForEach` key 当成了**全局命名空间**（以为跨实例同字符串会串节点），于是写下「key 必须含行列」。
**证据只来自一次观察**：`Wordle` 一片黑 —— 恰好那次是 B 型棋盘被撑爆、不是 key 的问题。
**反证**：我改了 `Wordle` 棋盘的 key，**症状零变化**；而且全库大量游戏用「只用列」的 key 都正常 ——
**key 是每个 `ForEach` 实例内部的作用域**。
**错误类型**：想当然的机制 + 把「相关」当「因果」。

### ② `1972` 的机制 → `1973`：「误读指标」

我写「省出的空间被 `layoutWeight` 吸走 ⇒ 下方更靠下」。
**实际**：那两次「变差」是**最低节点换人**（`Base Shift` 的 `lowest` 从 `'121'` 变成规则句；`Fraction Matcher` `8/21 → B`），
`max_bottom` 变大只是「另一个节点现在最靠下」，不是布局变差。
**现成的反例就在手边**：`Object Displacement` 自己也有 3 个 `layoutWeight(1)`，照样 **−90px 变好**
（因为那是统计卡在 **Row 里的横向**权重，只吃宽度、不吃竖直空间）。
**错误类型**：误读指标（把「最低节点换了」当成「布局下移」），且**编了一个机制**去自圆其说。

### ③ `1978` → `1983`：「单次测量」

我见 `Wordle` 抖 `±250px`，就把「`max_bottom` 单值不可信」写成判据。
**实际**：那次抖动是 **`Wordle` 真的在变**（键盘/棋盘时有时无，`blk` 也在 `1/60→0→0→2/48` 跳）——
**尺子忠实地报了对象的变化**。
**修正**：单值可作证据，前提「同款连跑 3 次跨度 ≤20px」；**跨度大 = 对象在变 = 那本身是要修的 bug**。
**错误类型**：单次测量 + 归因错误（把「对象不稳」记成「尺子不稳」）。

> **三条的共同病根**：**没有先证明「两次量的是不是同一个东西 / 同一个状态」**。
> 1961 是「同一个 key 吗」，1972 是「同一个节点吗」，1978 是「同一个状态吗」。
> ⇒ 这就是 `1973` / `1977` / `1983` 存在的理由。

## 3. 最该小心的一条

**`1973`**（`max_bottom` 变大 ≠ 变差）。

理由：
- 它是**唯一会让结论方向反掉**的一条 —— 另外两条的代价分别是「白改一处 key」和「不敢用数字」；
- 它解释的正是**最诱人的陷阱**：数字变大 ⇒ 直觉判「变差」⇒ 改错方向 ⇒ 再花 10 分钟编译白烧；
- 它还能**反向**用：若新的 `lowest` 是内容文字，**数字变大反而是改善**（`Pythagorean Triple Builder` `7 → ⌫`，`+18px`）。

## 4. 附：台账缺口（5 个编号）

（`grep` 全库只命中无关数字）。要么那几轮没立判据，要么立了没落盘 ⇒ **建议以后每条判据顺手写一行进本表**。

它不算「推翻」，但**照原文写代码会漏 43 处**，所以表里标了「⚠️ 有前提」。
