### 1.1 为什么 285 条是"假阳性"

游戏里的提示器是四参签名：
```ts
static make(cells: number[], zh: string, en: string, t0: number): HintResult
// 调用：Hint.make([..], TG2('答案是第 {0} 个', …), TG2('The answer is option {0}', …), t0)
```
- 第一个 `TG` 走**中文 key**（字典里有）✓
- 第二个 `TG2('The answer is …')` 是**英文字面量**，本来就该原样输出英文 —— **它不需要进字典**
- 而 `Hint.toastResult()` **只念 `r.zh`**（`Hint.ets:126`），`r.en` **从不显示**（只有 `Hint.ets:31` 的注释提到它）

⇒ 这 420 处"英文 key 不在字典里"**完全无害**。

### 1.2 我的扫描器踩的两个坑（记下来，下次别再犯）

| 坑 | 表现 | 修法 |
|---|---|---|
| **字典 key 没反转义** | `"❌ 墨色是{0}，\"{1}\"只是写在上面的字"` 在源码里是转义的，我拿带 `\"` 的去比 → **假报缺失** | 字典与调用点**都**过 `unescape()` |
| **没屏蔽注释** | `// 原来是 TG('按「' + …)` 这种被当成真调用 | 扫描前剥注释（`check_key_coverage` 是这么做的，我没做） |

> ⚠️ 上一轮那 4 条 `ms` 模板，就是**"拿子串查全句"**这第三种坑 —— 查字典必须用**完整 key**，不能用片段。

## 2 为什么 `check_key_coverage` 基线是 0 却漏了这 2 条

```python
# tools/check_key_coverage.py:60
SCAN_DIRS = ['components', 'pages', 'games', 'core']      # ← 没有 'ai'
```

而 `ai/Hint.ets` 里有 **3 处 TG 调用**，其中 2 处缺译文：

```
ai/Hint.ets:131   Hint.toast(TG('想得有点久，再点一次'));     ← timeout 分支
ai/Hint.ets:135   Hint.toast(TG('出错了，再点一次'));         ← error 分支
```

**各目录 TG 调用量**（说明盲区有多大）：

| 目录 | TG 调用 | 在扫描范围 |
|---|---|---|
| games | 9644 | ✅ |
| pages | 78 | ✅ |
| components | 55 | ✅ |
| core | 30 | ✅ |
| **ai** | **3** | **❌ 没有** |
| entryability / formwidget / entrybackupability | 0 | ❌（无内容，无所谓） |

⇒ 盲区**只有 `ai/` 一个目录、3 处调用**，所以"加进来"的成本极低，一旦加进来这 2 条就会被基线拦住。

## 6 附：一个不是 bug 但值得知道的写法

`games/GDivisibilityDash.ets` 有 **11 处**：
```ts
zh = TG('看末位：末位是偶数就能被 2 整除');
en = TG('Look at the last digit: even ⇒ divisible by 2');   // ← 英文字面量套 TG
```
`TG()` 拿到英文 key → 字典里没有 → **原样返回英文**（对任何语言都是），而 `en` 字段又**从不显示**。
⇒ **功能无害**，但会让"扫缺译文"的工具把它当成 11 条缺失 key（我第一次就是这么被骗的）。
**建议**：`en = 'Look at ...'`（去掉 `TG()` 包装）更诚实；不改也不影响用户。
