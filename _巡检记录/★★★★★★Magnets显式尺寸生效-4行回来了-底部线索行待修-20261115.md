# ★★★★★★ `Magnets`：显式尺寸生效，`4` 行全回来了 —— 只差底部线索行

> `2026-11-15 07:55` 真机实测（HAP `46553195`）。**这是今天第一个有截图证据的实质进展。**

## 一、⇒ 改了什么

**依据 dump（判据 `2674`）：`layoutWeight(1)` 覆盖父容器 `.width()`、`aspectRatio()`、`constraintSize()`。**

```typescript
// 新增常量（GMagnets.ets:34）
const MAG_CELL: number = 52;

// 格子（:649）：不再依赖 layoutWeight / aspectRatio
.width(MAG_CELL).height(MAG_CELL)

// 棋盘 Row（:705-708）：宽按内容算、高显式给
.width(4 * MAG_CELL + CLUE_W + 4 * Space.xs)   // = 276vp
.height(4 * MAG_CELL + 3)                        // = 211vp
```

## 三、⇒ 还差什么（明确的下一步）

**底部横向线索行 `3+ 1+ 1+ 3+` **没有出现**。**

**⇒ 所以那 `48px` 就是它 —— 它在棋盘之下、被挤出屏幕。**

**⇒ 下一步：把 `MAG_CELL` 从 `52` 收到 `48`（`4×48+3+44 = 239vp`，比 `211+44=255vp` 再省 `16vp` = `48px`），
   或找到那行线索的容器单独给它高度预算。**

**⚠️ 注意判据 `2668`：`blk` 在改前改后都是 `48px`，但**画面从 `2` 行变成 `4` 行** —— 只看 `blk` 会得出「没改善」的错误结论。**

## ⇒ 判据（`2676`）

**`blk` 可以**完全不动**，而画面已经大幅改善（`Magnets`：`blk` 恒 `48px`，可见行数 `2 → 4`）。**
**⇒ 判据：`blk` 衡量的是「最底那个块的溢出量」，不是「有多少内容看不见」。
    布局类改动必须看**截图里元素数量**（行/列/键位是否齐全），不能只看 `blk`。**

## ⇒ 判据（`2677`）

**显式尺寸（`.width(x).height(y)`）能压过 `layoutWeight`，而 `constraintSize`/`aspectRatio` 不能 —— 同一份 dump 里三者同时失效时，
只有显式尺寸是可靠解。**
**⇒ 判据：遇到 `layoutWeight` 撑爆容器，直接上显式尺寸；别在 `constraintSize` 上继续试（今天作者和我各试一次都无效）。**
