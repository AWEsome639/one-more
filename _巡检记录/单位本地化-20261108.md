# 单位本地化：`s` / `ms` / `k`·`M` 值不值得改

> 2026-11-08 22:5x ｜ 执行：game-balancer ｜ **只读 + 只写本 md**
> 目标：判断「时间单位写死 `s`」「compact 数字 `k`/`M`」这两件事**值不值得动**，再给清单与每语言正确写法。

---

## 0 结论（先说值不值得）

| 项 | 规模 | 值不值得改 | 理由 |
|---|---|---|---|
| **`s`（秒）** | **77 处 / 69 文件** | **✅ 值得改（性价比最高）** | **字典里已经有 `秒` 的 11 语言译文**，63/69 文件已 `import I18n` ⇒ 纯机械替换，**零新增翻译** |
| **`ms`（毫秒）** | 13 处 / 10 文件 | **🟡 可改可不改** | 字典里**没有 `毫秒`**，要新增 11 条；且 `ms` 是国际单位符号，中俄日韩都常见「320ms」 |
| **`k` / `M`** | **2 行**（`Common.ets` `fmtBest`） | **❌ 不建议改** | `k`/`M` 是国际通用（中文 App 也大量用 `1.2k`）；改 `万/亿` 要按语言分阈值、且窄卡片不省字符 ⇒ **收益 < 风险** |

**一句话**：**该改的只有 `s`，而且几乎零成本**（字典现成）；`ms` 顺手能改但收益小；`k`/`M` 明确不改。

### 1.2 compact 数字

```ts
function fmtBest(n: number, compact: boolean): string {
  if (compact) {
    if (v >= 1000) { return String(Math.round(v / 100) / 10) + 'k'; }   // 1240 → 1.2k
    return String(v);
  }
  if (v >= 1000000) { return String(Math.round(v / 100000) / 10) + 'M'; } // 1234567 → 1.2M
  …（千分位那支已按 ar 处理成 `٬`）
}
```
> 注：千分位分支**已经做过本地化**（阿语用 `٬` U+066C），注释里写明「不用 Intl，只换分隔符」——
> 说明这个文件的作者**已经在按这个标准做事**，只是 `k`/`M` 两支没跟上。

## 2 逐项判断：到底值不值得改

### 2.1 `s` —— **✅ 值得改**（理由三条）

**① 不是所有语言都长一样**（这是判断的核心）：

| 语言 | 正确写法 | 与现在的 `s` 相比 |
|---|---|---|
| en | `s` | 一样 |
| es / fr / de / pt / it | `s` | **一样**（5 个语言零变化）|
| ru | `с`（U+0441 西里尔 es） | **看起来几乎一样** —— 视觉上改了等于没改，但**字符集对了** |
| zh-Hans / zh-Hant | `秒` | **不一样**（「12s」→「12秒」）|
| ja | `秒` | **不一样** |
| ko | `초` | **不一样** |
| ar | `ثانية`（或缩写 `ث`） | **不一样**，且**长度风险** |

⇒ **12 个语言里 6 个输出完全不变，5 个有视觉变化，1 个（ru）是"字符集修正"**。

**② 成本极低**：字典现成（零翻译）、63/69 文件已 `import` I18n（只 6 个要补 import）；
替换是**纯机械**的：`+ 's'` → `+ L('秒', 's')`。

**③ 收益是"一致性"**：结果页说「1.5 秒」，HUD 说「1.5s」—— 同一个 App 两套写法。

**⚠️ 唯一风险：阿语长度**。`ثانية` 是 6 个字符，HUD 里是大字号（`FontSize.lg`）短宽度格，可能挤压。
⇒ **建议阿语用 `ث`**（阿拉伯语里 ثانية 的通行缩写，也正好是 Lead 提的那个）。

### 2.2 `ms` —— **🟡 可改可不改**（我倾向"顺手一起改"，但接受不改）

- **支持改**：既然 `秒` 本地化了，`毫秒` 不本地化就不一致；中文用户看到「1.5 秒」和「320ms」会略突兀。
- **反对改**：`ms` 是**国际单位符号**（ISO 80000-3），全球科技语境通用；而且这批读数**都是"反应时诊断值"**（如 `冲均值 320ms`），属于测量量而不是叙述文本。
- **如果要改**：要新增 `毫秒` 的 11 条译文（字典里没有），阿语建议 `مللي ث`。

⇒ **建议：跟 `s` 同一批改**（同一个机制、同一次编译），但要**先把 `毫秒` 加进字典**。

### 2.3 `k` / `M` —— **❌ 不建议改**（四条理由）

| 理由 | 说明 |
|---|---|
| **① 国际通用** | `1.2k` / `1.2M` 在中文 App 里也大量使用（GitHub、B 站、YouTube 全这样）。中文玩家读得懂 |
| **② 中文的 万/亿 要按语言分阈值** | 「12,000」中文该写 `1.2万`，英文仍写 `12k`；而「120,000」中文是 `12万`，英文是 `120k` ⇒ **阈值不同**，要写 per-locale 分支，不是换个后缀 |
| **③ 窄卡片不省字符** | `compact` 的存在理由是"标题区放不下"；`1.2M`（4 字符）vs `120万`（4 字符）—— **一样长**，没收益 |
| **④ 收益率最低** | 全库只有 2 行，改它不仅收益小，还要为 12 个语言各定一套阈值规则 |

**⇒ 明确不改。** 记一条已知项：**阿语的 `k/M` 会与阿拉伯-印度数字混排**（`١.٢k`），
和作者已经修过的「千分位 `٬`」是同一类问题，但**当前分数档位下几乎不会触达 1000 以上**（详见 §3.3）。

### 2.3.1 补一句量级：`k/M` 到底会不会出现
- `compact` 分支：卡片上「最高分 ≥1000」才出现 `1.2k`
- 非 compact：≥100 万才出现 `1.2M`
⇒ 前者**会**出现（高分玩家），后者基本到不了（单局分数 40~1600，累计分才可能）。

## 2.4 🔴 关键发现：`TG('秒')` 与 `L('秒','s')` **不是一回事**，别用错

查字典时发现**两套字典都有 `秒`，但内容不同**：

| 字典 | 入口函数 | `秒` 的值 | 适合 |
|---|---|---|---|
| `core/GameI18n.ets` | **`TG('秒')`** | en **Second** ｜ es **Segundo** ｜ fr **Seconde** ｜ de **Sekunde** ｜ pt **Segundo** ｜ ru **Секунда** ｜ it **Secondo** ｜ ja 秒 ｜ ko 초 ｜ ar ثانية | **叙述文本**（「还剩 5 秒」）|
| `core/I18n.ets`（EXTRA） | **`L('秒','s')`** | en `s` ｜ es/fr/de/pt/it `s` ｜ **ru `с`** ｜ ja 秒 ｜ ko 초 ｜ ar ثانية | **HUD 缩写**（「12s」）|

**⇒ HUD 里必须用 `L('秒','s')`**：
- 用 `TG('秒')` 会渲染成 `12Second`（**完整词 + 没空格**）——比现在的 `12s` 更糟
- `L()` 的注释明确写着「**只服务【界面文案】（EXTRA 字典），不碰 games/ 的谜题内容** ⇒ 安全」

**⚠️ 但要注意**：**目前 `games/` 里 `L()` 的调用数是 0**（全部走 `TG`/`TG2`）。
用 `L()` 做单位是**引入新用法**，不是沿用旧模式 ⇒ 方案里要么显式允许，要么加一个 `Sec()` 小助手转调 `L`（我倾向后者，语义更清楚）。

## 3 要改的清单（如果批准）

### 3.1 `s`：77 处 / 69 文件

**改法（一处一行，纯机械）**：
```diff
- Text((String(this.left) + 's')).fontSize(FontSize.lg)…
+ Text((String(this.left) + Sec())).fontSize(FontSize.lg)…   // Sec() = L('秒','s')
+ // 或直接 + L('秒', 's')（见 §2.4：HUD 必须用 I18n 的缩写，不能用 TG 的完整词）
```
- **63 个文件**：`L` 已可用（这些文件已 `import … from '../core/I18n'`，**只需把 `L` 加进那一行的 import 列表**）
- **6 个文件要补 import**：`GAnagramDefinition` `GBinaryPuzzle` `GDefinitionDash` `GRoomInspector` `GTicTacToe` `GWordle`
- **`GAlphabetSudoku` / `GTicTacToe` / `GSudokuHex` / `GBinaryPuzzle` 各有 3 处**，其余 65 个文件各 1 处

### 3.2 `ms`：13 处 / 10 文件（可选）

同一改法：`+ 'ms'` → `+ L('毫秒', 'ms')`，**前提是先把 `毫秒` 加进 `I18n.ets` 的 EXTRA**（11 语言）。

### 3.3 `k`/`M`：**不改**（只记录已知项）

## 5 如果批准，怎么落地（一次编译覆盖）

1. **先加字典**：`I18n.ets` 的 EXTRA 加 `毫秒`（11 语言）；`秒` 已有、若要用 `ث` 缩写则**改 `ar` 的值**（`ثانية` → `ث`，但要确认没有别处依赖长形式）
2. **机械替换**：`+ 's'` → `+ L('秒', 's')`；`+ 'ms'` → `+ L('毫秒', 'ms')`
3. **补 6 个 import**
4. **编译 + 真机验 4 个语言**：zh-Hans（秒）/ ja（秒）/ ko（초）/ ar（ث）—— 重点看**阿语 HUD 有没有溢出**
5. 断言基线仍 `200359 / 0`

**风险**：
- 97 处机械替换，**漏一处不影响编译**（只是那一处仍显示 `s`）⇒ 用 grep 复查替换后的残留
- 阿语/日语的**字宽变化**可能挤压 HUD 布局 ⇒ 必须真机看

---

## 6 我的建议（一句话）

**改 `s`（含 `ms` 顺手一起），不改 `k`/`M`。**

- `s` 的字典译文**已经躺在那儿**，63/69 文件已 import，这是**全库性价比最高的一次本地化**；
- `k`/`M` 是国际通用，改成 `万/亿` 要按语言分阈值、字符数还不省 —— **投入产出比明显更低**，
  而且它已经在 §2.3 那句"已知项"里说明白了。
