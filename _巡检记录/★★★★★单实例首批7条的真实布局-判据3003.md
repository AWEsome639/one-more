# 判据 3003：`over ≤ 10px` 的 `aspectRatio(1)` 方块 = **横屏专属伪影，不要改**

## 一、第一批干净数据（`02:33` 之后，单实例 + 当前代码）

| 游戏 | 耗时 | `blk` | `over` | 判定 |
|---|---|---|---|---|
| `Matrix Reasoning` | `76.9s` | `0` | `0` | ✅ |
| `Prime Hunter` | `71.8s` | `0` | `0` | ✅ |
| **`Simon Says`** | `70.3s` | **`2/48px`** | **`7px`** | 横屏伪影 |
| `Target 10` | `72.5s` | `0` | `0` | ✅ |
| `Visual Search Conjunction` | `72.5s` | `0` | `0` | ✅ |

| `Counting Sheep` | `72.2s` | `0` | `0` | ✅ |

⇒ 通过率 `7/7`，只有 `2` 款有 `blk>0`。

## 二、`Simon Says`：看了截图才敢下结论

底部裁图与整图都看过：

- 屏幕下半是**两块方形答题块**（绿 `A 🐸` / 红 `B 🍎`），**下沿顶到屏幕边缘并被切掉**
- 实测：块高 `281vp`（`756px→1600px`）、宽 `334vp`
- 代码：`.layoutWeight(1).aspectRatio(1)`，外面套一个宽度上限

```ts
.width(Math.min(Bp.width - 2 * Space.lg,
        2 * Math.max(140, Bp.height - (Bp.isShort() ? 200 : 230))))
```

## 三、为什么**不该改**

| 理由 | 算法 |
|---|---|
| 溢出极小 | `7px = 2.3vp` |
| **竖屏根本不触发** | `isShort()=false` ⇒ 取 `230` 分支 ⇒ `2×max(140, 780−230) = 1100`，再被 `360−40 = 320` 卡住 ⇒ 每块 `155vp`；竖屏可用高约 `530vp` ⇒ **装得下** |
| 改这个魔数会**反噬竖屏** | 它是 `isShort()` 三分支里的一个常量，横屏调小 = 竖屏也被调小 |

⇒ **与 `2992`/`2994` 那四款同性质：横屏专属伪影。**

## 四、判据

> **`over ≤ 10px` 且元素是 `aspectRatio(1)` 方块 ⇒ 先算竖屏分支，再决定改不改。**

⇒ 具体算法（三条都要过才动手）：
1. 取 `over` 换算成 `vp`（`/3`），**> 10vp 才值得看**
2. 把公式里的 `Bp.height` 换成**竖屏值**（`780` 或 `832`），看上限是否还绑得住
3. 若竖屏不触发 ⇒ **记下来、不改**，别拿横屏伪影去动三分支常量

## 五、这一条也解释了 `2995` 与它的关系

`Simon Says` 的方块之所以溢出，是因为**上方 chrome 吃掉了 `252vp`**（实测面板顶在 `252vp`），
而公式里假设 chrome 只有 `200vp` ——**乐观了 `52vp`**。

⇒ 但这不影响结论：竖屏时可用高 `530vp` 远大于方块 `155vp`，`52vp` 的乐观在这个游戏上不吃紧。
⇒ 真正被 `52vp` 吃掉的是**本来就更挤的横屏**。

⇒ 与 `2995`（chrome = `175vp`，占横屏 `33%`）合并看：
   **chrome 太厚是全局问题，但它是竖屏也成立的问题里最值得改的一条；「缩某一个游戏的魔数」不是。**
