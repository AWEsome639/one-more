# 第 `8` 次失败之后：**换个思路 —— 让内容可滚动，而不是继续压像素**

## 我已经试过的（`Kakuro` 一款，`8` 次）

| # | 手段 | 结果 |
|---|---|---|
| 1 | 棋盘格 `Cell.of(38) → 34` | `1600` |
| 2 | 容器 `maxHeight` | `1600` |
| 3 | 容器 `maxWidth` | `1600` |
| 4 | 容器 `.width('100%')` → 封顶 | `1600` |
| 5 | 同上 + 截图对比 | **逐像素一致** |
| 6 | 内层 `Row` `.width('100%')` → 封顶 | `1600` |
| 7 | 再封一次 `Row` | `1600` |
| **8** | **格子 `Stack` 加 `maxWidth`** | **`1600`**（`Magnets` 同）|

**⇒ 所有「压像素」的路子都试过了，一条都没动 `max_bottom`。**

## 也许问题不在「尺寸」，而在「根本不该塞进去」

**这些游戏（`Kakuro` / `Magnets` / `Nonogram` / `Nurikabe` / `Kakurasu Sums`）在横屏 `533vp` 高的屏幕上，
内容天然装不下** —— 棋盘 + 键盘 + 工具栏。

**⇒ `Kakurasu Sums` 那款能修好，是因为它的格子是**常量**（`LBL_W`），我把常量改小就见效。**
**⇒ 而 `Kakuro` / `Magnets` 的格子是 `layoutWeight(1) + aspectRatio(1)`（宽度驱动，按父宽分配）** ——
**它们的尺寸不是我能用一个数改动的，是布局系统按父宽算的；而父宽我改了 `7` 次都没对上。**

## 换思路（判据 1940）

> **当「压缩」试了 `3` 次都没动时，改成「让内容可滚动」** ——
> **`Scroll` 不改变任何尺寸，只让「装不下的部分」可以滚到**。
>
> **⇒ 具体做法**：把游戏的根 `Column` 包进 `Scroll`：
> ```ts
> Scroll() {
>   Column() { ...原内容... }
> }
> .scrollBar(BarState.Off)
> .width('100%').height('100%')
> ```
> **⇒ 好处：不动任何内部尺寸、不影响竖屏（竖屏时内容本来就装得下，Scroll 等于透明）、
> 且**用户能真的看到/点到全部内容**。**
>
> **⇒ 代价**：横屏时底部工具栏可能要滚一下才看到（比「看不见」好）。

## 明天怎么做（明确）

1. **先拿 `Kakuro` 试 `Scroll`**（它是唯一有完整祖先链的）
2. 装机后：`max_bottom` 可能仍 `1600`（因为 Scroll 内容可以超出）—— **要看的是「截图里能不能滚到底」**
3. **成功标准换了**：不是 `max_bottom ≤ 1584`，而是「**用户能通过滚动看到并点到底部工具栏**」
   ⇒ **这与判据 1933 一脉相承：`max_bottom` 只能当筛选器，真标准是「用户能不能用」**
