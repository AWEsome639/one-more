# 判据 3023：电视字号没跟着放大，根因**不是忘了**，是**求值时机不同**

## 一、`Cell` 会放大、`FontSize` 不会 —— 为什么

### `Cell.of()` 是**渲染时**才乘 `Bp.scale()`（惰性）

```
Cell.of(base) = round(base × Cell.k × Bp.scale() × shrink)
```
每次调用都现读 `Bp.scale()` ⇒ `Bp` 什么时候更新都对。

### `FontSize/Space/Radius` 是 `apply()` 里**赋常量**（急切）

```typescript
// UiMode.ets:99-108
FontSize.hero = s.hero; FontSize.xxxl = s.xxxl; ...
Space.xs = s.sxs; ...  Radius.xs = s.rxs; ...
```
`apply()` 执行那一刻把值写死；之后 `Bp` 再变，**它们不会跟着变**。

⇒ **同一个 `Bp.scale()`，一个惰性读、一个急切写 ⇒ 结果是「格子放大了、字没放大」。**

## 二、更要紧的：`apply()` 跑在 `Bp.update()` **之前**

```
EntryAbility.onCreate():44
  └─ loadUiMode():60  → UiModeMgr.apply(mode)      ← 此刻 Bp.dev = PHONE（静态默认值）

EntryAbility.onWindowStageCreate():126
  └─ Bp.update(wVp, hVp, dev):188                  ← 到这里才把 Bp.dev 设成 TV
```

`Bp` 的静态初值（`Bp.ets:33-37`）：

```typescript
static width:  number = 360;
static height: number = 780;
static dev:    string = BpDev.PHONE;   // ← 电视在 apply 那一刻还是 PHONE
static ready:  boolean = false;
```

⇒ **所以 `3022` 那个补丁（在 `apply()` 里判 `Bp.isTv()`）会读到 `false` ⇒ 静默失效。**

## 三、那为什么它现在还能工作（如果真要修）

`Index.ets:aboutToAppear()` **又调了一次**：

```typescript
aboutToAppear(): void {
  UiModeMgr.apply(UiModeMgr.current());
```

而页面创建发生在 `onWindowStageCreate` 里 `Bp.update()` **之后** ⇒ 这一次 `apply()` 时 `Bp.dev` 已经是 `TV`。

⇒ **补丁能生效，靠的是「第二次 `apply()`」这个隐式行为** —— 不是靠代码写对了。

## 四、所以正确的修法有两层

### 第一层（必须）：让 `apply()` 之后 `Bp` 一定是准的

```typescript
// EntryAbility.onWindowStageCreate()，Bp.update(...) 之后立刻补一句
Bp.update(wVp, hVp, dev);
UiModeMgr.apply(UiModeMgr.current());   // ★ 保证所有常量在 Bp 就绪后重算一次
```

⇒ 这一句让「`FontSize` 被冻结在错误的 `Bp` 上」这件事**不可能再发生**（对任何设备都成立，不只电视）。

### 第二层（电视字号本身）

```typescript
// UiModeMgr.apply() 开头
const fs: number = Bp.isTv() ? Bp.scale() : 1;
FontSize.hero = s.hero * fs; ...
```

⇒ 手机/平板/手表 `fs = 1` ⇒ 逐字节相同；电视 `fs = 1.45` ⇒ 字号与格子同比例。

## 五、判据

> **同一个系数，一处惰性读、一处急切写 ⇒ 两处结果会不一样。**
> 看到「A 跟上了、B 没跟上」，先问「它们的求值是同时机吗」，再问「是不是有人忘了」。

⇒ 三条：
1. **「X 没跟着变」的第一嫌疑是求值时机，不是遗漏** —— 这次 `Cell` 惰性、`FontSize` 急切
2. **凡是「在初始化里把全局常量写死」的地方，都要确认初始化时依赖已经就绪** ——
   `Bp.ready` 这个字段本来就存在（`Bp.ets:38`），但 `apply()` 没用它判
3. **`ready` 字段没人用 = 一个没被利用的护栏** —— `grep Bp.ready` 看一下它在哪被判过

## 六、这条把 `3004` 从「缺一块」升级成「缺两块」

| 层 | 状态 |
|---|---|
| `Cell` 的缩放 | ✅ 惰性读，正确 |
| `FontSize/Space/Radius` 的缩放 | ❌ **没写**（`apply()` 里没乘任何系数）|

## 七、★ `Bp.ready` 这个护栏**写了但从没人读**（实测）

```
static ready: boolean = false;    // Bp.ets:39   ← 定义
Bp.ready = true;                  // Bp.ets:61   ← 写 1 处（在 update() 末尾）
                                  // 读 0 处 ← 全库没有任何地方读它
```

```
$ grep -rn 'Bp.ready' entry/src/main/ets --include=*.ets
  写: 1 处
  读: 0 处
```

⇒ 作者**预见到**「`Bp` 可能还没就绪」这个问题（否则不会建这个字段），
   但**从没在任何地方用它判过** ⇒ `apply()` 照样在 `Bp.update()` 之前跑。

### 这说明什么

- **不是设计上认为「顺序无所谓」** —— 他建了 `ready` 字段，说明他知道顺序会出问题
- **是护栏建了没接上** —— 这类「半成品护栏」比完全没有更危险：
  后来读代码的人看到 `ready` 会以为「这里已经防住了」

### 判据补充

> **凡是「状态位 / ready 标志 / loaded 标志」，必须 `grep` 一次「它被读了吗」——
> 写了没人读的标志，是给后来人制造虚假安全感。**

⇒ 一条命令就能查：

```bash
grep -rn 'X.ready' --include=*.ets | grep -v 'X.ready ='    # 只数「读」
```

⇒ 今晚这个查法可直接用于：`Bp.ready`（`0` 读，死护栏）、
   `GameLog.ready` / `ProgressStore.ready` / `Sound.ready`（三个 `private` 的，另需单独查）。

## 八、电视这一项的完整诊断结论

| 层 | 结论 | 证据 |
|---|---|---|
| `Cell` 缩放 | ✅ 正确 | `Cell.of` 渲染时惰性读 `Bp.scale()` |
| `FontSize/Space/Radius` 缩放 | ❌ **没写** | `apply()` 里只有模式表，无任何设备系数 |
| **初始化顺序** | ❌ **`apply()` 早于 `Bp.update()`** | `EntryAbility:60` vs `:188` |
| **护栏** | ❌ **`Bp.ready` 写了不读** | 读 `0` 次 |
| 修法 | **两层**：先补 `apply()` 调用时机、再补设备系数 | 见第四节 |

⇒ **这个诊断比「电视字号小 34%」深了一层**：
   `3004` 说的是**现象**，`3023` 说的是**为什么现象修起来不会生效**。

## 九、四个 `ready` 标志实测：**只有 `Bp.ready` 是死的**

| 标志 | 写 | 读 | 结论 |
|---|---|---|---|
| `GameLog.ready` | `2` | `5` | ✅ 在用 |
| `ProgressStore.ready` | `1` | `1` | ✅ 在用（勉强）|
| `Sound.ready` | `3` | `2` | ✅ 在用 |
| **`Bp.ready`** | **`1`** | **`0`** | ❌ **死护栏** |

⇒ **`4` 个里只有 `1` 个是死的** ⇒ 这不是「全库普遍现象」，而是**这一处特定遗漏**。

⇒ 这个区分很重要：说「到处都是死护栏」是错的，说「`Bp.ready` 是唯一一处」才准确、才可修。

### 顺带：这个查法的精度

用一个「`X.ready` 只写不读」的检查去扫，**`4` 个命中 `1` 个** ⇒ 真阳率 `25%`、**误报 `0`**。
对比 `3018` 那个截图检测器（`54%` 误报、`0` 可用结论），**这个查法的精度高得多**。

⇒ 但我**今晚不把它加进断言脚本**：
  1. `check_assertions.sh` 是基线机制，加检查会动 `200359/0` 那个数
  2. `3018` 的教训：新检查先手工跑几轮、确认精度，再考虑自动化
  3. 这次样本只有 `4` 个，样本量太小

⇒ **做法**：先手工用这条命令，等它累计找到 `3` 个以上真死护栏再谈自动化。

```bash
# 逐个私有 static ready 查「读」的次数
for s in GameLog ProgressStore Sound Bp; do
  f=entry/src/main/ets/core/$s.ets
  echo "$s: 写 $(grep -c "$s\.ready *=" $f 2>/dev/null || echo 0) · 读 $(($(grep -c "$s\.ready" $f 2>/dev/null || echo 0) - $(grep -c "$s\.ready *=" $f 2>/dev/null || echo 0)))"
done
```
